## What Was Built

### 1. Base Layout — `layouts/app.blade.php`

**What:** A single Blade layout that all pages extend. Contains the `<html>` shell, theme init script, Vite asset loading, nav include, footer include, and named stacks.  
**Why:** Before this, every new page (`regulamin`, `for-venues`, etc.) had to copy-paste the full HTML scaffold. One change to the nav or footer meant touching every file. The layout makes changes in one place.

**Key architectural choices:**
- `@section('header')...@show` allows child views to completely replace the nav (used by `venues/show` which has a simpler back-link header)
- `@yield('body-class', 'min-h-screen flex flex-col bg-base text-fg')` — the default body class handles most pages; the map overrides to `h-screen flex flex-col` for full-height layout
- `@stack('scripts')` at the bottom of body — JS pushed from child views stays out of the layout logic
- Theme init `<script>` is the **first thing in `<head>`**, before any stylesheet. This is what prevents the white flash on page load for dark-mode users.

### 2. Flash-Free Theme System

**What:** Dark/light mode that (a) defaults to the user's OS preference, (b) persists a manual override in `localStorage`, (c) applies before the first paint — no visible flash.  
**Where:** Inline `<script>` in `layouts/app.blade.php` head, toggle button in `partials/nav.blade.php`.

**How it works:**
```javascript
// In <head> before stylesheet:
var stored = localStorage.getItem('uni-theme');
var prefersDark = window.matchMedia('(prefers-color-scheme: dark)').matches;
var dark = stored === 'dark' || (stored !== 'light' && prefersDark);
document.documentElement.classList.toggle('dark', dark);
```
The logic: if the user has explicitly set a preference, use it. Otherwise, follow the OS. The class is applied synchronously before the browser lays out a single pixel — the stylesheet that loads immediately after reads `.dark` and renders the right colours from the start.

**Toggle button behaviour:**
- Sun/moon SVG icons swap on click
- `MutationObserver` keeps icons in sync if the class changes from anywhere else
- Fires a `uni:theme-changed` custom event so other JS modules (the Leaflet map) can react without tight coupling

### 3. Dual-Theme CSS Variable System

**What:** All colours defined as CSS custom properties with `:root` (light) defaults and `.dark` class overrides. Semantic `@utility` classes (`text-fg`, `bg-surface`, `border-ui`, etc.) map to these variables.  
**Where:** `resources/css/app.css` — complete rewrite.

**Why CSS variables instead of Tailwind `dark:` variants?** The existing templates used hardcoded dark-only colours (`bg-[#111]`, `text-white/60`). Tailwind `dark:` would require duplicating every class. CSS variables flip everything in one place — add `.dark` to `<html>` and the whole UI switches.

**Variable families:**
| Family | Purpose | Light → Dark example |
|---|---|---|
| `--color-base` / `--color-surface` | Page backgrounds | `#F5F4F0` → `#0D0F14` |
| `--fg`, `--fg-muted`, `--fg-subtle`, `--fg-faint` | Text hierarchy | `#1a1a1a` → `#ffffff` |
| `--ui-border*` | All borders | `rgba(0,0,0,0.08)` → `rgba(255,255,255,0.08)` |
| `--ui-overlay` | Chip/badge fills | `rgba(0,0,0,0.04)` → `rgba(255,255,255,0.06)` |

Brand colours (`--color-primary`, `--color-accent`, `--color-ok`) live in `@theme` and do **not** flip — they're the same in both modes.

### 4. Leaflet Map Tile Theming

**What:** The map tile layer swaps between CartoDB Dark Matter and CartoDB Light when the theme changes.  
**Where:** `map.blade.php` and `venues/show.blade.php` JS sections.

**Why:** A dark base map on a light-mode page (or vice versa) looks broken and unmaintained. The swap happens via `tileLayer.setUrl()` — no map reinitialisation, no flicker.

```javascript
window.addEventListener('uni:theme-changed', ({ detail }) => {
    if (tileLayer) { tileLayer.setUrl(tileUrl(detail.dark)); }
});
```

The `uni:theme-changed` event is fired by the theme toggle in the nav and listened to by any JS that cares — a clean pub/sub pattern without shared state.

### 7. JSON-LD Bug Fix — `@context` as Blade Directive

**What:** The venue detail page was throwing HTTP 500 after the layout refactor.  
**Where:** `venues/show.blade.php` JSON-LD `<script type="application/ld+json">` block.  
**Root cause:** Blade compiled `"@context"` as a `@context` directive call (a real Laravel 13 Blade directive for dependency injection contexts). The template had been fine before because it wasn't inside a Blade layout — once it extended `layouts/app.blade.php`, Blade started processing all `@` sequences.  
**Fix:** Escape with `@@` — `"@@context"`, `"@@type"`. These render as literal `@context`, `@type` in the HTML output.

This is a non-obvious gotcha specific to JSON-LD inside Blade layouts. Worth knowing for any future schema markup work.

## Decision Register

### CSS Variables vs Tailwind `dark:` Variants

- **Chosen:** CSS custom properties with `.dark` class on `<html>`
- **Rejected:** Tailwind `dark:` variant classes on every element
- **Why:** The codebase had hardcoded dark-only values everywhere (not `dark:` variants). Converting to `dark:` would mean doubling the class count on every element. CSS variables flip everything in one selector — cleaner, and the theme-aware Leaflet integration (`tileLayer.setUrl`) needed a runtime JS hook anyway, which the custom event provides.

### Theme Init — Inline Script vs CSS `prefers-color-scheme` Media Query

- **Chosen:** Inline JS script in `<head>` applying `.dark` to `<html>`
- **Rejected:** CSS-only `@media (prefers-color-scheme: dark)` without JS
- **Why:** CSS-only theming cannot read `localStorage`. A user who manually switches to light mode would see dark mode again on next visit. The inline script is ~4 lines, runs synchronously before paint, and handles both system preference and stored override.

### Static Pages — Email CTA vs Registration Form (for-venues)

- **Chosen:** `mailto:` CTA for venue onboarding
- **Rejected:** Registration form, waitlist form
- **Why:** Phase 1. Manual, high-touch onboarding lets us understand what venue owners need before building a self-serve flow. Every venue added is a conversation. A form right now is infrastructure for a process we haven't validated yet.
