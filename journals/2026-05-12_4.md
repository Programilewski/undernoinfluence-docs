## What Was Built

### Phase 1 — Venue list analytics columns

Added two sortable columns to the admin venue list table: "Views 30d" and "Clicks 30d". These use Eloquent's `withSum` with a constrained relationship to compute 30-day totals from `venue_stats` in a single query (no N+1). Admins can now sort the venue list by traffic to immediately spot dead-weight venues vs traffic magnets without clicking into each one.

Files:
- `app/Filament/Resources/Venues/Pages/ListVenues.php` — added `getTableQuery()` override with two `withSum` calls
- `app/Filament/Resources/Venues/Tables/VenuesTable.php` — added `views_30d` and `clicks_30d` columns (numeric, sortable, green when >0)
- `app/Models/VenueStat.php` — added `HasFactory` trait
- `database/factories/VenueStatFactory.php` — new factory with `forDate()` and `withViews()` states
- `tests/Feature/AdminVenueListAnalyticsTest.php` — 4 tests covering column rendering, zero-stat venues, 30-day window exclusion, and sortability

### Phase 2 — Platform engagement dashboard widget

Created `EngagementStatsWidget` — a new `StatsOverviewWidget` on the admin dashboard showing platform-level traffic health alongside the existing operational counts widget. The existing `StatsOverview` (venue counts, products, stale data, pending claims) is untouched — this new widget sits below it.

Stats displayed:
- **Total views (7d)** with week-over-week trend arrow and percentage
- **Outbound clicks (7d)** (directions + website + Instagram combined) with trend
- **Unique sessions (7d)** — approximate unique visitors from `events` table distinct `session_id`
- **Top venue (7d)** — name of the venue with most views this week
- **Empty search rate (7d)** — percentage of discovery searches returning zero results (color-coded: green <15%, yellow 15-30%, red >30%)

Files:
- `app/Filament/Widgets/EngagementStatsWidget.php` — new widget with trend computation logic
- `app/Providers/Filament/AdminPanelProvider.php` — registered the widget
- `tests/Feature/AdminEngagementStatsTest.php` — 5 tests covering rendering, 7-day sums, trend comparison, top venue display, and empty search rate

### Phase 3 — Discovery insights widget

Created `DiscoveryInsightsWidget` — a custom widget on the admin dashboard showing what users are searching for, which categories are popular, and where unmet demand exists. This is the "gold data" that will power the V2 gap reports described in the SSOT.

Three columns displayed:
- **Top Searches** — the 10 most common search queries from `discovery_searched` events, extracted via PostgreSQL `properties->>'query'` jsonb operator
- **Popular Categories** — the 10 most filtered categories from `discovery_category_filtered` events, extracted via `jsonb_array_elements_text(properties->'category_slugs')`
- **Empty Result Hotspots** — the 10 most common zero-result filter combinations from `discovery_empty_results` events, showing which categories/districts have unmet demand

Period selector: 7 days or 30 days.

Files:
- `app/Filament/Widgets/DiscoveryInsightsWidget.php` — new widget with PostgreSQL jsonb queries
- `resources/views/filament/widgets/discovery-insights.blade.php` — three-column layout following the existing admin widget visual style
- `app/Models/AnalyticsEvent.php` — added `HasFactory` trait
- `database/factories/AnalyticsEventFactory.php` — new factory with `discoverySearched()`, `discoveryEmptyResults()`, and `discoveryFiltered()` states
- `tests/Feature/AdminDiscoveryInsightsTest.php` — 5 tests covering rendering, top queries, empty results, period filtering, and popular categories

## Decision Register

### Decision: separate engagement widget vs expanding StatsOverview

Chosen: create `EngagementStatsWidget` as a separate class from the existing `StatsOverview`.

Rejected: adding traffic stats to the existing `StatsOverview` widget.

Reason: operational health (venues, products, stale data, claims) and traffic health (views, clicks, sessions) are separate concerns. Keeping them as distinct widgets lets admins visually separate "is the platform structurally healthy?" from "is traffic growing?". Also avoids making the existing widget too wide.

Status: permanent.

### Decision: use withSum for venue list stats instead of raw SQL

Chosen: Eloquent `withSum` with constrained relationship aliases (`views_30d`, `clicks_30d`).

Rejected: raw SQL subqueries or separate N+1 queries per venue.

Reason: `withSum` is idiomatic Laravel, generates efficient correlated subqueries, integrates with Filament's sortable columns, and uses the existing `Venue::stats()` HasMany relationship. The `(venue_id, date)` unique index on `venue_stats` ensures these are index-scanned.

Status: permanent.

### Decision: PostgreSQL-specific jsonb queries for discovery insights

Chosen: use native PostgreSQL `->>'key'` and `jsonb_array_elements_text()` operators.

Rejected: deserializing JSON in PHP (would require loading all rows into memory) or creating denormalized tables.

Reason: the application uses PostgreSQL exclusively. These operators are performant on the existing `(type, created_at)` index for filtering, then extract JSON from the filtered result set. At current data volumes (<10K events/month), this is fast. If the events table grows very large, a materialized view or periodic aggregation could be added, but that's a future concern.

Status: permanent — revisit if database changes from PostgreSQL.

### Decision: no caching layer for dashboard queries

Chosen: query the database directly on each widget render.

Rejected: Redis/file caching of dashboard stats.

Reason: at current data volumes, these queries complete in single-digit milliseconds. The `pollingInterval = '60s'` on StatsOverview limits how often they run. Adding a cache layer would add complexity without measurable benefit. The discovery insights widget doesn't even set a polling interval — it only re-queries when the admin changes the period selector.

Status: revisit when events table exceeds 100K rows/month.

### Decision: admin sees all analytics regardless of plan tier

Chosen: admin panel shows all stats for all venues with no plan-tier gating.

Rejected: making admin view respect venue plan tiers.

Reason: plan tiers gate what venue owners see in their owner panel, not what admins see. Admins need full visibility to manage the platform, verify data, and manually compile gap reports for the V2 validation phase.

Status: permanent.

## Data Model State

No schema changes this session. All tables remain as documented in Sessions 1-3.

Key tables relevant to this session's work:

### `venue_stats` — daily per-venue engagement counters
- `id`, `venue_id` (FK), `date` (date)
- `views`, `direction_clicks`, `website_clicks`, `instagram_clicks`, `shares`, `card_clicks` (all integer)
- Unique constraint: `venue_id + date`
- Used by: Phase 1 list columns, Phase 2 dashboard widget, Phase 4 per-venue widget

### `events` — append-only analytics event log
- `id`, `type` (string 100), `venue_id` (FK nullable), `city_id` (FK nullable), `user_id` (FK nullable)
- `session_id` (string 100 nullable), `ip_hash` (string 64), `referrer` (nullable)
- `properties` (jsonb nullable), `created_at` (timestamp)
- Indexes: `(type, created_at)`, `(venue_id, type, created_at)`, `(city_id, type, created_at)`, `(session_id, created_at)`, `(user_id, created_at)`
- Used by: Phase 2 (unique sessions, empty search rate), Phase 3 (discovery insights), Phase 4 (referrers, recent events)

### `venue_feature_flags` — per-venue feature overrides
- `id`, `venue_id` (FK), `feature` (string/enum), `enabled` (boolean)
- `override_reason` (nullable enum), `notes` (text nullable)
- `enabled_by` (FK to users), `enabled_at`, `enabled_until` (nullable)
- Used by: `Venue::hasFeature()` gate for B2B plan tiers (not directly by this session's work, but context for analytics plan gating)

## Business Impact

- **Admin efficiency**: admins no longer need to click into each venue individually to see traffic. The venue list shows 30-day engagement at a glance, and the dashboard shows platform-level health. This saves significant time as venue count grows.
- **Data-driven decisions**: the Discovery Insights widget directly surfaces unmet demand — what users search for that doesn't exist on the platform. This is the core data that will power the V2 gap reports (the anchor feature of the Basic paid tier at 79 PLN/month).
- **V2 validation ready**: the spec says "Do not build the analytics dashboard until 3+ claimed venue owners respond to manual report delivery." With the Discovery Insights widget, admins can now manually pull gap data and send personal emails to owners ("14 people searched for Wino 0% in Mokotów and you don't carry any"). The widget makes this manual outreach feasible without building the full owner-facing dashboard yet.
- **Trend visibility**: week-over-week trend arrows on the engagement widget let you spot growth or decline at a glance — critical for investor conversations and for knowing whether marketing efforts are working.
