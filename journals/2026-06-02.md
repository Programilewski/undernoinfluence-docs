# 2026-06-02 — Discovery Venue Tile UX Hardening

## Session Overview

Goal: make discovery venue tiles behave like proper links without losing category tooltips, then tighten the card layout for venues with large alcohol-free offers.

Outcome: the card body now supports native browser navigation behavior (Ctrl/Cmd-click, middle-click, right-click open in new tab) while footer actions remain separate controls. Dense category rows now cap visible beverage swatches and keep counts visually attached to their category.

## What Was Built

- **Venue tile native link behavior** in `resources/views/components/venue-tile.blade.php`.
  - The visible tile body is a real `<a href>` to the venue profile.
  - A fallback stretched link covers empty card space.
  - Save, "Na mapie", and "Nawiguj" remain separate interactive controls above the link layer.
  - Product swatches remain inside the visible link, so native `title` tooltips still work.

- **Dense category row layout** for venues with many products.
  - Visible swatches capped from 8 to 6.
  - Hidden products show as `+N`, with tooltip containing hidden product names.
  - Category rows now use content-sized columns: label, swatches, count.
  - Counts stay next to the swatches instead of drifting to the far edge of the card.
  - Card padding, gaps, verified badge, swatches, and footer actions were tightened.

- **Local dense-offer fixtures** created in the database for visual QA:
  - `uni-density-10-beers-10-drinks` — 10 beers + 10 drinks.
  - `uni-density-15-beers` — 15 beers.
  - `uni-density-15-drinks` — 15 drinks.
  - `uni-density-15-beers-15-drinks` — 15 beers + 15 drinks.
  - These use stable slugs and can be updated/reused. They are local testing fixtures, not canaries.

- **SSOT updated** in `inspo/interactive_v1_feature_spec_SSOT.html`.
  - Updated implementation date to 2026-06-02.
  - Documented venue tile native link behavior.
  - Documented dense category swatch cap, `+N` overflow, tooltip behavior, and attached counts.
  - Corrected the older F9 audit row from "Deferred" to "Fixed".

## Decision Register

- **Use real anchors instead of JavaScript navigation.**
  - Chosen because it preserves browser behavior users expect: open in new tab, modifier-clicks, keyboard navigation, and screen-reader link semantics.
  - Avoided wrapping footer actions in the same link by keeping those controls as separate interactive elements.

- **Cap swatches at 6 per category row.**
  - Showing all products makes dense venues unreadable and inflates card height.
  - The card is for scanning; the venue profile remains the place for full inventory.

- **Keep count close to the category row.**
  - The previous fixed grid made counts look detached when rows had 10-15 products.
  - Content-sized columns better communicate "these 15 products belong to this category."

## Risk Register

- **Tailwind build drift.** New utility classes may not appear if the local dev server/build cache is stale. Run the frontend build/dev server if the browser does not reflect the card changes.
- **Nested interaction complexity.** The tile now intentionally mixes a body link and footer controls. Regression risk is around pointer layering and accidental navigation from action buttons.
- **Fixture visibility.** The dense `UNI Density:*` venues are active and visible in local discovery. They are useful for QA but should not be copied into production data.

## What to Test in the Browser

- On `/mapa/warszawa`, Ctrl/Cmd-click a venue tile body and confirm it opens the venue profile in a new tab.
- Middle-click and right-click the tile body; both should behave like a normal link.
- Hover product swatches and `+N` chips; tooltips should show product names.
- Click "Na mapie"; it should focus/open the map pin, not navigate to the profile.
- Click "Nawiguj"; it should open the directions redirect in a new tab.
- Check dense fixtures: counts should sit next to their swatches, not at the far edge of the card.

## Business Impact

- **Discovery feels more professional.** Native link behavior removes a common friction point for users comparing several venues.
- **Dense menus become scannable.** Venues with strong alcohol-free offers no longer dominate the list with long swatch rows.
- **Trust and usability improve together.** Tooltips preserve product detail without sacrificing list density.

## Session 2 — Admin Bar (WordPress-style admin chrome on public pages)

## Session Overview

Goal: decide whether a WordPress-style "edit as admin" bar on public venue pages is worth building or a security liability, then build it if sound.

Outcome: built and shipped an admin-only navigation bar that appears on every public page for logged-in admins. It is deliberately *navigation sugar only* — it links into the existing Filament admin panel and never edits anything inline, so it adds zero new write endpoints and zero new attack surface. The bar surfaces time-sensitive operational queues (claims, inaccuracy reports, and GDPR erasure deadlines) and gives one-click jumps to each venue's edit/analytics/claim records. The decision was formally recorded, and 7 new tests cover visibility gating and the queue badges.

## What Was Built

- **`app/View/Components/AdminBar.php`** (new) — class-based Blade component holding all the bar's logic.
  - Visibility is gated on the **admin role** (`isAdmin()`), not on edit-permission — because venue *owners* also pass the `update` policy check for their own venues, and the bar must be admin-only.
  - Computes global queue counts (pending claims, pending inaccuracy reports, active + due-soon erasure requests) and caches them for 60 seconds so the aggregates never run on every admin pageview.
  - Computes per-venue context only when a venue is in scope: analytics URL, open-report count, and a deep-link to the claim record if claimed.
  - Every link target is an existing Filament page that re-checks its own policy. The component holds no authority of its own.

- **`resources/views/components/admin-bar.blade.php`** (rewritten) — the bar's markup.
  - Left side (global, follows the admin everywhere): Panel link, an environment badge (`PROD` in red, other envs in amber — guards against editing the wrong database), Miejsca, and the three queue badges. The **Usunięcia** (erasure) badge turns red with a "pilne" count when a request is due within 7 days — this is a legal/GDPR clock, not a UX nicety.
  - Right side (only on a venue page): Edytuj, Statystyki (analytics deep-link), an open-report count, and live Aktywne/Nieaktywne + Przejęte/Nieprzejęte status, with "Przejęte" linking to the claim record.

- **`resources/views/layouts/app.blade.php`** (edited) — added `<x-admin-bar :venue="$venue ?? null" />` at the top of `<body>`. It is global; the venue-specific half only renders where a `$venue` exists. Non-admins and guests get nothing.

- **`tests/Feature/AdminBarTest.php`** (new) — 7 tests: admin sees edit + analytics links; guest sees nothing; non-admin owner sees nothing; pending claim/report counts render; erasure due-soon shows "pilne"; environment badge renders; claim status renders. Cache is flushed in `setUp()` so the cached counts don't bleed across tests.

- **Decision record** `inspo/.../decisions/product/admin-bar-navigation-sugar.md` (new) + a row in the Decisions Log.

## Decision Register

- **Admin bar is navigation sugar, never an editing surface.** *(permanent)*
  - Chosen: a thin bar that deep-links into the already-built Filament panel, which enforces its own policies.
  - Rejected: inline editing directly on the public page (click a field, save). That would mean new public write endpoints with hand-rolled auth — the classic place a solo founder ships an `is_admin` bug. Reusing Filament means the form, validation, and policy already exist and are already tested.
  - Result: spoofing the bar's HTML grants nothing, because the destinations re-check auth independently.

- **Gate the bar on `isAdmin()`, not on `@can('update', $venue)`.** *(permanent)*
  - The `VenuePolicy` lets owners pass `update` for venues they've claimed (and `before()` lets admins pass everything). Gating on `update` would leak the bar to owners on their own pages. The role check is the correct, narrower gate and matches how `canAccessPanel` already decides "admin".

- **Cache global queue counts for 60 seconds.** *(revisit if counts feel stale)*
  - The badges run three aggregate queries; without caching they'd fire on every admin pageview. 60s is a fair trade between freshness and load. The cost is that resolving a queue item can lag up to a minute in the badge.

- **Class-based component over an anonymous Blade component.** *(permanent)*
  - The logic (auth gate, cached aggregates, per-venue URLs) belongs in testable PHP, not in the template. Note for future work: in a class component, public methods are exposed to the view as closures (`$venuesUrl()`), not via `$this->venuesUrl()`.

- **One-click publish toggle and owner-impersonation were deferred.** *(revisit post-launch)*
  - A publish/unpublish toggle is genuinely useful but is a write action — it would be a conscious exception to the "no new write endpoints" rule and needs its own policy check + test. Impersonation is the highest-risk admin-bar feature and needs audit logging. Both deferred past launch.

## Technical Debt Log

| Item | Where | Priority | Notes |
|---|---|---|---|
| Queue-count cache invalidation | `AdminBar::globalQueueCounts()` | Low | Counts lag up to 60s after a queue item is resolved. Acceptable for admin-only traffic; revisit if it causes confusion. |
| Per-venue report link is unfiltered | `admin-bar.blade.php` (Zgłoszenia link) | Low | The open-report link lands on the reports index, not pre-filtered to this venue. Filament table filter query-params are fragile; the count badge already tells the admin there's something to look at. |
| Publish toggle deferred | Admin bar Tier 3 | Medium | No fast publish/unpublish from the bar yet; admins still go into Filament to change `is_active`. Build as a deliberate, policy-checked exception if it becomes a bottleneck. |
| Local `UNI Density:*` fixtures still active | DB (from Session 1) | Medium | Carry-over: deactivate before any production-like data export. |

## Risk Register

- **Cache staleness on queues.** Low impact: an admin might see a count that's up to 60s out of date. Mitigation: short TTL; could bust the cache on queue writes later if needed.
- **GDPR deadline reliance.** The erasure "pilne" badge is now a primary visual cue for a legal deadline. If the badge logic regresses, a deadline could be missed. Mitigated by a test asserting the due-soon path, but the real backstop should remain whatever notification/escalation exists server-side — the bar is a convenience, not the system of record.
- **Tailwind build drift.** New bar classes (zinc/amber/red badges) require a built stylesheet. `npm run build` was run this session; if the bar looks unstyled locally, rebuild.

## What to Test in the Browser

- Log in as an **admin** and open any public page — the dark bar should appear at the very top, sticky on scroll.
- The environment badge should read your current environment; on production it should be **red**.
- Create or have a pending claim / inaccuracy report and confirm the **Przejęcia** / **Zgłoszenia** badges show a count.
- Have an erasure request due within 7 days and confirm **Usunięcia** turns red with a "pilne" count; click it and confirm it lands on the erasure queue.
- Open a venue page as admin: confirm **Edytuj** and **Statystyki** deep-link into the Filament edit/analytics pages, and that "Przejęte" links to the claim.
- Log in as a non-admin **owner** (even on your own claimed venue) and as a **guest** — confirm the bar does not appear at all.

## Business Impact

- **Faster daily operations for a solo founder.** Fixing venue data no longer means navigating into the admin panel from scratch each time — the edit/analytics pages are one click from the live page. This compounds across the constant small corrections a directory needs before and after launch.
- **Legal risk made visible.** GDPR erasure requests carry a statutory deadline. Surfacing "X due soon" on every admin page turns an invisible clock into something hard to miss — directly de-risking a compliance failure in launch month.
- **Operational queues stop hiding.** Pending claims and accuracy reports are the raw material of a trustworthy directory; a persistent badge means they get worked, not forgotten.

## Session 3 — Polish localization: locale flip + full admin panel translation

## Session Overview

**Goal:** Run a Polish translation audit and fix the mixed Polish/English UI. The app
serves Polish users and businesses, but large parts of the experience were leaking
English.

**Outcome:** Two distinct problems found and fixed. First, a one-line root-cause bug:
the app's locale was set to English (`APP_LOCALE=en`), so every framework-generated
string — all Filament buttons, the venue-owner login page, table pagination/search,
form-validation errors, and the boilerplate in our notification emails — rendered in
English even though our own labels were Polish. Second, the internal admin panel's core
catalog (venues, products, brands, producers, categories, users, dashboard widgets, and
the analytics diagnostics screen) had never been translated. Both are now fully Polish.
All 523 tests pass.

## What Was Built

- **Locale flipped to Polish.** `APP_LOCALE` and `APP_FALLBACK_LOCALE` set to `pl` in
  `.env` and `.env.example`. This single change makes Filament render its entire UI in
  Polish (it ships a complete Polish translation set), fixing the venue-owner panel chrome
  that Polish business users actually see.
- **Polish framework translations added.** Created `lang/pl/validation.php`, `auth.php`,
  `passwords.php`, `pagination.php`, and `lang/pl.json`. These translate Laravel's
  built-in form-validation messages, password-reset messages, pagination, and the
  English boilerplate in notification emails ("Regards," → "Pozdrawiamy,", the
  copy-paste-the-link helper text, and the email footer).
- **Notification emails fully Polish.** The bodies were already Polish; the surrounding
  template chrome now is too (via `lang/pl.json`), so password-reset, email-verification,
  claim-approved/rejected, and erasure emails read as one coherent Polish message.
- **Entire admin catalog translated.** Navigation labels, model names, form fields,
  helper texts, table columns, filters, actions, modal confirmations, empty states,
  notifications, the importer, and dashboard widgets across Venues, Products, Brands,
  Producers, Categories, and Users. Added explicit Polish labels to fields that were
  previously relying on Filament's English auto-labels.
- **Analytics screens translated.** The admin venue-analytics diagnostics page (Free /
  Basic / Pro / Premium tiers), the owner-analytics preview partial, the venue-analytics,
  quick-info, mini-map, and discovery-insights widgets. The underlying report service was
  also Polished where it emits user-facing text: day-of-week abbreviations (Pn, Wt, Śr…)
  and the seasonal-forecast guidance notes.
- **`UserRole` enum now carries Polish labels** (implements `HasLabel`), so the admin
  Users table shows "Administrator / Właściciel lokalu / Użytkownik" instead of raw
  `admin/owner/user`.
- **Tests updated** to assert the new Polish strings (admin analytics page/widgets,
  discovery insights, engagement stats, venue list).

## Decision Register

- **Flip `APP_LOCALE` to `pl` rather than leaving English chrome.** The owner panel is
  used by Polish venue owners; a half-Polish/half-English screen undermines trust. Filament
  ships Polish, so the fix is essentially free. Rejected: leaving locale at `en` and
  hand-translating only our own labels (would still leave buttons, pagination, validation
  in English).
- **Translate the internal admin panel too (founder's request).** Even though it's
  founder-only tooling, we chose full Polish consistency over leaving it English. The
  moderation queues were already Polish; this removes the awkward split.
- **Translate enum *display* but keep backing values.** `catalog_completeness` level
  ('high/medium/low') and similar are mapped to Polish at the view layer only, because the
  string values are used in conditional logic. Changing the stored value would have broken
  comparisons.
- **Used `lang/pl.json` for mail chrome** rather than publishing/editing vendor mail Blade
  views — less surface area, survives framework updates, and is the idiomatic Laravel way
  to translate `@lang()` string keys.

## Technical Debt Log

- **Two locale sources of truth for plural-sensitive validation.** The Polish
  `validation.php` uses single-form messages for size rules (min/max/between) rather than
  full 3-form Polish pluralization. Acceptable and standard, but if precise grammar matters
  later, switch those to pluralized forms.
- **`lang/en/` is still present** (published defaults). Harmless with `pl` fallback; left
  in place as reference. Can be deleted if we want a pure single-locale tree.

## What to Test in the Browser

1. Owner panel (`/panel`): log in — the login page, "Zapisz zmiany"/"Utwórz"/"Usuń"
   buttons, table search and pagination, and modal confirm/cancel should all be Polish.
2. Trigger a validation error on the public register/login/claim forms — messages should be
   Polish ("Pole … jest wymagane").
3. Send yourself a password-reset or verification email — the closing ("Pozdrawiamy,"),
   the button helper text, and the footer should be Polish.
4. Admin panel: open Venues, Products, Brands, Producers, Categories, Users — all labels,
   filters, and the venue analytics/diagnostics page in Polish.

## Session 4 — Discovery web quality hardening

## Session Overview

**Goal:** Fix the `/mapa` web-quality audit issues regardless of priority, then verify the
actual impact with tests, build output, rendered HTML checks, and Lighthouse.

**Outcome:** The discovery page now passes the audit's accessibility failures and renders a
much smaller initial list. Lighthouse accessibility is now 100 for `/mapa`. The remaining
Lighthouse warnings are deployment/environment items: HTTP instead of HTTPS, local
`public/hot` dev-server mode, source-map/cache headers, and framework/vendor JS weight.

## What Was Built

- **Initial discovery list capped to 24 visible venue cards** in `DiscoveryPage`.
  - The map still receives all matching venues, so users do not lose pins when the list is
    shortened.
  - A `Pokaż kolejne lokale` button loads the next 24.
  - Search, filters, geolocation, and map-bounds changes reset the visible limit to 24.
  - Rendered `/mapa` HTML in the local dataset dropped from about **1.31 MB** in the audit
    run to about **675 KB**, with 24 rendered `.venue-item` cards.

- **Leaflet popup/tooltip HTML now sanitizes data before injection.**
  - Venue names, addresses, venue types, freshness labels, and category labels are escaped
    in `resources/js/discovery.js`.
  - Category colors and SVG icons are constrained before being inserted into marker/popup
    HTML.
  - Slugs used in popup links are URL-encoded.

- **Accessibility and Lighthouse fixes for `/mapa`.**
  - Added a page `h1` for the discovery page and changed venue card titles from `h3` to
    `h2` so the heading order is valid.
  - Changed the Leaflet map container from `role="application"` to `role="region"` with a
    clear label; the app does not implement full application-mode keyboard semantics.
  - Fixed low-contrast result metadata and venue tile metadata by moving from
    `text-fg-faint` to `text-fg-muted`.
  - Removed the mismatched venue-card link `aria-label`, so the accessible name matches
    the visible content.
  - Removed the mismatched mobile list/map toggle `aria-label`; the visible text now is
    the accessible name.
  - Fixed the hidden mobile drawer by adding/removing `inert` alongside `aria-hidden`.
  - Corrected the screen-reader live region so it announces `64 lokale`, not `64 64 lokale`.

- **Regression coverage added** in `tests/Feature/DiscoveryPageTest.php`.
  - Initial render is capped at 24 cards.
  - Map data still includes all matching venues.
  - Loading more expands the visible list.
  - Filter changes reset the visible limit.

- **SSOT updated** in `inspo/interactive_v1_feature_spec_SSOT.html`.
  - Discovery feature section now documents the 24-card initial list, load-more behavior,
    map payload separation, popup sanitization, and Lighthouse/accessibility outcome.
  - Frontend and accessibility audit sections now reflect the fixed `/mapa` findings.
  - Launch-readiness notes now distinguish code-level discovery fixes from remaining
    deployment issues.

## Decision Register

- **Cap rendered cards, not map results.**
  - Chosen because the oversized HTML came mostly from rendering every venue card. The map
    is the core discovery surface, so pins must still represent every matching venue.
  - Tradeoff: the list now has progressive reveal. This is acceptable because users can
    still scan the map and load more list cards explicitly.

- **Use `role="region"` for the map.**
  - `role="application"` is only appropriate when the component implements a complete
    application-style keyboard model. Leaflet does not make the whole UNI map a custom
    ARIA application. A labelled region is the more honest accessible structure.

- **Leave deployment warnings as deployment work.**
  - The local `public/hot` marker was restored after verification because it was present
    before this session.
  - HTTPS, cache headers, and source-map policy belong in production deployment, not in
    the discovery Blade fix.

## Risk Register

- **Progressive list reveal could hide venues from users who only scan the list.** Mitigated
  by clear load-more copy and preserving all pins on the map.
- **Popup SVG sanitization is intentionally conservative.** If an admin enters an unusual
  but valid SVG format, the marker may omit the icon rather than render unsafe markup.
- **Performance is still limited by local/dev conditions.** Production assets improved the
  Lighthouse total byte weight compared with dev assets, but local HTTP, cache headers, and
  Livewire framework JS still keep the performance score below launch targets.

## What to Test in the Browser

1. Open `/mapa` and confirm the list initially shows 24 venues plus a `Pokaż kolejne lokale`
   button when more results exist.
2. Click `Pokaż kolejne lokale`; more cards should appear without removing map pins.
3. Change search, city, category, freshness, verified, strict-zero, or map bounds; the list
   should reset to the first 24 matching cards.
4. Open a marker popup and confirm venue name, address, categories, freshness, and profile
   link render correctly.
5. On mobile, switch between `Mapa` and `Lista`; screen-reader-visible text should match the
   button's visible label.
6. Open/close the mobile drawer and confirm hidden drawer links are not keyboard-focusable.

## Business Impact

- **Faster first impression.** The discovery page no longer ships every venue card in the
  first HTML response, which lowers the first-load cost for the main consumer entry point.
- **Trust and safety improve.** Escaping map popup content removes a client-side injection
  risk in a surface that displays admin-entered venue/category data.
- **Accessibility is no longer a launch blocker for `/mapa`.** Lighthouse accessibility now
  reports 100 for the page, and the exact earlier failures are cleared.
