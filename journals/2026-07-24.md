# 2026-07-24 — Untangling the SSOT: what belongs where, and moving the compliance audits into docs/

## Session Overview

**Goal:** figure out what the giant interactive spec file (`inspo/interactive_v1_feature_spec_SSOT.html`) is actually *for*, and split out the parts that had crept in but don't belong there. It had grown to 693 KB by absorbing three very different kinds of content: the real product spec, day-to-day work logs, and frozen audit reports.

**Outcome:** established a clear, one-line rule for where every kind of project knowledge lives, then acted on it. The SSOT shrank from **6,785 → 5,702 lines (−1,083, ~16% lighter)**. The four compliance audits and the package-recommendations list were promoted into proper markdown files under `docs/` (which are readable on your phone via Obsidian/GitHub), and the SSOT now links to them instead of holding stale copies. The pure work-log sections (TODOs, bug log) were deleted because journals already cover them. No product code, database, or tests were touched.

## The core idea (why this session mattered)

The SSOT was becoming a place where the "single source of truth" quietly contradicted fresher copies elsewhere. We separated content by **lifecycle**, not topic:

- **Describes the current/target product** → stays in the SSOT (spec, decisions, versions) + links out.
- **Dated session history** (todos, "what shipped today", bug fixes) → belongs in `journals/`.
- **Canonical reference / audit records** → belongs in `docs/` as markdown; the SSOT links to it.

A key surprise drove the approach: several `docs/compliance/` files were **older** than the audit content sitting in the SSOT. So the fix wasn't "link the SSOT to docs" — it was "promote the fresh SSOT content *into* docs, then link." Linking to the stale files would have made the record worse.

## Decision Register

- **Sort project knowledge by lifecycle, not topic.** Product-state → SSOT; dated history → journals; reference/audits → docs/. *Rejected:* keeping everything in one mega-SSOT (unnavigable, self-contradicting) and a pure "topic" split (doesn't tell you where a bug log vs a feature spec goes). **Status: permanent.**
- **When `docs/` is staler than the SSOT, promote the SSOT content into `docs/` — never link to the stale file.** *Rejected:* the original plan of "replace SSOT sections with `see docs/…` links", which we discovered would have pointed at May-dated compliance drafts that are thinner than the June SSOT audits. **Status: permanent.**
- **Migrated sections leave a pointer stub that keeps its anchor id.** *Rejected:* deleting sections outright (would break every in-page and sidebar link to them). **Status: permanent.**
- **Prefer markdown in `docs/`/`journals/` over the HTML SSOT for reference material.** Reason: a 693 KB HTML file is unusable on a phone; markdown renders natively in Obsidian and GitHub mobile. Chose Obsidian over publishing the HTML as a hosted artifact (a snapshot would need constant re-syncing). **Status: decided.**
- **Engineering/UX audits: not migrated verbatim.** Decision is that resolved findings are low-value to relocate; the plan is to eventually collapse them to a one-line status each and leave detail in git history — but this was **not done this session** (see backlog). **Status: pending.**

## Learning Path

- **"Docs-as-code."** Keeping documentation as markdown in the repo (reviewed with code, exported to PDF only for signing) — your `docs/README.md` already commits to this; this session made the compliance area actually follow it.
- **Single Source of Truth, done right.** An SSOT works only when each fact lives in exactly one place; the failure mode is a "truth" file that accumulates copies. Search "single source of truth documentation antipattern."
- **Information architecture by lifecycle.** The insight that *how often a thing changes* (and who reads it) should decide where it lives — not what topic it's about.
