# 2026-06-18 — UI Polish: Brighter Colours, Tile Declutter, Show Page Card, Multi-City Flag

## Session Overview

**Goal:** A series of iterative UI improvements to the discovery tile and venue profile, driven by visual feedback — colours too dull, mobile tiles too cluttered, venue profile visually disconnected from the tile's design language, and a city-selector that shouldn't be visible for the Warsaw-only v1 launch.

**Outcome:** Six changes across four files. Beverage category colours are significantly brighter. The venue tile is cleaner on mobile (2-column grid, no quantity numbers, larger dots). The venue profile now shares the tile's card aesthetic — a surface + border wrapper with a stats strip at the bottom showing product count and coloured category icons. The freshness pill on the profile page matches the tile's tinted pill treatment. A `multi_city` feature flag in `config/uni.php` gates the city selector behind an environment variable, keeping it available for future expansion without showing it to Warsaw-only v1 users.

## What Was Built

### 1. Brighter beverage category colours — `resources/css/app.css`

**What changed:** Six CSS custom properties updated. All moved from desaturated, muted tones to vivid, high-saturation versions.

| Variable | Old | New | Category |
|---|---|---|---|
| `--color-drink-piwo` | `#B87A5E` (muted amber-brown) | `#F5A623` (golden amber) | Beer |
| `--color-drink-wino` | `#9b6b9b` (dusty mauve) | `#C44B9A` (vivid magenta-rose) | Wine |
| `--color-drink-spirits` | `#7c9b5e` (sage green) | `#5DBB63` (fresh green) | Spirits |
| `--color-drink-drinks` | `#5e8db8` (slate blue) | `#3BA7F5` (bright sky blue) | Cocktails |
| `--color-drink-cydr` | `#b8a25e` (khaki) | `#E8C840` (vibrant yellow-gold) | Cider |
| `--color-drink-musujace` | `#5eb8a2` (muted teal) | `#2ECFB4` (bright teal/mint) | Sparkling |

**Why:** These colours are the primary visual identity signal of the app — they appear in category pills, dot bars, icon tints, and the stats strip on the profile page. At their original saturation they blended into the dark background and failed to create the immediate "drink taxonomy at a glance" recognition that is the tile's core value. The new values are 30–40% more saturated while staying on-brand tones (earthy for beer/cider, jewel tones for wine/cocktails).

**Current state:** Active across every surface that uses these variables — discovery tiles, venue profile accordion, venue profile stats strip, category pills.

### 2. Venue tile declutter — `resources/views/components/venue-tile.blade.php`

**What changed:** Four targeted improvements:

**a) Larger, more breathable dots**
- `w-1.5 h-1.5` (6×6 px) → `w-2 h-2` (8×8 px)
- `gap-0.5` (2 px) → `gap-1` (4 px)

**b) 2-column category grid (was 3)**
- `grid-cols-3` → `grid-cols-2`
- On a narrow mobile screen (~375px with 20px side padding), the 3-column grid gave each column ~80px — not enough for 8 dots at 8px with 4px gaps (which requires ~92px). The 2-column grid gives ~160px per cell, eliminating wrapping.

**c) Quantity number removed from dot row**
- The `{{ $row['count'] }}` number next to each dot bar was removed.
- The dots remain and carry the quantity signal visually. Users who need the exact number can count the dots (max 8) — the founder's explicit decision.

**d) "X/Y kategorii" footer badge removed**
- The green `X/Y kategorii` badge in the card footer was removed entirely.
- `$categoriesUsed` and `$totalCategories` variables cleaned up from the PHP preamble.
- The product count in the footer was restyled: from `text-fg-subtle "X prod."` (small, muted) to a bold number `text-sm font-bold text-fg` followed by `text-xs text-fg-subtle "produktów"` — giving it the visual weight of a stat rather than a footnote.

**e) District badge more prominent**
- `text-xs text-fg-subtle border border-ui` → `text-xs font-medium text-fg border border-ui-strong`
- The district is valuable location context. Previously it looked identical to other muted metadata and was easy to miss.

**Why this matters:** On mobile, cards are the entire product experience — there is no sidebar or map visible. A cluttered card that wraps text onto multiple lines makes the product feel janky, which undermines trust before a user has even looked at a venue. The 2-column grid + removal of the quantity number removes the two primary sources of wrapping without losing meaningful information.

**Current state:** Tile renders cleanly on mobile. `$dotTotal = 8` and the filled/empty loop remain. `$totalProducts` still calculated and shown in footer.

### 3. Venue profile card treatment + stats strip — `resources/views/venues/show.blade.php`

**What changed:** Five improvements:

**a) Hero section wrapped in a surface card**
- The hero grid (`flex flex-col lg:grid lg:grid-cols-5`) is now wrapped in `<div class="rounded-2xl bg-surface border border-primary/20 overflow-hidden mb-8">`.
- Inner div gets `p-6 lg:p-8` padding.
- The `<hr class="my-6 border-ui" />` separator after the hero was removed — the card itself provides visual separation.

**b) Stats + category icon strip at the bottom of the hero card**
- A new `border-t border-primary/10` footer strip was added inside the card, below the hero grid:
  - Left: bold product count `text-sm font-bold text-fg tabular-nums` + `"produktów"` label — matching the tile footer's treatment
  - Right: coloured category icons from `$accordionCategories` with a count per category (`text-xs text-fg-subtle tabular-nums`)
- This gives the profile page an immediate visual summary that mirrors the tile's dot-bar pattern, but at the detail-page scale where there's room for icons + numbers.

**c) Freshness pill upgraded to proper pill treatment**
- Old: `<span class="text-[11.5px]" style="color: {{ $freshnessColor }}">{{ $freshnessLabel }}</span>` (plain coloured text inline in the "Menu" heading row)
- New: `<span class="inline-flex items-center text-[11px] font-medium px-2.5 py-1 rounded-full" style="background: color-mix(in srgb, {{ $freshnessColor }} 16%, transparent); color: {{ $freshnessColor }};">` — exactly matching the tile's freshness pill treatment.
- The freshness indicator now feels like a status badge, not an afterthought.

**d) Nearby venue cards get the primary border treatment**
- `bg-surface rounded-xl p-4 hover:bg-surface-hover` → added `border border-primary/20 hover:border-primary/40`
- Consistent with the venue tile card style. Without this, nearby cards looked like a different visual component to the main page tiles.

**Why this matters:** The tile and the profile page are viewed in sequence — the user sees a tile in the list, taps it, lands on the profile. Before this session, the profile page had no visual relationship to the tile — it was a flat two-column layout with no card framing. Now the hero card uses the same `bg-surface border-primary/20 rounded-2xl` vocabulary as the tile, creating continuity. The stats strip at the bottom bridges the two views: the same bold product count and category icons that appear in the tile are echoed at the bottom of the hero card before the user scrolls to the menu.

**Current state:** Profile hero is a card. Stats strip shows correct data from `$accordionCategories` (already computed for the accordion). HR removed.

### 4. Multi-city feature flag — `config/uni.php` + `resources/views/livewire/discovery-page.blade.php`

**What changed:**
- Added to `config/uni.php`:
  ```php
  'multi_city' => (bool) env('UNI_MULTI_CITY', false),
  ```
- Changed the city multi-select gate in `discovery-page.blade.php` from:
  ```blade
  @if ($cities->count() > 1)
  ```
  to:
  ```blade
  @if (config('uni.multi_city') && $cities->count() > 1)
  ```
- A comment on the Blade line explains the gate and how to re-enable: `set UNI_MULTI_CITY=true`.

**Why:** The v1 launch is Warsaw-only. The "Miasta" selector is meaningless when there is one city — it adds noise to the filter row, confuses users, and makes the product look unfinished (a dropdown with one option). However, the multi-city codebase is fully built and must not be hard-deleted. The feature flag approach means:
- v1 launch: selector hidden, zero user friction
- Multi-city expansion: add `UNI_MULTI_CITY=true` to the server's `.env` — no code change required

**Current state:** City selector hidden by default. `$cities` collection is still computed by the Livewire component (no server cost removed). The gate only prevents rendering.

## Business Impact

**Colour is free signal.** The most common first reaction to the discovery page is a rapid scan for "does this place have what I want?" The category dot bars encode that answer, but only if the colours are legible at a glance. Vivid amber for beer, vivid magenta for wine — these map to mental models users already have. Muted versions of those colours just look like UI noise. Brightening them costs nothing and directly improves the speed of the discovery moment.

**Mobile-first declutter = more tiles per minute.** On a phone, a user scanning the venue list is swiping through cards. Each card that wraps text or has misaligned elements costs a fraction of a second to parse, and that friction compounds across 20 venues. The 2-column grid eliminates the layout fragmentation that was making tiles feel unpolished. A clean, scannable card earns a tap; a cluttered one gets scrolled past.

**Profile page visual continuity = trust.** A product where the list view and the detail view look like they were designed by two different people feels unfinished. The hero card now speaks the same language as the tile — same surface, same border, same stats treatment. A founder-level insight: the first thing investors or potential venue partners see when you send them a link is the profile page. It now looks like a product, not a prototype.

**Multi-city flag = commitment to Warsaw without closing the door.** Removing the city selector for v1 makes the discovery page feel complete and intentional rather than "we built multi-city but only have one city." When Warsaw is validated and Kraków or Wrocław is next, flipping `UNI_MULTI_CITY=true` in the server env is a 10-second operation. This is the right balance between launch focus and future scalability.

#### 4. SEO soft 404 fixes — `CityController`, `city/show.blade.php`, `categories/show.blade.php`, `SitemapController`

**The problem:** Google's "soft 404" penalty applies when a page returns HTTP 200 but contains no useful content — an empty venue list with "Brak lokali" text and a navigation link. Google sees this as a content-empty page claiming to be a valid URL. It wastes crawl budget and can depress the domain's trust signal.

**Four fixes applied:**

**Fix 1 — `CityController::district()`:** Added `abort_if($venues->isEmpty(), 404)` after fetching the venue list. A district URL with zero active venues now returns HTTP 404. The sitemap already filtered out empty districts, so legitimate indexed URLs will never hit this. The abort protects against URLs that were once valid but became empty as venues deactivated.

**Fix 2 — `city/show.blade.php`:** Added `@if ($stats->total === 0)` guard emitting `<meta name="robots" content="noindex, follow" />`. A city overview page with zero venues won't be indexed. (A hard 404 would be wrong here — the city exists as a data entity; it just has no venues yet.)

**Fix 3 — `categories/show.blade.php`:** Same `noindex` guard when `$venues->isEmpty()`. A category page with no venues in Warsaw is not indexable content.

**Fix 4 — `SitemapController`:** Two additions:
- Cities: added `->whereHas('venues', fn ($q) => $q->where('is_active', true))` to the `$activeCities` query. A city without active venues no longer gets a sitemap entry.
- Categories: added `->whereHas('products.venues', fn ($q) => $q->where('is_active', true))` to the category loop. A category with no active venues in any venue's menu no longer gets a sitemap entry.

**Why sitemap hygiene matters:** The sitemap is a contract with Google — "I am claiming these URLs have content worth indexing." Breaking that contract by listing URLs that return noindex or 404 wastes crawl budget and signals that the site owner doesn't understand their own content. Filtering at the source is cleaner than patching each page.

**Current state:** All 53 city/category/sitemap tests pass. No regression.

#### 5. Venue JSON-LD fixes — `resources/views/venues/show.blade.php`

**The problem:** The `LocalBusiness` JSON-LD block had three issues that would cause Google's Rich Results validator to reject it:
1. **Null fields serialised as JSON `null`** — when a venue has no phone or no coordinates, `json_encode` produced `"telephone": null` and `"geo": null`. These are invalid in JSON-LD; a missing property must be omitted, not nulled.
2. **No `@id`** — Schema.org's LocalBusiness requires a stable identifier for Google to connect the entity to its Knowledge Graph.
3. **No `sameAs`** — Instagram handles and website URLs, when present, should be declared as same-as links to help Google understand the entity across the web.

**Fixes applied:**
- Wrapped the schema array in `array_filter()` to strip null values before `json_encode`.
- Added `'@id' => route('venues.show', $venue->slug)` — the canonical URL is the stable entity ID.
- Added `'sameAs'` array populated from `$venue->website_url` and `$venue->instagram_handle` (constructed as full Instagram URLs), filtered to remove nulls.

**Current state:** Venue pages now emit valid JSON-LD. The Instagram URL is constructed as `https://www.instagram.com/{handle}` with `ltrim('@')`.

#### 6. WebSite schema + og:site_name — `resources/views/home.blade.php`, `resources/views/layouts/app.blade.php`

**`og:site_name`:** Added globally in `layouts/app.blade.php` above the `@stack('meta')` push. Every page now declares `<meta property="og:site_name" content="Under No Influence" />`. This is a one-line addition that improves how link previews render on social platforms — the site name appears beside the page title.

**`WebSite` JSON-LD on homepage:** Added a `WebSite` schema block with:
- `@type: WebSite` with a `#website` fragment `@id`
- `name`, `url`, `description`, `inLanguage: pl-PL`
- `potentialAction` — a `SearchAction` pointing to the discovery page with a `q` query parameter

**Why the SearchAction matters:** Google uses this to display a sitelink search box in its results — when someone searches for "Under No Influence" on Google, a search input can appear directly in the search result, pointing at the discovery page. It's not guaranteed, but declaring it is the prerequisite.

**Current state:** Homepage emits valid WebSite JSON-LD. og:site_name is global.

### Business Impact

**Removing /dla-lokali eliminates a credibility trap.** Any venue owner who found the old page and read about a self-service panel, analytics dashboard, and verified badge flow would contact UNI expecting to be able to set up these things themselves. That conversation damages trust before a relationship has started. With the page gone, owners who contact UNI get a direct, honest response: "we add and verify venues manually, here's how it works."

**The SEO fixes protect launch-day crawl quality.** Google's first crawl of a site after launch is disproportionately important — it sets the baseline for how much the domain is trusted. Soft 404s and sitemap URLs that return noindex degrade that first impression. Fixing them before launch means the first crawl sees a clean, internally consistent site: every URL in the sitemap has content, every content page is indexable, and there are no 200-responses pretending to be 404s.

**WebSite schema + SearchAction is a small bet on a sitelink search box.** When "Under No Influence" becomes a known brand query in Google, this schema is what triggers a search input directly in the search result. It costs nothing to add and has no downside. The upside is that a user searching for the brand can jump straight to a specific venue search without visiting the homepage first.

**Blocking all AI crawlers protects the core asset.** The venue database — manually curated, verified, structured — is what makes UNI worth using. If that data is absorbed into AI systems before UNI has established a distribution moat (users who come back, SEO rankings, brand recognition), then the data has been given away for free. The robots.txt block is not a guarantee (determined scrapers ignore it) but it signals intent and increases the legal/ethical weight of any future enforcement if canary venues surface in a competitor's product.

**What changed:** Two env variables were missing from `.env`, causing both the client-side snippet and the `PostHogService` server-side captures to short-circuit on every request:

## Session 6 — Blade @context Bug Fix, Code Review, PostHog Audit, SSOT Restructure

### Session Overview

**Goal:** Fix a homepage 500 error, run a code review on the current diff, verify PostHog's installation end-to-end, and restructure the feature spec SSOT into a coherent, version-separated document.

**Outcome:** Two silent bugs fixed (one causing a 500, one corrupting all venue JSON-LD silently). Full PostHog integration audited and inventoried. SSOT restructured from a flat 30+ item list into 7 clearly separated groups with version dividers, a dedicated PostHog Integration section, and cross-links between related sections.

---

### What Was Built

#### 1. Homepage 500 fix — Blade `@context` directive clash

**Root cause:** Laravel 13 introduced `@context` as a Blade directive. The WebSite JSON-LD block in `home.blade.php` contained `"@context": "https://schema.org"` in a raw `<script>` block. Blade's parser scanned the template text and compiled `@context` as a PHP directive — `if (context()->has(...))` — which was never closed, causing a `ParseError` at compile time.

**Fix:** Changed `"@context"` → `"@@context"` in the JSON-LD block. In Blade, `@@` outputs a literal `@` in the rendered HTML.

**Why this is subtle:** Blade's directive parser is positional — it scans ALL text in a template file for `@keyword` patterns regardless of whether they appear inside `<script>` tags, PHP string literals, or HTML attributes. The fix is the same everywhere: `@@context` → rendered as `@context`.

---

#### 2. venues/show.blade.php — silent JSON-LD @context corruption

**Found by:** Code review of the working tree diff. Zero user-visible symptoms — no 500 error — but all venue pages were emitting broken JSON-LD.

**Root cause:** `'@context' => 'https://schema.org'` inside a PHP array literal within a `{!! json_encode([...]) !!}` block. Blade compiled the array key into a PHP directive call, corrupting the array before `json_encode` ran. Confirmed by reading the compiled view file in `storage/framework/views/`.

**Fix:** Changed `'@context'` → `'@@context'` in the PHP array inside the Blade template.

**Business impact:** Every venue page was serving broken structured data to Google since this code was deployed. Google's Rich Results validator would have rejected every LocalBusiness schema. The fix restores valid JSON-LD across all ~63 Warsaw venue pages.
