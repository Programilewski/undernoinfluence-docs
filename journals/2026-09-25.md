## Decision Register

### 1. Every process that writes the application's logs shares a umask

**Chosen:** all three writers — cron, the queue worker and php-fpm — run with umask 0002, set explicitly at each one.

**Rejected:** running everything as a single user, which would collapse the deploy user into the web user and hand the web server write access to the code it serves. Also rejected: a separate log file per writer, which splits one day's story across three files; and a nightly `chmod` to repair it, which fixes the symptom forever while the cause survives.

**Why it came up at all:** the worker runs as the web user, cron runs the scheduler as the deploy user, and both append to the same daily log file — which is created fresh at midnight by whichever arrives first. With the default umask that file is not group-writable, so the first writer locks the others out until the next midnight, and **the ones locked out fail with no error anywhere.**

**Status:** permanent. The specific value follows from the rule, which is that the writers agree.

### 2. A queued job waits; it is not lost

**Chosen:** the documents describe what actually happens — queued work waits in a table and is delivered when a worker runs — and state the recovery, which is to start the worker and let the backlog drain.

**Rejected:** leaving the existing wording ("lost, not delayed") on the grounds that it conveys the right urgency. Also rejected: simply replacing "lost" with "delayed", which understates what the owner experiences and makes the checklist row read as optional.

**Why it matters more than a word:** somebody who believes the mail was destroyed goes hunting through the database to work out who was never told, and sends it again by hand — on top of a backlog that is about to deliver itself. **Duplicate mail to venue owners is worse than the original silence**, because it is the first thing the product does after failing them.

**Status:** permanent while the queue is a database table. A move to an in-memory driver makes the old wording correct again and would have to carry the record with it.

### 3. Regex ordering in the web server config is load-bearing

**Chosen:** the PHP handler first, the `.mjs` type rule second, the versioned-asset cache rule third — with a comment in the file saying why the order cannot be changed.

**Rejected:** putting the new cache rule at the top where it reads most naturally.

**Why:** the web server takes the **first** matching pattern. A cache rule above the `.mjs` rule wins for the map library's own files, takes the JavaScript content type with it, and **every map on the site goes blank again** — while the change reads as a caching tweak. Moving the PHP handler to the top is defence of a different kind: no PHP lives under those paths today, but if any ever did, a pattern above it would serve the source of the file to anyone who asked.

**Status:** permanent, and the reasoning lives in the config file rather than only here.

### 4. The environment keeps its own secret

**Chosen:** the backup archive password was generated on the box with `openssl rand` and never printed into the session transcript. You read it out yourself and put it in your password manager.

**Rejected:** generating it on the laptop and copying it over, and printing it for convenience.

**Why:** a secret that has only ever existed in one place cannot have leaked from a second one. The counterweight is real and worth naming: **an encrypted archive whose password exists nowhere is not a backup, it is a tidy way of deleting data on a schedule.** Which is why reading it out is a backlog item and not an afterthought.

**Status:** permanent — it is the same rule already applied to `APP_KEY` and the database password.

## Learning Path

Four ideas from today, each worth ten minutes because each explains a whole class of future problem.

**A running process is not a working one.** `supervisorctl` reporting RUNNING proves a process exists. A worker pointed at the wrong queue, started before the database was reachable, or running last week's code all report RUNNING. The only real proof is work going in and coming out — which is why the evidence in this journal is a consumed job with a duration, not a status line.

**Silent failures are the expensive ones.** A web server failure is loud and gets fixed in an afternoon. A scheduler that never runs, a log write that is refused, an asset served with the wrong content type — all three produce a system that looks correct from every angle. Almost all of today's work was on the silent half, and the heartbeat exists because a healthy machine with a broken crontab is indistinguishable from a healthy machine.

**Two settings decide a file's permissions, not one.** One setting decides which group a new file belongs to; another decides whether that group may write to it. Each is useless alone, and getting one right feels like getting it right. This is the shape of decision 1 and it recurs on every server with more than one user.

**First match wins.** The web server takes the first pattern that matches a URL, not the best one. That single sentence explains both why the map broke three days ago and why today's caching change had to go below it rather than above it.
