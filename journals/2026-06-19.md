### What Was Built

#### PostHog analytics phrasing fix (`inspo/interactive_v1_feature_spec_SSOT.html` — analytics section)

The "Third-party analytics data map" paragraph previously said *"PostHog is not the V1 canonical analytics source. It is now explicitly config-gated: POSTHOG_PUBLIC_ENABLED=false and POSTHOG_SERVER_ENABLED=false by default."* This was wrong on both counts — PostHog has been live in production since 2026-06-18 with both flags set to `true`.

The paragraph was rewritten to: *"PostHog is additive — it mirrors the same events as the first-party stack but is not a replacement for canonical analytics data. Both SDKs are enabled in production. First-party events table + venue_stats remains canonical for all owner-facing reports and B2B analytics — PostHog is used for session exploration, funnel analysis, and behavior debugging."*

**Why it matters:** The old text would mislead any future developer into thinking PostHog was off by default and optional. The new text accurately describes the dual-system architecture and prevents the temptation to shortcut owner-facing analytics through PostHog.

#### `map_area_searched` double-capture documented in `#todos`

Added a red-bordered technical debt callout to the TODOs section explaining that `map_area_searched` fires twice for the same user action — once from the PHP/Livewire server side (on component re-render after bounds filter) and once from the `discovery.js` JS client side (on "Search this area" click). This results in doubled PostHog event counts for that action.

The callout documents: why it's acceptable at V1 scale, the recommended V2 fix (consolidate to server-side only via Livewire dispatch, or gate the JS capture behind a flag the Livewire event clears), and explicitly warns against trying to deduplicate via PostHog post-hoc filtering.

**Why it matters:** Double-capture will make `map_area_searched` counts unreliable in PostHog analytics. At 50–60 venues and small traffic it doesn't distort decisions, but if left undocumented it will cause confusion when the data is first used seriously.

#### `#v1-scope` — proper section for "V1 Scope & State" sidebar link

**The bug:** The sidebar link "V1 Scope & State" pointed to `id="overview"`, which is the document's `<div class="page-header">` — the title, subtitle, and badge. Clicking it just scrolled to the top of the document, not to any meaningful scope content.

**The fix:** The "Current implementation wrap — 2026-06-19" callout (which genuinely describes V1 scope and current app state) was wrapped in a new `<section class="spec-section" id="v1-scope">` with a proper section header ("V1 Scope & State — What is built, what is locked for V1, and what is intentionally deferred — as of 2026-06-19"). The sidebar link was updated from `href="#overview"` to `href="#v1-scope"`. The back-reference in Decision Registry entry D-01 was also updated.

The page title header (`id="overview"`) still exists for document structure purposes but is no longer linked from the sidebar — it's simply the document's visual top.

**Why it matters:** A spec document's navigation must be trustworthy. A link labelled "V1 Scope & State" that navigates to a generic page title destroys confidence in the rest of the nav. This fix makes the sidebar a reliable table of contents.

#### PostHog analytics role decision record (`inspo/UNI-Obsidian-Vault/uni-vault/decisions/product/posthog-analytics-role.md`)

Wrote a formal Problem → Solution record formalising PostHog's role. Added to the Decisions Log.

The core decision: first-party `events` table, `venue_stats`, and `AnalyticsGateway` are the canonical source for all owner-facing reports and B2B analytics. PostHog is additive — session exploration, funnel debugging, and behaviour analysis — and must not be used as a shortcut for building owner-facing metrics.
