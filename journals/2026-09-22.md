## What Was Built

### Your question about the Syncthing gate had a better answer, and it is now the plan

Yesterday's gate said: before creating the workspace repository, open the Syncthing ignore patterns on the homeserver and on the phone and confirm `.git` is listed. That protects against a real problem — a git object store is thousands of small files written in a particular order, Syncthing replicates files as they settle in arbitrary order, and three devices writing one object store with no locking corrupts it. What gets corrupted is the only copy of every journal and decision record UNI has.

**But your instinct was right that a gate is a weak answer.** It depends on a setting typed by hand on each device, Syncthing does not sync that setting between devices, and it is exactly the kind of thing that is forgotten on the fourth device in a year. It is a promise about configuration, not a property of the thing being protected.

**The better solution is `git init --separate-git-dir`.** The object store goes to `~/uni-docs.git`, outside every Syncthing folder. What stays inside `docs/` is a **117-byte text file** named `.git` whose entire contents are one line naming where the real repository lives. Git behaves exactly as normal from inside `docs/` — `status`, `log`, `commit`, `push`. Tested in a scratch directory today before it was written down, because a claim like that is worth ten seconds of proof.

**Why this is better, in one sentence:** there is no object store in the synced folder, so there is nothing for Syncthing to corrupt, on any device, regardless of what anybody typed into it. And if the 117-byte pointer does replicate, it is harmless — the phone gets a text file naming a path that does not exist there, and nothing on the phone runs git.

The ignore pattern stays as well, because two cheap defences beat one. It is no longer the thing the split depends on, and **session B step 2 no longer waits on step A10.** Recorded as [[decisions/product/the-workspace-git-store-lives-outside-syncthing]].

### On removing the community report — the long answer

**What exists today:** a "Coś się nie zgadza?" button on every venue page, a form requiring an e-mail address and at least a sentence, an admin queue to review it, an owner-panel widget, a table with a 12-month anonymisation rule, and eight test files. `/faq` and `/kontakt` both promise it in writing, including *"zgłoszenie czyta człowiek i odpisuje na podany adres"*.

**Three reasons to keep it.**

1. **Every tile claims the menu was checked.** "Sprawdzona karta" and "Zaktualizowano [date]" are the product's central promise. Nobody is phoned to verify a menu (19.09), owner access is closed in V1, and there is no other inbound channel. **Removing the report does not reduce the number of wrong menus — it removes the only way of hearing about one**, while the badge goes on claiming the menu is right.
2. **It is the mission test, almost literally.** A wrong menu sends somebody to a venue where there is nothing they can drink — the exact failure UNI exists to prevent. The report is the cheapest possible repair path for it.
3. **V2 makes it a legal duty.** The moment an owner manages their own menu, UNI hosts someone else's content and DSA Art. 16 requires an easy electronic notice mechanism. Removing it now means rebuilding it later under a deadline, and the V1 reports would not carry forward.

**The real argument on your side**, and it is a good one: the form collects an e-mail address, which is personal data, with a retention window that **is not currently enforced anywhere, because nothing scheduled has ever run.** One fewer public surface collecting an address is one fewer promise UNI is not keeping.

**So there is a third option worth more than either:** keep the button, **drop the e-mail field**, and make the report genuinely anonymous — a venue id and a note, nothing identifying, no retention window, no personal data at all. It costs the ability to reply, so `/faq` and `/kontakt` change from "we will write back" to "a person reads every one". It also matches the two-path design you already proposed: anonymous now, account-weighted later, one table throughout. **Say the word and it is a short session.**

**E-mail alone is the weakest of the three**, because the button carries the venue id automatically. An e-mail arrives saying "the place on Mokotowska had no alcohol-free beer" and the first job is working out which of seventy venues that is.

## Session 5 — UNI runs on the home server, and the box earned its keep four times

**Goal:** put the application on the home server — the environment decided this morning as the one where UNI is *used* on real devices over Tailscale rather than tested in a desktop browser.

**Outcome:** it runs. Phone, mobile data, real HTTPS, populated catalogue, working maps. **Four defects surfaced that the laptop could not structurally have found**, three of them would have hit production on a bare box with nothing to debug with, and all four are fixed and either tested or written into the deploy checklist.

**It took an afternoon and most of it was not wasted.** The parts that were wasted were mine, and they are recorded below because the pattern in them matters more than the individual mistakes.

### What was built

An Incus **system container** on the home server — not Docker, and not the host. A system container has systemd, cron and supervisor, so every step looks like a real server, where a Docker container is one process with no init. n8n and restic were never touched. And `incus delete uni --force` returns a clean box in seconds, which is the freedom this environment was chosen for and which got used twice.

Inside it: PHP 8.4.25 from `ppa:ondrej/php`, PostgreSQL, nginx and PHP-FPM, a `uni` deploy user owning the code, the application at tag `v0.1.3`, the schema migrated from nothing, an admin account, the demo catalogue, and Tailscale publishing it over real HTTPS with a valid certificate.

### The four defects, in the order they appeared

**1. `.env.example` could not boot the application — and it is the production environment file.**

`env('KEY', 'default')` returns the default only when the key is *absent*. Present-but-empty returns `''`, and the default never applies. `.env.example` shipped `BACKUP_NOTIFICATION_EMAIL=` against a config default, so spatie/laravel-backup got an empty address, rejected it, and **every artisan command threw before doing anything** — not `migrate`, not `schedule:run`, not `config:cache`.

A production box built from `.env.example`, which is the documented procedure, could not have run a single command. It was invisible on the laptop because this machine's `.env` omits the key entirely, which is exactly the case where the default works. Two tests now pin it, including one for the whole class of defect.

**2. `composer.json` claimed PHP `^8.3` while `composer.lock` demanded `8.4.1`.**

The box was provisioned on Ubuntu 24.04's stock PHP 8.3 on the strength of the declared constraint, and `composer install` refused with twenty-two conflicts. `composer.json` says what the application claims to support; the lock says what its dependencies actually demand, and the lock is what installs. Fixed to `^8.4.1` — no dependency version changed, only the lock's hash — with two tests keeping the pair honest.

**3. `public/vendor/maplibre-gl/` is gitignored and never reached the server.**

Vite's `vendorMapLibre` plugin copies the map library out of `node_modules` at build time. It is gitignored, so no clone has it, and the asset transfer shipped only `public/build`. Every page rendered perfectly and **every map was blank**: `map-loader.js` fetched `/vendor/maplibre-gl/6.9.0/maplibre-gl.mjs`, got a 404, and that appeared in the browser console and nowhere on the server.

**4. nginx serves `.mjs` as `application/octet-stream`, and a dynamic `import()` refuses it.**

Same symptom, entirely different cause, immediately after fixing the third. The file returned **200**; the browser downloaded it and declined to execute it, because Ubuntu 24.04's `mime.types` has no `.mjs` entry and a module import requires a JavaScript type. Nothing in the Laravel log, nothing in nginx's error log, `curl` perfectly satisfied. Fixed with `default_type` in a location matching `.mjs` — deliberately not a `types { }` block, which inside `server` replaces the inherited map rather than adding to it and would silently drop every other MIME type on the site. **This one applies to production identically, so it is now deploy-checklist C7.**

### Two more things the environment taught, which were not defects

**Laravel refused requests with a 400 and was right to.** `bootstrap/app.php` calls `trustHosts()`, so only `APP_URL`'s host reaches the application — the Host header otherwise becomes every absolute URL the request builds, including canonical tags and the sitemap. Every 400 during setup was `APP_URL` not matching what the client sent. The rule to carry: **`APP_URL`'s host must be exactly what the browser puts in the address bar.**

**The page loaded with no styling, and that was mixed content.** Tailscale terminates TLS and proxies to the container over plain HTTP. The application trusts no proxies — deliberately, because `trustProxies(at: '*')` once made every rate limiter spoofable including Filament's login limit — so Laravel correctly saw a plain HTTP request and built `http://` asset URLs, which the browser refuses on an HTTPS page. `URL::forceScheme('https')` only runs when `isProduction()`, and this is `preprod`. Fixed with `fastcgi_param HTTPS on` in the nginx PHP block, which is true here because this container is only ever reached through the Tailscale proxy. **It also fixed the consent cookie**, which is `Secure` and was being discarded — the 02.09 bug, reproduced by environment rather than by code.

### Demo data, and a rule that had been standing in for itself

The venue form's city dropdown was empty, because the seeders gated everything on `app()->environment('local')`. That made the home server useless for the one thing it exists for.

**The `local` check was never the rule.** `nothing-false-is-published-to-a-visitor` is about production, because production is the only environment an ordinary visitor reaches. So the guard is now `! isProduction()` in one place, `App\Support\DemoData`, and `DemoDataSeeder` is a single entry point that **throws** in production rather than quietly doing nothing — because somebody who types it on the wrong box needs to be told.

It hit a wall worth knowing about: `FakeVenueSeeder` uses factories, factories need faker, and **faker is a dev dependency**. So demo data cannot run on a `--no-dev` install. Fine on the home server, which exists for using the application. **A real problem for staging**, which is production-shaped *and* seeded-by-definition. The fix is a deterministic faker-free seeder, which also makes the data reproducible — written down before it is urgent.
