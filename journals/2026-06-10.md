# 2026-06-10 — Category-Aware Sort on Discovery Page

## Session Overview

**Goal:** Fix the discovery page sort so that when a user selects a category filter (e.g. "piwo"),
venues are ranked by how many products they carry in *that* category — not by overall breadth score.

**Outcome:** Implemented and tested. The "Najlepsza oferta" sort now adapts to the active category
filter. A venue with 15 beers will rank above a venue with 2 beers even if the latter has 30 total
products. Updated the SSOT feature spec, created a decision record, and updated the Decisions Log.
All 41 discovery tests pass (40 existing + 1 new).

## What Was Built

- **Category-aware sort in `VenueQuery`** (`app/Services/Discovery/VenueQuery.php`).
  Two new methods: `applyBestSort()` now accepts a `$categories` parameter, and a new
  `categoryBreadthExpression()` builds a SQL subquery that counts a venue's products in the
  selected categories. When category pills are active, `category_breadth` becomes the primary
  sort key, with overall `breadth_score` as the second key. When no category is selected, sorting
  is identical to before (overall breadth first). Handles multi-category selection (sums across
  slugs) and the special `drinki` category (counts rows from `venue_drinks` instead of
  `venue_products`).

- **New test** (`tests/Feature/Discovery/DiscoveryPageTest.php`).
  `test_category_filter_sorts_by_category_specific_breadth`: creates two venues — one with high
  overall breadth but few beers, one with lower breadth but many beers — and asserts that the
  beer specialist ranks first when the "piwo" category filter is active. All 41 discovery tests
  pass.

- **SSOT updated** (`inspo/interactive_v1_feature_spec_SSOT.html`). Four locations updated:
  1. Venue cards list item — added category-aware sort bullet point alongside the existing default sort description
  2. "Sort 1 (Default)" filter card — updated description to explain both modes (with/without category filter) and added the `Category-aware ranking` chip
  3. "Filter Behavior Rules" callout — added sentence about category filter sort behavior
  4. Scoring Logic section — added new "Category-Aware Sort" feature card before the existing "Category Diversity Tiebreaker" card

- **Decision record** (`inspo/UNI-Obsidian-Vault/uni-vault/decisions/product/category-aware-sort.md`).
  Structured Problem/Solution record documenting the decision, alternatives considered (keep overall
  breadth, category subquery at query time, denormalized per-category columns), rules, and revisit
  triggers.

- **Decisions Log updated** (`inspo/UNI-Obsidian-Vault/uni-vault/decisions/Decisions Log.md`).
  New row added to the Product Decisions table.

## Decision Register

- **Sort by category-specific product count when a category filter is active, not by overall
  breadth.** *(permanent, revisit at >1000 venues if subquery performance degrades)*
  - Chosen because the whole point of selecting "piwo" is to find the best beer selection. Sorting
    by overall breadth defeats that intent — a wine bar with 30 products and 2 beers would outrank
    a beer specialist with 15 beers and 16 total products.
  - Rejected: pre-computed per-category breadth columns. Would require a migration + observer sync
    for every category, adding schema complexity for marginal query-time savings at current scale.
  - Rejected: keeping overall breadth as the only sort signal. Simple but wrong from a user intent
    perspective.
  - Implementation: SQL subquery (`category_breadth`) counts products in selected categories at
    query time. Added as the first `ORDER BY` clause when categories are active. Falls through to
    `breadth_score` → `catalog_category_diversity` → `custom_drink_diversity` → `name` as
    tiebreakers.

## Risk Register

- **Category breadth subquery at scale.** At current volume (~70 venues), the correlated subquery
  is negligible. At 1000+ venues it could add latency. Mitigation: the query only fires when
  category filters are active (not on every page load), and the fallback to denormalized columns
  is straightforward if needed.
- **Multi-category sort sums across categories.** If a user selects "piwo" + "wino", a venue with
  5 beers + 0 wines and another with 2 beers + 3 wines would both score 5. This is correct (total
  breadth in selected categories) but could feel counterintuitive. Mitigation: users rarely select
  multiple categories; single-category is the dominant use case.

## Business Impact

- **Category filters are now actually useful for finding the best venue.** Before, selecting "piwo"
  just hid non-beer venues but still sorted by overall menu size. Now the beer specialist with
  15 beers ranks above the wine bar that happens to stock 2 beers. This is the behavior users
  expect — "show me the best places for beer" — and it directly improves the discovery experience.
- **Strengthens the B2B pitch to category specialists.** A pub that invests heavily in craft beer
  now gets rewarded with top placement when consumers filter for beer. This creates a clear
  incentive: "add more beer products to rank higher in the beer filter." That's the virtuous loop
  UNI needs — venues with deep category selection attract the most category-interested users.
- **No new infrastructure or data model changes.** The feature is a SQL subquery at query time,
  not a new column or migration. Zero deployment risk.
