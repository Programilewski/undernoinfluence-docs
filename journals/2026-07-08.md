# 2026-07-08 — Security Re-Audit of Public Routes + `maps` Redirect Decision

## Session Overview

No feature work this session — it was a review-and-document pass. The goal was to understand what the venue outbound-link handler (`VenueRedirectController`) does, then answer two direct questions: are the public routes vulnerable to injection attacks (SQL injection, and "prompt injection" in logs and anywhere else it could occur), and is the codebase worth the effort to re-learn. ## Decision Register

**Keep the `maps` outbound-redirect type despite no UI link.**
The venue redirect handler supports four link types: directions, website, instagram, and `maps`. The `maps` type builds a Google Maps *search* link (a "show this place on a map" pin lookup) and is distinct from `directions` (turn-by-turn navigation). It is fully built and has three passing tests — but no button on any venue page or listing card generates it, so it looks like dead code.

- **Chosen:** keep it as-is. It's deliberate, tested infrastructure one button away from being live. Deleting it throws away the finished half of a feature and would cost more to rebuild than the ~10 lines it saves. It carries no cost while dormant — nothing calls it, it's not a security or performance risk.
- **Rejected:** deleting the handler branch, route constraint, analytics entry, and the three tests. Rejected because our own rules say tests aren't removed without approval, and because tested-but-unreferenced is not the same as cruft.
- **Rejected:** adding an inline "no UI link yet" reminder comment. Unnecessary once the decision record exists.
- **Status:** Decided. Revisit when finalising the venue-page call-to-action set, or if `maps` is still unlinked at launch — then either wire up a "Show on map" button or delete it with its tests.

## Security Posture (this session's findings)

Re-audit of `routes/web.php` and everything the public routes reach, focused on injection. All clean, no fixes:

- **SQL injection — not vulnerable.** Every public route is route-model-bound or regex-constrained, and resolves through parameterized Eloquent/query-builder calls. The handful of raw-SQL blocks interpolate only static text or `?` placeholders; user values are always bindings.
- **Prompt injection (LLM) — no attack surface.** The app makes no AI/LLM calls at all, so there is nowhere for untrusted text to reach a model. This class of attack simply doesn't apply to us today.
- **Log forging — safe.** Every log line uses a fixed message; user-supplied text (search terms, user-agents, referrers) is stored only in the structured JSON context, which can't be used to fake log entries. Honeypot IPs are hashed, not stored raw.
- **Stored XSS in the admin panel — safe.** The one screen that shows user-typed search text back to us (the Discovery Insights widget) relies on Blade's automatic escaping, so a malicious `<script>` search shows as harmless text.
- **Analytics ingest endpoint — hardened.** The public event endpoint is consent-gated, rate-limited, and only accepts a fixed list of event types with validated IDs. Outsiders can't inject arbitrary events or data.

This complements — and re-confirms on the current code — the broader 2026-05-15 security audit already in the SSOT.

## Business Impact

Two kinds of value this session, both about de-risking rather than shipping:

- **Security confidence for launch.** You now have a written, re-confirmed answer that the public site has no SQL-injection, log-injection, or stored-XSS exposure, and that "AI prompt injection" is a non-issue because we run no AI. This is the kind of thing an investor, a partner venue's IT person, or a GDPR reviewer might ask about — and it's now documented in the SSOT rather than living in one conversation.
- **Onboarding cost is now known.** The app is ~12.5k lines of application code (169 files), ~7k lines of tests (362 tests), and 36 Blade views — but nearly half the code is the Filament admin panel, which is repetitive and low-surprise. The real "brain" (search, ranking, analytics, venue actions) is ~5–6k lines. Practical re-learning time: a couple of hours to orient, about a day for the core logic, 2–3 days to be fully fluent including the admin. Useful for planning when to bring in a second pair of hands.
