## Finding two: the importer's own shape pushes toward breaking the OSM decision

`VenueImporter` marks latitude and longitude as required. The only coordinates in existence for your 60–70 venues are the ones in `uni_filtered_venues.csv`, and they came out of OpenStreetMap along with the address, the phone, the amenity type and the `osm_id`. `osm-dropped` (01.06) says plainly: **no OSM venue attributes may be stored in the venues table** — the decision that cost the entire seeding pipeline to establish.

So as it stands, the only way to satisfy the importer is to paste in the data the project decided not to hold. The fix is two lines and a test: make the coordinates optional, import a worklist, then use the bulk geocoding that already exists in the panel — which `osm-dropped` explicitly permits, because sending an address to a geocoder and getting a point back is a service call, not a derived database.

**The business consequence, stated plainly:** the CSV cannot shortcut the enrichment. It can only tell you *which* venues to enrich. That was already true before today; what is new is that the tooling no longer quietly invites you to do it the other way.

## Finding three: an imported venue cannot go live, and the real work has no importer

`venue-activation-gate` and the `kebab-rule` mean a venue becomes visible only once it has at least one named NoLo drink attached. **There is no import path for the venue↔drink relationship**, and there is a good reason not to rush one: `VenueProductObserver::productAttached()` is called by hand from the panel because pivot tables do not fire Eloquent events, and each attach also marks the offer fresh, writes an offer-log row with the correct discovery type, recalculates the venue score and calls `activateIfReady()`. ## Learning Path

Two concepts, because you asked for both to be explained properly and they are worth holding on to beyond this session.

**Forwarded headers.** A web server knows one address for certain — whoever opened the TCP connection. When something sits in front of the app, that address is the middleman's, so proxies add `X-Forwarded-For` with the real visitor. It is a string anyone can send, so an app that reads it is trusting the client. That is fine when a proxy you control overwrites it, and it is a hole when nothing does. The whole of §3.1 is that sentence applied seven times.

**TOTP, which is what "2FA app" means.** The server and your phone share one secret, generated once and shown as a QR code. Both sides run the same function over that secret plus the current time in 30-second steps, which produces the same six digits without the phone and the server ever talking to each other. That is why it works on a plane, and why the secret has to be treated like a password in the database. Recovery codes matter for us specifically: you are the only admin.

## The real finding: the GUS geocoder returns nothing, and no test can see it

Your question — drop the coordinate requirement, resolve from the address via the government API — is the right design, and better than what the document had proposed. Testing all three of its assumptions live:

**It costs nothing to drop the requirement.** `venues.latitude` and `venues.longitude` have been `nullable` since the table was created. The `required` rule lives only in `VenueImporter`. No migration.

**But the government endpoint the code calls is not answering.** Called for real today:

| Endpoint | Result |
|---|---|
| `geo.stat.gov.pl/api/fts/gc/pkt` (forward) | HTTP 200 and `relevance: 0.0, src: null` for every payload shape tried — street alone, street + number, city in the string, `ul.` prefix, full woj/pow/gmina/miejscowość fields, and `useExtServiceIfNotFound` both ways. The service discards anything under 0.6, so the panel button fails every time |
| `geo.stat.gov.pl/api/fts/ref/qq` (reverse) | HTTP **500 "Read timed out"** from their backend, twice |

**Nothing in the test suite could ever have told us**, because all nine geocoding tests use `Http::fake()`. This is the same defect as the three features the 09.09 session found had never worked — an integration whose failure is invisible from inside the application.

**And the service that does work is GUGiK's**, the state mapping authority rather than the statistical office: `services.gugik.gov.pl/uug/?request=GetAddress&address=...&srid=4326`. Four real addresses returned correct WGS84 points with accuracy scores (Górczewska 124 at 0.8, Floriańska 3 in Kraków at 1.0), postcodes, TERYT codes, and — usefully — ranked alternatives, so a wrong street is visible rather than silent. No key, no auth, 6 ms.

**Why this is worth the small piece of work:** GUGiK is the state address register published as open data, not ODbL. Nominatim works too (checked — it answers, and it is permitted by `osm-dropped` as a service call), but every response carries *"Data © OpenStreetMap contributors, ODbL 1.0"*, and the point of your question was to stop having that conversation. A government source ends it.

**Two things no government service gives us**, both now written down so they do not surprise the cataloguing session: the **Warsaw district** (`citypart` is null for every Warsaw address; GUS's nearest field is the gmina, which for Warsaw is "Warszawa", so `district_id` would stay empty — and district pages depend on it), and **a pin you can trust without looking** — 0.8 is a good match, not a verified one, so sixty pins get eyeballed on `/mapa` once.

## The main thing: the import can now be done the compliant way

Before today the venue importer demanded a latitude and a longitude on every row, and the only coordinates in existence for your worklist came out of the OSM export — the exact data `osm-dropped` forbids storing. So the tool quietly pushed you toward breaking the decision that cost the entire seeding pipeline to establish.

Three changes close that, and the third is the one nobody asked for:

1. **Coordinates are optional in the importer.** The database columns were always nullable; the requirement lived only in `VenueImporter`.
2. **`GugikGeocodingService`** geocodes against `services.gugik.gov.pl/uug/` — the national address register, published as open data, no licence question, about six milliseconds a lookup. It is wired first in the provider list on the venue page and in the bulk actions, ahead of GUS and Nominatim.
3. **A venue without coordinates cannot go live.** This one only became visible once the change was made: `MapData::forVenues()` casts coordinates with `(float)`, so a null would have become `0.0` — a pin in the Gulf of Guinea and a "nearest" sort measuring distances from there. `Venue::activateIfReady()` now requires a point, and the map payload filters out any venue lacking one in case a venue is activated by hand.

**The acceptance rule is stricter than the API's own score**, because the score cannot be trusted on its own: a query for Floriańska 3 in Kraków returned Ariańska, Słowiańska and Loretańska at 0.52–0.65, while an exactly correct Warsaw address scored 0.79. A match is taken only when the city matched exactly, the returned street name contains the requested one (register prefix stripped, diacritics normalised), the house number is the one asked for, and the point is inside 60 km of the city centre.

**And the GUS request was fixed too.** It never sent `miejsc_nazwa`, so every lookup asked for a street name with no town attached, nationwide — the API's own documented example includes that field. Their index is not answering at all today, but if it recovers, the request is now well formed. Its forward path also has tests for the first time.

**The lesson from that outage is now enforced.** `GeocodingLiveTest` calls the real services and sits in a `live` group that `phpunit.xml` excludes from the default run — `php artisan test --group=live`. Nine mocked tests could not see a dead integration, because a mock proves we parse a shape, not that anybody still sends it. Run it before a cataloguing session.

## The second thing: you will now find out when the scheduler stops

`uni:heartbeat` runs every five minutes and records that the scheduler ran. The admin dashboard's first widget reports how long ago that was and turns red after fifteen minutes — three missed runs, not a blip.

**Why it matters more than it sounds:** a missing or mistyped crontab line produces no error anywhere. Every page renders perfectly while nothing scheduled ever runs — freshness badges rot and `model:prune` stops deleting personal data, which makes the published retention untrue rather than merely stale. A healthy box with a broken crontab looks identical to a healthy box, which is why uptime monitoring does not answer this question. v7 §5.1 approved a heartbeat back in August and v8 §0 recorded it as settled; it had never been built.

The same command checks disk usage and mails admins once a day above 80%. **That is the alarm the 27.08 notes wanted a paid Ploi tier for**, now owned by us, in the same mail path as every other notification, with no new dependency — which is why P14b is a smaller question than it was this morning.

## Three smaller truthfulness fixes

- **`abv_status = unknown` no longer renders "bezalkoholowe".** The label read *"bezalkoholowe, ABV do potwierdzenia"* — a claim and its withdrawal in one string, where the reader keeps the claim. It now reads *"ABV do potwierdzenia"*, which is what `abv-trust-model` specified all along. No product carries this state yet; the first one arrives during cataloguing.

- **The terms stopped denying the analytics cookie PostHog sets.** They now say our own analytics sets no cookies, and that PostHog — which sets its own — loads only after consent and stops when consent is withdrawn. `PublishedPagesAreTrueTest` asserts all three, and that `/register`, `/profil` and `/login` still 404.

# Session 5 — "The map on mobile is not showing", and the tap that granted consent instead

## Session Overview

**Goal:** you reported that the map does not show on mobile. Find out why and fix it.

**Outcome:** reproduced in a real browser at phone size, and the cause was not the map. **The consent dialog covered the map button**, and the element under your thumb was "Zaakceptuj wszystkie" — so the first tap granted analytics consent and did not open the map. Fixed, plus an older consent bug that fell out of it, plus the blind spot in the check that should have caught both. Six of six map surface checks pass at two viewports, 684 PHP tests still pass.

---

## What was actually happening

The consent panel is a modal anchored to the bottom of the screen. On a 390×844 phone viewport it is **435 pixels tall — more than half the screen.** The floating "Mapa" button sits at the bottom right, y 772–820, which is inside that panel.

Measured in Chrome at that size, on a first visit:

- The element at the map button's centre point was the consent panel's **"Zaakceptuj wszystkie"** button.
- One tap there set `uni_consent=granted`, created a PostHog cookie, left the view on the list, and produced no map canvas.
- No JavaScript error. Nothing in any log. Calling the toggle directly worked perfectly and produced a 390×764 map, which is how I knew the map itself was fine.

**So the reported symptom was real and the underlying defect was worse than a missing map.** `consent-banner-design` exists to stop this product nudging anyone toward accepting, and placing the accept button under the site's primary mobile control is the strongest nudge available. A tap aimed at a map is not an unambiguous indication of anybody's wishes, so what it produced was not consent in the first place.

## Why nothing caught it

`scripts/check-map-render.mjs` exists for precisely this family of bug — its own opening comment describes "a CSS cascade change collapsed a container to zero height so the map rendered perfectly into a box nobody could see". It ran at 1280×900 and nowhere else. On a desktop the map is on screen from page load and never touches that button, so the check was green the whole time the map was unreachable on every phone.

That is the second time in two days that a check was passing because it was not looking where the bug was — the first being nine geocoding tests that could not see a dead API.

## The second bug, which fell out of the fix

Once the check started rejecting consent like a real visitor, the homepage failed with `TypeError: window.posthog?.opt_out_capturing is not a function`.

`window.posthog?.x()` guards the object, not the method — and PostHog's CDN snippet installs a **stub object** before the library arrives, so the object exists while the method does not. `revokeConsent()` therefore threw, and because the throw happened before `visible = false`, **the dialog stayed open over the whole page while the decision had already been stored.** "Odrzuć wszystkie" looked broken while doing exactly what it was asked — which is almost word for word what `check-consent-cookie.mjs` was written about in August, for a different cause.

## Learning Path

**Forwarded headers.** A web server knows one address for certain: whoever opened the connection. A proxy in front adds `X-Forwarded-For` with the real visitor — a string anyone can send. Trusting it without a proxy in place means every rate limit is keyed on a value the attacker chooses.

**TOTP, which is what a 2FA app is.** Server and phone share one secret, shown once as a QR code. Both run the same function over that secret and the current 30-second time step, producing the same six digits without ever talking to each other. That is why it works on a plane, and why recovery codes matter when you are the only admin.

**Why a mock is not a test of an integration.** A mock says "given this response, we behave correctly". It cannot say "this response is what arrives". Both of today's invisible failures lived in that gap.

**Modal dialogs.** `aria-modal="true"` is a promise that nothing behind the dialog is interactive. A control that stays *visible* behind a translucent modal breaks that promise in the worst way: it looks available, and the tap lands on whatever the modal put there instead.

# Session 6 — "Is there code work before production?" Production was about to be built from a schema file nobody had updated since August

## Session Overview

**Goal:** answer three questions — is there code work left before production, is anything else not working, and are the migrations in their best state, given that nothing is in production and one file per table is allowed.

**Outcome:** the migrations question turned out to be the most important of the three. A second, forgotten description of the database — a schema dump file — was what actually built every fresh database, and it still contained the two tables removed on 01.09, one of them carrying a `session_id`. Every test for eleven days ran against them, and the first production deploy would have created them. The dump is gone, the migrations are 27 files with one per table, a test now fails if either comes back, and a full production rehearsal — production mode, empty database, every cache on, the admin panel driven in a real browser over HTTPS — found one real day-one blocker (you could not log in to `/admin`) and nothing broken on the public site.

## The main thing: the file that built the database was not the migrations

Laravel has two ways to build an empty database. It can run the migration files one by one, or it can load a single SQL snapshot called a schema dump and then run only the migrations newer than it. **If the snapshot exists, it wins.** ADR-010 kept one and required it to be regenerated every time a migration changed.

On 01.09 two orphan tables were removed — `venue_visits`, which held a `session_id` the identifier decision forbids, and `user_venue_saves`. Their migration files were deleted, the local database lost the tables, and the snapshot was never regenerated. So from that day the local database was right and **every other database built from this repository was wrong**: the test database, a Ploi staging site, and production's first `php artisan migrate`. Nothing in the test suite could notice, because the suite was running on the wrong schema too.

This is the second time. On 24.08 the same snapshot was found still holding the four `events` identifier columns from June. A rule that depends on remembering a manual step failed twice in ten weeks, so the step is gone rather than re-promised.

It had also hidden two tests that were passing for the wrong reason. One inserted into `venue_visits` — a table that only existed because of the stale file. The other was meant to prove the database refuses a negative visit count, but it was written for the old column layout and passed because the columns did not exist. It would have kept passing with the protection deleted. It now names the constraint it expects.

## Is there code work before production — what the rehearsal found

I built a throwaway database in production mode, ran the production seeders into it, cached configuration, routes, events, views and Filament exactly as the deploy will, served it, and visited every public page and every admin page. Then I deleted all of it.

**One real blocker, and it is small: nobody can log in to `/admin` on a fresh production box.** The local admin comes from the seeder, which only runs locally. # Session 7 — The first admin can get in, the map library is patched, and the admin map had never drawn

## The first admin

`php artisan uni:create-admin` asks for an e-mail address, a name and the password twice, then creates an admin and prints the login address. The password is only ever typed at the prompt, never passed as an option, so it does not land in the server's shell history. It requires twelve characters. If the e-mail already belongs to an account, it offers to promote that account instead, says so plainly if the account is a venue owner who would lose the owner panel, and changes nothing unless you say yes. Every grant writes an audit record (`admin_created` or `admin_promoted`, with the previous role). Deploy checklist **A10** now says to run it over SSH after the first deploy.

## The map library: what the upgrade actually took

The fix for GHSA-jrc7-96c5-q579 exists only in MapLibre 6, and 6 is a different kind of package: ES modules only, no default export, and its background worker is a separate file the build tool has to be told about.

**Proof that it would have broken:** I built the real production bundle with 6.9.0 and our unchanged loader, served it, and ran `npm run check:render`. **All six map checks failed** — homepage, `/mapa` and a venue page, desktop and phone — with `Cannot read properties of undefined (reading 'Map')`. A version bump that passes every PHP test and blanks the product's core screen is exactly the failure the render check was built for.

**The fix** is one file, `resources/js/map-loader.js`: take the library as a namespace, and hand it a worker URL that Vite builds as a self-contained file. After it: six of six on the production bundle, three more clean runs, and six of six on a dev server. `npm run check:map` and `npm run check:consent` pass, and `npm audit --omit=dev` reports **0 vulnerabilities**.

**What it costs:** 5.x carried its worker inside one 270 KB (gzipped) file. 6.x under Vite is a 280 KB file plus a 143 KB worker, so **a page that draws a map downloads about 150 KB more on a first visit**, cached afterwards. Pages without a map download none of it, because the library already loads only when a map is about to be drawn. It is a real cost on a phone connection, and it is the price of the patch — there is no 5.x release with the fix.

**Your dev server needs a restart.** The `npm run dev` that was running during this session still serves the pre-bundled 5.24.0 it built on 30.08, so maps in it fail with a cross-origin worker error until Vite is restarted and re-bundles 6.9.0. That is not a production problem: a fresh dev server with the same page-on-one-port, assets-on-another setup passed all six checks.

## The admin map that never drew

The location preview on a venue's edit page (*"Podgląd lokalizacji"*) was missing entirely — not just its map, its heading too. The cause is a Livewire rule: a component's first HTML element is its root. The widget's view began with `@vite(...)`, so its first element was a `<script>` tag, and when the widget arrived (widgets load after the page) Livewire kept the script and discarded the preview. It has been that way since the panel moved off Leaflet. The script now loads through a Filament render hook scoped to the venue edit page only, and the widget has one root. Verified in a browser on both the dev server and the production bundle: the preview renders a map.

## Learning Path

**Migrations and schema dumps.** Migrations are step-by-step instructions for building the database; a schema dump is a photograph of the finished result. Laravel prefers the photograph when one exists, because it is faster — which means an old photograph silently wins over new instructions. Laravel's docs, "Squashing Migrations".

**ES modules and default exports.** A JavaScript library can offer one main thing (a "default export") or a collection of named things. MapLibre 5 offered a default; 6 offers only the collection, so code asking for "the default" received nothing and every map failed. MDN, "JavaScript modules".

**Web Workers.** A map does its heavy work — cutting tiles, placing labels — in a background thread called a worker, so the page stays responsive. The worker is a separate file, browsers only run one from the page's own origin, and build tools need to be told it exists. MDN, "Using Web Workers".

**One root element per component.** Livewire keeps a component in step with the server by tracking a single outer element. Anything placed before it becomes, in effect, the component — which is how a script tag replaced a whole map preview. Livewire docs, "Components".

**Development versus production dependencies.** A package that only builds the site (Vite, formatters) never reaches a visitor; a package bundled into the site (MapLibre) does. That is why the same audit reported eight issues in total and zero in what ships, and why the two get different urgency.

**Audit logs versus analytics.** Analytics answers "what do visitors do" and holds no identities. The audit log answers "who changed what" and deliberately does hold the actor — which is why it has a twelve-month retention and analytics has none. Granting admin rights belongs in the second.
