# 2026-09-29 — The deployment plan, built and proved on a stand-in server

## Session Overview

**Goal:** find out what comes next, write yesterday's eight-phase deployment plan out as exact commands, and then do every part of it that can be done from the PC without you.

**Outcome:** the "what's next" answer came first — Leantime is an aside, so the real list is the deployment plan. You asked for it in detail, which became `roadmap/deployment-runbook.md`. Reading Deployer's own source code while writing that runbook found six things the plan would have got wrong, three of them serious enough to break or endanger the first deploy. Then you asked for everything that could be done here, so everything was: the Ansible playbook, the deploy recipe, the CI workflow and four new tests exist in the application, the documents no longer describe Ploi, and Ansible, Deployer and `gh` are installed on your PC. **The playbook and the deploy recipe were then run for real** against a throwaway Ubuntu 26.04 machine built on your PC — provision twice, deploy, deploy again, roll back — and that run found four more problems no amount of reading had. All are fixed. **Nothing has touched the laptop or the VPS yet**; everything left needs a password, a console login, a phone or a decision from you.

## What Was Built

### Found by reading the tools, not assumed — the ten findings the runbook rests on

| # | What was wrong | How it was found | What happens now |
|---|---|---|---|
| 1 | **If `shared/.env` were ever missing, Deployer would ship `.env.example` to the server** — debug mode on, no encryption key. The first error page would print the database password | Deployer's `deploy:env` task copies `.env.example` into place when no `.env` exists; `deploy:shared` then makes that copy permanent | `deploy.php` replaces the task: the deploy **stops** if the file is missing, or its key is empty on anything but the first deploy. | 2 | **The second deploy would have failed** with "Operation not permitted" | Deployer's Laravel recipe changes the group of all of `storage/`, but files the web server wrote there belong to the web server and only an owner may change a file's group | Deployer only touches the release's own cache folder; the playbook owns `storage/`. Proved: a second deploy over files the web server had written succeeded |
| 3 | **Ansible cannot run as `deploy`** — the plan limited `deploy` to one command | Ansible has to install packages and write system files | Two server users: `admin` (Ansible, full rights, behind a password) and `deploy` (Deployer, one command) |
| 4 | **The servers never need access to GitHub** | Deployer 8 can archive the tag on the PC and upload it | No GitHub key on either server; one fewer credential per machine |
| 5 | **A rollback only swapped the folder** — the old code would keep running for up to an hour | Read in Deployer's rollback task | The reload is hooked onto rollback. Proved: workers restarted with new process numbers |
| 6 | **The `/admin` allowlist decided on 16.09 was missing from the plan** | Checked the plan against the admin-access-is-three-layers record | In the playbook as one setting; *how* your browser reaches it from Tailscale is an open question |
| 7 | **A clean copy of the code cannot build its CSS** | Running the deploy: the Filament admin theme imports its styles from the PHP packages folder, which a clean copy does not have | The build step installs the PHP packages first. Every clean build — including the one the plan was built around — would have failed |
| 8 | **Deployer's upload needs `rsync` on the server** | Running the deploy | Added to the playbook |
| 9 | **The playbook assumed that installing software starts it** | Running the playbook: the database was installed and stopped | Every service now has an explicit "running, and starts at boot" step |
| 10 | **No release before `v0.1.5` can go through the new process** | The deploy refuses a tag without a passed CI run, and CI did not exist before today | `v0.1.4` ships the old way; `v0.1.5` is the first new-process release |

## Decision Register

### 1. The servers never hold a GitHub key — **adopted, permanent**

Recorded: no-server-holds-a-github-credential.

**Chosen:** the PC packs the tag and uploads it. **Rejected:** one read-only GitHub key per server (yesterday's plan). **Why:** a server that cannot read the repository cannot leak its history if broken into, and it is one fewer credential to create, rotate and delete. The cost is a temporary file on the PC during each deploy, now ignored by git.

### 2. Two server users: `admin` for building, `deploy` for deploying — **adopted, permanent**

Recorded: building-a-server-and-deploying-to-it-are-two-users.

**Chosen:** `admin` has full rights behind a password you type on every playbook run; `deploy` can only reload PHP. **Rejected:** giving `deploy` full rights (then a stolen deploy key is full control of production), or `admin` without a password (then the PC's key alone is). **Why:** the tool that runs on every release holds the least power.

### 3. Deployer as a standalone file, not a project dependency — **adopted for now, revisit**

**Chosen:** the standalone file in your user folder. **Rejected for now:** adding it to `composer.json`. **Why:** dependency changes need your approval, and nothing depends on the choice — every command works either way. Worth changing the day a second machine deploys.

### 4. The runbook points at the files instead of copying them — **adopted, permanent**

**Chosen:** once a file exists in the application, the runbook describes it and links to it. **Rejected:** keeping full copies in the runbook. **Why:** the plan's own principle — a second copy of the setup drifts from the first. The runbook keeps what is not in any file: the order, the reasons, the proof and the manual steps.

### 5. Prove the playbook and deploy on a stand-in before touching a real machine — **adopted**

**Chosen:** a throwaway Ubuntu 26.04 container on the PC. **Rejected:** stopping at syntax checks and waiting for the home server. **Why:** it found four real problems, each of which would otherwise have been found during a sitting on the real box — one of them (the clean build) would have blocked every deploy.

### 6. Services are started explicitly, even where Ubuntu would anyway — **adopted, permanent**

**Why:** "it works because of a default nobody wrote down" is the failure class this project keeps paying for (the missing cron line, the web server's missing file type, the empty environment value).

### 7. A deploy without its settings stops — **adopted, permanent**

Recorded: a-deploy-without-its-settings-stops. **Chosen:** the deploy refuses to run if the server's settings file is missing, or its encryption key is empty outside the very first deploy. **Rejected:** trusting the runbook's order, or having Ansible write a starter file (which would assemble secrets on the PC). **Why:** Deployer's default fills the gap with the example file — debug on, no key — and the first error page would print the database password.

### 8. `v0.1.5` is the first release of the new process — **consequence, permanent**

**Why:** a deploy requires a passed CI run on the tag, and no earlier tag can have one. **Rejected:** a bypass switch for old tags — a switch that turns off the most important check is the one that stays on.

- **Yesterday's plan, Finding 4 (a deploy key per server)** — replaced by decision 1.
- **Yesterday's plan, step 2.3 (`deploy` runs Ansible)** — replaced by decision 2.

## Business Impact

Nothing a visitor sees changed today. What changed is **how close UNI is to having a production server at all**. Yesterday the plan was a document; today the machinery exists, is tested, and has been run end to end on the same operating system production will use. The part of the 25–35 hour estimate that was writing and debugging is mostly done — about half of it — and what remains is the part only you can do: passwords, the providers' consoles, and a phone in your hand.

Three findings protect the launch directly. A missing settings file would have put the database password on a public error page. The second release would have failed to deploy. Each was found on a machine that cost nothing and was thrown away afterwards.

Dropping Ploi also shortens the privacy work: the compliance hour now asks for OVH's DPA (a download) instead of Ploi's (a request and a wait), and the privacy policy needs one fewer recipient.

## Learning Path

- **Idempotence — "running it twice changes nothing".** The test for whether a playbook describes a server or just performs a one-off sequence. Today's third run, after a live deploy, reported zero changes. Search: "Ansible idempotency".
- **Reading the tool's source, not its reputation.** Three of today's findings came from reading 50-line files inside Deployer — the defaults a tool picks are what it does to you when you forget something. Search: "Deployer recipe laravel.php".
- **Least privilege.** Two users on each server, each able to do exactly its job: the everyday tool is the weakest. Search: "principle of least privilege sudoers".
- **Supply-chain pinning.** CI steps reference a code fingerprint (a commit SHA), not a name like "v7" that its owner can re-point. Search: "GitHub Actions pin to commit SHA".
- **Clean-room builds.** A build that only works in a folder that already has things in it isn't a build — that is what "a clean checkout" catches. Search: "reproducible builds clean checkout".
