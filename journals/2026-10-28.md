## Decision Register

### 1. Claims and proposals share one status enum

**Chosen:** `ReviewStatus` (pending, approved, rejected) for both. **Rejected:** one enum per table. **Why:** both are "something waiting on an admin", with the same three values enforced by the database. Two enums would be two copies of one list. **Status:** revisit if either table ever gains a state the other lacks; then split it.

### 2. "Named publicly" stays as a separate word from "recipe"

**Chosen:** `namedPublicly()` is defined as `recipes()`, so the rule lives in one line. **Rejected:** deleting the word and writing "recipe" everywhere. **Why:** on a page, "may this name be shown?" is a policy question, and the code should ask it in those words, even though today the answer is "only if it's a recipe". **Status:** permanent.

### 3. Strict mode stays off

**Tried:** `Model::shouldBeStrict()`, which turns three silent mistakes into errors. **Rejected:** keeping it on. Filament's own two-factor login code and the venues import rely on reading or filling fields that aren't database columns, and both broke. **What it bought anyway:** the venue-editor bug (7c). **Status:** revisit when Filament changes; it's worth one run before each release.

### 4. An owner may delete their own venue (my finding withdrawn)

**The review said** the venue policy letting an owner delete their venue was probably unintended. **It is intended:** the owner panel's "Usuń lokal i dane" is the self-service erasure, and a test pins it. Only the repetition was removed, and the policy now says why delete is allowed. **Status:** permanent.

### 5. The discovery page is measured, not changed

**Measured** with the local scale seeder: the map page took about 0.5 s with 1,000 venues and about 0.8 s with 5,000, on this PC. **Rejected:** rebuilding how the map loads its data now. **Why:** the measure-costs-before-accepting rule. At ~30 venues at launch it's irrelevant; the numbers say when to look again. **Status:** revisit at ~1,000 live venues.

### 6. Small leftovers left alone

The footer's city list and the "is any venue owner-managed" check are each one cheap query per page, called from views. The old-style accessors weren't rewritten: the framework still supports them, and rewriting would be churn. Rector added `strict_types` only where it judged it safe, and 89 files still don't have it, because adding it everywhere can change how values convert. **Rejected:** fixing these for tidiness alone. **Status:** permanent unless one of them causes a problem.

### 7. A slug helper shared between two models

**Chosen:** a small `HasUniqueSlug` trait in `app/Models/Concerns`, a new folder. **Rejected:** keeping two copies. **Why:** you asked for "all", and the copies had already drifted in their fallback word. **Status:** permanent. Flagged because the codebase rule asks before new folders; this one sits inside an existing folder.

## Learning Path

- **Enums over strings.** A status typed as `'pending'` in 46 places is 46 chances to misspell it, and a misspelling fails silently. Search for "PHP 8.1 backed enums" and "Laravel enum casting".
- **A name that lies is a bug.** `VenueProductObserver` observed nothing; `DetachVenueProductAction` detached nothing. Search for "intention-revealing names" (Kent Beck, Robert C. Martin).
- **Stale in-memory data.** The breadth bug: a value was summed from data loaded earlier, after the database had changed. Search for "stale cache" and Laravel's `load` versus `loadMissing`.
- **The N+1 query problem.** One query per recipe instead of one for all. Search for "N+1 query problem".
- **Fail loudly in development.** Strict mode found a bug just by being switched on. Search for Laravel's "Model::shouldBeStrict".
- **Measure before you optimise.** The discovery page was timed, not rewritten. Search for "premature optimisation" (Knuth).
