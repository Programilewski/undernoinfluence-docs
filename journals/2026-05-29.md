# 2026-05-29 — Seeding Queue Tooling: Google Search, Nominatim Compliance, Reverse Geocoding, Mini Map

## Session Overview

**Goal:** Enhance the Seeding Queue edit page with tools that speed up venue research and coordinate verification — a Google Search shortcut, API response caching for Nominatim compliance, reverse geocoding (both providers), and a visual map preview.

**Outcome:** Five capabilities added. ## What Was Built

### 1. "Search Google" Button on Seeding Queue Edit Page

**File:** `app/Filament/Admin/Resources/SeedingQueue/Pages/EditSeedingQueue.php`

Added a gray "Search Google" header action that builds a Google search URL from the venue's name, street name, street number, and city name, then opens it in a new tab. The URL is constructed using `http_build_query` for proper encoding.

**Why:** During the seeding workflow, the researcher frequently needs to verify a venue's existence, check its menu, or find its website. Previously this required manually typing the venue name into Google. One click now does this directly from the review page, saving 10–15 seconds per venue across hundreds of reviews.

---

### 2. Nominatim API Response Caching

**File:** `app/Services/NominatimGeocodingService.php`

Added a 30-day cache layer keyed by normalized `street|city` (lowercased, MD5 hashed). Key design decisions:

- **Caches both hits and misses.** A miss is stored as `false` in the cache. This prevents re-requesting the same address that previously returned no results — the most important optimization for Nominatim compliance, since repeated "not found" lookups waste API calls without any benefit.
- **Cache key is address-based, not venue-based.** Multiple venues at the same address (e.g., two bars in the same building) share one cached result. The key is `nominatim:` + MD5 of the lowercased `street_number street_name|city_name`.
- **Batch geocoding skips sleep for cached venues.** The `geocodeBatch()` method now checks `Cache::has()` before each venue. If the result is cached, no API call is made and no 1.1-second rate-limit sleep is needed. Only actual API calls trigger the sleep. This means re-geocoding a batch of 20 venues where 18 are cached takes ~2.2 seconds instead of ~22 seconds.

**Nominatim compliance status after this change:**

| Requirement | Status |
|---|---|
| Max 1 request/second | ✅ 1.1s sleep between API calls |
| Custom User-Agent | ✅ `UnderNoInfluence/1.0 (pawel.milewski00@gmail.com)` |
| Cache results | ✅ 30-day TTL, hits and misses cached |

### 3. Reverse Geocoding — Nominatim

**File:** `app/Services/NominatimGeocodingService.php` — new `reverseGeocode()` method

Calls `GET /reverse?lat=X&lon=Y&format=json&addressdetails=1&zoom=18`. Returns a structured array with `display_name`, `road`, `house_number`, `suburb`, `city`, and `postcode`. Returns `null` on API error or when Nominatim returns an error response (e.g., coordinates in the ocean).

**Why Nominatim reverse works well here:** The `/reverse` endpoint returns the closest addressable OSM object to the given coordinates. At zoom level 18 (building-level), this typically returns the exact building or the nearest street address. The `suburb` field reliably returns Warsaw district names ("Ursynów", "Wola") — the same field used by forward geocoding for district auto-fill.

---

### 4. Reverse Geocoding — GUS

**File:** `app/Services/GusGeocodingService.php` — new `reverseGeocode()` method

Uses the `GET /api/fts/ref/qn` endpoint (nearest search) with an empty query, a tight bounding box (±0.002° ≈ ±220m around the point), `idx=pkt` (address points only), and `bboxm=hard` (strict bounding). Returns `street` (`ul_nazwa_glowna`), `number` (`pkt_numer`), `city` (`miejsc_nazwa`), `postcode` (`pkt_kodPocztowy`), and `district` (`gm_nazwa`).

**Why the GUS approach is different:** GUS has no dedicated reverse geocoding endpoint. The `ref/qn` endpoint is a text search with optional spatial filtering. By sending an empty query with a tight hard-bounded bbox, it effectively returns the nearest address point(s) within ~220m of the coordinates — a functional reverse geocode.

### 5. Reverse Geocoding Buttons on Seeding Queue Edit Page

**File:** `app/Filament/Admin/Resources/SeedingQueue/Pages/EditSeedingQueue.php`

Two new header actions: "Reverse (Nominatim)" (warning/orange) and "Reverse (GUS)" (info/blue). Both:

1. Check that the venue has coordinates — show an error notification if not.
2. Call the respective service's `reverseGeocode()` method.
3. **Save address fields to the model:** `street_name`, `street_number`, `postal_code` are updated from the result. `district_id` and `city_id` are auto-filled from the returned suburb/gmina/city by case-insensitive name match.
4. **Refresh the form inputs** via `$this->refreshFormData()` — the address fields update in the form immediately, same as forward geocoding updates coordinates.
5. Show a success notification with the full address string.

**Why the reverse geocoding buttons write to the model (not just display):** The user explicitly asked for the same behaviour as forward geocoding — coordinates fill the form inputs automatically, so address fields should too. This makes the workflow symmetrical: geocode fills coordinates from address, reverse geocode fills address from coordinates.

#### 2. Slug Correction Bug Fix — Inverted Condition in Model Hook

**File:** `app/Models/Venue.php` (line 68)

The `Venue::booted()` updating hook had a condition that was backwards:

```php
// BEFORE (broken): returned early when slug === base name
// This is exactly the case where the slug SHOULD be upgraded
if ($venue->slug === $base) {
    return;
}

// AFTER (fixed): returns early when slug already differs from base name
// Already-customized slugs (with street suffix, numeric suffix) are left alone
if ($venue->slug !== $base) {
    return;
}
```

**The effect of the bug:** When reverse geocoding filled in `street_name` on a venue whose slug was still the bare name (e.g., `waza-smakow`), the hook detected that `street_name` was dirty, computed the base slug, saw that `slug === base`, and *returned early* — skipping the upgrade. The slug was never corrected. This affected every venue that was imported without a street and later had its address filled via reverse geocoding.

#### 3. Filament Form Slug Refresh After Reverse Geocoding

**File:** `app/Filament/Admin/Resources/SeedingQueue/Pages/EditSeedingQueue.php`

Both reverse geocode actions (Nominatim and GUS) called `$this->refreshFormData(array_keys($update))` after saving. The `$update` array contained address fields (`street_name`, `street_number`, `postal_code`, `district_id`, `city_id`) but **not** `slug`. Even though the model hook correctly saved the new slug to the database, the Filament form kept showing the old slug until the page was manually refreshed.

**Fix:** Added `$this->record->refresh()` (to reload the model from DB, picking up the hook-modified slug) and added `'slug'` to the `refreshFormData()` array for both reverse geocode actions.
