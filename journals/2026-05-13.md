# 2026-05-13 — Documentation SSOT

## Session Overview

Goal: create a practical documentation system for the project without building a separate wiki app. The founder needs one place to track what the app does, what data it collects, how security is handled, what vendors/dependencies exist, and which legal/compliance records still need review.

Outcome: `docs/` is now structured as the project source of truth for technology, business, compliance, and cross-cutting concerns. The interactive SSOT feature spec was also updated to point at this documentation model.

No Laravel application code was changed.

---

## What Was Built

### Documentation root

Added `docs/README.md` as the entry point for all project documentation.

It defines:

- Markdown as the source of truth.
- PDF exports as future release/audit snapshots, not the editing format.
- `TODO` and `TBD` as explicit markers for unknowns.
- the rule that documents should link to each other rather than duplicate decisions.

### Compliance documentation

Added `docs/compliance/` with:

- `README.md` — compliance map and working rules.
- `privacy-notice.md` — public privacy notice template for users.
- `ropa.md` — Article 30 GDPR/RODO processing register template.
- `data-map.md` — internal data-flow and storage map.
- `vendors/README.md` — vendor, subprocessor, and license register.
- `dpa/README.md` — data processing agreement register.
- `dpia/README.md` — data protection impact assessment area.
- `incidents/README.md` — privacy/security incident register.

The compliance structure is intentionally split. Public policy, internal audit records, vendors, incidents, and DPIAs have different audiences and should not live in one giant document.

### Technical documentation

Added `docs/tech/` with:

- `README.md` — technical documentation map.
- `stack.md` — Laravel/PHP/PostgreSQL/Filament/Livewire/Tailwind stack template.
- `architecture.md` — application boundaries, system context, data ownership, and runtime architecture template.
- `dependencies.md` — Composer/NPM dependency inventory and license/risk tracking.
- `adr/001-example.md` — architecture decision record example.

The ADR template uses:

- Decyzja
- Kontekst
- Alternatywy odrzucone
- Konsekwencje

### Business documentation

Added `docs/business/` with:

- `README.md` — business documentation map.
- `model.md` — B2C/B2B marketplace model.
- `pricing.md` — package and monetization assumptions.
- `metrics.md` — acquisition, activation, monetization, and marketplace quality metrics.
- `competitors.md` — competitor and positioning notes.

### Cross-cutting documentation

Added `docs/cross-cutting/` with:

- `analytics.md` — analytics plan that links business metrics, compliance, data map, and technical event sources.
- `security.md` — authentication, authorization, data protection, logging, operational security, and incident response notes.

This solves the original problem: analytics and security do not belong under only "technology" or only "business". They cut across domains, so they are tracked once and referenced from the domain documents they affect.

## Decision Register

### Decision: Markdown in repo, not a separate wiki app

Chosen: keep documentation in `docs/` as Markdown files.

Rejected: building or adopting a separate wiki application right now.

Reason: the project is still founder-led and fast-moving. Markdown in the repo keeps documentation close to implementation, makes review easier, and avoids another system to maintain.

Status: current operating model.

### Decision: domains plus cross-cutting concerns

Chosen: split docs into stable domains (`tech`, `business`, `compliance`) plus cross-cutting concerns (`analytics`, `security`).

Rejected: putting analytics/security inside every domain document.

Reason: analytics, security, privacy, vendors, and licensing affect multiple areas. Tracking them once reduces duplication and keeps ownership clearer.

Status: permanent unless the project grows into a larger team with dedicated ownership.

### Decision: compliance is a folder, not one document

Chosen: split compliance into privacy notice, ROPA, data map, vendors, DPA, DPIA, and incidents.

Rejected: one master legal/compliance document.

Reason: public user-facing privacy language and internal audit records need different levels of detail. Mixing them makes both worse.

Status: permanent.

## Risk Register

| Risk | Impact | Mitigation |
|---|---|---|
| Docs look complete but still contain `TODO`/`TBD` | False confidence before launch | Treat all draft docs as operational checklists, not legal approval |
| Compliance wording is not legally reviewed | Privacy notice or ROPA may be incomplete | Have the final `privacy-notice.md` and `ropa.md` reviewed before public launch |
| Vendor/license register stays stale | Subprocessor and license risk becomes invisible | Update `docs/compliance/vendors/README.md` whenever a service or package becomes production-critical |
| Analytics tracking grows faster than privacy docs | Data collection may drift from disclosed purposes | Every new analytics event should update `docs/cross-cutting/analytics.md` and relevant ROPA sections |

## Business Impact

This gives the project an operational control center before launch.

The important founder-level benefit is not "documentation for documentation's sake". It is knowing:

- what the app claims to do;
- what data is collected;
- which vendors touch data;
- which metrics matter;
- what security assumptions exist;
- what still needs legal, technical, or business review.

This structure also supports future monetization work. Pricing, metrics, analytics, and compliance now have a place to evolve without mixing product planning with legal records.
