## Learning Path

**Run the check against the broken code before trusting it on the fixed code.** Twice today a check passed for the wrong reason: once because a browser property reports "no position" for anything pinned to the screen, and once because a shared browser remembered the answer to the question being tested. Both would have gone green on the fixed code and looked like proof. A test that has never failed has never shown it can.

**A browser context is a private window.** Tabs in one browser share cookies, so the second page a script opens is not a first visit. Any check about "what a new visitor sees" needs a fresh context per page, or it only ever checks the first page.

**`aria-modal` is a claim, not a style.** It tells a screen reader that everything outside the dialog is unreachable. That is right for a dialog that really blocks, and wrong for one that doesn't. A sighted visitor would never notice the difference; a blind visitor is told the page is not there.

**"Non-blocking" is not the same as "optional".** EDPB guidance forbids treating inaction as consent. It does not require stopping anybody from reading. Our panel stores nothing and loads no analytics until a button is pressed, so scrolling past it grants nothing. That is what made removing the block safe.

### Backups — what runs where, and what it costs

**Local development will never send a backup to Scaleway.** The backup goes to the bucket only when the production environment variables are set, meaning the Scaleway key, the bucket name and the endpoint. On this laptop they are empty, and they will stay empty. The secret belongs in Ploi's environment for the production site, not in a file on your machine. Locally, a backup either writes to the laptop's own disk or does not run at all. **There is no storage bill from development.**

**Installing the packages is a code change, not an action on the bucket.** It adds two lines to `composer.json`. Nothing is uploaded, scheduled or charged. It is done here because this is where the code is written, and it reaches the server with the next deploy.

**Object lock is a setting on the production bucket, not a development step.** The bucket (`uni-backups-prod`) was created on 17.09 and is the production one. Object lock can be switched on at any point before the server's first real backup, so deploy day is fine. I listed it early only because it cannot be turned off once on, and it is the kind of step that gets forgotten.

**How it gets tested without paying for anything:**
- **On the laptop, against the local disk, at zero cost:** the database dump, the encryption, the rotation down to 7 daily + 4 weekly, and a restore into an empty database. That is everything except the upload, and it proves the restore procedure Art. 32(1)(d) asks for.

**2. On the server, once** (SSH, in the site folder):

```bash
sudo apt install 7zip                                  # only needed for restores
```

```bash
php artisan tinker --execute '$c = Storage::disk("backups")->getClient(); $b = config("filesystems.disks.backups.bucket"); $c->putObjectLockConfiguration(["Bucket" => $b, "ObjectLockConfiguration" => ["ObjectLockEnabled" => "Enabled", "Rule" => ["DefaultRetention" => ["Mode" => "COMPLIANCE", "Days" => 35]]]]); print_r($c->getObjectLockConfiguration(["Bucket" => $b])["ObjectLockConfiguration"]);'
```

It should print `COMPLIANCE` and `35`. Then run `php artisan backup:run` **again**, to prove uploads still work into a locked bucket. That is the one thing no laptop test can show.

- non-current version expiration: **1 day**
- current version expiration: **45 days**
- incomplete multipart abort: **1 day**

**6. Scaleway billing → a budget alert** at a few euros. Real usage is megabytes, so anything that reaches the alert means something is wrong.

**7. The restore rehearsal on the server.** Art. 32(1)(d) asks for a *tested* restore, and this is the step that closes checklist A6:

Never into staging. Repeat it quarterly.

## Learning Path

**A switch is only honest if there is one of it.** The owner panel went wrong in August because three documents disagreed about whether it was exposed. Today's rule works because every owner surface — the panel, the claim form, the policy's sentences — reads one variable, and one test pins its default.

**A request is not a grant.** The form writes a pending row and nothing else. That separation is why it could be built without the verification design self-service would need.

**Identity is not a name.** The importer merged a chain because it treated a name as a key. Names repeat; a name *at an address in a city* doesn't.

**A check that has never failed has never shown it can.** Twice today a new check passed on broken code — the browser check that never saw the consent panel after the first page, and my first scroll check. Running against the old code first is what caught both.
