# 2026-05-15 — Business Logic, Accessibility & Laravel Practices Audits

## Session Overview

**Goal:** Conduct three parallel audits — business logic edge cases/abuse cases, WCAG 2.1 AA accessibility, and Laravel best practices — and document all findings in the SSOT.

**Outcome:** 82 issues identified across the three audits. The most impactful items were curated into three new SSOT sections: Business Logic Audit (BL1–BL12), Accessibility Audit (A11–A21), and Laravel Best Practices Audit (LP1–LP9). All are document-only — no code changes were made in this session.

## What Was Built

### Business Logic Audit (BL1–BL12)

Reviewed all controllers, models, Livewire components, observers, and services for race conditions, state machine violations, abuse vectors, and data inconsistency risks. Key findings:

| ID | Severity | Issue |
|---|---|---|
| BL1 | Critical | `role` is in User model's `$fillable` — mass assignment could escalate privileges |
| BL2 | High | Save/unsave toggle has no DB unique constraint — race conditions can create duplicates |
| BL3 | High | VenueStat increment uses read-then-write instead of atomic `increment()` — counts can drift |
| BL4 | High | VenueRedirectController doesn't check `is_active` or `is_canary` — inactive venues are accessible via old slugs |
| BL5 | High | Product model uses `$guarded = []` — all columns are mass-assignable |
| BL6 | Medium | Claim approval has no guard against approving an already-approved claim |
| BL7 | Medium | Freshness confirmation has no cooldown — users can spam-confirm to inflate scores |
| BL8 | Medium | A venue can show a "Fresh" badge while its menu is empty |
| BL9 | Low | Breadth score can drift from actual product count if observer misses an edge case |
| BL10 | Low | Profile email change doesn't trigger re-verification |
| BL11 | Low | Search has no server-side debounce — rapid requests could overload the DB |
| BL12 | Low | Proposal name uniqueness is not enforced at the database level |

### Accessibility Audit (A11–A21)

Reviewed all Blade views, Livewire components, and Alpine.js interactions against WCAG 2.1 AA. Key findings:

| ID | Severity | Issue |
|---|---|---|
| A11 | High | `<html>` tag missing `lang="pl"` attribute |
| A12 | High | Search input has no associated `<label>` or `aria-label` |
| A13 | High | Map container lacks ARIA role and accessible description |
| A14 | High | No skip-to-content link |
| A15 | Medium | Mobile hamburger menu missing `aria-expanded` and `aria-controls` |
| A16 | Medium | Form validation errors not associated via `aria-describedby` |
| A17 | Medium | Icon-only buttons (save, share, report) have no accessible name |
| A18 | Medium | Freshness indicators rely on colour alone — no text/icon fallback |
| A19 | Low | No ARIA live region for dynamic content updates (search results, map) |
| A20 | Low | Category filter pills lack proper radio/checkbox semantics |
| A21 | Low | Heading hierarchy has gaps (h1 → h3 in some views) |

### Laravel Best Practices Audit (LP1–LP9)

Reviewed routes, controllers, models, services, config, and Artisan commands against modern Laravel conventions. Key findings:

| ID | Severity | Issue |
|---|---|---|
| LP1 | High | Route closures in `web.php` prevent route caching — should be controller methods |
| LP2 | Medium | SEO meta duplicated across controllers — should be a shared Blade component or service |
| LP3 | Medium | `app()` helper used instead of constructor DI in several services |
| LP4 | Medium | Legacy accessor style (`getXAttribute`) instead of `Attribute` casts |
| LP5 | Medium | Notification logic inline in controllers — should use Notification classes |
| LP6 | Low | Raw SQL used in a few places where Eloquent query builder would suffice |
| LP7 | High | Sitemap controller has N+1 query problem (C×K + C×D×K queries) |
| LP8 | Low | Venue model is ~500 lines — could benefit from traits or service extraction |
| LP9 | Low | Artisan commands use `$this->info()` inconsistently vs `$this->line()` |

## Decision Register

| Decision | Choice | Why |
|---|---|---|
| Document only, no implementation | Three audit sections added to SSOT | The user explicitly asked for audits to be documented in the SSOT, not implemented. This creates a prioritised backlog for future sessions. |
| Curate findings into top items | 12 + 11 + 9 = 32 items in SSOT from 82 raw findings | The audit agents found many low-impact or duplicate issues. Only the most actionable items were included to keep the SSOT useful as a working document. |
| Severity classification | Critical/High/Medium/Low | Aligned with the existing SSOT convention. Critical = data corruption or privilege escalation. High = incorrect behaviour or significant UX failure. Medium = best-practice gap. Low = nice-to-have improvement. |

## Business Impact

- The three audits created a comprehensive, prioritised backlog of improvements across security, accessibility, and code quality.
- The business logic audit identified two critical security issues (BL1, BL5) that could allow data tampering — these should be fixed before any public launch.
- The accessibility audit provides a roadmap to WCAG 2.1 AA compliance, which matters for public sector partnerships and demonstrates social responsibility aligned with the brand.
- The Laravel practices audit identifies performance bottlenecks (sitemap N+1, route caching) that will matter at scale.
