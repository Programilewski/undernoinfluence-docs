# 2026-06-22 — GDPR/ePrivacy Full Compliance Sprint

## Session Overview

Three connected sessions in one day. All were driven by a single question: *if a user clicks "Odrzuć wszystkie" on the cookie banner, does the application actually stop tracking them?* The answer, before today, was no — in several distinct ways. The day closed every gap, brought the test suite to 407/407, and produced auditable code paths to support the compliance story with a future UODO inspector or DPA partner.

**Session 1 — Frontend analytics module refactor:** Centralised all client-side analytics into a single ES module (`analytics.js`) that owns consent grant/revoke/check, PostHog capture, and identity. Four other files were updated to import from it. Previously, `venue-analytics.js` was sending server-side dwell events to declined users; this was corrected.

**Session 2 — Backend analytics GDPR compliance:** `EventLogger` was discovered to be writing four personal identifiers (`ip_hash`, `session_id`, `user_id`, `referrer`) to the `events` table on every interaction, regardless of consent. All four were stripped. A data migration nullified all existing rows. The admin dashboard's "unique sessions" stat (which would have returned zero permanently) was replaced with a total event count.

**Session 3 — Deferred compliance fixes + test suite green:** Four remaining items fixed: PostHog CDN lazy init (CDN request deferred until after consent), server-side analytics endpoint consent gate, email removed from PostHog identify payload, and PII columns formally dropped from the `events` table schema. Five test failures caused by the column drop were resolved.

## What Was Built

### 1. `resources/js/analytics.js` — Analytics authority module

**What changed:** Was a thin 8-line `capture()` wrapper. Now exports six named functions that cover the entire consent + identity + capture lifecycle. All PostHog operations in the application go through this module — no other file calls `window.posthog` directly.

| Export | Purpose |
|---|---|
| `capture(event, props)` | Fires a PostHog event. No-op if consent not granted. |
| `grantConsent()` | Calls `initPostHog()` (triggers CDN load), then `posthog.opt_in_capturing()`. The only place the CDN loads. |
| `revokeConsent()` | Calls `posthog.opt_out_capturing()`. |
| `isConsentGranted()` | Reads `uni_consent` cookie, returns bool. Gate used by `venue-analytics.js` and `app.js`. |
| `identify(userId, props)` | Calls `posthog.identify()`. Guards on `isConsentGranted()`. |
| `applyStoredConsent()` | Reads cookie on page load; calls `grantConsent()` if `uni_consent=granted`. Called at module init in `app.js`. |

**PostHog CDN lazy init:** `posthog.init()` (which triggers the CDN script load) was removed from `app.blade.php`. The `<head>` stub only sets up the queue object. `initPostHog()` inside `analytics.js` is called exclusively from `grantConsent()` — meaning zero PostHog network activity until consent is granted. The API key and host are passed via `<meta>` tags.

**Legal basis:** PKE Art. 5(3) — storage/reading on terminal device requires prior consent except for technically necessary purposes. The CDN request itself is a network event observable by PostHog infrastructure before any cookies are set. Deferring it is the only compliant solution.

**Current state:** Active.

### 2. `resources/js/consent.js` — Cookie consent Alpine component

**What changed:** Replaced a thin bottom bar (barely visible) with a category-based bottom panel. The panel slides up from the bottom and is backed by a 30% black overlay, requiring explicit user action. Two toggle rows: "Funkcjonalne" (always-on, grayed, shows an informational message if user tries to disable) and "Analityczne" (off by default). Three action buttons: "Odrzuć wszystkie" | "Zapisz preferencje" | "Zaakceptuj wszystkie". A persistent cookie icon in the corner reopens the panel after a decision is made.

**Why the redesign matters legally:** The original thin bar was a passive acceptance pattern — users could scroll past it without making a choice. EDPB guidelines (and the GDPR Art. 7 requirement for "unambiguous indication") require that consent be an active, freely given choice. The new panel demands a click. "Odrzuć wszystkie" is equally prominent as "Zaakceptuj wszystkie" — which is an explicit requirement: refusing consent must be as easy as granting it.

**Cookie security:** The `uni_consent` cookie is now written with `; Secure` flag. Without it, a browser transmits the cookie over plain HTTP as well as HTTPS. Belt-and-braces.

**Current state:** Active.

### 4. `app/Http/Controllers/AnalyticsEventController.php` — Server-side consent gate

**What changed:** Added `abort_unless($request->cookie('uni_consent') === 'granted', 403)` as the first line of the controller. The endpoint was previously open to all POST requests regardless of consent.

**Why this matters:** `venue-analytics.js` was already gated client-side with `isConsentGranted()`. But a technically motivated user (or a browser extension, or a scraped automation) could POST directly to `/analytics/events` and write server-side event rows without going through the UI consent flow. The server-side gate closes that gap. Defence in depth: the client gate prevents normal-user leakage; the server gate prevents deliberate bypass.

**Legal basis:** GDPR Art. 6(1)(a) — no lawful basis for processing analytics data about a user who has not consented.

**Current state:** Active. Test `event_endpoint_requires_consent_cookie` in `AnalyticsEventEndpointTest` covers this.

### 5. `app/Services/EventLogger.php` — Personal identifiers removed

**What changed:** The `log()` method previously wrote `user_id`, `session_id`, `ip_hash` (SHA-256 of IP + app key), and `referrer` on every event. All four fields removed. The `Illuminate\Http\Request` constructor dependency and the `sanitizedReferrer()` helper deleted.

**Why these are personal data:** A SHA-256 hash of an IP address is pseudonymous personal data — re-identification is possible under the right conditions (court order, ISP logs, limited IP space). A session ID links all HTTP requests in one browsing session to a single user without requiring authentication. Pseudonymous data is not anonymous — it falls squarely within GDPR's scope.

**Why "genuinely anonymous" matters:** Stripping these fields means the `events` table now falls outside GDPR entirely (there is no person the data could be attributed to). This eliminates the need for a legal basis for server-side analytics — a stronger compliance position than "legitimate interest," which is increasingly contested at European DPAs including UODO.

**Legal basis addressed:** GDPR Art. 5(1)(c) data minimisation — only personal data that is necessary for the specified purpose should be collected. Anonymous aggregate behavioural signals (which venue, which event type, which city) are retained. Individual-level linkage is not.

**Current state:** Active. Test `event_logger_stores_no_personal_identifiers` enforces this.

### 6. `database/migrations/2026_06_22_094306_nullify_identifiers_in_events_table.php`

**What changed:** Data migration that nullified all existing event rows (`UPDATE events SET user_id = NULL, session_id = NULL, ip_hash = NULL, referrer = NULL`). Also dropped the two indexes that were built specifically for identifier-based queries: `events_session_id_created_at_index` and `events_user_id_created_at_index`.

**GDPR principle:** Art. 5(1)(e) storage limitation — personal data no longer necessary for its original purpose must be erased. The historical identifier data was retained under an implicit 90-day retention policy. This migration makes erasure immediate and complete.

**Current state:** Applied and confirmed.

### 8. `app/Services/Analytics/DiscoveryAnalytics.php` and `VenueAnalytics.php` — distinctId hardened

**What changed:** `distinctId()` now returns `hash('sha256', session()->getId() . config('app.key'))` for anonymous users, instead of the raw session ID. For authenticated users it still returns `auth()->id()`.

**Why:** The raw session UUID sent to PostHog as a `distinctId` could in theory be correlated with the Laravel session store (if someone had access to both PostHog and the Redis/DB session backend). Adding the `app.key` salt breaks this correlation — the PostHog distinctId is now a one-way token that cannot be reversed to a session ID. This is data minimisation applied to third-party data sharing.

**Current state:** Active.

---

### 9. `resources/js/app.js` — Email removed from identify payload

**What changed:** `window.__authUser` previously contained `{id, email, name}`. The `email` field was removed. PostHog `identify()` now receives only `{name}`.

**Why:** Sending an email address to a third-party analytics service (PostHog) requires that the user's consent scope covers that specific data type. The `uni_consent=granted` banner text only mentions "cookies analityczne" — it does not specifically mention sharing the email with PostHog. Under GDPR Art. 5(1)(c), only data necessary for the analytics purpose (person stitching across sessions) should be shared. A numeric user ID achieves stitching without the email.

**Current state:** Active.

## Business Impact

**This closes the gap between the consent banner and the code.** Before today, clicking "Odrzuć" stopped PostHog from setting cookies — but the server was still writing a row to the database with the user's session ID, hashed IP, and referring URL. That is deceptive design. The EDPB and UODO both have enforcement authority over it. The fix is now complete.

**The compliance position is stronger than most SaaS products at this stage.** The typical approach: claim legitimate interest for server-side analytics (legally contested in Europe) + consent for PostHog (required). UNI's position after today: server-side analytics data is genuinely anonymous (no GDPR scope, no legal basis required) + PostHog is strictly consent-gated with CDN lazy loading. This is auditable, defensible, and differentiating for a product built around trust in the sober-curious community.

**The owner analytics product (V2) is built on clean foundations.** When venue owners pay for traffic data, every number in their dashboard will be derived from data that has no compliance entanglement. Showing an owner "your venue had 200 menu views this month" will be based on genuinely anonymous aggregate data. Clean data is a competitive advantage in due diligence and in partner conversations.

**The "Źródła ruchu" panel is gone — this is a one-time loss.** Referrer URLs were useful for attribution (which Instagram post drove traffic to which venue). That capability is permanently removed from the admin widget. Future referrer-equivalent tracking would require adding UTM parameter support (explicit, disclosed, not personally identifiable) — a V2 decision.

## Learning Path

**If you want to understand why the CDN lazy init matters:**
The key is that HTTP requests themselves carry information (IP, User-Agent, timing) even before any cookie is set. PostHog's CDN can fingerprint a visitor from the request to load the script, before `posthog.js` runs a single line. Loading the CDN only after consent is the only fully clean interpretation of "no terminal storage without consent."

**If you want to understand why "genuine anonymity" is better than "legitimate interest":**
GDPR legitimate interest (Art. 6(1)(f)) requires a balancing test: your legitimate business interest vs the individual's rights. For analytics, this test is increasingly failing at European DPAs — the CNIL (France), DSB (Austria), and UODO (Poland) have all found that server-side analytics linked to IP addresses or session IDs cannot rely on legitimate interest without a DPIA. Genuine anonymity (no person the data can be attributed to) exits GDPR entirely — no balancing test needed, no legal basis required, no DSR exposure.

**If you want to understand the Secure cookie flag:**
`Secure` tells the browser: "only send this cookie over HTTPS connections." Without it, if a user ever hits an HTTP URL (a redirect, a mixed-content link, a bookmark to `http://`), the browser will include the `uni_consent` cookie in the request. An attacker on the same network could read it via a passive capture. For a consent cookie, this is low practical risk — but the `Secure` flag costs nothing and is correct hygiene.

**Useful references:**
- EDPB Consent Guidelines 05/2020 — the authoritative document on what GDPR Art. 7 requires for valid consent UIs
- UODO — uodo.gov.pl — the Polish supervisory authority; their enforcement decisions are in Polish but their DPA registration forms are the ones UNI would use
- PostHog consent docs — eu.posthog.com/docs/privacy/consent-management
- GDPR Recital 26 — "solely anonymous information" is outside GDPR scope; explains why genuine anonymity is a better posture than pseudonymous + legal basis

#### 3. `resources/css/app.css` — Three changes

**Change A — `float-card` animation added (lines 586–591):**
A new `@keyframes float-card` using only `translateY()`. Two utility classes: `.animate-float-card` (6s, no delay) and `.animate-float-card-delayed` (6s, 3s delay). WCAG finding WG4. At 0.48 opacity on `#f7f8fb` surface, the calculated contrast ratio was ~3.1:1 — below the 4.5:1 AA threshold for small text. At 0.60 the calculated ratio is ~4.9:1, which passes. Dark mode `--fg-faint` (0.42 on a near-black background) was already at ~7.6:1 and was not changed.

**Change C — `prefers-reduced-motion` media query added (new block before Discovery section):**
WCAG finding WG1. All eight animation utility classes (`animate-float-card`, `animate-float-card-delayed`, `animate-float-marker`, `animate-float-marker-delayed`, `animate-radar-light`, `animate-radar-light-delayed`, `animate-radar-glow`, `animate-radar-glow-delayed`) plus `animate-progress-bar` and `.chunk` are disabled with `animation: none !important` when the user's OS-level "reduce motion" preference is active. SC 2.2.2 requires auto-playing motion lasting more than 5 seconds to be pausable or stoppable. The animations are indefinite — this media query is the correct solution.

#### 4. `resources/views/livewire/discovery-page.blade.php` — `aria-expanded` on dropdowns

**What changed:** Added `:aria-expanded="open.toString()"` to both the city filter dropdown trigger button (~line 118) and the district filter dropdown trigger button (~line 157). Alpine.js reactively updates the attribute on each toggle click.

**Why:** WCAG SC 4.1.2 requires that UI components expose their name, role, and state to assistive technology. But the expanded/collapsed state was invisible to screen readers — a user on NVDA or JAWS had no way to know whether the dropdown was open or closed without visual inspection. This is a one-attribute fix with no visual effect.

**Current state:** Active.

#### 5. `resources/js/consent.js` — Initial focus management for cookie modal

**What changed:** In the `init()` method, when `this.visible` is true (i.e., no prior consent decision), added `this.$nextTick(() => { const panel = this.$el.querySelector('[role="dialog"]'); if (panel) { panel.querySelector('button')?.focus(); } })`.

**Why:** WCAG SC 2.4.3 (Focus Order) requires that when a dialog opens, focus moves into the dialog. With no focus management, keyboard-only and screen reader users land on `<body>` and must Tab through the entire page before reaching the cookie consent buttons. The `$nextTick` waits for Alpine to render the visible dialog, then focuses the first button ("Odrzuć wszystkie").

**Limitation:** The `reopen()` method (triggered by clicking the persistent cookie icon after a decision is made) does not yet include this focus management pattern. It is marked Partial in the WCAG audit table (WG6). The complete solution requires a focus trap (WG2) to be implemented at the same time.

**Current state:** Active (partial — covers initial page load; `reopen()` still needs focus management paired with WG2 focus trap).
