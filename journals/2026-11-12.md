## What Was Built

**1. "Wyodrębnij z obrazami": a PDF menu read with every page as text and as an image.** Paweł asked how PDFs are read. The answer: text first (`pdftotext -layout`), with a page becoming an image only when its text fails the quality check (too short, wrong code page, interleaved columns). He worried that text loses something, and it can: a readable text layer can still put a price on the wrong drink in two columns, separate a heading from its drinks, or drop a 0% icon. Two readings catch a disagreement but not the same mistake made twice. He asked for an option to "send both when we want". On a menu's page, the actions menu now has *Wyodrębnij z obrazami* next to *Wyodrębnij*:
- It rasterises every page, the readable ones too.
- It sends the text and the images together, and tells the model the images are the same pages: use them for what belongs to what, and the text for spelling.
- It reads twice, as always.

Only a PDF offers it: a photo is already an image, and a web page is never rendered. Both readings record the choice (`menu_extractions.with_page_images`). The confirmation states the measured average cost of the chosen mode, kept apart from text-only reads: about $0.02 per menu estimated until measured, against $0.005 for text. Reading again replaces the lines still waiting, as before. The extractions list on a menu's page shows the mode ("tekst" / "tekst + obrazy stron"). Where: `MenuTextExtractor`, `MenuText`, `MenuReadingPrompt`, `ReadMenuAction`, `ReadMenuActions`, `ViewMenuSource`, `ExtractionsRelationManager`, the `menu_extractions` create migration. Tests: 9 new, in `MenuTextExtractorTest`, `ReadMenuActionTest` and `AdminMenuLibraryTest`.

**2. Each Brave candidate remembers the query that found it; Wyszukiwania shows the yield per query.** 11.11 measured that half of the verified candidates were not venues, and the plan was to "tune the query templates". When checked, nothing tied a candidate to its query, so yield per query could not be measured at all. Now a source-A candidate keeps its run (`sourcing_search_id`) and the query that first returned its domain (`found_by_query`). That is UNI's own query, so ADR-012's "nothing of Brave's result is kept" still holds. Wyszukiwania has a header button, *Wydajność zapytań*. Per query, over every run, it counts the candidates, those with a downloaded menu, the venues they became and the rejections, best first. Kandydaci shows the query under the source. The `sourcing_searches` create migration was renamed to run before the candidates' (needed for the foreign key). Where: `SearchForVenuesAction`, `VerifySourcingDomain`, `SourcingSearch::queryYield()`, `SourcingCandidate::search()`, `ListSourcingSearches`, `SourcingCandidatesTable`. Tests: 3 new.

**3. The Anthropic processor agreement: found, recorded, not yet read in full.** Anthropic's Commercial Terms incorporate its Data Processing Addendum by reference in the data-privacy section, so the agreement comes with the API terms; nothing has to be signed. They also say customer content is not used for training. Recorded as the first real rows of `compliance/dpa/README.md` and `compliance/vendors/README.md`. The DPA's own text, its sub-processor list and the transfer mechanism (US) were not read. That is one step left before a bulk run: open it from the console and note its version.

**4. Chains: checked, found broken, written up.** In the code, a domain is one candidate. A second location's menu replaces the first as the current file and deletes it, and linking a menu to a venue moves every menu of the candidate. The 11.11 workaround ("start from a location's page") therefore doesn't work. Semolino's live site on 12.11: the locations are separate pages in the sitemap; Piastów and Ursus link the same `Menu-Kleszczowa.pdf`, while Wilanów links its own 2026 PDF. Written as [[decisions/product/a-sourcing-candidate-is-a-location]] (recommended, waiting on Paweł). Not built, because it changes ADR-012's one-candidate-per-domain rule and touches fetching, finding, linking, rejection and erasure.

**5. Records and the resume point.** New decision records: [[decisions/product/menus-are-read-as-text-images-on-request]] (decided, built) and the chains record (open), both in the decisions index. The backlog row for the pipeline in `roadmap/undone-inventory.md` is updated. §12 of [[briefings/next-session-2026-11-10]] is the resume point for 13.11. The workspace index was rebuilt.

**Side effect, said plainly:** applying the two edited create migrations meant `migrate:fresh --seed` on the PC's dev database (the pre-production rule). It wiped the local candidates, menus and readings from the 11.11 live runs. They were test runs and the measurements are in the 11.11 journal, but the 11.11 local data is gone.

## Business Impact

Both features cut the admin time per approved venue, which is what stands between UNI and its ~30 launch venues. Image readings make the approval screen trustworthy on awkward menus without making every menu dearer. The yield table turns "tune the queries" from guesswork into a number: which query actually produces venues. Catching the chain bug before the first real batch avoids losing a location's menu silently, and Warsaw's chains are among the venues most likely to carry branded 0% drinks.
