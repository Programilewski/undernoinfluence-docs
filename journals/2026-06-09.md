## Decision Register

- **Keep `@js($venuesForMap)` inlined in HTML rather than moving to an async API.** *(permanent,
  revisit at >300 venues)*
  - Chosen because the payload is ~15-20 KiB at 71 venues — trivial. Even at the 500-venue cap
    it would be ~100-150 KiB. The Lighthouse "document request latency" flag (439 KiB) is driven
    by server response time and dev-mode asset weight, not the venue JSON.
  - Rejected: async API endpoint (`/api/venues/map`). Would require authentication (or become an
    abuse/scraping surface without it), introduces a race condition where the map renders empty
    before the fetch completes, adds CORS/caching complexity, and all for moving ~15 KiB out of
    the HTML. Classic over-engineering for negligible gain.
  - Revisit when venue count passes ~300 and a production Lighthouse run shows LCP above 2.5s
    attributable to document size rather than TTFB or JS bundle.

- **No code changes needed for the current Lighthouse score.** *(permanent until post-deploy
  re-test)*
  - The Performance 78 is explained by: unminified JS (618 KiB, fixed by `npm run build`),
    unused JS (737 KiB, mostly Livewire/Alpine runtime — cost of the stack), and localhost TTFB.
  - Best Practices 81 is entirely HTTPS/CSP/HSTS/COOP — server config that resolves on
    production deploy with TLS.
  - Expected production score: 85-90+ without any code changes.

- **No wasted engineering effort.** By analyzing the actual data before jumping to an API
  solution, we avoided building unnecessary infrastructure (auth, rate limiting, endpoint
  maintenance) that would have added complexity without improving user experience.

  means the codebase is launch-ready from a web performance perspective.
