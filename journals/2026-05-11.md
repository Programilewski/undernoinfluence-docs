## What Was Built

### 1. URL Architecture — `/szukaj` to `/mapa`

**What:** Renamed the discovery page route from `/szukaj` to `/mapa/{city?}`. The route supports an optional city slug as a path parameter for single-city entry points (e.g., `/mapa/warszawa`). Unknown city slugs return 404.

**Where:**
- `routes/web.php` — route definition changed
- All test files that referenced `/szukaj` updated to `/mapa`

**Why:** `/mapa` is more intuitive (it's a map page) and the city parameter supports multi-city expansion. The path param gives clean SEO-friendly URLs for single-city pages while the Livewire component handles multi-city state via query params.

**Current state:** Working. `/mapa` shows all venues, `/mapa/warszawa` shows Warsaw-scoped venues.

### 9. Multi-Select District Filter with City Grouping

### 10. "Search in Area" Resets City/District Filters

**What:** When a user pans the map and clicks "Szukaj w tym obszarze", the `searchInArea()` method now clears `selectedCities` and `selectedDistricts` before setting the geographic bounds.

**Where:**
- `app/Livewire/DiscoveryPage.php` — `searchInArea()` method
- Alpine `syncDiscoveryUrl()` — updates browser URL via `history.replaceState`

**Why:** If a user selects Kraków, pans the map to Warsaw, and clicks "search in area", they expect to see Warsaw venues. Without clearing the city filter, the query intersects "city = Kraków" with "bounds = Warsaw" — which returns nothing. Clearing the city/district filters makes bounds-based search show everything in the visible area.

**Current state:** Working. After "search in area", city and district filters are cleared and the URL updates to reflect the new state.

### 11. Smart URL Management via Alpine `replaceState`

**What:** `selectedCities` and `selectedDistricts` are NOT managed by Livewire's `#[Url]` attribute. Instead, after any change, Livewire dispatches a `sync-discovery-url` event. Alpine catches it and rewrites the browser URL using `history.replaceState`:
- 0 cities → `/mapa`
- 1 city → `/mapa/{slug}` (clean path URL)
- 2+ cities → `/mapa?miasta[0]=a&miasta[1]=b` (query params)
- Districts always use query params: `?dzielnice[0]=5&dzielnice[1]=12`

**Where:**
- `app/Livewire/DiscoveryPage.php` — `syncUrl()` dispatches event
- `resources/views/livewire/discovery-page.blade.php` — `syncDiscoveryUrl()` Alpine method

**Why:** Livewire's `#[Url]` always uses query params (`?miasta[0]=warszawa`), which is ugly for single-city pages. The clean `/mapa/warszawa` URL is better for sharing, bookmarks, and SEO. The `mount()` method handles both formats: path params (from `/mapa/warszawa`) and query params (from `?miasta[]=...`).

**Current state:** Working. The `mount(?string $city)` reads from path params for single-city entry; query params for multi-city. `history.replaceState` keeps the URL in sync without full page reloads.

## Decision Register

### D-30: Multi-select cities with query params vs. path-only routing
- **Chosen:** Hybrid approach — single city uses clean path URL (`/mapa/warszawa`), multi-city uses query params (`?miasta[0]=...&miasta[1]=...`)
- **Rejected:** Path-only for all cases — impossible with multi-select (`/mapa/warszawa+krakow` is not standard)
- **Rejected:** Query-params-only — ugly URL for the common single-city case
- **Why:** Most users will select one city. They should get a clean, shareable URL. Multi-city is the power-user case where query params are acceptable.
- **Status:** Permanent

### D-31: District filter shows all districts, not just those with venues
- **Chosen:** Show all districts for selected cities regardless of whether venues have `district_id` set
- **Rejected:** Only show districts with active non-canary venues (previous behavior) — resulted in the filter never appearing because no Warsaw venues have `district_id` assigned yet
- **Why:** The filter must be visible to be useful. Users need to see it exists and works. Empty results for a selected district are handled by the existing "Brak wyników" empty state.
- **Status:** Revisit — once venues have district_id assignments, we could re-add the `whereHas` filter to hide truly empty districts

### D-32: "Search in area" clears city and district filters
- **Chosen:** Clear both selectedCities and selectedDistricts when searching by map bounds
- **Rejected:** Keep city filter active during bounds search — leads to impossible intersections (e.g., Kraków city filter + Warsaw bounds = 0 results)
- **Why:** Bounds-based search is inherently geographic. Adding a city filter on top is redundant at best and contradictory at worst. Users who click "search in area" want to see everything in that area.
- **Status:** Permanent

### D-33: City search in dropdown
- **Chosen:** Client-side Alpine search filter in the city dropdown (x-show + includes())
- **Rejected:** Server-side Livewire search — unnecessary for a small list of active cities (currently ~5)
- **Why:** Fast, no server round-trip, scales fine up to 50+ cities. Only if hundreds of cities exist would server-side search be needed.
- **Status:** Permanent

### D-34: URL state management — manual `replaceState` vs. Livewire `#[Url]`
- **Chosen:** Manual management via Alpine `history.replaceState` for city/district; Livewire `#[Url]` for other filters
- **Rejected:** `#[Url]` for everything — can't produce clean `/mapa/warszawa` path URLs (always generates query params)
- **Rejected:** Manual management for ALL filters — too much work, error-prone, loses Livewire's automatic URL sync
- **Why:** Hybrid gives the best of both worlds. City/district need custom URL logic; categories, search, sort, etc. work perfectly with `#[Url]`.
- **Status:** Permanent

### D-35: No 301 redirects
- **Chosen:** No redirects from old `/szukaj` URL. The app is not in production yet.
- **Rejected:** Add 301 redirects from `/szukaj` to `/mapa`
- **Why:** No users, no bookmarks, no SEO juice to preserve. Redirects add complexity with zero benefit.
- **Status:** Permanent

### D-36: Category route changed to use `seo_slug`
- **Chosen:** `{category:seo_slug}` route binding with `-bezalkoholowe` suffixed URLs
- **Rejected:** Keep `{category:slug}` — misses SEO opportunity for high-intent "bezalkoholowe" search terms
- **Why:** Every URL containing "bezalkoholowe" is a ranking signal for the primary user intent. This is a free SEO win.
- **Status:** Permanent

## Learning Path

### For this session's work

- **Livewire `#[Url]` vs. manual URL management:** Livewire's `#[Url]` attribute automatically syncs a component property with query params in the browser URL. It's perfect for simple key-value filters. But it can't produce path-based URLs like `/mapa/warszawa` — it always uses `?key=value`. When you need a mix of path and query param URLs, you manage the URL manually with `history.replaceState` in JavaScript, and read the values in `mount()`.

- **Alpine `x-show` for client-side filtering:** Instead of sending every keystroke to the server to filter a list, Alpine's `x-show` directive hides items client-side using JavaScript string matching. This is instant (no network round-trip) and perfect for lists under ~100 items.

- **`history.replaceState` vs `pushState`:** `replaceState` changes the URL without adding a history entry (no new "back" button step). `pushState` adds an entry. For filter changes, `replaceState` is correct — you don't want every checkbox toggle to add a back-button step.

- **Route regex constraints for disambiguation:** When two routes have the same URL pattern (e.g., `/{city}/{category}` and `/{city}/{district}`), Laravel can't tell them apart. A regex `where()` constraint on one route (e.g., matching `-bezalkoholowe` suffix) lets Laravel resolve the ambiguity without a prefix like `/kategoria/`.

### Decision Register

#### D-37: OSM light tiles as the standard light-mode tile provider
- **Chosen:** OpenStreetMap `tile.openstreetmap.org` for light mode across all maps
- **Rejected:** CARTO `basemaps.cartocdn.com/light_all` (was used on venue show page)
- **Why:** The discovery page already used OSM for light mode. Using CARTO only on the venue show page created a visual inconsistency when switching between pages. OSM tiles are free without API keys.
- **Status:** Permanent

#### D-38: Window globals for analytics wrappers vs. module-only
- **Chosen:** Expose `window.__capture`, `window.__track`, `window.__trackVenue` for Blade inline usage
- **Rejected:** Import-only (would require making every Blade template a JS module consumer)
- **Why:** Blade templates need to call tracking functions from `@click` directives. Alpine `@click` handlers execute in the global scope, so the functions must be on `window`. The `__` prefix signals "internal API, not for end users."
- **Status:** Permanent

#### D-39: Keep legacy `window.uniTrack` as a bridge
- **Chosen:** Keep the function with delegation to the new module
- **Rejected:** Remove it immediately
- **Why:** No remaining Blade callers, but removing it requires certainty that no Filament panel or admin code calls it. The bridge costs nothing and prevents a silent failure if something does.
- **Status:** Revisit in 2 weeks — remove if no callers found

#### D-40: VenuePresenter as static methods, not a service
- **Chosen:** Static methods on a final class (`VenuePresenter::categoryRows()`)
- **Rejected:** Instance-based service injected via DI container
- **Why:** The presenter is stateless — it takes a venue and returns display data. There's nothing to inject. Static methods are simpler, require no registration, and the `once()` caching in `activeCategories()` handles per-request performance.
- **Status:** Permanent
