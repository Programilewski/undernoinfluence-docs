# 2026-05-12 — Session 2

## Session Overview

Goal: correct the B2B venue-claim flow so a newly registered public user does **not** instantly receive access to the owner panel.

Outcome: implemented the intended approval-gated model. A public user can create an account and submit a claim request, but `/panel` is now owner-only. Admin approval is the only path that upgrades the user to `owner` and unlocks the venue panel. The SSOT was updated to document this final behavior.

## What Was Built

### Owner panel access is now approval-gated

- Changed `App\Models\User::canAccessPanel()` so the Filament `panel` panel is accessible only to users with `role = owner`.
- Disabled Filament owner-panel self-registration in `PanelPanelProvider`.
- `/panel/register` is no longer exposed.
- Admins are still redirected from `/panel` to `/admin` by `PanelAuthenticate`.

Why: the previous behavior let ordinary `role=user` accounts enter `/panel` immediately. That made B2B access feel self-serve, when the business requirement is manual verification first.

### Public claim form added at `/zglos-lokal`

Added a normal authenticated frontend claim flow:

- `GET /zglos-lokal` shows the Polish claim form.
- `POST /zglos-lokal` stores a pending claim.
- The form supports two paths:
  - user selects an existing unclaimed venue;
  - user selects `Nie ma mojego lokalu na liście` and submits data for a new venue.
- The form collects:
  - contact name;
  - contact email;
  - optional phone;
  - preferred verification method;
  - message for manual verification;
  - new venue name/city/address/website when needed.

### New venue claim handling

If the user says their venue is not listed, the app now creates an inactive draft venue:

- `is_active = false`
- `source = claim_submission`

- the claim links to that draft venue

On admin approval, the venue is activated and assigned to the owner.

## Decision Register

### Decision: move claiming out of Filament owner panel

Chosen: claim requests happen in the public Laravel frontend at `/zglos-lokal`.

Rejected: allowing `role=user` into `/panel` just to submit a claim.

Reason: `/panel` should mean “verified owner workspace,” not “any user with an account.” Keeping pre-approval users out protects the B2B boundary and avoids confusing them with empty owner-panel UI.

### Decision: create inactive draft venues for “not in list” claims

Chosen: create an inactive venue immediately, linked to the pending claim.

Rejected: storing all new venue data only inside `venue_claims`.

Reason: admin approval can reuse the same venue assignment flow for both existing and new venues. The draft remains invisible publicly until approved.

### Decision: public account remains separate from B2B permission

Chosen: `/rejestracja` creates `role=user`; approval upgrades to `role=owner`.

Rejected: a separate owner-registration endpoint that implies immediate owner status.

Reason: public identity and venue ownership are different trust levels.

## Technical Debt Log

- The claim form uses a plain Blade `<select>` for venues. It is acceptable for current scale, but if the venue list grows large this should become searchable/autocomplete.
- New venue drafts use the selected city center coordinates until admin corrects location. Admin review must treat location as unverified.
- `claim_type` and claim statuses are strings. Enums could reduce typo risk later, but this follows the existing table convention.

## Data Model State

`venue_claims` now supports richer manual verification:

- existing venue claims: `claim_type = existing`, `venue_id` points to an existing active unclaimed venue.
- new venue claims: `claim_type = new`, `venue_id` points to an inactive draft venue, and submitted venue fields preserve what the user entered.

`venues` ownership remains:

- `is_claimed`
- `claimed_by`
- `claimed_at`

`users.role` remains the owner-panel gate:

- `user`: public account, no `/panel` access.
- `owner`: approved B2B owner, can access `/panel`.
- `admin`: admin panel only, redirected away from `/panel`.

## Analytics Events Catalog

Updated claim-related events:

- `claim_submitted`: captured from `/zglos-lokal`; includes `claim_id`, `venue_id`, `claim_type`, `verification_method`.
- `claim_approved`: captured from admin claim approval; includes `claim_id`, `venue_id`, `claim_type`, `reviewed_by`.
- `claim_rejected`: captured from admin rejection; includes `claim_id`, `venue_id`, `claim_type`, `reviewed_by`.

## Risk Register

| Risk | Impact | Mitigation |
|---|---|---|
| Users who expected `/panel` immediately now see forbidden access | Confusion after registration | CTAs route them to `/zglos-lokal`; copy explains panel access is granted after verification |
| New venue drafts have approximate coordinates | Public map quality risk if activated without review | Draft venues are inactive until admin approval; admin should verify location before/after approving |
| Duplicate claims for the same venue | Operational confusion | Validation blocks pending/approved claims for the same venue |
| User submits multiple pending claims | Review queue spam | Validation blocks more than one pending claim per user |
