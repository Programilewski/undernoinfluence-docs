## What Was Built

### 1. Map Layout — Airbnb-Style (not full-screen)

**What:** Map changed from full-screen to a contained rounded rectangle with padding.  
**Where:** `resources/views/map.blade.php` — outer container, map div.  
**Why:** Full-screen maps feel like dev tools, not products. Airbnb's discovery UX
(contained map + list side-by-side) is the established mental model users understand.
The rounded corners and shadow give it a "card" feel that matches the dark theme.  
**Key classes:** `rounded-2xl overflow-hidden shadow-xl` on the map wrapper.
`overflow-hidden` is what clips the Leaflet tiles to the rounded border.  
**Gotcha:** `overflow-hidden` on the map container clips Leaflet controls if they're
positioned near the edges. Not currently an issue but worth knowing.

### 2. Search Bar + Filter Chips

**What:** Full-width search input above the map and list. Submits via GET — URL is
shareable and indexable. Filter chips for alcohol level and venue category (currently mock/disabled).  
**Where:** `map.blade.php` (search form), `VenueController@index` (filtering logic),
`Venue::scopeSearch()` (query scope).  
**Why:**
- GET form = bookmarkable, shareable URLs (`/venues?search=craft+beer+warszawa`)
- Server-side filtering = the filtered result is what Google indexes, not the full list
- `ILIKE` on PostgreSQL = case-insensitive Polish character search without collation config
- Scope on the model = reusable for Livewire, API, or Filament filters later

**Filter chips state:** Disabled (`cursor-not-allowed opacity-40`) — visual placeholder.
Data model doesn't support filtering by alcohol level or category yet (no `venue_products` data).

### 3. City Filter + Auto-Pan Map

**What:** A `<select>` dropdown in the search bar filters venues by city. When a city
is selected, the map auto-pans to that city's centre at zoom 13.  
**Where:** `map.blade.php` (select element), `VenueController@index` (`$citySlug` param),
`Venue::scopeInCity()` (scope), `CitiesSeeder` (25 Polish cities seeded).  
**Why:** City-scoped URLs are the primary pSEO pattern. `/venues?city=bialystok` is a
distinct, indexable page. The city centre coordinates in the `cities` table drive the
map pan — the map doesn't have to guess where a city is.  
**Smart map view logic (JS):**
```
if (selectedCity)         → setView(city.lat/lng, zoom 13)
else if (markers exist)   → fitBounds(all markers + 15% padding)
else                      → fitBounds(Poland)
```
This replaced the old `fitBounds(polandBounds)` which always showed all of Poland even
when filtered to one city.

### 5. Analytics Infrastructure — Events Table

**What:** Append-only `events` table. Every page view and user interaction fires an
event row. No updates, ever — only inserts.  
**Where:** `database/migrations/2026_04_07_174634_create_events_table.php`,
`app/Models/Event.php`, called from `VenueController` and `EventController`.

**Schema:**
```
id              bigint, auto-increment
type            varchar(100)  — dot-notation e.g. "venue.list.viewed"
venue_id        nullable FK → venues
city_id         nullable FK → cities
product_id      nullable FK → products
user_id         nullable FK → users
session_id      varchar(100)  — Laravel session ID
ip_hash         varchar(64)   — SHA-256(ip + app.key), GDPR-safe
referrer        varchar       — HTTP Referer header
properties      jsonb         — flexible event-specific payload
created_at      timestamp     — NO updated_at (append-only)
```

**Indexes (5 composite):**
```sql
(type, created_at)              — filter by event type over time
(venue_id, type, created_at)    — "how many times was venue X viewed this week?"
(city_id, type, created_at)     — "which city page drives the most traffic?"
(session_id, created_at)        — unique visitor counting
(user_id, created_at)           — per-user behaviour (future)
```

**Why append-only?** Immutable event logs are the gold standard for analytics.
You can always rebuild aggregates from raw events. You cannot recover deleted rows.
This table is the foundation for Credibility Score, B2B analytics dashboards, and
eventual API monetization.

**Why `ip_hash` not raw IP?** GDPR. IP addresses are personal data. A SHA-256 hash
keyed with `app.key` (a server-side secret) cannot be reversed, but CAN count unique
IPs within a session. If you rotate `app.key`, old hashes become incomparable — a
feature, not a bug, for privacy.

**Why `defer()`?** Laravel 11+ `defer()` runs a callback after the HTTP response is
sent. Zero latency impact — the user gets the page instantly, then the DB write happens.
No queue infrastructure needed.

**Events currently firing:**
| Event type | Where fired | `properties` payload |
|---|---|---|
| `venue.list.viewed` | `VenueController@index` | `search`, `result_count`, `city_id` |
| `venue.show.viewed` | `VenueController@show` | `venue_id`, `city_id` |
| `venue.map.pin.clicked` | `map.blade.php` JS → `/api/track` | `venue_id` |
| `venue.navigate.clicked` | `venue-tile.blade.php` JS → `/api/track` | `venue_id` |
| `bot.honeypot.triggered` | `routes/web.php` closure | `path`, `user_agent` |

### 6. Client-Side Analytics Endpoint

**What:** `POST /api/track` accepts client-side events (map clicks, button clicks) and
writes them to the events table. Rate-limited to 60 req/min per IP.  
**Where:** `app/Http/Controllers/EventController.php`, `routes/web.php`.  
**Why:** Server-side page views only tell you who loaded the page. Client-side events
tell you what they did. A user who clicks 3 map pins is far more engaged than one who
bounces — and this distinction powers Credibility Score ranking later.

**Security on the endpoint:**
- `throttle:60,1` middleware — rate limited
- `type` validated by regex `^[a-z][a-z0-9]*(\.[a-z][a-z0-9]*)+$` — only known-format event names accepted
- CSRF token required — prevents third-party POSTs
- `defer()` — DB write never blocks the response

**JS tracking function (in map.blade.php):**
```javascript
function track(type, data = {}) {
    fetch('/api/track', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json', 'X-CSRF-TOKEN': csrfToken },
        body: JSON.stringify({ type, ...data }),
    }).catch(() => {}); // fire-and-forget — never block UX on analytics
}
```
The `.catch(() => {})` is intentional — analytics failure must never break UX.

### 12. AI Scraping Protection — 4 Layers

**Layer 1 — `robots.txt`**  
**Where:** `public/robots.txt`  
Blocks 11 named AI training crawlers. Key distinction: `Googlebot` (indexing) is
allowed; `Google-Extended` (AI training) is blocked. These are separate bots.

**Layer 2 — `X-Robots-Tag: noai, noimageai` header**  
**Where:** `app/Http/Middleware/SetSecurityHeaders.php`, registered globally in `bootstrap/app.php`.  
HTTP-header signal for crawlers that check headers before loading HTML. Complements
the `<meta name="robots" content="..., noai, noimageai">` tag in the page.

**Layer 3 — Coordinate Fuzzing**  
**Where:** `VenueController@index` — applied to the collection after DB query, before view.  
Fuzz amount: ±0.0005° latitude, ±0.0007° longitude ≈ ±55 m.  
The map still works (discovery use case doesn't need 1m accuracy). Google Maps navigation
routes to the address string, not the coordinates. Bulk-scraped datasets are systematically
wrong. Accurate coordinates served only via authenticated API (future).

**Layer 4 — Honeypot**  
**Where:** Hidden `<a>` in `map.blade.php` → `GET /export/venues.json` → fires
`bot.honeypot.triggered` event → returns 404.  
Named to look like a bulk data export endpoint — exactly what scrapers search for.
Every hit is logged in the events table with user agent. Invisible to real users
(`display:none; visibility:hidden; position:absolute; left:-9999px`).

**What scraping protection does NOT do:** Stop a determined scraper who runs headless
Chrome, reads the page like a human, and extracts HTML. The real moat is the NoLo
score, Credibility Score, and behavioural data — none of which are in public HTML.

## Decision Register

### `defer()` vs Queued Job for Analytics
- **Chosen:** `defer()` — built-in Laravel 11, zero infrastructure
- **Rejected:** Queue worker + job class
- **Why:** Queue requires Redis or database queue table, a worker process, and
  monitoring. `defer()` achieves the same result (non-blocking write) with zero ops
  overhead. Good until traffic justifies dedicated queue infrastructure.
- **Migrate when:** >500 concurrent users, or analytics writes start failing under load.

### GET form vs Livewire for Search
- **Chosen:** HTML GET form
- **Rejected:** Livewire reactive search
- **Why:** GET URLs are indexable by Google. Each search+filter combination produces
  a distinct URL that can appear in search results. Livewire would be better UX
  (no page reload) but the URLs wouldn't be indexable.
- **Migrate when:** Search is used heavily and page reload feels slow. Solution: add
  Livewire with `history.pushState` to preserve URLs.

### name+URL only in JSON-LD vs full structured data
- **Chosen:** name + URL only
- **Rejected:** Full address + coordinates in JSON-LD
- **Why:** Google only needs enough to understand the list structure. Including coordinates
  in structured data turns the HTML page into a bulk geo-data API — a direct threat to
  the future paid API product.

### Coordinate fuzzing in controller vs model accessor
- **Chosen:** Controller (in-memory mutation of collection)
- **Rejected:** Model accessor (always applied)
- **Why:** Fuzzing should only apply to public-facing views. A model accessor would also
  fuzz data in the admin panel, Filament tables, and future API responses. Controller
  mutation is surgical.

## Session 2 — End of Day Wrap-Up

**Goal:** Make the project self-documenting across sessions — not just today's session but every future one.  
**Outcome:** Journals system created, CLAUDE.md updated with standing instructions, and `/wrap` skill built so writing the journal at the end of a session is a single command.

### What Was Built

#### `journals/` Directory and Format

**What:** A `journals/` directory in the project root. Every working session gets its own file (`YYYY-MM-DD.md`). `journals/README.md` defines the section format and hosts the global Canary Register.  
**Where:** `journals/README.md`, `journals/2026-04-05.md`, `journals/2026-04-07.md`.  
**Why:** As a founder who doesn't read code daily, you need a way to re-enter the project after any gap — a week, a month, or a handoff to a developer — without asking "what was I doing?". The journals answer: what exists, why it exists, what's broken, what's next. They're also the onboarding document for any future developer or investor.

The format was designed around your actual needs, not a generic dev log:
- **Decision Register** — the road not taken is as important as the road taken. Any future "why did we do it this way?" question is answered here.
- **Business Impact** — every technical change connects explicitly to acquisition, retention, or monetization. Code changes that don't serve the business shouldn't exist.
- **Risk Register** — things that can go wrong, quantified by likelihood and impact. Gives you visibility into technical risk without needing to read the code.
- **Canary Register** — the global list lives in `README.md` so it's never lost and is always updated. Each daily journal copies the current state.

#### `journals/2026-04-05.md` — Reconstructed

**What:** Journal for the initial session (April 5) reconstructed from git history and the initial commit state.  
**Why:** Without a record of the founding decisions (why Filament, why PostgreSQL, why Leaflet), you'd have no baseline to compare against. The April 5 journal is now the starting point of the project's written history.

#### CLAUDE.md — Project Journals Section

**What:** A "Project Journals" instruction block appended to `CLAUDE.md`.  
**Where:** `/var/www/undernoinfluence/CLAUDE.md`.  
**Why:** `CLAUDE.md` is loaded at the start of every Claude Code session. Adding standing instructions there means the AI assistant will write a journal at the end of every session regardless of whether you remember to ask — and regardless of which session it is. The instructions cover: file naming, section format, writing voice, when to update the README canary register, and how to handle multiple sessions in one day.

This makes the journals system **session-agnostic** — no reliance on memory, no need to repeat yourself.

#### `/wrap` Skill — `.claude/skills/wrap/SKILL.md`

**What:** A project-level Claude Code skill invoked by typing `/wrap`.  
**Where:** `.claude/skills/wrap/SKILL.md`.  
**Why:** Even with standing instructions in `CLAUDE.md`, writing the journal is most reliable when explicitly triggered at a natural session close point — when you feel "we're done for today." `/wrap` is that trigger. It takes 10–20 seconds and produces a complete journal entry.

What the skill does when invoked:
1. Gets today's date
2. Reads `journals/README.md` for format
3. Checks if today's journal already exists (appends a Session N block if so)
4. Reconstructs the full session from conversation context — does not ask you to summarise
5. Writes all applicable sections
6. Updates the Canary Register in `README.md` if new canaries were added

The skill was also registered in the `Skills Activation` section of `CLAUDE.md` so future sessions know it exists and that it is **user-invocable only** (never auto-triggered).

### Decision Register

#### Journals in `journals/` vs a Wiki, Notion, or README

- **Chosen:** `journals/` directory, Markdown files, committed to the repo
- **Rejected:** External wiki (Notion, Confluence), README history section, separate docs repo
- **Why:** Markdown in the repo means:
  - Journals are versioned with the code — you can check out any commit and read the journal from that day
  - No external service dependency — journals are always accessible
  - The AI assistant can read them directly as files — no API calls, no auth
  - Diffs in git show exactly what changed between sessions
- **Status:** Permanent for Phase 1.

#### `/wrap` as user-invocable vs automatic (token threshold, Stop hook, timer)

- **Chosen:** User-invocable — type `/wrap` when you feel the session ending
- **Rejected:** Automatic trigger at context limit, automatic Stop hook, scheduled timer
- **Why:** Automatic triggers at context limits produce incomplete journals — the session gets cut off mid-thought. A Stop hook fires too early (before you've reviewed the work). A timer doesn't know when real work happened vs when you stepped away. You know when the session is over; `/wrap` puts you in control of that moment.
- **Status:** Permanent. Can add a reminder reminder to CLAUDE.md if forgetting becomes a pattern.
