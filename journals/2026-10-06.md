### 3. `uni:prune-expired-cache`, the IP-hash rows fix

**The problem, in plain terms.** UNI limits how often one visitor can hit certain pages (reports, redirects to venues, analytics events, the venue-request search), so a bot can't flood them. To count a visitor, the limiter writes a small row to the database's `cache` table. The row's name is an MD5 hash of the visitor's IP address (on IPv6, of their /64 block). MD5 of an IPv4 address isn't anonymous: there are only about 4 billion addresses, so a laptop can recover the original in minutes. Each row is marked to expire after a minute, but **Laravel's database cache only deletes an expired row when somebody reads that same key again.** A visitor who comes once and never returns leaves their row behind forever, and it ends up in every nightly backup. Found on 03.10.

**What:** a new command, `uni:prune-expired-cache`, scheduled every five minutes. It deletes rows whose expiry time has passed, and nothing else. A rate-limiter row now lives at most a minute plus five.

**Why it can't break anything else that uses the cache.** The cache is used by much more than the rate limiters: Filament's login throttle and its protection against reusing a two-factor code, the scheduler heartbeat (30 days), geocoding results (30 days) and the admin bar's counters (60 seconds). The prune removes only rows that are already past their expiry, and Laravel already treats those as missing, so it removes nothing a reader could still get. A geocoding result is removed only after its 30 days, when it would have been fetched fresh anyway.

**Why not the alternatives:**
- **A file cache** has the same leftover-file problem, plus a permission clash between users, the kind fixed on 04.10 for the shared log file.
- **Redis** is new infrastructure for one problem.
- The cache has to stay shared between the web, the queue worker and cron anyway: cron writes the heartbeat and the admin dashboard reads it.

**Tests (6 new, against the real database cache):**
- a one-time visitor's limiter row is gone once it expires;
- geocoding-style 30-day entries and entries stored forever survive;
- with expired and live rows mixed, only the expired ones go;
- a row is pruned at the exact second Laravel stops returning it;
- an empty table isn't an error;
- the schedule test now checks that it runs every five minutes.

Run once locally, it removed 2 leftover rows.

**Also changed:** `database/schema.md`, in the same commit as the code, as its rule requires. The `cache` row used to say the table existed for two-factor replay protection; it now lists everything that uses the cache, states "expired rows pruned every five minutes", and explains why. This isn't a breach of "anonymisation, not deletion": that rule is about product rows, and an expired cache entry holds nothing worth keeping.

## Decision Register

### 1. Dependency updates: everything until the first production deploy, then three tiers — **permanent, with a trigger**

**Chosen:**
- **Until the very first production deploy:** take every patch and minor update, and major ones too when they test clean.
- **From the first production deploy onwards:**
  - **Security advisories:** fixed immediately, with `composer audit` in CI, shipped as a standalone commit so they can be rolled back alone.
  - **Patch and minor updates:** one batch on a fixed rhythm, about every two weeks, deployed to the home server first and then to production.
  - **Major versions:** one at a time, a deliberate task with its own commit.

**Rejected:**
- **"Only what's vulnerable"** (the first recommendation): before launch it saves nothing, and it lets the gap to current versions grow.
- **"Always update everything, immediately", after launch:** every update ships code nobody has tried to real users.
- **"Update rarely", after launch:** one big jump after six months is far harder to debug than ten small ones.

**Why:** your words: *if we are not in prod yet, we can afford the newest versions.* After launch, the risk moves from "outdated" to "untested in front of users", and the tiers handle each risk separately.

### 2. Expired cache rows are pruned on a schedule — **permanent** (open question 13, answered)

**Chosen:** a scheduled prune every five minutes. **Rejected:** moving the rate limiters to files (same leftover problem) or Redis (new infrastructure); turning rate limiting off (it's the only defence for the report forms). **Why:** the smallest change that brings the IP-derived rows from "forever" to "minutes", and it touches nothing else that relies on the cache.

### 3. The privacy policy is written from the app, not the other way round — **standing rule**

The current privacy policy page is a rough draft, not fit for production. **No code decision is to be justified or rejected by what the draft says.** The policy gets written from what the app actually processes. Until then, each data question is framed as *what is processed, why, on what basis, for how long*, and the answers are collected as inputs for the policy (now a block in `undone-inventory.md` §C).

**Why it matters:** 03.10 framed the IP-hash rows as "contradicting the privacy policy", which treated a draft as a promise. The real question was whether keeping them forever was justified. It wasn't, so they're now pruned.

### 4. The nginx server logs are kept and disclosed briefly — **decided**

**What they are:** nginx is the web server that receives every request before the application sees it. By default on Ubuntu it writes one line per request (full IP address, time, page, the page the visitor came from, browser and device) to `/var/log/nginx/access.log`. The files rotate daily and are kept for about 14 days. The Ansible nginx role sets no logging of its own, so this default applies. The error log records the IP for failed requests too. Neither is in the backups.

**Chosen:** keep the default and disclose it **in a sentence or two, only as much as the law requires**: server logs including the IP address, kept for security and diagnosing faults, legitimate interest, about 14 days.

**Rejected:**
- **Shortening the retention:** marginal gain.
- **Logging a truncated IP:** loses the ability to trace a specific attacker.
- **Turning the access log off:** leaves you blind after an attack or a bot flood.

**Why:** the logs are how an incident gets investigated, and two weeks of them is a normal, defensible security practice.

### 5. Is two-factor sign-in still needed with `/admin` behind Tailscale? — **answered, record unchanged**

You asked whether hiding the admin panel behind Tailscale makes two-factor sign-in unnecessary. It doesn't, and the admin-access-is-three-layers record (16.09) already says why. Tailscale stops anyone on the internet from reaching `/admin`. Two-factor sign-in protects against a device that is **already inside** the private network being compromised: malware on the PC, or a stolen laptop with a saved password. Tailscale trusts that device by design. Two further facts:
- Two-factor sign-in today exists only on the **owner panel**, as an option. The owner panel can never sit behind Tailscale, because owners sign in from their own phones.
- Two-factor sign-in on `/admin` is decided but **not built yet**.

No change was made; recommendation: keep the record as it is.

## Learning Path

- **Semantic versioning.** `13.25 → 13.34` (minor) promises nothing breaks; `12 → 13` (major) means something may. That's why minors are batched and majors are deliberate. Search "semver explained".
- **Lazy versus active expiry.** Many caches only delete an expired entry when someone asks for it ("lazy expiry"). Fine for performance, a problem when the entry holds personal data. Hence the scheduled ("active") prune. Search "cache lazy expiration vs active expiration".
- **Why hashing an IP isn't anonymising it.** A hash of something drawn from a small, known set (4 billion IPv4 addresses) can be reversed by trying them all. Search "hashed IP addresses personal data GDPR" and "pseudonymisation vs anonymisation".
- **Legitimate interest.** The GDPR basis for processing that a service genuinely needs, such as security logs and abuse prevention, without asking consent. It must still be disclosed. Search "GDPR recital 49 network security legitimate interest".

### 3. Fault 1, examined in depth

**What a visitor is promised:** the FAQ says "Sprawdzona karta" means *someone from UNI went through this card by hand in the last six months*. The drink page says *"Najpierw te, w których potwierdziliśmy ten napój najświeżej"* and *"Każda pozycja pochodzi z karty napojów lokalu"*.

**What the data actually holds** for each drink at a venue:
- `confirmed_at` is **one date with no source**. Your confirmation and an owner's click write the same column. A product you checked in February and the owner confirmed in October shows your February source next to an October date.
- An owner's addition carries **no source and no date of its own**.
- **House drinks have no `added_by` at all**, so an owner's house drink can't be told apart from yours, except in the offer history.

**Where it reaches the visitor:**
1. "Sprawdzona karta" is decided for the whole venue and covers rows added after the check.
2. "Zaktualizowano dziś" is reset by owner changes.
3. Drink pages print "Potwierdzone dziś" for an owner's click.
4. **Drink pages sort venues by `confirmed_at`, newest first, and show at most 24.** An owner can press "Nadal w ofercie" once a day, so a persistent owner keeps their venue at the top of every drink page, above venues checked at the source. **That's a ranking lever** an owner can pull without paying, the kind the what-the-badges-claim record rules out ("cannot be bought").
5. The "sprawdzone" filter and the city page's "ze sprawdzoną kartą" count include these venues.

**What was already right:** the offer history tags every owner change as owner-reported, so trends are clean; owners can't touch the verification fields or the source; the admin products table shows who added each row; "Nowe" marks stay honest.

**First proposal, withdrawn:** four options for the badge (mark owner rows; date the badge and mark rows added after it; queue owner additions for admin approval; let owner edits cancel the badge), plus four sub-decisions. Several assumed you'd keep checking each venue's menu indefinitely, which is where your correction came in.

## Decision Register

### 1. The final system is automatic: badges are rules over recorded evidence — **permanent direction**

**Your words:** *"The final system is supposed to automatic and autonomous… some badges need admin governance. It does not. The V1 where I need to verify is where I do manually a lot of things, but its not intended for a final version. It is needed since app is small and has no users/owners."*

**Chosen:** every badge and every ordering on a public page becomes a **rule the app computes from evidence it has recorded**: what kind of evidence, what date it describes, where it came from. Your manual check in V1 is just the first kind of evidence, with nothing special about it.

**Rejected:** a badge that stays an admin switch; an admin approval queue for owner additions; "an admin re-check turns an owner row into a checked one" as the only path. Each assumed a person in the loop forever, which doesn't scale and isn't the product.

**Consequence for fault 1:** the problem doesn't go away, it becomes more basic. ### 2. Community contributions stay founder-reviewed, in V1 and beyond — **permanent for now; revisit with AI moderation**

**Chosen:** before any badge or ordering changes, record evidence per fact. Then deciding the badge rules becomes the next single problem.

**Proposed shape**, awaiting your answers (see Open Questions):
- **Evidence kinds** describe how something was known, not who typed it (the same principle as the offer-logs-record-knowledge-not-authorship record):

## Learning Path

- **Provenance.** Recording where a fact came from, when and how, alongside the fact itself. It's what separates a database you can trust from one you have to. Search "data provenance" and "W3C PROV overview".
- **Append-only logs and event sourcing.** Storing every piece of evidence as a new row that's never edited, and deriving the current state from it. The current state can always be rebuilt and explained. Search "append-only log design" and "event sourcing explained Martin Fowler".
- **Denormalisation.** Copying the latest value onto the row pages read, so they don't recompute it from history on every request. That's the "latest per kind on each row" half of option A. Search "denormalization tradeoffs".
- **Rules over switches.** A badge computed from data can be audited and explained; a switch someone flips can only be trusted. Search "trust and safety signals ranking manipulation" for how review platforms guard rankings against the people being ranked.
