## What Was Built

### 1. Filament Owner Panel Custom Theme

**What:** Created a Tailwind CSS theme for the owner panel (`/panel`) so custom utility classes (like `grid-cols-3`, `gap-6`, etc.) compile correctly inside Filament views.

**Where:**
- `resources/css/filament/panel/theme.css` (new) — imports Filament's base theme + scans custom view/component paths
- `app/Providers/Filament/PanelPanelProvider.php` — added `->viteTheme(...)` and removed the default `AccountWidget`
- `vite.config.js` — added the theme CSS to Vite's input array
- `package.json` / `package-lock.json` — Tailwind updated to v4.2.4

**Why:** The owner dashboard displayed as a full-screen SVG icon with no layout. Filament panels use their own Tailwind build pipeline — custom classes in panel views don't get included unless a dedicated theme CSS file exists with `@source` directives pointing at the custom component paths. Without it, every custom Tailwind class in the panel was silently dropped.

**Current state:** Fully working. Dashboard renders correctly with proper grid layout.

### 2. Stale Products Count Fix (SQL Bug)

**What:** Fixed a SQL operator precedence bug in `VenueStatusWidget` that caused every venue to show 134 stale products regardless of how many products it actually had.

**Where:** `app/Filament/Panel/Widgets/VenueStatusWidget.php`

**Why:** The query used `orWherePivotNull('confirmed_at')` without wrapping the `OR` in a closure. SQL evaluates `AND` before `OR`, so the query was: `(venue_id = X AND confirmed_at < threshold) OR (confirmed_at IS NULL)` — the second clause matched *every* product in the entire `venue_products` table, not just this venue's products. Wrapping in `->where(function ($query) { ... })` scopes the `OR` correctly.

**Current state:** Fixed. Shows accurate counts per venue.

### 3. Breadth Score Removed from Owner Dashboard

**What:** Removed the breadth score stat from the owner panel dashboard widget.

**Where:**
- `app/Filament/Panel/Widgets/VenueStatusWidget.php` — removed `$breadthScore` variable
- `resources/views/filament/panel/widgets/venue-status.blade.php` — removed breadth stat card, changed grid from 4-col to 3-col

**Why:** Breadth score is an internal ranking metric used by the platform to sort venues in search results. It was never spec'd for the owner dashboard — owners don't need to see their ranking score. Showing it leaks internal business logic and creates confusion ("what does this number mean? how do I improve it?").

### 6. Admin ProductsRelationManager ISE Fix

**What:** Fixed `Call to a member function gt() on string` error in the admin panel's products relation manager.

**Where:** `app/Filament/Resources/Venues/RelationManagers/ProductsRelationManager.php` line 55

**Why:** The `confirmed_at` pivot value arrives as a raw string from the database, not a Carbon instance. The code called `$state->gt(...)` expecting a Carbon object. Fixed by wrapping in `Carbon::parse($state)->gt(...)`.

## Decision Register

### D-23: Spec document hierarchy — newest files are authoritative

- **Chosen:** `roadmap/v1.md` (May 5) and `decisions/v1-locked.md` (May 4) are the authoritative spec sources. The Obsidian vault (`inspo/UNI-Obsidian-Vault/`) is historical context only.
- **Rejected:** Treating all spec documents equally by content, regardless of date.
- **Why:** The founder corrected the AI for using outdated Obsidian vault specs (April 17-22) instead of checking modification dates. The vault has not been maintained — many decisions there have been superseded by the newer locked decisions file. Always check `stat -c '%Y' <file>` when multiple sources exist for the same topic.
- **Status:** Permanent. When in doubt, the newest document wins.

### D-24: Breadth score — internal metric, not for owners

- **Chosen:** Breadth score is never shown to venue owners. It's an internal ranking signal.
- **Rejected:** Displaying it on the owner dashboard as a "score" or "completeness" indicator.
- **Why:** Breadth score was added to the owner dashboard in a previous session without checking if it was spec'd. It wasn't. Exposing internal ranking metrics to the subjects being ranked creates perverse incentives and support burden.
- **Status:** Permanent. Breadth score stays in admin and search ranking only.

### D-25: Category slugs — stable even when display names change

- **Chosen:** When renaming categories (e.g., "Koktajle" -> "Drinki"), the slug (`koktajle`) stays unchanged.
- **Rejected:** Renaming both slug and display name together.
- **Why:** URLs like `/kategoria/koktajle` and SEO pages like `/warszawa/mokotow/koktajle` depend on the slug. Changing it would break existing links, require redirects, and lose any SEO value accumulated on that URL.
- **Status:** Permanent. Slug changes require a migration with 301 redirects.

### D-26: Password change — inline on profile page, not separate page

- **Chosen:** Password change form lives on the same `/profil` page as the name/email form, separated by a visual divider.
- **Rejected:** (a) Separate `/profil/haslo` page — unnecessary navigation for a simple form. (b) Modal/dialog — overkill for three fields.
- **Why:** Keeps the profile page as a single destination for all account management. The route is `PUT /profil/haslo` (separate from `PUT /profil` for profile update) so each form submits independently with its own validation and flash messages.
- **Status:** Permanent.

If you add custom Tailwind classes to panel views (like `grid-cols-3` or `gap-6`), they won't compile unless you create a dedicated theme CSS file with `@source` directives pointing at your custom component paths. The command `php artisan make:filament-theme {panel}` scaffolds this file. Without it, Filament's default theme only includes classes used by Filament's own components.

- **SQL operator precedence (AND before OR):** SQL evaluates `AND` before `OR` just like math evaluates multiplication before addition. `WHERE a = 1 AND b = 2 OR c IS NULL` means `(a = 1 AND b = 2) OR (c IS NULL)` -- not `a = 1 AND (b = 2 OR c IS NULL)`. In Laravel's query builder, always wrap `OR` conditions in a `->where(function ($query) { ... })` closure to control grouping explicitly.

- **Slug stability:** URL slugs should be treated like database primary keys -- once published and potentially indexed by search engines or bookmarked by users, changing them breaks things. When renaming a category's display name, the slug stays constant. If a slug absolutely must change, it requires a database migration plus 301 redirects from the old URL to the new one.
