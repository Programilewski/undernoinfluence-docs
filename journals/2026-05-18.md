# 2026-05-18 — Email Verification Overhaul + Venue Activation Gate

## Session Overview

**Goal:** Two distinct product problems, resolved through extended design discussion before any code was written.

**Problem 1 — Email verification had no teeth.** Every user (B2C and B2B) was stopped at a confirmation wall immediately after registration, before getting any value from the app. But once an owner's claim was approved, `/panel` did not check email verification at all — so the wall was friction with no enforcement. A venue owner with a mistyped email could access the dashboard with zero recourse.

**Problem 2 — Venues went live the moment their claim was approved.** An admin click was the only quality gate. Pubs without a single non-alcoholic menu item could appear on the map.

**Outcome:** Both problems are now solved. Email verification is enforced contextually (not as an upfront wall) and at the panel level. Venues approved by admin stay hidden until their first non-alcoholic product is attached — at which point they go live automatically. The product catalog and proposal review flow serve as the quality gate, eliminating the need for a second manual admin approval. Three decision records written. SSOT updated. 462 tests passing.

## What Was Built

### Email Verification: Remove the Registration Wall

**File:** `app/Http/Controllers/Auth/RegisterController.php`

**What:** Removed the three-line block that redirected all newly registered users to `/weryfikacja-email` immediately after signup.

**Before:** After registration → forced redirect to email confirmation page → user can't do anything until they click the email link.

**After:** After registration → user lands on their profile (or their intended destination). The verification email is still dispatched silently in the background via the `Registered` event. No forced redirect.

**Why:** For a B2C user who just wanted to browse venues or save a place, a mandatory email-confirmation wall before seeing anything delivers negative first value. The email link still exists — it just waits until it's actually needed. B2B users coming from a claim CTA are redirected to `/zglos-lokal` (stored in `url.intended`), which already carries the `verified` middleware. They see the verification prompt contextually — when they try to do something that requires it.

### Email Verification: Gate the Owner Panel

**File:** `app/Providers/Filament/PanelPanelProvider.php`

**What:** Added `Illuminate\Auth\Middleware\EnsureEmailIsVerified::class` to the panel's `authMiddleware` stack, after `PanelAuthenticate`.

**Why:** Previously, `canAccessPanel()` only checked that the user had `role = 'owner'`. An approved owner with an unverified (or mistyped) email had full dashboard access. This broke the communication channel — any important message (claim decision, product approval, compliance notice) sent to that address would fail silently and permanently.

**How it works:** If an unverified owner reaches `/panel`, `EnsureEmailIsVerified` calls `redirect()->guest(route('verification.notice'))`, which stores `/panel` as the session's intended URL. After the owner verifies their email, `EmailVerificationController::verify()` calls `redirect()->intended(route('profile'))`, which resolves to `/panel` — sending them straight back.

### Venue Activation Gate: Claim Approval No Longer Makes Venue Live

**File:** `app/Services/Actions/ApproveVenueClaimAction.php`

**What:** Changed `'is_active' => true` to `'is_active' => false` in the claim approval transaction.

**Before:** Admin approves claim → venue immediately appears on the map, regardless of whether it has any non-alcoholic products.

**After:** Admin approves claim → owner gets `role = 'owner'` and can log into `/panel`. Venue stays invisible (`is_active = false`) until the first product is attached.

**Why:** An empty venue appearing on the map undermines the entire platform. UNI's value proposition is "go here and you'll find something to drink." A listing with zero products violates that promise. The admin's job is to verify the ownership claim — not to certify the menu. Menu certification is now automatic.

---

### Venue Activation Gate: `Venue::activateIfReady()`

**File:** `app/Models/Venue.php`

**What:** Added a new method to the Venue model:

```php
public function activateIfReady(): void
{
    if (! $this->is_active && $this->products()->exists()) {
        $this->update(['is_active' => true]);
    }
}
```

**Why:** The activation logic needs to run from two different code paths (owner attaches a catalog product; admin approves a product proposal). Centralising it in the model means neither caller needs to know the condition — they just call `activateIfReady()` and the venue decides for itself whether it's ready.

**Guard:** Only activates if `is_active = false`. If admin has manually deactivated a venue that already has products (e.g. for a rule violation), and the owner later adds another product, the venue re-activates. This is an acceptable edge case for V1; a manual deactivation reason flag can address it later.

### Venue Activation Gate: Observer Hook

**File:** `app/Observers/VenueProductObserver.php`

**What:** Added `$venue->activateIfReady()` at the end of `productAttached()`.

**Why:** `productAttached()` is already called (manually — pivot tables don't fire Eloquent events) every time an owner attaches a catalog product via the `AttachVenueProductAction`. By the time this observer method runs, Filament has already inserted the pivot row, and `AttachVenueProductAction` has updated it. So `$venue->products()->exists()` returns true on the very first product. No additional coordination needed.

### Venue Activation Gate: Proposal Approval Hook

**File:** `app/Services/Actions/ApproveProductProposalAction.php`

**What:** Added `$proposal->venue->activateIfReady()` after `$proposal->venue->markOfferFresh()`.

**Why:** The proposal approval path bypasses the observer entirely — it calls `products()->attach()` directly. Without this hook, an owner whose first product came via a proposal (rather than the catalog) would be stuck with an invisible venue even after the proposal was approved. Same trigger, different path.

### Venue Activation Gate: Dashboard Banner

**Files:** `app/Filament/Panel/Widgets/VenueStatusWidget.php`, `resources/views/filament/panel/widgets/venue-status.blade.php`

**What:** The `VenueStatusWidget` now computes `isAwaitingActivation` (true when the venue has no products and `is_active = false`) and passes it to the view. The blade template renders an amber banner above the venue header block when this flag is true.

**Banner copy:** *"Twój lokal nie jest jeszcze widoczny na mapie. Dodaj przynajmniej jedną opcję bezalkoholową do menu, aby lokal pojawił się w wynikach."* Direct CTA link goes to the products relation manager tab.

**Why:** The owner needs to know immediately why their venue isn't appearing. A silent `is_active = false` with no explanation would generate support messages. The banner is one concrete action, no options to ignore.

**Condition logic:** `$venue && !$venue->is_active && $totalProducts === 0`. If a venue is deactivated by admin but has existing products, `$totalProducts > 0` — the activation banner won't show, which is correct (the problem is not "no products").

## Business Impact

**Email verification (no wall, contextual prompt):** The change is invisible to users who never claim a venue. For B2C users, registration now delivers immediate value instead of stopping them at a confirmation screen. The expected result is lower registration abandonment. For B2B users, the verification prompt appears at exactly the moment it's meaningful — when they try to submit their claim — making it feel necessary rather than arbitrary.

**Panel email verification gate:** Closes a real operational risk. An approved owner with an unverified email was a dead communication channel — any dispute, update, or compliance notice would fail silently. This is now impossible.

**Venue activation gate:** This is the platform's quality floor. It means every venue on the map has at least one validated non-alcoholic product. UNI's core promise — "go here and you'll find something" — is now enforced by the system, not by Pawel reviewing each venue manually post-approval. As the number of venue owners grows, this saves significant admin time and protects the user experience from thin listings.

**Founder time saved:** Previously, reviewing and rejecting empty venues was manual work. Now the system holds venues until they're ready. Pawel's review time per claim stays constant regardless of how many owners onboard.

## Learning Path

**Why is the email verification middleware on `authMiddleware` and not the regular `middleware`?** Filament panels have two middleware stacks. Regular `middleware` runs on every request to the panel, including the login page. `authMiddleware` runs only after authentication is confirmed. `EnsureEmailIsVerified` needs to know who the user is before it can check their email — so it belongs in `authMiddleware`, after the user is identified.

**Why does `redirect()->guest()` work for the verification redirect?** Laravel's `guest()` redirect method stores the current URL in the session as `url.intended` before redirecting. This is the same mechanism that powers "log in, then go to the page you were trying to reach." After verification, any call to `redirect()->intended($fallback)` reads this stored URL. The owner gets sent back to `/panel` without any custom code.

**Why is `activateIfReady()` on the Venue model and not a service or action class?** The decision to activate is intrinsically about the venue's own state (`is_active`, `products().exists()`). A method that only reads and writes its own model's state belongs on the model. A service or action class implies external coordination or side effects — this has none.
