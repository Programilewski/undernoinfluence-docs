## What Was Built

### VenueAnalyticsReportService

**File:** `app/Services/VenueAnalyticsReportService.php` — 763 lines, all new.

This is the intelligence engine of the product. One public method, `generateAll(Venue $venue): array`, eager-loads all needed relationships (`products.category`, `drinks`, `districtRelation.city`, `offerLogs`, `stats`) and calls 17 private report methods, returning a keyed array. Each report returns a structured array with a `status` field (`ok`, `insufficient_data`, `not_applicable`) and the data payload.

**Why this structure:** Each report is independently testable. The service is injected via Laravel's container (`app(VenueAnalyticsReportService::class)->generateAll()`), so any PHP context can call it — including future artisan commands for emailing reports to owners.

The 17 reports, grouped by tier:

**FREE TIER — Profile Health**
- `verification_impact` — compares 30-day view totals before and after the venue's `claimed_at` date. Returns a multiplier (e.g. "2.4×"). If not claimed, returns `status: not_claimed`. Guards division by zero.
- `catalog_completeness` — calls `VenueScoring::calculate()` and maps breadth score to low/medium/high (thresholds: <4 low, 4-7 medium, 8+ high). Shows category coverage as `X of Y active categories`.
- `blank_menu_warning` — uses `Venue::freshness_days` model attribute and compares to district peers with recent updates (within 7 days). Flags venues stale >30 days.
- `monthly_views` — sums all `venue_stats` columns for the trailing 30 days. Returns views, direction clicks, website clicks, Instagram clicks, and a computed outbound total.

**BASIC TIER — Demand Intelligence**
- `gap_report` — the anchor feature. Queries `discovery_empty_results` events, uses PostgreSQL `jsonb_array_elements_text(properties->'categories')` to unnest the category array per event, scopes to the venue's city, groups by category slug, and cross-references with the venue's product catalog. Shows which categories users searched for but the venue doesn't carry. Admin sees all results; thresholds (≥10 district, ≥25 city) are annotated but not filtered.
- `category_demand_ranking` — merges `discovery_category_filtered` and `discovery_empty_results` events for the venue's city (30d). Unnests both `category_slugs` and `categories` JSON arrays, ranks by event count. Cross-references each category with the venue's catalog (checkmark/cross).
- `breadth_percentile` — computes percentile rank of this venue's breadth score within its district. Falls back to city scope if fewer than 5 venues are in the district. Uses `count(venues with score < this venue) / total * 100`.
- `seasonal_forecast` — V1 is editorial static text. Returns a note that data-driven seasonal forecasting is V2.

**PRO TIER — Competitive Intelligence**
- `competitor_gap` — uses `Venue::scopeNearby()` (haversine, 1km radius) to find nearby venues, then queries `VenueOfferLog` for `product_added` actions from those venues in the past 30 days. Cross-references with this venue's missing categories. Returns `status: no_coordinates` if `lat/lng` are absent.
- `search_spike_alerts` — for each category in the venue's city, compares 7-day search count vs 28-day weekly average. Spike threshold: ≥50% increase AND ≥15 absolute events in 7d.
- `new_competitor_nearby` — queries venues within 500m (`Venue::scopeNearby(0.5)`) claimed in the last 30 days with `breadth_score >= 3`. Returns list with name, `claimed_at`, and breadth score.
- `district_demand_map` — monthly search volume by category for the venue's city, comparing current 30d vs prior 30d. Trend = `(current - prior) / prior * 100`. Supply overlay: counts venues in district carrying each category.
- `mom_demand_trend` — total discovery events (all types) current 30d vs prior 30d, scoped to city. Returns absolute counts and percentage change.

**PREMIUM TIER — Engagement Detail**
- `freshness_warning` — pulls `freshness_days`, `freshness_state` from the venue model. Computes days until 60-day warning and 90-day cliff. Admin sees a preview of what the scheduled email would say.
- `trending_products` — queries `VenueOfferLog` for `product_added` in trailing 30d across the venue's city, groups by `subject_id` (product), requires `COUNT(DISTINCT venue_id) >= 5`. Cross-checks if this venue carries each trending product.
- `strongest_category_badge` — for each category the venue carries, uses PostgreSQL `DENSE_RANK() OVER (PARTITION BY category_id ORDER BY product_count DESC)` window function to rank this venue vs all district venues. Badge-worthy if rank ≤ 2.
- `click_detail_report` — day-of-week aggregation via `EXTRACT(DOW FROM date)` from `venue_stats` for 90d. Hour-of-day aggregation via `EXTRACT(HOUR FROM created_at)` from the `events` table for click event types. Returns peak day and peak hour.

## Decision Register

### Decision: service class vs Filament widget for per-venue analytics

**Chosen:** `VenueAnalyticsReportService` as a standalone Laravel service class, called from a thin Filament page.

**Rejected:** implementing reports as Filament `StatsOverviewWidget` instances on the Edit page.

**Reason:** 17 reports spread across 4 tiers cannot fit into widgets without a chaotic UI. More importantly, widgets are lifecycle-bound to Livewire's polling/rendering cycle — they can't be easily called from artisan commands or tested in isolation. A service class is callable from anywhere: admin panel, scheduled command, queue job, API. When V2 delivers owner-facing reports, the same service will power them; no duplication.

**Status:** permanent. The thin-page-calling-service pattern should be the template for any future Filament analytics pages.

---

### Decision: all 17 reports visible to admin without plan-tier gating

**Chosen:** admin sees all reports for all venues regardless of the venue's plan tier.

**Rejected:** making admin respect the venue's `hasFeature()` gate.

**Reason:** plan tiers gate what venue *owners* see. Admins need full visibility for platform governance, manual report delivery (the V2 validation step), and debugging. Tying admin visibility to plan tiers would actively hurt the manual outreach workflow.

**Status:** permanent.

---

### Decision: "Insufficient data" display vs silent hiding of unavailable reports

**Chosen:** when a report can't be computed (no district, no coordinates, zero events), display a gray "Insufficient data — [reason]" card rather than hiding the report.

**Rejected:** hiding unavailable reports so the page looks cleaner.

**Reason:** admins need to know what data is *missing*. If a venue has no coordinates and the Competitor Gap report is silently absent, an admin reviewing the page has no way to know they're missing intelligence. Showing the reason creates actionable awareness ("this venue needs coordinates added") and avoids confusion.

**Status:** permanent for admin view. Owner-facing V2 may choose to hide instead of show — that's a different UX audience.

---

### Decision: V1 seasonal forecast is editorial static text

**Chosen:** `seasonal_forecast` returns a hardcoded string noting that data-driven seasonal trends are a V2 feature.

**Rejected:** attempting V1 data-driven seasonal forecasting from limited events data.

**Reason:** the events table has been live for weeks, not years. There is no seasonal signal in the data yet. Building a seasonal model now would be computation on noise. The editorial note gives context to admins without pretending to have data that doesn't exist.

**Status:** revisit Q1 2027 when 12 months of events data exists.

---

### Decision: breadth percentile falls back from district to city when n < 5

**Chosen:** if fewer than 5 venues are in the district, compute percentile from city scope instead.

**Rejected:** returning "insufficient data" when a district has fewer than 5 venues.

**Reason:** Warsaw has ~17 districts. At launch, many districts will have only 1-3 claimed venues. Returning "insufficient data" for almost all venues would make the report useless. The city fallback gives a meaningful number ("better than 60% of Warsaw venues") even when district data is sparse. The report notes which scope was used so the admin understands the comparison.

**Status:** revisit when district data density improves. May want to lower the threshold to 3 or raise it to 10 based on real data distribution.

---

### Decision: PostgreSQL DENSE_RANK window function for strongest category badge

**Chosen:** native PostgreSQL `DENSE_RANK() OVER (PARTITION BY category_id ORDER BY product_count DESC)` to rank venues by category depth.

**Rejected:** PHP-side sorting and ranking (load all venues, sort in memory).

**Reason:** the window function handles ties correctly (two venues with the same product count both get rank 1), is computed in a single query, and scales to any number of venues. PHP-side sorting would require loading all district venues' product counts into memory and is fragile around ties.

**Status:** permanent — PostgreSQL-specific, consistent with the rest of the application's analytics queries.

## Learning Path

- **Window functions in PostgreSQL** — `DENSE_RANK() OVER (PARTITION BY ... ORDER BY ...)` is used by the Strongest Category Badge report. If you haven't seen window functions before: they compute a value *per row* relative to a group of rows, without collapsing the group into one row (unlike `GROUP BY`). The [PostgreSQL docs on window functions](https://www.postgresql.org/docs/current/tutorial-window.html) are the best reference.
- **`jsonb_array_elements_text()`** — PostgreSQL set-returning function used throughout the gap report and discovery insights. It explodes a JSON array stored in a jsonb column into individual rows, making it possible to `GROUP BY` individual array elements. Essential for any analytics on the `events.properties` column.
- **Filament `InteractsWithRecord` trait** — the mechanism that lets a Filament page load a model from the URL route parameter without extending `EditRecord` or `ViewRecord`. The `VenueAnalytics` page uses it to get the venue without triggering Filament's form/edit lifecycle.
