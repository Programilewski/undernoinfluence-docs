## What Was Built

### 1. `ProductsRelationManager` Lazy-Loading Fix (User-Applied)

**File:** `app/Filament/Admin/Resources/Venues/RelationManagers/ProductsRelationManager.php`

**The bug:** Yesterday's brand migration promoted `products.brand` from a plain string column to a `BelongsTo` relationship. The `ProductsRelationManager` table had `TextColumn::make('brand')`, which Filament resolves by calling `$product->brand` on each row. Since `brand` is now a relationship (not a column), this triggered lazy loading — which is disabled in this app's development environment via `Model::preventLazyLoading()` in `AppServiceProvider`. The result was a `LazyLoadingViolationException` 500 on every page load of `/admin/venues/{id}/edit`.

**The fix (applied by the user):**
1. Changed `TextColumn::make('brand')` → `TextColumn::make('brand.name')` so Filament knows it's traversing a relationship, not reading a column.
2. Added `->modifyQueryUsing(fn ($query) => $query->with('brand'))` to the table so the relationship is eager-loaded in a single JOIN query instead of firing one query per product row.

**Why this matters beyond the immediate fix:** `modifyQueryUsing` is the correct extension point for any time you need to add eager loads, scopes, or custom joins to a Filament relation manager table — Filament builds the query internally, so you can't just wrap it yourself. `recordTitleAttribute` on the relation manager tells Filament which attribute to use as the human-readable label for records in dropdowns and confirm modals — it's the "display name" contract for that relationship.

### 4. `ProductImporter` Brand FK Fix

**File:** `app/Filament/Admin/Imports/ProductImporter.php`

**The bug:** After yesterday's migration, `products.brand` no longer exists as a column. The importer still had `ImportColumn::make('brand')` with plain `->rules(['required', 'max:255'])` — no relationship resolver. Filament would attempt to set `$product->brand = 'Heineken'` on the model, which either silently failed (if the attribute wasn't fillable) or threw an error on save. Either way, brand data would be lost on every CSV product import.

**The fix:**
```php
ImportColumn::make('brand')
    ->requiredMapping()
    ->relationship(resolveUsing: fn (string $state): Brand => Brand::firstOrCreate(['name' => trim($state)]))
    ->rules(['required', 'max:255'])
    ->examples(['Heineken', 'Oddbird']),
```

Filament's `->relationship()` on a `BelongsTo` column calls `$product->brand()->associate($brand)` after the resolver runs, which correctly sets `brand_id`. The `firstOrCreate` approach means CSV imports can introduce new brands without a separate pre-seeding step — the importer is self-healing with respect to the brand catalog.

**Why `firstOrCreate` instead of a strict lookup:** Product CSVs are an admin-only tool used for seeding. The risk of creating a slightly mis-named brand is lower than the risk of blocking an entire import because one brand hasn't been pre-created. Admin can clean up duplicates via `BrandResource` after import.

## Learning Path

**Understanding `LazyLoadingViolationException`:**
- The exception always follows the pattern: `Attempted to lazy load [relationship] on model [Model] but lazy loading is disabled.`
- Check the **Queries** tab in the error page — if the related table is absent from the query log, it wasn't eager-loaded.
- Fix: either `->with('relationship')` on the query, or `->modifyQueryUsing()` in a Filament table/relation manager.

**How Filament ImportColumn relationships work:**
- `->relationship(resolveUsing: ...)` tells Filament this column maps to a `BelongsTo` or `BelongsToMany` relationship, not a database column.
- For `BelongsTo`, Filament calls `$record->relation()->associate($resolved)` after the resolver runs — this sets the FK column automatically.
- The `resolveUsing` closure receives the raw CSV cell value and must return a model instance (or null, if nullable).

### 5. New Artisan Command: `venues:import-research-csv`

**File:** `app/Console/Commands/ImportResearchCsv.php`

**Usage:**
```bash
php artisan venues:import-research-csv /path/to/your-research-file.csv
```

**What it does:**
1. Opens the CSV and builds a column index from the header row (case-sensitive, trimmed).
2. Pre-loads all existing `osm_id` values into a hash map — deduplication is O(1) per row.
3. Pre-loads all `cities` by lowercase name — city lookup is also O(1).
4. For each data row:
   - Skips if `name` is blank.
   - Skips if `osm_id` already exists in the database.
   - Determines `seeding_status` by priority: `is_permanently_closed = yes` → Skip; `Has_0% = yes` → Ready; otherwise Draft.
   - Maps all other CSV columns to DB columns (see table below).
   - Accumulates rows into a batch.
5. Inserts in chunks of 500 using `Venue::insert()` — bypasses Eloquent events, fast for bulk loads.
6. Prints a progress bar and summary line.

**CSV → DB column mapping:**

| CSV column | DB column |
|---|---|
| `name` | `name` |
| `website` | `website_url` |
| `address` | `street_name` |
| `house_number` | `street_number` |
| `city` | `city_id` (lookup by name; NULL if not found) |
| `postcode` | `postal_code` |
| `latitude` | `latitude` (NULL if blank) |
| `longitude` | `longitude` (NULL if blank) |
| `osm_id` | `osm_id` (NULL if blank) |
| `amenity` | `venue_type` (mapped: restaurant→restauracja, pub/biergarten→pub, bar→bar, else inne) |
| `phone` | `phone` |
| `notes` | `admin_notes` |
| `Menu_last_updated` | `menu_last_updated_note` |
| `is_more_interesting` | `is_more_interesting` (yes→true) |
| `is_permanently_closed` | `is_permanently_closed` (yes→true) |
| `is_too_ambiguous` | `is_too_ambiguous` (yes→true) |

**Fixed defaults on every imported row:** `is_active = false`, `source = 'osm'`, `slug = Str::slug($name) + 4-char random suffix`.

## Session 3 — Seeding Queue: Delete, Edit Page, Filters, and Dual Geocoding (GUS + Nominatim)

## Session Overview

**Goal:** Make the Seeding Queue a fully functional venue review tool. The queue existed but had no way to delete a venue, no detail/edit page, no data completeness filters, and no way to fill in missing coordinates from the admin panel. The session also introduced the GUS API (free Polish government geocoder) as documented in new local docs.

**Outcome:** Six separate capabilities added to the Seeding Queue. The queue now supports: permanent deletion (single and bulk), a full edit page per venue, four new data filters, and dual-source geocoding — GUS API and Nominatim (OSM) — available both as bulk table actions and as single-venue buttons on the edit page. Both geocoders auto-fill district when the returned suburb/gmina matches a known district name. Significant debugging work uncovered that GUS returns zero results when sent "Warszawa" as the city name (Warsaw is split into district gminas in Polish TERYT), and that Nominatim's structured `city` param works correctly and also returns the Warsaw district via `suburb`. Both services now apply a 60km city-radius post-validation to protect against wrong-city matches on common street names. 15 passing tests.

### 4. GUS Geocoding Service

**File:** `app/Services/GusGeocodingService.php` (created)

A service that calls the Polish government's GUS FTS API (`geo.stat.gov.pl/api/fts/gc/pkt`) to resolve street addresses to GPS coordinates. Key characteristics:

- **Batch API**: sends all addresses in a single HTTP request using the `reqs[]` array. Each request item carries the venue's database ID as a correlation key, so responses can be matched back to venues.
- **No API key**: the GUS API is free for commercial and non-commercial use. Attribution required.
- **Relevance threshold**: results below 0.6 relevance are discarded.
- **City radius validation**: if the venue has a city with map coordinates, the returned GPS point must be within 60km of the city centre. This prevents common street names (e.g. "Główna 1") from matching a city different from the venue's intended location.
- **No `miejsc_nazwa` sent**: see Decision Register. Sending the city name actively breaks results for Warsaw.

Returns coordinates (`latitude`, `longitude`), the `gm_nazwa` field (gmina/district name from TERYT), and the relevance score. The `gm_nazwa` is used for automatic district assignment.

---

### 5. Nominatim Geocoding Service

**File:** `app/Services/NominatimGeocodingService.php` (created)

A service that calls OpenStreetMap's Nominatim API (`nominatim.openstreetmap.org/search`). Key differences from GUS:

- **No batch API**: requests are sequential, one per venue. A 1.1-second sleep between calls enforces Nominatim's usage policy (max 1 req/sec for the public instance).
- **Structured query params**: uses `street` (housenumber + streetname combined), `city`, and `countrycodes=pl`. The city name works correctly for Nominatim including Warsaw — unlike GUS.
- **`addressdetails=1`**: requests address breakdown. The `suburb` field from the response gives the Warsaw district name ("Ursynów", "Wola", etc.) directly, matching our `districts` table names.
- **Same city radius validation**: 60km post-filter, identical to GUS.
- **Required `User-Agent`**: Nominatim's usage policy requires identifying the app. Hardcoded to `UnderNoInfluence/1.0 (pawel.milewski00@gmail.com)`.
- **`importance` not used as threshold**: Nominatim's `importance` field is not comparable to GUS's `relevance` — it measures the object's global prominence (a famous cathedral scores high; a house number scores near-zero). The first returned result is used directly, validated only by city radius.

### 6. Two Action Classes

**Files:**
- `app/Services/Actions/GeocodeVenueAction.php` (created) — wraps GUS service
- `app/Services/Actions/GeocodeVenueNominatimAction.php` (created) — wraps Nominatim service

Both follow the same pattern:
- `execute(Venue $venue): bool` — single venue, returns success/failure
- `executeBatch(Collection $venues): array{geocoded, skipped}` — batch, returns counts

**Why separate action classes from the service layer:** The service is responsible for the HTTP call and parsing. The action is responsible for the business rule: "when to set district_id, which fields to update, what counts as success." This separation means the services are testable in isolation and the actions can be swapped to a different geocoder without touching the Filament UI.

**Dual geocoder strategy hedges accuracy risk.** No single geocoder is perfect for Polish addresses. GUS has excellent coverage but poor accuracy for non-standard addresses (named forts, industrial complexes, shopping centres with numeric access roads). Nominatim uses OSM data which is often more current and more precise for these cases. Having both available lets the researcher choose based on the type of address.
