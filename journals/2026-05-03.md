# Session Journal — 3 May 2026 (Saturday)

## Session Overview

**Goal:** Build the foundational infrastructure for three systems identified in the April 30 discrepancy audit: custom venue drinks, product proposals (venue owners suggesting new products), and offer change auditing. Also redesign the venue profile page layout and tighten the freshness model.

**Outcome:** Four new database tables created and migrated (`venue_drinks`, `product_proposals`, `venue_offer_logs`, plus scoring fields on `venues` and `products`). Three new Eloquent models with factories. Two Eloquent observers for automatic audit logging. A full Filament admin resource for reviewing product proposals. A new Filament relation manager for managing custom drinks on venues. The venue show page was redesigned from a 2-column split (info | map) to a stacked layout with collapsible category sections. The freshness model was overhauled — shifted from `last_menu_check_at` to `offer_updated_at` as the primary signal, changed thresholds from 90/180 to 30/90 days, and renamed states from fresh/stale/expired to fresh/aging/stale/unknown. Discovery page sorting now uses a proper `VenueScoring` service instead of raw product count. Alpine.js was added as a bundled dependency.

## What Was Built

### 1. Custom Venue Drinks — `venue_drinks` table + `VenueDrink` model

**What:** A new table and model for drinks that are unique to a specific venue — house cocktails, custom mocktails, signature recipes. Each drink belongs to one venue, has a name, optional description, optional photo, and a `base_category` enum (`mocktail`, `koktajl_nolo`, `drink_spirytus_0`, `virgin_classic`).

**Where:** `database/migrations/2026_05_03_090557_create_venue_drinks_table.php`, `app/Models/VenueDrink.php`, `database/factories/VenueDrinkFactory.php`

**Why:** This directly addresses Discrepancy #8 from the April 30 audit. Previously, "custom drinks" were impossible to represent — the `products` table requires a `brand` (NOT NULL), and the only workaround was stuffing "receptura" into the brand field. `venue_drinks` is a first-class table owned by the venue, not a hack on the global product catalog. This is the foundation for the custom drinks feature described in the vault spec.

**Current state:** Schema migrated and live. Model has an observer (`VenueDrinkObserver`) that auto-logs changes and touches `offer_updated_at` on the parent venue. Factory is ready for testing. Filament relation manager (`DrinksRelationManager`) is registered on the venue resource, so admins and venue owners can add/edit/remove custom drinks through the panel.

### 2. Product Proposals — `product_proposals` table + `ProductProposal` model

**What:** A workflow for venue owners to suggest products that aren't yet in the UNI catalog. The owner fills in the product name, producer, category, and optionally uploads a label photo. The proposal goes into a "pending" queue. An admin reviews it — approving creates the product in the global catalog and attaches it to the venue; rejecting records an optional reason.

**Where:** `database/migrations/2026_05_03_090556_create_product_proposals_table.php`, `app/Models/ProductProposal.php`, `database/factories/ProductProposalFactory.php`, `app/Filament/Resources/ProductProposals/ProductProposalResource.php`

**Why:** The current system only lets owners attach *existing* products to their venue. If a product doesn't exist in the catalog, the owner is stuck. This creates a bottleneck: either the admin has to manually add every product, or the catalog stays incomplete. Product proposals solve this by letting owners do the data entry, with admin approval as a quality gate. The Filament resource shows a badge count of pending proposals in the navigation — admin sees "3 waiting" at a glance.

**Current state:** Full admin review interface built in Filament with approve/reject actions. The "propose" button is wired into the owner's `ProduktyRelationManager` as a "Nie widzę mojego produktu" (I don't see my product) action with a form. Factory has `approved()` and `rejected()` states for testing.

### 3. Venue Offer Audit Log — `venue_offer_logs` table + `VenueOfferLog` model

**What:** An immutable audit trail of every change to a venue's offer — products added/removed, drinks added/updated/removed. Each log entry records who did it, what was changed (polymorphic `subject_type`/`subject_id`), what action occurred, and optional metadata (e.g., the drink name and category at the time of the action).

**Where:** `database/migrations/2026_05_03_090558_create_venue_offer_logs_table.php`, `app/Models/VenueOfferLog.php`, `app/Observers/VenueDrinkObserver.php`, `app/Observers/VenueProductObserver.php`

**Why:** Two reasons. First, trust: UNI's credibility depends on knowing *when* and *by whom* a venue's menu was last updated. Second, future analytics: the B2B owner dashboard will show activity timelines ("your last update was 3 weeks ago — venues that update monthly get 2x more views"). The audit log is the raw data for both of those features.

**Current state:** Logging is wired automatically for venue drinks (via Eloquent observer on `VenueDrink`) and manually for product attach/detach (via `VenueProductObserver` called from Filament relation managers — pivot tables don't fire Eloquent events). The `VenueProductObserver` is not a true Eloquent observer; it's a service class called explicitly from the `ProduktyRelationManager` and `SwiezoscRelationManager`.

### 4. Scoring Fields on Existing Tables

**What:** Added `offer_updated_at` (nullable timestamp) to `venues`, and `sku` (nullable string) + `is_approved` (boolean, default true) to `products`.

**Where:** `database/migrations/2026_05_03_090558_add_scoring_fields_to_venues_and_products.php`

**Why:** `offer_updated_at` replaces `last_menu_check_at` as the primary freshness signal — it's automatically touched whenever any product or drink changes, rather than requiring a manual admin check. `is_approved` on products supports the proposal workflow (a product can exist but not yet be approved for display). `sku` is a placeholder for future product identification/deduplication.

**Current state:** Migrated and live. All observers and relation managers write to `offer_updated_at`.

### 5. VenueScoring Service

**What:** A service class that calculates breadth score for a venue by counting products per category *and* custom drinks per base_category. Also provides a `sort()` method that ranks venues by total breadth, then category diversity.

**Where:** `app/Services/VenueScoring.php`

**Why:** Replaces the primitive `products_count` ordering on the discovery page. The old sort treated a venue with 10 beers and no other categories the same as a venue with 2 beers, 2 wines, 2 spirits, 2 ciders, and 2 drinks. The new scoring rewards diversity. Custom drinks are included in the calculation (prefixed as `drink:mocktail`, `drink:koktajl_nolo`, etc.) so venues that invest in house recipes get credit.

**Current state:** Integrated into `DiscoveryPage.php` — the default sort now uses `VenueScoring::sort()` instead of `orderByDesc('products_count')`. The discovery page also eagerly loads `drinks` and counts them.

### 6. Freshness Model Overhaul

**What:** Three connected changes: (a) the primary freshness signal moved from `last_menu_check_at` to `offer_updated_at`, (b) thresholds changed from 90/180 days to 30/90 days, (c) state names changed from `fresh`/`stale`/`expired` to `fresh`/`aging`/`stale`/`unknown`.

**Where:** `app/Models/Venue.php` (renamed `freshnessState()` → `computeFreshnessState()`, added `freshness_state` and `freshness_days` accessors), `venue-tile.blade.php`, `venues/show.blade.php`, `ProduktyRelationManager.php`, `SwiezoscRelationManager.php`, `tests/Feature/VenueModelTest.php`

**Why:** The old model was passive — freshness only changed when an admin manually updated `last_menu_check_at`. The new model is active — freshness updates automatically whenever the venue's offer changes (via observers). The tighter thresholds (30/90 instead of 90/180) create urgency: a venue that hasn't updated in a month starts showing "aging" instead of still appearing "fresh." This incentivizes venue owners to keep their menus current, which is UNI's core value proposition.

**Current state:** All 6 freshness tests updated and passing with new method name and thresholds. All templates updated to use the new accessor and state names. The old `freshnessState()` static method is now `computeFreshnessState()`.

### 7. Venue Show Page Redesign

**What:** Complete layout overhaul of the venue profile page. Previously: 2-column layout (3/5 info left, 2/5 map+image right). Now: stacked single-column layout — Row 1 is venue info + map side-by-side, Row 2 is the full-width drinks menu with collapsible category accordion cards in a 2-column grid, Row 3 is nearby venues in a 3-column grid. Contact info (phone, website, Instagram, email) moved inline into the header area. Opening hours are collapsible (show today, expand for full week). Freshness badges now appear in the venue header. The old breadth progress bars were removed and replaced with colored count badges on each category accordion.

**Where:** `resources/views/venues/show.blade.php` (491 lines changed — effectively a rewrite)

**Why:** The old layout wasted horizontal space on desktop (the right column was just a map and optional image). The drinks menu was a flat list buried below contact info. The new layout puts the menu front and center — it's the main reason users visit a venue page. The collapsible accordions let venues with large menus (10+ categories) stay organized without overwhelming the user. The 2-column category grid fills the full width on desktop, making better use of screen real estate.

**Current state:** Template rewritten. Uses Alpine.js `x-data`/`x-show` for accordion toggle and opening hours expand/collapse. Map includes a `setTimeout(() => map.invalidateSize(), 200)` fix for tile rendering after layout settles.

## Decision Register

### Freshness signal: `offer_updated_at` vs `last_menu_check_at`

- **Chosen:** New `offer_updated_at` column on venues, auto-touched by observers whenever products or drinks change.
- **Rejected:** Continuing to use `last_menu_check_at` — this required manual admin updates, which made freshness a lagging indicator of human effort rather than actual offer currency. Also rejected: computing freshness from `MAX(venue_products.confirmed_at)` on every page load — too expensive.
- **Why:** Active freshness (automatically updated) is more honest and more scalable than passive freshness (manually updated). When a venue owner adds a product through the panel, the freshness immediately resets. No admin intervention needed.
- **Status:** Permanent. `last_menu_check_at` is still in the schema but no longer drives the primary freshness display. It may be repurposed for "last admin audit" separately.

### Freshness thresholds: 30/90 vs 90/180

- **Chosen:** Fresh ≤ 30 days, aging 31–90 days, stale > 90 days.
- **Rejected:** The previous 90/180 thresholds — too generous. A venue that hasn't confirmed its menu in 3 months was still showing "fresh," which undermines trust.
- **Why:** Tighter thresholds create urgency for venue owners and honesty for consumers. 30 days as the "fresh" window aligns with typical menu rotation cycles. A monthly check-in is a reasonable expectation for engaged venue owners.
- **Status:** Revisit after launch — if venues struggle to maintain freshness, the thresholds can be relaxed. Currently not extracted to config (still hardcoded in `Venue::computeFreshnessState()` and Filament components).

### Freshness state naming: fresh/aging/stale/unknown vs fresh/stale/expired

- **Chosen:** `fresh` / `aging` / `stale` / `unknown`.
- **Rejected:** Previous `fresh` / `stale` / `expired`. "Expired" implies the data is invalid, which is too strong. "Unknown" is more honest for venues that have never had their offer updated. "Aging" is a gentler intermediate state than "stale."
- **Why:** Language shapes perception. "Expired" sounds like the venue is dead. "Stale" sounds like neglect. "Aging" sounds like it just needs a refresh — which is the action we want to encourage.
- **Status:** Permanent.

### Custom drinks: separate `venue_drinks` table vs `is_custom` flag on `products`

- **Chosen:** Separate `venue_drinks` table owned by the venue.
- **Rejected:** Adding `is_custom` and `venue_id` to the `products` table (the approach suggested in the discrepancy audit). The products table is a global catalog — mixing venue-specific items into it would create data integrity problems (what happens when a venue is deleted? Do you cascade-delete products that might be referenced elsewhere?).
- **Why:** Clean separation of concerns. Global catalog products are shared across venues. Venue drinks are venue-specific. Different lifecycle, different ownership, different deletion rules.
- **Status:** Permanent. The `VenueScoring` service already counts both tables in its breadth calculation.

### Venue show page: stacked layout vs 2-column split

- **Chosen:** Stacked layout — info+map top, full-width menu middle, nearby bottom.
- **Rejected:** Previous 2-column layout (info left, map+image right). The right column was mostly empty space on pages without images, and the map was squeezed into a narrow column on desktop.
- **Why:** The menu is the primary content on a venue page. It deserves full width. The map is secondary context — it helps you find the venue, but you're on the page because you want to see what they serve.
- **Status:** Permanent unless user testing reveals people can't find the map.

### Product proposals: admin approval vs auto-accept

- **Chosen:** Admin approval required for all proposals.
- **Rejected:** Auto-accepting proposals (would pollute the catalog with duplicates and low-quality entries).
- **Why:** The product catalog is a curated, shared resource. One bad entry affects every venue that might use that product. Quality gate is essential. The Filament resource makes review fast — one click to approve, one click to reject.
- **Status:** Permanent. May add auto-approve for trusted owners (high credibility score) in the future.

### Audit logging: observers vs event listeners

- **Chosen:** Eloquent observers for `VenueDrink`, manual service calls for pivot table changes.
- **Rejected:** Laravel event listeners with custom events — more infrastructure for the same result. Also rejected: a single `activity_log` package (like spatie/activitylog) — adds a dependency for something simple.
- **Why:** Observers are the simplest approach for model lifecycle hooks. Pivot tables don't fire Eloquent events, so the `VenueProductObserver` is called explicitly from Filament — this is documented in the class PHPDoc.
- **Status:** Revisit if audit logging requirements expand beyond offer changes. Spatie activity log may make sense at that point.

## Open Questions

1. **Backfill `offer_updated_at`?** Every existing venue has `offer_updated_at = null`, so they all show "unknown" freshness. Should we backfill from `last_menu_check_at`? This is a one-line SQL update but it's a data decision, not a code decision.

2. **Keep or remove `last_menu_check_at`?** It's now partially orphaned — the venue show page still displays it ("Sprawdzono 15 March 2026") but it no longer drives freshness badges. Options: (a) keep it as "last admin audit date" separate from offer freshness, (b) remove it entirely and rely on `offer_updated_at`, (c) merge both into one column.

3. **Venue drinks on the public show page?** The `venue_drinks` data is not yet displayed on the public venue profile page. The template only shows `$productsByCategory` (from the pivot). Should custom drinks appear in a separate section? Mixed into the category grid? This needs a UI decision.

4. **Breadth cap: still undecided.** The `VenueScoring` service counts all products + drinks but doesn't cap at any number. The old 4-product cap (from `drinkAvailability()`) and the spec's 5-product cap are both unimplemented in the new scoring. Is there a cap?

5. **Category names: still undecided.** Carry-forward from April 30 — "Spirits" (English) vs "Destylaty" (formal Polish) vs current mixed naming.

6. **URL structure: still undecided.** Carry-forward — `/venues/{slug}` vs `/warszawa/lokal/{slug}`. Blocking decision before Google indexing.

## Learning Path

### For this session's work

- **Eloquent Observers:** Observers hook into model lifecycle events (creating, created, updating, etc.) and run code automatically. UNI uses them on `VenueDrink` to auto-log changes and update freshness. Key limitation: pivot tables (`venue_products`) don't fire Eloquent events, which is why the `VenueProductObserver` has to be called manually from Filament. [Laravel Docs: Observers](https://laravel.com/docs/eloquent#observers)

- **Polymorphic relationships (`morphTo`):** The `venue_offer_logs.subject` column stores both the type (`App\Models\Product` or `App\Models\VenueDrink`) and the ID. This lets one audit log table track changes to different model types without separate columns for each. [Laravel Docs: Polymorphic Relations](https://laravel.com/docs/eloquent-relationships#polymorphic-relationships)

- **Filament Actions:** Actions are buttons with optional modal forms. UNI uses them in the `ProductProposalResource` for approve/reject, and in `ProduktyRelationManager` for the "propose" button. The key pattern: `.schema([...fields...])` defines the modal form, `.action(fn ($data) => ...)` runs when submitted. [Filament Docs: Actions](https://filamentphp.com/docs/actions)

- **Alpine.js in Blade:** Alpine.js adds reactive behavior to server-rendered HTML without a build step. `x-data` initializes state, `x-show` toggles visibility, `@click` handles events, `x-transition` animates. UNI uses it for the category accordions and opening hours toggle on the venue show page. [Alpine.js Docs](https://alpinejs.dev/)

# Session 2 — Chunk Visualization for Venue Cards

## Session Overview

**Goal:** Replace the percentage-based drink availability bars on venue cards with a "chunk" visualization — one small square block per product, grouped by category, with overflow badges, freshness indicators, and verified checkmarks. This is a frontend-only task wiring up the visual layer for the scoring/breadth system built in Session 1.

**Outcome:** The venue tile component (`venue-tile.blade.php`) was completely rewritten with chunk visualization. A freshness label accessor was added to the Venue model. The CSS got a new chunk entrance animation. Factory states and seeders were updated to properly set `offer_updated_at` so freshness badges actually render. The database was re-seeded with varied freshness states and two venues with 15+ products to test overflow. Several layout iterations were made based on live feedback — the final design uses a responsive grid (single-column on mobile, 3-column on `sm`+) with aligned label widths and per-category colors from config.

---

## What Was Built

### 1. Chunk Visualization in Venue Tile

**What:** Complete rewrite of the venue card component. The old design showed percentage-fill progress bars per drink category (capped at 100%). The new design shows individual square "chunks" — one per product — grouped by category in a grid layout. Each chunk has a tooltip with the product name on hover. Categories with more than 8 products show 8 chunks plus a `+N` overflow badge (hoverable to see hidden product names). Each category row shows: bare icon → label text → chunks → overflow badge → bold count number.

**Where:** `resources/views/components/venue-tile.blade.php` (128-line net change)

**Why:** The percentage bars were lossy — "Piwo: 75%" tells you nothing about how many beers the venue serves or which ones. Chunks are 1:1 with real products: 8 visible squares means 8 real products. This directly communicates breadth (the core ranking signal) in a glanceable visual. Users can hover individual chunks to see product names without clicking into the venue.

**Current state:** Working. Layout is responsive:
- **Mobile:** single column, one category per row, icon+label fixed at `w-20` so chunks align vertically
- **Desktop (`sm`+):** 3-column grid, 2 rows for 6 categories, same `w-20` label alignment within each column

**Design iterations during session:**
1. Started with vertical stacked rows (one category per line, full width) — too tall, wasted space
2. Switched to horizontal `flex-wrap` — better on desktop, cramped on mobile
3. Tried `grid-cols-2` on mobile — too tight with chunks inside
4. Final: `flex-col` on mobile (one per row), `grid-cols-3` on desktop (3×2 grid)

### 2. Freshness Badge — Colored Dot + Polish Timestamp

**What:** A new visual layer below the venue type/district metadata row. Shows a colored dot (green/amber/red) with monospace Polish text indicating when the offer was last updated.

**Where:** `resources/views/components/venue-tile.blade.php` (freshness section), `app/Models/Venue.php` (new `getFreshnessLabelAttribute()` accessor)

**Why:** Users need to know how current a venue's menu data is. The old design showed generic tags ("Aktualne", "Starzejące się", "Nieaktualne") that looked identical to venue type badges. The new design is a distinct visual layer — just a dot and timestamp, no pill/tag styling — so it reads as data quality rather than venue metadata.

**Three states:**
- **Fresh (≤30 days):** green dot with subtle glow + "Zaktualizowano X dni temu" (or "Zaktualizowano dziś" for 0–1 days)
- **Aging (31–90 days):** amber dot + "Zaktualizowano X dni temu"
- **Stale (91+ days):** red dot + "Zaktualizowano X mies. temu"
- **Unknown (null):** nothing rendered — decided to hide rather than show "Brak danych"

### 3. Freshness Label Accessor on Venue Model

**What:** New `getFreshnessLabelAttribute()` computed property returning Polish-language freshness text.

**Where:** `app/Models/Venue.php` (new method between `getFreshnessDaysAttribute` and `computeFreshnessState`)

**Why:** The Blade template shouldn't contain date formatting logic. The accessor centralizes the Polish text generation and handles edge cases (today = "dziś", ≤90 days = "X dni temu", >90 days = "X mies. temu", null = null).

### 4. Chunk Entrance Animation

**What:** CSS `@keyframes chunk-in` animation — chunks scale from 0 to 1 with a bouncy easing curve. Each chunk in a row gets a staggered 40ms delay for a sequential "pop in" effect.

**Where:** `resources/css/app.css` (new `.chunk` class and `@keyframes chunk-in`)

**Why:** Matches the React reference prototype's animation. Gives visual life to the chunks without being distracting. The stagger makes long rows (8+ chunks) feel dynamic rather than appearing all at once.

### 5. Category Colors from Config

**What:** All chunk colors (fill, border), icon colors, overflow badge colors, and count number colors are derived from `config('drinks.{slug}.color')` — CSS custom properties like `var(--color-drink-piwo)`.

**Where:** `resources/views/components/venue-tile.blade.php` (inline styles using `color-mix()`)

**Why:** The initial implementation used a single accent color for all chunks. The founder chose per-category colors (option B) — each category's chunks are visually distinct. Colors come from the existing config system, not hardcoded Tailwind classes, so adding a new category automatically gets its color.

**Color mixing:** Uses CSS `color-mix(in srgb, ...)` for opacity variants:
- Chunk fill: 45% category color
- Chunk border: 35% category color
- Overflow badge bg: 15% category color
- Count text: full category color

### 6. Factory & Seeder Freshness Fix

**What:** Updated `VenueFactory` states (`fresh()`, `stale()`, `expired()`) to also set `offer_updated_at` alongside `last_menu_check_at`. Updated `VenueTableSeeder` to assign random freshness states (40% fresh, 30% aging, 30% stale) via `offer_updated_at`. Updated `DatabaseSeeder` dev venue #5 from "unknown" to "fresh" state.

**Where:** `database/factories/VenueFactory.php`, `database/seeders/VenueTableSeeder.php`, `database/seeders/DatabaseSeeder.php`

**Why:** Session 1 added `offer_updated_at` but never set it — all 36 venues had `null`, so no freshness badges rendered. The factory states only set `last_menu_check_at` (the legacy field). Now both fields are set together, and fresh-seeded data shows the full range of freshness states.

**Note on thresholds:** Factory state names are slightly misleading now — `fresh()` = ≤29 days, `stale()` = 31–89 days (which maps to "aging" in the UI), `expired()` = 91–400 days (which maps to "stale" in the UI). This naming mismatch is a minor debt item.

### 7. Test Data: High-Product Venues for Overflow Testing

**What:** Seeded 20 additional products (12 beers, 8 drinks) and attached all of them to two venues ("Bar Zero Proof" and "Kafeteria Trzeźwa") to create overflow scenarios.

**Where:** Manual tinker commands (not in seeders — ephemeral test data)

**Why:** The existing product catalog only had 12 products total, with max 3 per category per venue. No venue could trigger the 8-chunk overflow. With 15 beers and 10 drinks attached, the overflow badge (`+7` and `+2` respectively) is visible and testable.

## Decision Register

### Chunk color: single accent vs per-category colors

- **Chosen:** Per-category colors from `config('drinks.{slug}.color')` (option B)
- **Rejected:** Single `--color-accent` for all chunks (option A) — cleaner but less informative. The founder explicitly chose B because categories should be visually distinguishable at a glance.
- **Why:** Users scanning the discovery page need to quickly see "this venue has beers and wines" vs "this venue only has beers." Color-coded chunks make that instant.
- **Status:** Permanent.

### Chunk color source: hardcoded Tailwind vs config-driven

- **Chosen:** Colors from `config/drinks.php` applied via inline `style` attributes using `color-mix()`
- **Rejected:** Hardcoded Tailwind utility classes per category — would require updating templates when a category is added/renamed
- **Why:** The founder specifically requested that adding a new category with a color in `config/drinks.php` should "just work" without template changes.
- **Status:** Permanent.

### Mobile layout: 2-column grid vs single column

- **Chosen:** Single column (`flex-col gap-1.5`) with fixed `w-20` label widths for alignment
- **Rejected:** `grid-cols-2` on mobile — tried it, the chunks made each cell too wide and the grid looked cramped
- **Why:** Each category row contains icon + label + up to 8 chunks + overflow + count. That's too much content for a 2-col mobile grid.
- **Status:** Permanent.

### Desktop layout: flex-wrap vs 3-column grid

- **Chosen:** `grid-cols-3` on `sm`+ — 3 categories per row, 2 rows for 6 categories
- **Rejected:** `flex-wrap` — uneven row lengths depending on label/chunk counts, no alignment between columns
- **Why:** The grid ensures each category gets equal space and chunks align within columns (via the shared `w-20` label width).
- **Status:** Permanent.

### Freshness "unknown" state: show vs hide

- **Chosen:** Hide completely — don't render any badge when `offer_updated_at` is null
- **Rejected:** Showing "Brak danych" with a grey/red dot — initially implemented, then discussed with Claude (internal AI advisor) and the founder. Conclusion: if `offer_updated_at` is set automatically when products are attached (via the observer), then every venue with products starts as "fresh." A venue with no products shouldn't be on the B2C page at all. So "unknown" is either a data bug or an empty venue — neither should show a badge.
- **Why:** Simpler UI, fewer visual states for users to parse, and the edge case shouldn't exist in production.
- **Status:** Permanent.

### Freshness badge: inline with metadata vs separate row

- **Chosen:** Separate row below venue type + district
- **Rejected:** Inline in the same `flex-wrap` row as type badge and district — the "Brak danych" grey tag was visually indistinguishable from "BAR / PUB" and "Śródmieście." It read as venue metadata, not data quality.
- **Why:** Freshness is a different layer of information. Venue type and district are static facts. Freshness is a dynamic data-quality signal. Mixing them makes users treat freshness as "just another tag."
- **Status:** Permanent.

### Verified checkmark: `is_verified` vs `claimed_at`

- **Chosen:** Keep using `is_verified` for the checkmark badge
- **Rejected:** Switching to `claimed_at` (as the original spec suggested) — the founder decided to keep the current editorial verification system rather than switching to claim-based verification.
- **Why:** `is_verified` is an admin editorial decision. `claimed_at` means the owner has claimed the profile, which doesn't guarantee data quality. Different concepts, different trust signals.
- **Status:** Permanent.

## What Was Built

### 1. Bug Fix: VenueScoring Crashes on Drinks-Only Venues

**What:** `VenueScoring::calculate()` threw `Call to a member function getKey() on int` when a venue had custom drinks but no products. The root cause: `$venue->products` returns an `EloquentCollection` when empty, and calling `groupBy()->map->count()` on an empty EloquentCollection preserves the Eloquent type. When `merge()` was called on this empty EloquentCollection with integer values from the drink counts, it tried to call `getKey()` on integers.

**Where:** `app/Services/VenueScoring.php` lines 19–25

**Why:** This is a production-ready bug. Any venue that has custom drinks (from Session 1's `venue_drinks` table) but no products in the pivot table would crash the discovery page. The fix wraps both relation collections in `collect()` to ensure base Collection type, which handles merge correctly.

**Current state:** Fixed and tested. 7 unit tests cover all scoring scenarios including the drinks-only edge case.

### 2. Bug Fix: Dynamic Tailwind Classes in Venue Status Widget

**What:** The owner panel's venue status widget used dynamic string interpolation for Tailwind classes: `border-{{ $staleProductsCount > 0 ? 'warning' : 'gray' }}-200`. Tailwind's JIT compiler can't detect these dynamically constructed class names, so the CSS is never generated.

**Where:** `resources/views/filament/panel/widgets/venue-status.blade.php` lines 32–34

**Why:** This means the "stale products" card in the owner dashboard either had no border/background styling (if Tailwind purged the classes) or only worked because of coincidental class generation from elsewhere. The fix uses Blade's `@class()` directive with full static class names, which Tailwind JIT can properly detect.

**Current state:** Fixed. Uses conditional `@class([...])` syntax with full class names.

### 3. Dead Code Removal — 4 Items

**What:** Removed 3 files and 1 method that were orphaned or unreachable:

1. **`app/Http/Middleware/RedirectAdminFromOwnerPanel.php`** — This middleware was never registered in any panel provider or route group. The same functionality (redirecting admins away from the owner panel) already exists in `PanelAuthenticate::authenticate()`. The middleware was created in an earlier session but never wired up, then superseded by the PanelAuthenticate approach. Safe to remove because existing tests verify the redirect behavior works via PanelAuthenticate.

2. **`database/seeders/TagSeeder.php`** — References `App\Models\Tag` which doesn't exist. The `tags` and `product_tag` tables were dropped in a migration. The seeder was never called from `DatabaseSeeder`. Safe to remove because the model doesn't exist.

## Decision Register

### Dead seeder handling: delete FakeVenueSeeder/VenueTableSeeder vs keep

- **Chosen:** Keep both files
- **Rejected:** Deleting them — they're referenced in journal entries as standalone dev tools ("run with `php artisan db:seed --class=FakeVenueSeeder`"). They're functional code, not broken references.
- **Why:** They serve a legitimate development purpose even though `DatabaseSeeder::seedDevVenues()` supersedes them. They test different scenarios (random distributions vs curated states). Removing them saves nothing and might surprise someone who uses them.
- **Status:** Permanent. They're optional dev tools.

### VenueScoring fix: `collect()` wrapper vs changing relation return types

- **Chosen:** Wrap `$venue->products` and `$venue->drinks` in `collect()` before groupBy/map
- **Rejected:** Overriding the relation return type or using `->toBase()` — more invasive, affects other code that depends on Eloquent collection methods
- **Why:** `collect()` is the minimal fix. It converts the Eloquent collection to a base Collection, which handles `merge()` correctly with non-model values. No side effects on the rest of the codebase.
- **Status:** Permanent.

### Registration UX: fix now vs flag for later

- **Chosen:** Flag for later — documented the issue in tests and this journal
- **Rejected:** Changing `canAccessPanel()` to also allow role='user' — this would let any registered user access the full owner panel, which may not be the desired behavior. The founder needs to decide the onboarding flow.
- **Why:** The current behavior is *secure* (nobody gets unauthorized access), just bad UX. Changing it requires a product decision about whether new registrations should immediately access the panel or go through an approval/claim flow first.
- **Status:** Open question for founder.
