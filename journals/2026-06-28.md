## What Was Built

### 1. OSM Dark Map Tile Experiment (reverted)

**What changed:** Temporarily swapped the dark map tile URL from CARTO to native OSM (`tile.openstreetmap.org`) with a CSS `invert(100%) hue-rotate(180deg)` filter applied to `map.getPane('tilePane')`. The `applyTiles()` function in `resources/js/map-config.js` was extended to read a `filter` property from tile config and apply it to the tile pane DOM element.

**Why reverted:** This was a visual prototype only — the user wanted to see how OSM tiles look in dark mode. After seeing the result (inverted OSM: blue water stays blue, parks turn purple-magenta), the decision was to stay with CARTO dark tiles (`dark_all`), which are purpose-built for dark cartography and look significantly better. CARTO is already OSM data underneath.

**Current state:** Fully reverted. `map-config.js` is back to CARTO dark / OSM light. No filter logic remains.

**Key comparison insight:** CARTO dark tiles are purpose-built — designed cartographers chose every color for dark-background legibility. CSS inversion is a programmatic hack: it turns greens magenta, white roads grey, and can't compensate for all hue shifts cleanly. The CSS filter approach is free and zero-dependency, but the visual quality gap is significant for a product where map trust is a core UX signal.

### 3. `config/logging.php` — Log Driver `single` → `daily`, 30-day Retention

**What changed:** Two edits to `config/logging.php`:
1. Stack channel default changed from `env('LOG_STACK', 'single')` to `env('LOG_STACK', 'daily')`
2. Daily channel retention changed from `env('LOG_DAILY_DAYS', 14)` to `env('LOG_DAILY_DAYS', 30)`

**Why:** The `single` driver writes everything to one file — `storage/logs/laravel.log` — forever. In production, a busy application can fill a disk in days. More critically, Laravel request logs include IP addresses and request payloads. An unbounded single log file is a GDPR-adjacent risk: PII accumulates in a place with no retention control. The `daily` driver creates one file per day and automatically deletes files older than the configured retention period. 30 days is the right balance: enough history to debug recent incidents, not so much that PII lingers.

**Why not `stderr`:** Stderr is the right choice for containerised deploys (Docker, Kubernetes) where log aggregators collect from stdout/stderr. UNI deploys to a VPS, not a container platform — `daily` with rotation is the appropriate production default.

**Current state:** Active. No env variable override needed — the default is now correct.

### 4. `resources/views/home.blade.php` + `HomeController.php` — Dynamic City Name

**What changed:** Two hardcoded "Warszawie" strings in `home.blade.php` replaced with `{{ $city->name_locative }}`. `HomeController` updated to query `City::active()->first()` and pass `$city` to the view.

**Why:** The V1 roadmap flagged 12 hardcoded "Warszawie" occurrences as a multi-city blocker. Investigation found only 2 in views (the other 10 were already dynamic or in legal/address text that is legitimately city-specific). Both were in `home.blade.php`: the venue count badge ("47 lokali w Warszawie") and the subheadline. The `City` model already had a `name_locative` computed attribute with Polish declension forms for Warsaw, Kraków, Wrocław, Gdańsk, Poznań — the infrastructure was ready, just not connected.

**Technical detail:** Polish grammar requires locative case for "w [city]" ("in [city]"). `name_locative` returns "Warszawie" for Warsaw, "Krakowie" for Kraków, etc. Using the raw `name` column ("Warszawa") would produce grammatically incorrect Polish ("w Warszawa"). This was already solved in the City model — this change just wires it up.

**Privacy policy note:** The one remaining "Warszawa" string is the UODO postal address ("ul. Stawki 2, 00-193 Warszawa") — a real government office address, intentionally not changed.

**Test fix required:** `HomeController` now calls `City::active()->first()` which returns null in tests using `RefreshDatabase` with no city seeded. Two tests hit the home route: `ExampleTest` and `AnalyticsGatewayTest::posthog_script_requires_public_enabled_flag`. Both were updated to call `City::factory()->create(['is_active' => true])` before the request. `CityFactory` already existed.

**Current state:** Active. Dynamic for all cities in the `cities` table.

### 6. `docs/breach-runbook.md` — GDPR Art. 33 Breach Notification Runbook

**What changed:** Created `docs/breach-runbook.md` — a practical, actionable breach response document.

**Contents:**
1. **What counts as a breach** — definition + UNI-specific table listing which tables contain personal data (`users`, `venue_claims`, `venue_erasure_requests`, `venue_inaccuracy_reports`, `user_venue_saves`, `audit_logs`, sessions) and which are genuinely anonymous (`events` table — confirmed by the 2026-06-22 PII column drop)
2. **Severity matrix** — Critical/High/Medium/Low criteria with UODO notification and user notification requirements for each
3. **The 72-hour clock** — broken into Hour 0–4 (contain), 4–24 (assess), 24–48 (draft), 48–72 (file), with the key legal note that "likely" breach triggers the clock, not confirmed breach
4. **Containment checklist** — 7 items including APP_KEY rotation procedure, session invalidation, PostgreSQL credential rotation
5. **UODO filing** — portal URL (uodo.gov.pl/p/formularz-naruszen), required information per Art. 33(3), and a Polish-language filing template ready to use
6. **User notification** — when required, and a Polish-language email template
7. **Post-incident** — pointer to incident register at `docs/compliance/incidents/README.md`
8. **Quick reference table** — portal URL, incident register path, APP_KEY rotation command, backup comparison procedure

**Why this matters:** Art. 33 GDPR requires notifying UODO within 72 hours of becoming aware of a breach. Poland's UODO is an active enforcement authority. In a breach scenario, the last thing you want is to spend precious hours of the 72-hour window figuring out where to file, what to write, or what your own data map looks like. This document answers all of those questions in advance so the response is a checklist, not a research project.

**Current state:** Active at `docs/breach-runbook.md`.

### 8. Test Suite: 2 Tests Fixed

**What changed:** `tests/Feature/ExampleTest.php` and `tests/Feature/Analytics/AnalyticsGatewayTest.php` both added `City::factory()->create(['is_active' => true])` before making requests to the home route.

**Why:** The `HomeController` change (item 4 above) introduced a `City::active()->first()` call that returns null in empty test databases. The tests use `RefreshDatabase` which wipes and rebuilds the database for each test — no city exists unless explicitly seeded. Both tests hit `GET /`, which now requires an active city. The correct fix is to seed the dependency in the tests, not to make the production code handle a state that won't exist in production.

## Business Impact

**The CVE patch removes the last security gap that could be cited in a responsible disclosure.** CVE-2026-48019 was in Laravel's email validation — the same validation that runs when venue owners submit claims. Patching it before launch means no one can file a "you launched with a known High vulnerability" report. It also signals maturity: the project is tracking `composer audit` and responding quickly.

**The dynamic city name is a small change with a large strategic implication.** Every hardcoded "Warszawie" was a line of code that would need to be found and changed when expanding to Kraków or Wrocław. Removing them now means the homepage is already city-agnostic in code — launch in a second city and the hero immediately reads "X lokali w Krakowie" without touching the template. This is exactly the kind of 15-minute investment that saves 3 hours of frustration during a time-pressured expansion.

**The breach runbook converts a legal obligation into an operational procedure.** GDPR Art. 33 says notify UODO within 72 hours. Without a runbook, those 72 hours would be spent figuring out what counts as a breach, where to file, what to write, and who to notify — all under stress. With the runbook, the first hour is containment, not research. This matters most for a solo founder: there's no team to delegate to, so pre-written procedures are the only way to act quickly and correctly under pressure.

**The programmatic SEO pages (already built, confirmed this session) are the highest-leverage SEO asset in V1.** A user searching "bezalkoholowe piwo Mokotów" or "nolo bar Śródmieście" will land directly on a page purpose-built for that query — with venue list, JSON-LD structured data, and breadcrumbs. Google's crawl efficiency is also maximised: the sitemap pre-declares every valid city/district/category combination, so Googlebot doesn't need to discover them through link-following. This is the kind of SEO architecture that typically takes a team several sprints; it was built during V1 development and confirmed complete today.

## Learning Path

**Why CARTO dark tiles beat CSS inversion:**
CSS `invert(100%) hue-rotate(180deg)` is mathematically elegant but perceptually wrong. Human color perception is non-linear — inverting a green (#22c55e) produces a magenta-ish result (#dd3aa1) which has no geographic meaning. CARTO's cartographers chose dark tile colors based on perceptual salience: roads need to be visible but not dominant, water should read as water, and parks should feel natural even on a dark background. That's hundreds of design decisions that a CSS filter can't replicate.

**Why the 72-hour GDPR clock starts at "aware," not "confirmed":**
GDPR Art. 33(1) says "without undue delay and, where feasible, not later than 72 hours after having *become aware* of it." "Aware" means you have reasonable grounds to believe a breach has likely occurred — not that you've completed a forensic investigation. This is intentional: regulators want early notification, not notification only after you're certain. The practical implication: if your hosting provider tells you the server was breached, the clock starts then — even if you don't yet know which data was accessed. File a partial notification, mark it as ongoing, and update UODO as you learn more.

**Why `composer update` should be targeted, not full:**
A full `composer update` resolves all packages to their latest allowed versions simultaneously. With 100+ packages, each with their own minor-version changes, the probability of a silent behavioral change is non-trivial. A targeted update (`composer update package-a package-b`) limits the blast radius: only the named packages and their direct dependencies update. If a test breaks after a targeted update, you know exactly which package caused it. This is especially important for framework updates (Laravel 13.x minor versions sometimes have subtle middleware behavior changes).
