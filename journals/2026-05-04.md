## Decision Register

### D-01: Badge system — Binary, not tiered

- **Chosen:** Single binary badge: "Zweryfikowany" (verified) or nothing. Based on `is_claimed` + `offer_updated_at` within 90 days.
- **Rejected:** Gold/Silver/Bronze tiers from SCORING.md. Three tiers require threshold tuning, tier transition logic, UI for 3 states, communication of tier meanings to owners, and handling edge cases (what happens at the boundary?). All of this for a platform with zero users and no data to calibrate thresholds against.
- **Why:** ADR-004 already decided binary. SCORING.md's tier system was aspirational spec written before implementation began. Binary is instantly understandable, impossible to game, and can be extended to tiers in V2 if owner behavior data shows differentiation motivates engagement.
- **Status:** Permanent for V1. SCORING.md §2 is formally superseded.

### D-02: URL structure — Keep current Polish slugs, city-as-anchor

- **Chosen:** Current route structure stays: `/miejsce/{slug}`, `/{citySlug}`, `/{citySlug}/{districtSlug}`, `/kategoria/{slug}`. Polish slugs for Polish SEO. No `/pl/` locale prefix.
- **Rejected:** (a) English slugs — lose Polish SEO value. (b) `/pl/` locale prefix — unnecessary complexity for a Polish-only V1, creates ugly URLs, adds routing overhead with zero SEO benefit since there's no alternate language to differentiate from.
- **Why:** Polish slugs win in Polish search results. The city slug acts as an implicit locale anchor — when expanding to Berlin, routes become `/berlin/lokal/{slug}` with hreflang tags, not `/de/berlin/...`. This is how Booking, Tripadvisor, and Yelp handle it.
- **Status:** Permanent. This was already implemented in `routes/web.php` — the decision doc just formally locks it so it stops appearing as an "open question."

### D-03: Venue images — None in V1

- **Chosen:** No venue image upload, no venue photos displayed.
- **Rejected:** (a) Owner-uploaded venue photos — moderation burden, storage/CDN cost, quality control risk. (b) Google Places API photos — session-expiring URLs, per-request API costs, ToS restrictions, attribution clutter.
- **Why:** The chunk visualization IS the visual identity of venue cards. Bad photos hurt trust more than no photos. And the moderation queue for images is a real operational cost with unclear return at this stage.
- **Status:** Revisit when claimed owners provide feedback showing strong demand.

### D-04: Drink images — None in V1

- **Chosen:** No drink images — neither catalog product label photos nor custom drink photos.
- **Rejected:** "Allow photos for custom drinks only" — creates an inconsistency (why can I see my mocktail photo but not my venue?). Also adds upload UX, moderation queue, and S3 storage infra for an unvalidated feature.
- **Why:** Catalog products are known brands — the name is sufficient. Custom drinks photos are nice-to-have but owners haven't asked for them. Validate the data-first value proposition before adding media.
- **Status:** Revisit when claimed owners request it.

### D-05: Opening hours — Not stored, not displayed in V1

- **Chosen:** Don't store or display opening hours. Link to Google Maps/Instagram where owners already maintain this data.
- **Rejected:** Structured opening hours table (day-of-week, open/close, exceptions). Deceptively complex schema, high maintenance burden, and stale hours actively damage trust — a user who shows up to a "closed" venue that UNI said was open will not return.
- **Why:** UNI's value prop is "what NA drinks they serve," not "when are they open." Don't compete with Google on operational data. Note: the `opening_hours` JSONB column already exists on venues but should not be exposed in V1.
- **Status:** Revisit in V2 if claimed owners want to self-manage hours through the panel.

### D-06: Map markers — Dot + popup, not inline chunks

- **Chosen:** Color-coded dot on marker (verified = brand accent, unclaimed = grey). Full chunk bar + venue name appears in popup/tooltip on tap.
- **Rejected:** Rendering chunk bars directly on/near map markers. At typical mobile zoom levels, colored squares would be ~3px wide and illegible. The marker's job is "something interesting here, tap me" — the popup's job is "here's why."
- **Why:** Mobile-first design. Map real estate is tiny. Markers need to communicate "tap me" at a glance, not render a full data visualization.
- **Status:** Permanent.

### D-07: Scoring recalculation — Denormalized `breadth_score` column

- **Chosen:** Add `breadth_score` integer column to `venues` table, updated synchronously in the existing observers whenever products or drinks change. Sort listing pages by `ORDER BY breadth_score DESC` with an index.
- **Rejected:** (a) Calculate on read (current approach) — `VenueScoring::calculate()` loads all products and drinks per venue, groups in PHP. The `sort()` method does this for every venue in the collection = N+1 on listing pages. (b) Debounced queue job — overkill for V1 data volume. (c) Nightly cron recalculation — too much lag, doesn't leverage existing observer infrastructure.
- **Why:** The current scoring approach doesn't scale even at modest data volumes. A denormalized column costs one integer, one index, and ~5 lines in each observer. Read-path performance goes from "load all relations for every venue" to "ORDER BY indexed column." This is the single highest-leverage performance fix available.
- **Status:** Permanent. Part of the coupled batch (P6 in priority list).

### D-08: Score formula — Flat category count, no weights (confirming ADR-008)

- **Chosen:** 6 equal categories, no multipliers, no rarity scoring. Breadth = total distinct products across categories. Diversity tiebreaker = number of categories used. Brand diversity deferred.
- **Rejected:** Per-product weights, per-category multipliers, scarcity-based dynamic weights — all rejected in ADR-008 for the same reasons: editorial burden, gameability, unfair to specialists.
- **Why:** All weight systems were designed before having real user data. Ship simple, observe behavior, add complexity only if data demands it.
- **Status:** Permanent for V1. Confirming ADR-008.

### D-09: Districts — Normalize to FK table

- **Chosen:** Create `districts` table (id, city_id, name, slug), add `district_id` FK to `venues`, migrate existing free-text data via mapping array.
- **Rejected:** (a) Keep free-text — prevents clean filtering, breaks pSEO slugs, causes duplicates ("Mokotów" vs "mokotów" vs "Mokotow"). (b) Derive from coordinates via PostGIS polygon matching — rabbit hole for V1.
- **Why:** Districts normalization is a prerequisite for programmatic SEO pages (city × district × category), reliable filtering, and B2B analytics ("Your venue is one of 3 verified spots in Mokotów"). Current free-text `district` column has no constraints.
- **Status:** Part of the coupled batch (P6 in priority list).

### D-10: Owner product-adding UX — Improve Filament, don't rebuild

- **Chosen:** Enhance the existing Filament-based product management with better search and category pre-filtering within Filament's component patterns.
- **Rejected:** Building a custom Livewire product browser from scratch — significant effort to rebuild something that exists. The current Filament UX is functional, just not optimized.
- **Why:** The owner panel is already Filament. Don't rebuild it in custom Livewire for one flow. If real owner feedback (post-launch) shows the adding experience is a bounce point, then invest in a custom UX in V2.
- **Status:** V2 consideration. Improve Filament UX incrementally for now.

### D-11: Community reporting — Not built, no pre-design

- **Chosen:** Don't build community reporting in V1. Don't pre-design the schema either.
- **Rejected:** Designing abuse-prevention schema now (trust levels, activity scores, account age gates). No users = no abuse patterns to design against. Trust-level thresholds depend on behavior patterns that can't be predicted.
- **Why:** Premature optimization. Build it when the platform has users and data quality issues actually surface.
- **Status:** Deferred to post-launch.

### D-12: Locale / i18n — Polish only, no infrastructure

- **Chosen:** No `/pl/` prefixes, no translation tables, no multi-language slugs. Add `hreflang` middleware when expanding to non-Polish cities.
- **Rejected:** Building locale infrastructure now — adds routing complexity with zero benefit for a Polish-only product.
- **Why:** Every minute spent on i18n infrastructure is a minute not spent on the data flywheel. Polish only until proven otherwise.
- **Status:** Revisit when first non-Polish city is added.

### D-13: `offer_updated_at` integrity — Hourly check, not DB trigger

- **Chosen:** Hourly scheduled Laravel command that catches drift: `WHERE offer_updated_at < GREATEST(max product updated_at, max drink updated_at)`.
- **Rejected:** (a) Database trigger — heavy for V1, adds DB-level complexity. (b) Nightly job — 24 hours of potential drift is too long for a platform where freshness is the core trust signal.
- **Why:** Observers handle the normal Eloquent path. The hourly check is a safety net for raw queries, bulk operations, or tinker commands that bypass observers. 1-hour max drift is acceptable.
- **Status:** Permanent. Implement as part of P8 in priority list.

### D-14: Badge freshness — Binary, 90-day window

- **Chosen:** "Zweryfikowany" badge requires `is_claimed` + `offer_updated_at` within 90 days. No staleness tiers. Stale venues lose the checkmark immediately — owner can re-confirm products instantly to restore it.
- **Rejected:** (a) 4-tier staleness from SCORING.md (Fresh/Aging/Stale/Expired) — too many states for V1 badge logic. (b) Grace period before badge drops — adds complexity and delays the urgency signal that drives owner engagement.
- **Why:** Binary badge + immediate drop creates the sharpest incentive for owners to keep data fresh. A grace period softens the urgency. Owners can fix it instantly by confirming their products, so the "punishment" is always reversible.
- **Status:** Permanent for V1. SCORING.md §3 tiers are superseded for badge purposes (freshness dots on venue tiles remain as a separate visual layer).

## Learning Path

### For this session's work

- **Architecture Decision Records (ADRs):** The existing ADRs in `inspo/UNI-Obsidian-Vault/uni-vault/decisions/adr/` are individual decision documents. The new `decisions/v1-locked.md` is a consolidated decision register — it references ADRs where they exist and creates new locked decisions where they don't. The key difference: ADRs document one decision in depth; the decision register is a quick-reference table showing what's been decided and what's superseded.

- **Denormalized columns:** The `breadth_score` column (D-07) is a deliberate denormalization — storing a computed value on the row instead of calculating it on read. This trades write-time cost (recalculate on every product change) for read-time performance (simple indexed column sort). The tradeoff is worth it when reads vastly outnumber writes, which is true for a discovery platform (many users browsing, few owners updating).

- **Adversarial review as a design tool:** This session used two AI systems — one with strategic context but no codebase access, one with full codebase access but initially less strategic context — to cross-check each other. The result was better than either could produce alone: the strategic LLM caught product-level concerns (URL locale strategy, scoring incentive design), while the codebase-aware system caught implementation realities (N+1 queries, coupled migrations, existing observer patterns).

## Decision Register

All decisions in this session were implementations of the locked decisions from Session 1's `decisions/v1-locked.md`. No new architectural forks were encountered.

### Claim flow: allow role='user' into panel vs require admin pre-approval

- **Chosen:** Allow role='user' into the panel. They see only Dashboard + ClaimVenue page (VenueResource hidden by policy).
- **Rejected:** Keeping the 403 and requiring admin to manually change role before owner can even submit a claim — this was the broken status quo.
- **Why:** The time between "I want to manage my venue" and "I see some value" must be under 2 minutes. Blocking at registration kills the entire B2B funnel.
- **Status:** Permanent. Implements D-02 from decision doc.

### "Stare Miasto" district mapping: create separate district vs map to Śródmieście

- **Chosen:** Map to Śródmieście (Stare Miasto is historically part of Śródmieście dzielnica).
- **Rejected:** Creating a separate "Stare Miasto" district — it's not an official Warsaw administrative district.
- **Why:** The `districts` table represents official dzielnice. Informal neighborhood names can exist as aliases in the future, but the primary model should be authoritative.
- **Status:** Permanent.

### District page with only canary venues: 404 vs empty page

- **Chosen:** Return 200 with empty venue list. The district exists — it's just that all venues happen to be canaries (hidden from public).
- **Rejected:** Old behavior of 404 when no non-canary venues exist in a district — this leaked information about which districts have only canary venues.
- **Why:** A district is a real geographic entity. Whether it has visible venues is a data state, not a routing concern.
- **Status:** Permanent.

### Discovery page sort fallback (no geolocation): breadth_score vs products_count

- **Chosen:** `orderByDesc('breadth_score')` — the denormalized column that includes both products and drinks.
- **Rejected:** `orderByDesc('products_count')` — only counts pivot products, ignores custom drinks entirely.
- **Why:** `breadth_score` is the true measure of a venue's NA offering diversity. `products_count` was a placeholder from before the scoring system existed.
- **Status:** Permanent.

## Learning Path

### For this session's work

- **Laravel Policies:** Policies are classes that organize authorization logic around a model. Laravel auto-discovers them by convention (`App\Policies\VenuePolicy` for `App\Models\Venue`). The `before()` method can grant blanket access (admins). Individual methods (`view`, `update`, `attachProduct`) define granular permissions. Filament respects these automatically on resource pages. [Laravel Docs: Policies](https://laravel.com/docs/authorization#creating-policies)

- **Denormalization:** Storing a computed value (`breadth_score`) directly on the row instead of calculating it on every read. The tradeoff: slightly more work on write (recalculate when data changes), dramatically less work on read (simple indexed column sort). Worth it when reads vastly outnumber writes — which is always true for a discovery platform. The key implementation pattern: use `updateQuietly()` to avoid triggering timestamps/events when updating the derived column.

- **Database normalization:** Moving from a free-text string column (`district`) to a FK pointing at a reference table (`districts`). Benefits: consistent data, clean URLs from slugs, enables COUNT/GROUP BY without string matching, prevents typos. The transition pattern: add FK as nullable, backfill, verify, then eventually drop the old column.

- **Query scoping vs authorization:** Query scoping (`where('claimed_by', auth()->id())`) limits what's returned from the database. Authorization (policies) prevents actions even if someone manually crafts a request. You need both: scoping for UX (owner only sees their venue), policy for security (owner can't edit someone else's venue even with a direct URL).

### 4. D-09: Migrated All Free-Text District References to FK

**What:** Every place in the codebase that read the free-text `district` varchar column was migrated to use the `district_id` FK and the `districtRelation` relationship. This affected:

- **Model scopes:** `scopeSearch`, `scopeInDistrict`, `scopeWithDistrict` in `Venue.php` — all now use `district_id` or `districtRelation`
- **Livewire:** `DiscoveryPage.php` — district filter casts to int, map data uses relation, district dropdown queries `District` model
- **Controllers:** `VenueController.php` — added `districtRelation` to eager loads
- **Filament admin:** `VenuesTable.php` — column and filter now use `districtRelation.name` and `district_id`
- **Blade templates:** `venue-tile.blade.php`, `venue-list-row.blade.php`, `venue-status.blade.php`, `discovery-page.blade.php`, `venues/show.blade.php` — all `$venue->district` replaced with `$venue->districtRelation->name`
- **Tests:** `VenueModelTest.php`, `DiscoveryPageTest.php` — all create `District` models and use FK IDs

**Where:** 12+ files (see above)

**Why:** Session 2 created the `districts` table and added the FK column, but many read paths still used the old free-text column. This created a risk of divergence — the FK and free-text column showing different values. Migrating all reads to the FK is the prerequisite for eventually dropping the free-text column entirely.

**Current state:** Committed on 04.05.2026. The free-text `district` column still exists on the table but is no longer read anywhere in the application. Ready for a DROP COLUMN migration.

### 5. D-14: Simplified Freshness to Binary

**What:** Replaced 3-tier freshness logic (fresh/aging/stale) with binary (fresh/stale) everywhere:

- `Venue::computeFreshnessState()` — now returns only 'fresh' (≤90 days) or 'stale' (>90 days), no 'aging' middle tier
- `venues/show.blade.php` — freshness badge reduced from 3 states to 2 (Aktualne/Nieaktualne), product opacity from 3 tiers to binary
- `venue-tile.blade.php` — removed 'aging' color from freshness map
- `VenueFactory.php` — removed `expired()` state, updated `stale()` to 91–400 day range

**Where:** `Venue.php`, `show.blade.php`, `venue-tile.blade.php`, `VenueFactory.php`, `VenueModelTest.php`

**Why:** Decision D-14 locks the badge as binary — "Zweryfikowany" or nothing, with 90 days as the threshold. The 3-tier system from SCORING.md was aspirational complexity for a V2 feature. The middle "aging" state confused the mental model: is it still good? Should I trust it? Binary is clear — it's current, or it's not.

**Current state:** Committed on 04.05.2026. Tests updated: the old `test_freshness_state_is_aging_at_31_days` now correctly asserts 'fresh' at 31 days.

## Decision Register

### Static page filenames: English internal, Polish URL

- **Chosen:** Rename `jak-to-dziala.blade.php` to `how-it-works.blade.php`. Keep `/jak-to-dziala` as the URL.

- **Why:** Internal file naming convention should be consistent. URLs are user-facing and SEO-sensitive; filenames are developer-facing and consistency-sensitive. These are independent concerns.
- **Status:** Permanent.

### Copy voice: Conversational Polish vs. formal documentation

- **Chosen:** Conversational "knowledgeable friend" voice — direct, specific, using natural Polish sentence structure. "Każdy kwadrat to jeden konkretny produkt" instead of "Wizualizacja produktów odbywa się za pomocą kolorowych kwadratów."
- **Rejected:** (a) Formal documentation style — reads like a translated SaaS help page, feels corporate and impersonal. (b) Marketing-speak with exclamation marks — feels pushy, undermines the "no influence" brand identity.
- **Why:** UNI's brand promise is honest, transparent data. The voice should match: direct, concrete, no hype. The page should read like someone explaining the product to you over coffee, not a corporate FAQ bot.
- **Status:** Permanent voice direction for all user-facing copy.
