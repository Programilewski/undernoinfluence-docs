# 2026-05-14 — First-Party Analytics Gateway and Menu-Time Collection

## Session Overview

Goal: turn the analytics/privacy decisions from discussion and SSOT planning into working code.

Outcome: analytics collection is now first-party by default, routed through a clear backend gateway, and able to collect menu/category attention time on venue profiles. PostHog is no longer a silent production dependency; it is config-gated and off unless explicitly enabled.

---

## What Was Built

### Analytics gateway

Added an injected analytics boundary:

- `AnalyticsGateway` contract;
- production `DatabaseAnalyticsGateway`;
- `FakeAnalyticsGateway` for tests;
- split venue and discovery analytics surfaces.

This makes analytics calls obvious in code and prevents controllers from directly mixing `EventLogger`, `VenueStat`, and `PostHogService`.

Current high-level calls include:

- venue viewed;
- outbound clicked;
- menu viewed;
- category viewed;
- category browsed;
- discovery searched;
- discovery category filtered;
- discovery empty results;
- map area searched.

### First-party menu-time events

Venue profile menus now collect first-party duration events:

- `venue_menu_viewed`;
- `venue_category_viewed`.

The browser-side timer:

- tracks visible menu time;
- tracks open category accordion time;
- pauses when the tab is hidden;
- flushes on `visibilitychange` and `pagehide`;
- ignores sub-2-second noise;
- caps duration at 900 seconds.

Events go to `POST /analytics/events`, not PostHog.

### Protected analytics endpoint

The duration endpoint is:

- CSRF-protected;
- rate-limited with `analytics-events`;
- restricted to active, non-canary venues;
- restricted to active categories;
- limited to 1-900 seconds per event;
- routed through `AnalyticsGateway`.

### PostHog gating

PostHog now has explicit flags:

- `POSTHOG_PUBLIC_ENABLED=false`;
- `POSTHOG_SERVER_ENABLED=false`.

The public layout only loads the PostHog script when both a key and the public flag are present. Server-side PostHog capture also requires the server flag.

This fixes the policy contradiction where the app could claim no third-party analytics while still loading PostHog if a key existed.

### Retention and small-bucket privacy

Added:

- `analytics:prune-events`;
- daily schedule for raw event pruning;
- `ANALYTICS_RAW_EVENT_RETENTION_DAYS=90`;
- `AnalyticsBucketPrivacy`;
- `ANALYTICS_SMALL_BUCKET_THRESHOLD=5`.

This gives the future owner analytics product a privacy rule: narrow aggregates below `k=5` unique sessions should be hidden or merged before being shown.

### Privacy policy and SSOT

Updated the privacy policy to mention:

- first-party server-side analytics;
- aggregated time interaction with venue menus;
- 90-day raw event retention;
- PostHog disabled by default unless policy/consent posture changes.

Updated `inspo/interactive_v1_feature_spec_SSOT.html` to mark the gateway, first-party duration events, PostHog gating, retention pruning, and small-bucket suppression as implemented.

## Decision Register

### Decision: first-party analytics is canonical

Chosen: local `events` + `venue_stats` are the V1 source of truth.

Rejected: relying on PostHog for V1 collection.

Reason: the B2B product needs trustworthy data that is not blocked by ad blockers and does not require third-party tracking consent as the default path.

### Decision: menu time is raw now, aggregate later

Chosen: collect raw `venue_menu_viewed` and `venue_category_viewed` events now, then aggregate for owner dashboards later.

Reason: missing early data cannot be recreated. Dashboards can wait.

### Decision: gateway over facade

Chosen: injected `AnalyticsGateway`.

Rejected: static `Analytics::...` facade.

Reason: injected contracts are clearer in this codebase and easier to fake in tests.

## Risk Register

| Risk | Impact | Mitigation |
|---|---|---|
| Duration data can be noisy | Menu-time reports may overstate attention | Pause on hidden tab, ignore <2s, cap at 900s, aggregate before display |
| Endpoint can still be spammed | Raw event volume could be inflated | CSRF, route throttling, active venue/category validation, outlier handling at query time |
| Small aggregate buckets can identify behavior | Privacy risk for narrow reports | Suppress or merge buckets below `k=5` unique sessions |
| PostHog accidentally enabled in production | Privacy policy mismatch | Requires explicit public/server flags, not only `POSTHOG_KEY` |
| Gateway adds abstraction | Future developers need to know where analytics lives | SSOT and tests document gateway as the application-facing boundary |

- "People looked at your profile" becomes basic traffic proof.

## Session 2 — Email Verification, Polish Notifications, Disposable Email Blocking

### What Was Built

#### Email verification (mandatory)

Enabled `MustVerifyEmail` on the `User` model. Registration now always redirects to `/weryfikacja-email` (the notice page) rather than directly to the profile or intended URL. The intended URL (e.g., the claim form) is preserved in the session and used after the verification link is clicked.

Added:

- `app/Notifications/VerifyEmailNotification.php` — Polish, queued, uses a signed temporary route URL, 60-minute expiry;
- `app/Notifications/ResetPasswordNotification.php` — Polish, queued, replaces the Laravel default English reset email;
- `app/Http/Controllers/Auth/EmailVerificationController.php` — three actions: `notice`, `verify`, `resend`;
- `resources/views/auth/verify-email.blade.php` — Polish notice page, consistent dark UI with existing auth views.

Routes added to `/weryfikacja-email`:

- `GET /weryfikacja-email` → `verification.notice`;
- `GET /weryfikacja-email/{id}/{hash}` (signed) → `verification.verify`;
- `POST /weryfikacja-email/wyslij` (throttled 6/min) → `verification.send`.

The `/zglos-lokal` venue-claims routes are now guarded by `verified` middleware. Unverified users are redirected to the notice page automatically.

#### Disposable email blocking

Added `app/Rules/NotDisposableEmail.php` — a static-list domain check covering ~70 of the highest-volume temp-mail services. No new package dependency. Applied to the email field in `RegisterController`.

Error message: *"Adresy e-mail z jednorazowych serwisów nie są dozwolone. Użyj swojego stałego adresu e-mail."*

#### Polish password reset emails

`User::sendPasswordResetNotification()` now dispatches `ResetPasswordNotification` instead of the Laravel default. The email is entirely in Polish with the subject *"Resetowanie hasła — Under No Influence"*.

### SSOT & Documentation Updates

Updated `inspo/interactive_v1_feature_spec_SSOT.html`:
- Onboarding section step 02 now describes the full email verification flow, disposable-email check, and Polish notifications.
- TODOs callout updated: email verification and Polish reset email are no longer "optional recommended" — marked as shipped Session 2.
- New auth hardening table added to the Fixed Bugs section with 3 rows covering each feature, including rationale and trade-offs.

### Decision Register

**Decision: claim form requires verified email**

Chosen: add `verified` middleware to `/zglos-lokal`.

Reason: a venue owner claim is a semi-legal act — requiring a working email address before allowing it reduces fraudulent claims and ensures approval notification emails reach the owner.

**Decision: static domain list over package**

Chosen: maintain a ~70-domain static list in `NotDisposableEmail`.

Rejected: adding a third-party package like `propaganistas/laravel-disposable-email` (CLAUDE.md prohibits adding dependencies without approval).

Trade-off: list is not exhaustive and will not catch new disposable domains automatically, but it blocks the vast majority of high-volume temp-mail services used by bots.
