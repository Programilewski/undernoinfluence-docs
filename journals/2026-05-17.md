# 2026-05-17 — Bug Documentation & "Na mapie" Navigation Fix

## Session Overview

**Goal:** Two tasks. First: document the two map-marker bugs that were fixed in the 2026-05-16 session (the PC shut down before the journal was written, so the SSOT was never updated). Second: fix a newly-reported bug where clicking the "Na mapie" button on a venue card was navigating to the venue detail page instead of zooming the discovery map to show the venue's location.

**Outcome:** Both 2026-05-16 bugs are now documented in `inspo/interactive_v1_feature_spec_SSOT.html`. The "Na mapie" navigation bug is fixed. The root cause turned out to be a deeper HTML structural problem — buttons nested inside an `<a>` tag is invalid HTML, and some browsers bypass JavaScript event propagation entirely when this nesting occurs. The fix restructured the venue tile to eliminate the illegal nesting.

---

## What Was Built

### Bug documentation added to SSOT (2026-05-16 carry-over)

**File:** `inspo/interactive_v1_feature_spec_SSOT.html`

Two bugs from the previous session were documented in the Fixed Bugs section:

1. **Map container zero-height (Critical)** — `#main-content` had no classes in `layouts/app.blade.php`, breaking the flex chain needed for Leaflet to have a non-zero rendering area. All markers were rendering into a 0×0 pixel container and were therefore invisible. Fixed via a scoped `@push('head')` style block in `discovery-page.blade.php`.

2. **`applyBestSort()` SELECT reset (Medium)** — `DiscoveryVenueQuery::applyBestSort()` called `->select('venues.*')` before adding diversity subqueries. This reset the SELECT clause and wiped the `products_count` and `drinks_count` columns added by `withCount()`. Every venue showed 0 products on map pins when the "best" sort was active.

### "Na mapie" button navigation bug — fixed

**File:** `resources/views/components/venue-tile.blade.php`

**What was wrong:** Clicking "Na mapie" on a venue card was correctly zooming the map to the venue's location (the `flyTo` animation played), but then also navigating to the venue detail page. This was not intended — "Na mapie" should only show the pin on the discovery map without leaving the page.

**Root cause (after two attempts):** The venue tile used an `<a href="...">` as its outer wrapper (making the whole card a link), with `<button>` elements inside it for "Na mapie", "Nawiguj", and "Save". Nesting `<button>` inside `<a>` is invalid HTML — interactive elements cannot be nested inside anchor elements per the HTML specification. Some browsers (especially Safari and WebKit-based) handle this by processing the `<a>` navigation at the browser's input event level, before JavaScript event dispatch begins. This means calling `event.stopPropagation()` inside the button's click handler has no effect — the browser has already committed to navigation before any JavaScript runs.

**First attempt (did not work):** Added `@click="$event.target.closest('button') && $event.preventDefault()"` to the outer `<a>`. This would have caught the event on the `<a>` side and called `preventDefault()`. However: if `stopPropagation()` on the button DOES work, the `<a>` never receives the event and `preventDefault()` is never called (no navigation, but the fix is irrelevant). If `stopPropagation()` DOES NOT work (the actual bug), the `<a>` receives the event but the browser had already committed to navigation at the input level — `preventDefault()` is too late.

**Actual fix:** Removed the `<a>` wrapper entirely. The outer element is now a `<div>` with an explicit Alpine `@click` handler that handles navigation for non-button/non-link clicks:

```html
<div
    @click="!$event.target.closest('button, a') && (window.location.href = '...')"
>
```

Logic:
- Click on "Na mapie" button → `@click.stop` on the button fires, propagation stopped, `div` never sees the click. Even if propagation fails, `closest('button')` returns truthy and `window.location.href` is not set.
- Click on "Nawiguj" button → same as above, `window.open` handles Google Maps redirect.
- Click on the venue name link (now a proper `<a href="...">`) → `closest('a')` returns truthy, div's handler skips navigation, the `<a>` handles it natively. Right-click "Open in new tab" preserved on the name.
- Click on card body (category chips, freshness indicator, type badge) → `closest()` returns null, `window.location.href` fires, card navigates.

The CSS (`.venue-item`) and JS impression tracking (`querySelectorAll('.venue-item')`) both use class selectors, so the tag change from `<a>` to `<div>` has no downstream impact.

## Business Impact

The "Na mapie" bug was a usability problem on the discovery page's most important interaction surface — the venue list. Users who are evaluating multiple venues typically scan the list, then click "Na mapie" to locate a venue on the map before deciding to visit. If that click unexpectedly leaves the discovery page, the user loses their scroll position, their active filters, and the mental context of which venues they were comparing. This friction reduces map engagement, which is one of the page's differentiating features over a static list. The fix restores the intended flow: browse list → locate on map → navigate or visit profile.

## Session 2 — Discovery Map Developer Documentation

### Session Overview

**Goal:** Build a set of learning documents that explain the discovery map system to a developer who is intermediate in PHP/Laravel, intermediate in JavaScript (but weak on async), and a complete beginner in Livewire, Alpine, and Filament. Documents needed to be mobile-readable. User then asked to consolidate all docs into a single self-contained interactive HTML file using React.

**Outcome:** Eight files created in a new `learning/` directory — seven markdown documents covering every major subsystem of `/mapa`, plus a self-contained interactive HTML app that presents all seven chapters as a polished mobile-first learning tool. The HTML file has zero local dependencies (everything from CDN) and can be opened directly on a phone.

---

### What Was Built

#### `learning/` directory — new

Created from scratch. Contains all developer education material for the discovery map.

---

#### `learning/01-overview.md`

**What:** The Big Picture. Explains the three-layer technology stack (Livewire/Alpine/Leaflet), what each file does, the concept of two parallel venue representations (list vs map), and the complete request lifecycle when a filter changes.

**Why:** A beginner in Livewire needs a mental model before reading individual files. This doc answers "why does changing a PHP property update both the list and the map?" without requiring the reader to trace code.

---

#### `learning/02-data-flow.md`

**What:** Traces a venue from the database row to a Leaflet pin in five steps: query → shape for JS → embed in page globals → Alpine reads globals → re-sync on filter changes via Livewire event.

**Why:** The two-data-set pattern (Eloquent collection for the list, slim PHP array for the map) is non-obvious and confuses beginners. This doc explains why the split exists and where the 500-venue cap lives.

**Key facts documented:**
- `DiscoveryVenueQuery` always loads `products.category`, `drinks`, `city`, `districtRelation` with the query
- `DiscoveryMapData::forVenues()` caps at 500 venues and produces the JS-friendly array
- `@js(...)` Blade helper JSON-encodes PHP values safely for inline scripts
- The `venues-updated` Livewire event is dispatched on every `render()` and is how Alpine learns about filter changes

---

#### `learning/03-filters-and-livewire.md`

**What:** Full explanation of Livewire state management for the discovery filters. Covers: public properties, the `#[Url]` attribute, `wire:model.live`, `wire:model.live.debounce.300ms`, the `updated*()` hooks pattern, the `DiscoveryFilters` value object, how each filter type maps to a SQL clause, the three sort modes (best/name/nearest) and their SQL, and why cities/districts don't use `#[Url]`.

**Why:** Livewire is invisible to beginners — it feels like magic. This doc demystifies every step from "user clicks a checkbox" to "SQL WHERE clause changes."

---

#### `learning/04-map-markers-and-clustering.md`

**What:** Explains Leaflet `divIcon`, the marker cluster group configuration, and the three-step process for creating one marker (category selection logic, pin HTML construction, adding to the cluster lookup dict).

**Why:** The category priority logic — "which category shows on the pin?" — is the most non-obvious piece of JS in the whole project. When a filter is active, only filtered categories are candidates; among those, the one with the highest product count wins. This behaviour is undocumented anywhere else.

**Key facts documented:**
- `this.markerMap` is the central lookup dict `{ venueId: LeafletMarker }`
- Tooltips are desktop-only (bound with `bindTooltip`, skipped on mobile)
- `fitBounds` is skipped on mobile when the map view is active to prevent the map jumping while the user browses it

---

#### `learning/05-interactivity.md`

**What:** Documents every interactive behaviour: hover highlight (CSS filter on the Leaflet marker DOM element), card click → map focus (desktop: `flyTo` + popup; mobile: switch view + `panTo`), pin selection state, the cluster animation edge case (re-apply `venue-pin--selected` class after `animationend`), the `closest('button, a')` card click guard, and card impression tracking via `IntersectionObserver`.

**Why:** The hover highlight implementation is surprising — it reaches into the Leaflet DOM directly and applies a CSS `filter` property, bypassing React/Alpine reactivity entirely. The cluster animation edge case is the kind of thing that only makes sense once you understand that a cluster "exploding" is an animation that creates DOM elements mid-flight.

---

#### `learning/06-url-management.md`

**What:** Explains the two-mechanism URL system: `#[Url]` for simple query string filters vs `history.replaceState` for cities/districts. Covers why cities need clean path segments (`/mapa/warszawa`) that `#[Url]` can't produce, the full `syncUrl()` → Alpine event → `syncDiscoveryUrl()` → `replaceState` flow, how `mount()` reads cities/districts on page load with input validation, canonical URL strategy for SEO, and why bounds are intentionally not URL-persisted.

**Why:** The split mechanism is a genuine design decision that looks like inconsistency until you understand the SEO rationale. This doc prevents a future developer from "simplifying" city handling into `#[Url]` and breaking the canonical URL structure.

---

#### `learning/07-alpine-component.md`

**What:** Explains Alpine.js itself from scratch for a beginner: what it is, how `Alpine.data()` registration works, where `x-data="discovery()"` hooks into the Blade template, the full state object structure, a table of all Alpine directives used in the project, the `init()` startup sequence, `$nextTick`, bidirectional communication with Livewire (`$wire` for Alpine→PHP, `dispatch` for PHP→Alpine), the mobile view toggle and `invalidateSize()`, and how inline `x-data` components work for the dropdowns.

**Why:** Alpine is the layer that beginners most often want to skip or treat as magic. This doc explains every `@click`, `x-show`, `x-ref`, and `x-model` used in the discovery page without requiring any prior Alpine knowledge.

---

#### `learning/README.md`

**What:** Index file for the `learning/` directory. Lists all 7 docs with one-line descriptions, and suggests a reading path: Docs 1–3 for the server-side picture, Docs 4–5 for map debugging, Doc 6 for URL problems, Doc 7 for list-map communication problems.

---

#### `learning/interactive.html` — self-contained interactive React app

**What:** A single 1,860-line HTML file that presents all 7 chapters as a polished interactive learning experience. Zero local dependencies — all libraries loaded from CDN. Can be opened directly in any mobile browser (Safari, Chrome) without a web server.

**Libraries used (all CDN):**
- React 18 + ReactDOM (unpkg)
- Babel Standalone — compiles JSX in the browser at load time
- Tailwind CSS — utility styling
- marked.js v4 — parses markdown to HTML (v4 chosen over v9 for the `highlight` callback API)
- highlight.js + atom-one-dark theme — syntax highlighting for PHP, JS, HTML code blocks

**Architecture:**
- Each chapter's markdown content is embedded in `<script type="text/markdown" id="chN">` tags — this avoids the need to escape backticks inside JavaScript template literals (the primary reason for this pattern over embedded template literals)
- Three views: Home (chapter card grid), Chapter (reading mode), Search (full-text search)
- All state managed in a single `App` component; no external state library needed

**Interactive features:**
- Chapter card grid on home screen — colour-coded by chapter, with emoji, number badge, and description
- Gradient progress bar in the header (fills as chapters are read)
- Per-chapter reading progress bar (scroll-based, updates in real time)
- Auto-mark-as-read: scrolling past 85% of a chapter marks it read automatically
- Manual "Mark read" button as fallback
- Table of contents extracted from h2 headings — sidebar on desktop, "Contents" dropdown on mobile
- Prev/Next navigation at the bottom of each chapter
- Full-text search across all 7 chapters with excerpt preview and keyword highlighting
- Dark/light mode toggle — respects system preference on first load, overridable
- All read state and dark mode preference persisted in `localStorage`
- Smooth fade-in animations on view transitions
- Card hover lift effect on desktop

**Why CDN-only / self-contained:** The user needs to read this on a phone. A file that works by simply being opened in a browser — with no build step, no dev server, no npm install — is the lowest-friction format possible. AirDrop, email, or Google Drive the file to the phone; open it; done.

**Trade-off accepted:** Babel Standalone compiles JSX at page load time, which adds 1–3 seconds of compile delay on first open. For a reference document that is opened occasionally (not a production app), this is acceptable. If the compile delay becomes annoying, the fix is to pre-compile the JSX using Vite or esbuild and output a static bundle.
