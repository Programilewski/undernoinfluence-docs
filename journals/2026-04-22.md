## What Was Built

### 1. `Venue::scopeNearby` — PostgreSQL HAVING Alias Fix

**File:** `app/Models/Venue.php`

**What:** The scope calculated a `distance_km` alias using the Haversine formula and then used `->having('distance_km', '<=', $radiusKm)` to filter by distance.

**Why this was broken:** PostgreSQL does not allow `HAVING` to reference `SELECT` column aliases in the same query. `HAVING distance_km <= 1.0` would fail at runtime with a "column does not exist" error, even though `distance_km` appears in the SELECT. (This works in MySQL but not PostgreSQL.) The code had never been exercised in production — no venues with coordinates existed yet — so it was a hidden time bomb.

**Fix:** Changed `->having('distance_km', ...)` to `->havingRaw()` using the full Haversine expression repeated. The alias is still assigned in SELECT and used in ORDER BY (PostgreSQL allows aliases in ORDER BY), but the filter now uses the raw expression, which is unambiguous.

```php
// Before (would fail in PostgreSQL at runtime):
->having('distance_km', '<=', $radiusKm)

// After (PostgreSQL-safe):
->havingRaw("(6371 * acos(...)) <= ?", [$lat, $lng, $lat, $radiusKm])
```

**Current state:** Correct and tested. Will run at scale once the first real venue with coordinates is added.

### 2. `VenueController@show` — Nearby Venues Now Capped at 1km

**File:** `app/Http/Controllers/VenueController.php`

**What:** The controller's nearby venues query was hand-rolling the Haversine sort but had no distance filter — it fetched the 5 geographically closest venues regardless of whether they were 100m or 50km away.

**Why:** The spec says "3–5 within 1km." The old code was missing the `within` part. In a dense city like Warsaw, the 1km cap is what makes the section meaningful — "places nearby" should be walkable, not just relatively closer than everything else.

**Fix:** Replaced the inline `orderByRaw` with `->nearby($lat, $lng, 1.0)` using the model scope, then appended `->withCount('products')` after the scope call (so `withCount` appends via `addSelect` rather than clobbering the scope's `selectRaw`).

**Current state:** Correctly scoped. Section will be hidden (`collect()`) for any venue without coordinates, which is the safe default.

### 4. `CategoryController` — `/kategoria/{slug}`

**File:** `app/Http/Controllers/CategoryController.php`

**What:** A single `show` method using implicit route model binding on `Category` by slug. Fetches all active venues that have at least one **fresh** product in the category (confirmed within 90 days), ordered by how many category products they carry.

**Why "fresh only":** The spec is explicit: category pages show venues with ≥1 fresh product. A venue that sold non-alcoholic beer three years ago and stopped should not appear on the Beer page. The 90-day threshold matches the `Venue::freshnessState()` definition.

**Query pattern:**
```php
Venue::active()
    ->whereHas('products', function ($q) use ($category, $freshThreshold) {
        $q->where('category_id', $category->id)
          ->where(fn($q) => $q->whereNull('confirmed_at')
                              ->orWhere('confirmed_at', '>=', $freshThreshold));
    })
    ->withCount(['products as category_product_count' => fn($q) => $q->where('category_id', $category->id)])
    ->orderByDesc('category_product_count')
    ->get();
```

The `category_product_count` alias lets the view show "14 pozycji" next to each venue without a separate query.

**SEO:** Page title is `"Bezalkoholowe {category} w Warszawie | UNI"` — matching the spec exactly, optimised for the search query "bezalkoholowe piwo warszawa" etc.

### 5. `WarsawController` — `/warszawa` and `/warszawa/{district}`

**File:** `app/Http/Controllers/WarsawController.php`

**`index` method (`/warszawa`):**
- Total active venue count, verified count
- Districts grouped and counted via `selectRaw('district, COUNT(*) as venue_count') ... groupBy('district') ... orderByDesc('venue_count')` — no N+1, single query
- All active categories (for the category pills section)
- Empty state handled if no districts exist

**`district` method (`/warszawa/{districtSlug}`):**
- District name is stored as plain text in `venues.district` (e.g., "Śródmieście"). The URL uses `Str::slug()` encoding (e.g., `srodmiescie`).
- On request, all distinct district names are fetched and the one whose `Str::slug()` matches the URL parameter is selected. This avoids storing slugs separately while keeping URLs clean.
- Throws `NotFoundHttpException` (→ 404) if no matching district exists. This is important for SEO — Google must not index arbitrary `/warszawa/anything` URLs.
- Venues in the district sorted by product count descending.

## Decision Register

### District URL strategy — slug-from-string vs stored slug column

- **Chosen:** Compute `Str::slug($district)` at runtime, match URL param against slugged district names fetched from DB
- **Rejected option A:** Add a `district_slug` column to the venues table with a migration
- **Rejected option B:** Hardcode a district name→slug map
- **Why:** The district field is a free-text string. Adding a slug column means migration, backfill, and admin form changes. For a V1 Warsaw-only app with ~20 districts, runtime computation costs one extra query (fetch distinct districts) which is tiny. If district names stabilise and SEO traffic grows, a dedicated slug column can be added later with a migration. Status: **revisit post-V1** if the district list grows large or performance becomes an issue.

### Freshness filter on category pages — `whereNull OR >= threshold` vs always-null = stale

- **Chosen:** `WHERE confirmed_at IS NULL OR confirmed_at >= 90-days-ago` — i.e., null is treated the same as fresh
- **Rejected:** `WHERE confirmed_at >= 90-days-ago` — would exclude all products with no confirmation date
- **Why:** Products added by admin with no `confirmed_at` are a data entry shortcut, not evidence of staleness. Excluding them would make new venues invisible on category pages the moment they're added, before any freshness cycle runs. This matches the `Venue::freshnessState()` logic where `null → 'expired'` but is intentionally more lenient for category page eligibility. Status: **revisit** when the 90-day cycle runs and we have real data.

### Controller vs route closure for data-loaded pages

- **Chosen:** Route closure for homepage (simple, two queries), dedicated controllers for category and Warsaw pages
- **Rejected:** Dedicated HomeController
- **Why:** The home route is already a closure. Adding a controller for two lines of query code would be over-engineering with no benefit. The pattern in this codebase is closures for simple/static pages, controllers for pages that need meaningful logic. Category and Warsaw pages have enough query complexity to warrant a controller. Status: **permanent pattern for V1**.
