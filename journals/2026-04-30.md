## The 12 Discrepancies Found

Here's a founder-friendly summary of each gap, ordered by severity:

### Stale or contradictory documentation (fix the docs)

1. **SCORING.md still describes Gold/Silver/Bronze badges** — but ADR-004 already decided on a binary checkmark. Anyone reading SCORING.md without also reading the ADR would plan for three tiers that aren't coming. The doc needs a "superseded" note or a rewrite.

2. **SCORING.md says `confirmed_at` column is missing** — but it was already added in the April 22 migration. The doc is outdated. (However, `confirmed_source` truly is missing — that part is correct.)

### Spec exists, implementation is a placeholder or wrong

3. **Breadth bars are too simple** — the spec says bars should reflect brand diversity and product variety. The code just multiplies product count by 25 and caps at 100. A venue with 4 identical beers from the same brand fills the bar to 100%, which defeats the purpose.

4. **Breadth bars don't filter by availability or freshness** — the spec says only available, non-stale products should count. The code counts everything, including products marked as unavailable and products not confirmed in over a year.

5. **Breadth cap is 4, spec says 5** — the multiplier is 25 (so 4×25=100%), but the V1 spec says the bar should cap at 5 products. Either the code or the spec needs to change.

6. **Two category names don't match** — the V1 spec uses "Destylaty" and "Koktajle" (Polish). The code uses "Spirits" (English) and "Drinki" (informal Polish). For a Polish-facing platform, the naming should be consistent and deliberate.

### Spec exists, nothing is built

7. **Districts are free text** — `venues.district` is a plain string. No districts table, no city scoping, no slugs. Two cities with the same district name (e.g., "Stare Miasto" in both Warsaw and Kraków) can't be distinguished. Blocks pSEO routes like `/warszawa/mokotow/piwo`.

8. **Custom drinks have no schema support** — the vault has a full spec (photo gate, venue ownership, verification flow) but the code has zero infrastructure: no `is_custom` flag, no `venue_id` on products, `brand` is NOT NULL so custom drinks can't even be stored properly. The only "custom drink" indicator is a fragile check for the word "receptura" in the brand field.

9. **Credibility score is fully specced but not built** — the vault defines a 0.00–1.00 score with 5 weighted inputs, a configurable checkmark threshold, and nightly recalculation. None of this exists. The current verified checkmark is a manual admin toggle with no computation behind it. This blocks: automated verification, discovery page default sort, and the future B2B owner dashboard.

10. **URL structure doesn't match spec** — the spec says `/warszawa` for discovery and `/warszawa/lokal/{slug}` for venue profiles (SEO-friendly, city-scoped). The code uses `/venues` and `/venues/{slug}`. This must be decided before Google indexes the site.

11. **Freshness thresholds are hardcoded in 8 places** — the 90-day "fresh" and 180-day "stale" numbers are scattered across models, controllers, Filament components, and templates. No config extraction. One change requires editing 8 files.

12. **User flagging is fully specced but not built** — the vault describes a sophisticated system where users can flag products as unavailable, with silent activity-based flag weighting to prevent abuse. No model, no UI, no routes. Depends on user registration being built first.

## Open Questions

1. **Breadth cap: 4 or 5 products?** The code caps at 4 (multiplier 25), the spec says 5. Which is the correct product count for a "full" breadth bar? This affects how generous the bars look — 4 is stricter, 5 is more forgiving.

2. **Category names: Polish or English?** "Spirits" is English, "Drinki" is informal Polish. The V1 spec used "Destylaty" and "Koktajle" (formal Polish). For a Polish-facing platform, should all categories use formal Polish names?

3. **URL structure: decide before launch.** `/warszawa/lokal/{slug}` (spec) vs `/venues/{slug}` (current). This is a blocking decision — once Google indexes the URLs, changing them is painful.

4. **Districts normalisation: bundle with other schema work?** Creating a `districts` table, custom drinks schema changes, and `confirmed_source` column could all go in one migration batch — or be done incrementally. What's the preference?

## Learning Path

### For this session's work

- **ADRs (Architecture Decision Records):** A lightweight format for recording significant design decisions. Each ADR captures the context, decision, and consequences. UNI's vault has 8+ ADRs in `inspo/UNI-Obsidian-Vault/uni-vault/decisions/adr/`. The key insight: ADRs supersede earlier specs. When SCORING.md says "Gold/Silver/Bronze" but ADR-004 says "binary," the ADR wins.

- **Spec drift:** The natural phenomenon where documentation and code diverge over time. Especially common in early-stage projects where decisions are made quickly and docs aren't updated. The discrepancy report is a point-in-time snapshot of spec drift — it'll need refreshing as items get resolved.

- **Schema normalisation:** The districts issue (Discrepancy #7) is a classic normalisation problem. "Stare Miasto" as a free-text string works fine until you have two cities with the same district name. A separate `districts` table with a `city_id` foreign key eliminates the ambiguity. The tradeoff is slightly more complex queries (a JOIN instead of a WHERE) but much cleaner data.
