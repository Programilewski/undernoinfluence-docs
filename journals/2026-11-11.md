### The sourcing pipeline, step 3, commits 1 and 2

| Commit | What it does, in plain words | Where |
|---|---|---|
| **1 — fetching** | `php artisan uni:fetch {url}` fetches one menu as "UNIbot" and files it under the venue's candidate. ## What Was Built

### Commit 3 — the menu library and the reading (the extraction call)

**What:** a new admin screen, **Biblioteka menu**. *Pobierz z sieci* fetches up to five menu URLs (replacing the `uni:fetch` command, removed at Paweł's request). *Wyodrębnij* (on one menu or several) queues a job that sends the menu's text and page images to `claude-haiku-5-5` **twice in parallel** (decision 14), asks for the §6 schema as structured output, pairs the two readings line by line, and stores the result. Each reading's model, tokens, cost and notes are kept; the confirmation shows the cost per menu measured so far. **Where:** `ReadMenuAction`, `AnthropicMessages` (raw HTTP through Laravel's client, API version `2026-10-21`), `MenuReadingPrompt`, `MenuReading`, `MenuReadingComparison`, job `ReadMenu`, the `MenuSources` admin resource, new tables `menu_extractions` and `menu_lines`. **Why:** it is the step that turns a PDF into lines a person can approve. **Details that matter:** the system prompt says the menu is a third party's data, never instructions (prompt injection); a refused reading is retried once on `claude-sonnet-5-5` because Haiku has no server-side fallback; a menu that would exceed 100K tokens is refused before it is sent (above that Haiku costs 5×); unbranded lines and smoothie-type drinks are dropped (decisions 1 and 2) unless one reading kept them, in which case the line stays with both readings shown. **Live:** Semolino and Tygmont, ≈ $0.005 per menu, 27 s for both; the first run's "disagreements" were mostly "0.0%" vs "0,0%" — the comparison now treats those as equal, and a re-read showed only real differences ("Lech Limonka" vs "Lech Free Limonka"; Żywiec split into two lines by one reading, one line by the other). **Queue fix:** the database queue re-offered a job after 90 s and two workers run, so a long reading would have been paid twice; `retry_after` is now 900 s, and a shared rule records it (`.ai/rules/jobs.md`).

### Commit 4 — matching each line to the catalogue

**What:** every line goes through the catalogue's own resolver (no second matcher) and gets one of: a certain product (a confirmed spelling or a unique exact name), suggestions, a product missing from a known brand, an unknown brand, a brand without a product, or a house drink. Each menu gets a verdict: *Kwalifikuje się* / *Tylko sugestie* / *Nic nie kwalifikuje*. A new list, **Pozycje z menu**, shows every line across menus; filtered to *Nieznana marka* and grouped by brand it is the brand queue. *Dopasuj ponownie* re-matches after the catalogue changes. **Where:** `MenuLineMatcher`, enums `MenuLineMatch` and `MenuVerdict`, the `MenuLines` resource; `has_price` added to the reading schema. **Why:** a line is only useful once UNI knows which product it is — and the worst error this product can make is matching a menu's alcoholic "Heineken" to Heineken 0.0. **Live:** Semolino qualifies on its two house drinks, its beers wait as unknown brands (Peroni, Książęce); Tygmont has only suggestions, Heineken 0.0 proposed first by the model.

### Commit 5 — the approval screen

**What:** a menu's page is where it is decided. *Utwórz lokal* creates the venue from the address typed there and places it with **GUGiK** (inactive until the activation gate switches it on); *Powiąż z lokalem* links an existing one. Each line: **Zatwierdź** (writes through `RecordMenuItemAction`, the same path as hand entry, with the menu's page and fetch date as the source), **Popraw** (pick the product — the printed spelling is saved as a confirmed alias so the next menu matches by itself, and a product whose strength the menu doesn't print is refused — or rewrite the house drink and link the recipe it is built on), **Odrzuć** (kept, with the reason). *Zatwierdź pewne* (Ctrl/Cmd+Shift+A) approves every line that is priced, certainly matched, and agreed by both readings. *Odrzuć lokal* rejects the candidate with a reason — "Nazwa lokalu to marka alkoholu" among them (decision 11) — deletes its menu files (decision 6) and rejects its waiting lines. *Otwórz menu* (Ctrl/Cmd+Shift+O) opens the private file through an admin-only address; a fetched web page is served sandboxed so its scripts never run with UNI's origin. **Where:** `DecideMenuLineAction`, `SourcingVenueAction`, `MenuFileController` + route `/admin/menu-sources/{id}/plik`, the menu page's actions. **Why:** ADR-012's central rule — nothing publishes itself — lives here.

### Commit 6 — `/bot` and the privacy policy

**What:** the public page UNIbot's User-Agent names: what it reads, that nothing is published before a person checks it, what it obeys (robots.txt under `UNIbot`, the TDM opt-out), what it keeps, how to block it; with a short English section. `bot` added to the reserved paths in the same commit (the support rule). The privacy policy (still a draft) gains the menus UNIbot reads and **Anthropic as a recipient** (menu text only, never users' data). **Why:** ADR-012 requires a named bot with a page and a policy paragraph before the first bulk run.

### Commit 7 — finding the menu from a venue's page (step 4)

**What:** *Znajdź menu na stronie lokalu* reads the page and the site's `sitemap.xml`, collects links that name a menu, follows the best menu page one level down for the files it links, and ranks: drinks before food, a file before a page, the newest first. It fetches only a convincing result; a weak guess is listed, not fetched. Dates are read from the file's address with the prototype's rules and its listed bugs fixed (a domain like `maj.pl` is not May; `202506` is read; "2025-26" gives 2026; image sizes and ten-digit ids are not dates). **Where:** `MenuFinder`, `MenuLink`, `MenuDate`, `FindMenuAction`. **Live:** from Semolino's Woronicza page it found the **May 2026** menu — newer than the 2025 file fetched on 11.11. From Semolino's homepage it finds nothing useful: Semolino is a chain of six, and its "Zobacz menu" links go to an ordering platform.

### Commit 8 — Brave source A (step 5)

**What:** a new list, **Kandydaci**, with *Szukaj lokali (Brave)*: choose query templates and districts (at most 30 searches a run), queued. Each result gives only a domain; it is dropped if blocked (shops, delivery, social, reviews, press, producers', government and university sites), already known (any candidate, rejected included, or a listed venue's site), or if its homepage shows no Warsaw address or phone. What remains becomes a candidate holding only the domain and UNIbot's own homepage address — nothing of Brave's result is stored, as its terms require. Runs are listed in **Wyszukiwania** as counts. *Znajdź menu* runs per candidate or in bulk and writes the outcome on the candidate. **Real-site test (5 searches):** 39 results, 22 domains, 8 verified candidates, **4 of them venues** (The Exchange, Dom Whisky, the InterContinental, Crowne Plaza's The HUB); the others were a brewers' association, a beer federation, a `.ua` site and a university. Menu picks: right at The Exchange (*Drinks.pdf*) and Dom Whisky (cocktail menu); **wrong** at both hotels (a kids' menu, a half-board food menu), and bar photos counted as menus. Fixed and tested: kids'/half-board/breakfast/lunch/event menus are excluded, an image must name a menu itself, and the address check reads the footer (where venues print it — the first version missed it).

### Commit 9 — the refresh (step 6)

**What:** *Odśwież* (one or several menus) and a weekly job (Mondays 04:30, up to 50 approved venues' menus not checked for four weeks). The venue's page is read again, not just the old file, so a replaced PDF is noticed. Same file, or a page whose text did not change → only the date is renewed. A new file → replaces the old one, is read again, its lines go to approval. A page that no longer answers → flagged "lokal mógł zostać zamknięty", file kept. A site that now refuses UNIbot → its file is deleted. **The diff:** lines already on the venue's offer show *W ofercie* (approving them renews the date checked); *Zniknęło z karty (N)* lists items listed from this menu that the new reading no longer has, and removes them from the offer only when Paweł chooses — items from other sources (the owner, another menu) are never offered for removal, and a failed reading proves nothing vanished. **Where:** `RefreshMenuAction`, `MenuOfferDiff`, jobs `RefreshMenu` and `QueueMenuRefreshes`.

## Business Impact

**Speed to launch:** the ~30 venues needed for launch no longer have to be typed by hand from scratch: the pipeline finds candidates, finds and reads their menus and matches them, and the remaining work is approving. Measured: about $0.005 to read a menu twice; a Brave search finds a handful of verified candidates. **Trust:** every public fact still passes through Paweł; the matching refuses the one error that would hurt most (an alcoholic beer shown as 0%); the bot is named, explained and easy to block, as ADR-012 promised. **Retention of data quality:** the weekly refresh keeps approved menus current and flags venues that may have closed — the freshness promise on venue pages now has a machine behind it. **Cost:** Haiku ≈ $2.50 per 1,000 menus read twice at today's size; Brave per search; no new fixed cost.
