**Preserved from old migrations — everything that mattered:**
- All 18 PostgreSQL CHECK constraints (coordinates, breadth_score, venue_type, source, plan, role, abv, abv_status, abv_status_value, country_code, claim status/type/method/role, inaccuracy status, added_by, stats non-negative, visit confirmed_at pair, auditable pair, feature flags feature/reason)

- All composite indexes (is_active+is_canary, category+active+approved, etc.)
- FK semantics: `restrictOnDelete` for city, category; `nullOnDelete` for claimed_by, district_id, producer, reviewed_by; `cascadeOnDelete` for venue_products, claims, drinks, stats, visits

**What was removed (intentionally):**
- Tags/product_tag tables (created in April, dropped weeks later — net effect was zero)
- All intermediate ALTER TABLE, rename, and data mutations that represented the path to the current state, not the state itself
- Category data mutations (5 separate migrations) — replaced by the already-existing `CategorySeeder`

**One bug hit during migration:**
PostgreSQL does not auto-create FK indexes (unlike MySQL). Chaining `->constrained()->restrictOnDelete()->index()` in a single column definition caused a "duplicate constraint" error where Laravel generated the same anonymous constraint name twice for multiple FK columns in the same `Schema::create` block. Fixed by moving all explicit `$table->index()` calls to the end of the create block, keeping them separate from `->constrained()` chains.

## Learning Path

**Why does PostgreSQL need explicit FK indexes?**
MySQL auto-creates an index for every foreign key. PostgreSQL does not. This is why the old code had a separate `add_missing_indexes_to_venues_table` migration. In the clean squash, all indexes are declared explicitly at table creation time.

**What is a partial unique index?**
A standard unique index enforces uniqueness across all rows. A partial unique index enforces uniqueness only within a subset (e.g. "only one pending claim per venue"). PostgreSQL's `WHERE` clause on `CREATE UNIQUE INDEX` makes this possible. It is not expressible in standard Laravel Blueprint syntax — must be written as a raw `DB::statement`.

**What is a schema dump and why does it matter?**
`php artisan schema:dump` writes the current database schema to `database/schema/pgsql-schema.sql`. On a fresh install, Laravel loads this file first (a single fast SQL execution) and then runs only the new migrations that arrived after the dump. This makes CI cold starts much faster than running every migration from scratch. The dump must be regenerated after squashing or it will encode an outdated state.

#### `resources/css/app.css` + `resources/css/design-system.css` — dark mode text + font

**What changed:** `--fg` in the dark mode block changed from a dimmed off-white to `#ffffff` (pure white). `--font-sans` in design-system.css changed from `'Inter'` (which was never loaded via Bunny Fonts) to `'Alexandria'` (which was already loaded and displayed correctly).

#### Bug Fix 1 & 2 & 3 — Three deleted files calling non-existent routes

**What changed:** Three PHP files were permanently deleted:
- `app/Notifications/ResetPasswordNotification.php`
- `app/Notifications/VerifyEmailNotification.php`
- `app/Http/Controllers/Concerns/InteractsWithIntendedUrl.php`

**Why this mattered:** The v1 branch stripped all public auth routes (login, register, password reset, email verification). These three files were left behind, each calling routes that no longer exist. The notification files would crash the queue worker with a `RouteNotFoundException` any time something triggered a password reset or email verification request — for example, an admin-panel operation or any code that called `$user->sendPasswordResetNotification()`. **Current state:** No dead notification files in the codebase. Queue worker can no longer crash from a route lookup in a notification class.

#### Bug Fix 4 — $topCategorySlugs accordion priority corrupted by sort

**What changed:** `resources/views/venues/show.blade.php` — removed `->sortByDesc('count')` from the `$topCategorySlugs` derivation.

**Why this mattered:** `VenuePresenter::accordionCategories()` sorts categories with piwo=priority 0, drinki=priority 1, everything else by count. This means piwo is always first, drinki always second — reflecting their business importance as the two most recognisable NA drink categories. The view was then re-sorting by count, which would silently push drinki out of the top-3 auto-expanded set whenever another category (e.g. wino) had more items. A venue with 8 wines and 3 cocktails but only 2 custom drinks would open the wine accordion by default instead of drinki — wrong priority from a product standpoint.

**Current state:** The first 3 categories in `accordionCategories()` display order are now auto-expanded. Piwo and drinki always appear in the top 3 if they have any products.

#### Bug Fix 5 — Nearby venues "napojów" count excluded custom drinks

**What changed:**
- `app/Http/Controllers/VenueController.php`: `->withCount('products')` → `->withCount(['products', 'drinks'])`
- `resources/views/venues/show.blade.php`: `{{ $nearby->products_count }} napojów` → `{{ $nearby->products_count + $nearby->drinks_count }} napojów`

**Why this mattered:** Custom drinks live in the `venue_drinks` table, not in the `venue_products` pivot. A venue that had only house cocktails (zero catalog products) would show "0 napojów" in the nearby strip even though it had a full drinks menu. This was a data accuracy issue, not a visual bug — the wrong number was shown.

#### Bug Fix 6 — window.__capture() without optional chaining

**What changed:** `resources/views/venues/show.blade.php` — `window.__capture('venue_viewed', {...})` → `window.__capture?.('venue_viewed', {...})`

**Why this mattered:** `window.__capture` is set by `analytics.js` if PostHog loads. With PostHog config-gated off (the default), the variable is undefined. Calling an undefined function throws a `TypeError` in the browser console — a visible JavaScript error on every venue profile page load, for every visitor, in the default production configuration.

#### Bug Fix 7 — "Pełna mapa" link bypassed analytics redirect

**What changed:**
- `app/Http/Controllers/VenueRedirectController.php`: added `'maps'` to the allowed type list and a `resolveUrl()` case that builds the Google Maps search URL from venue lat/lng
- `resources/views/venues/show.blade.php`: hardcoded Google Maps URL → `route('venues.redirect', [$venue->slug, 'maps'])`

**Why this mattered:** Every outbound link from a venue profile (Nawiguj, website, Instagram) routes through `VenueRedirectController`, which increments `VenueStat` counters and writes to the `events` table. The "Pełna mapa" link was a bare hardcoded URL that bypassed the entire analytics stack — map link clicks were completely invisible to the analytics system. Now they are tracked.

#### Bug Fix 8 — $totalProducts out of scope in OG meta tag

**What changed:** `resources/views/venues/show.blade.php` — added `@php $totalProducts = $venue->products->count() + $venue->drinks->count(); @endphp` immediately before `@push('meta')`. Removed the duplicate definition from the later `@php` block.

**Why this mattered:** In Blade, `@push` blocks are evaluated eagerly in file order. `$totalProducts` was defined 34 lines after `@push('meta')` used it. The result: the OpenGraph description tag for every venue profile showed "0 napojów" in social media previews (Facebook, Twitter, WhatsApp link previews). Every venue looked empty when shared. This had been broken since the OG tag was added.

#### Bug Fix 9 — House recipe detection inline in Blade template

**What changed:**
- `app/Models/Brand.php`: added `public function isHouseRecipe(): bool` — `str_contains(mb_strtolower($this->name ?? ''), 'receptura')`
- `resources/views/venues/show.blade.php`: replaced inline string match with `$product->brand?->isHouseRecipe() ?? false`

**Why this mattered:** The rule "a brand name containing 'receptura' identifies a house recipe product" is a business rule. Having it inline in a Blade template meant it could only be found by reading the template, couldn't be tested independently, and would need to be duplicated if the same check was ever needed elsewhere (e.g. in an export or an API). Moving it to the model gives it a single canonical home.

#### Bug Fix 10 — SVG category icons rendered without sanitization (stored XSS)

**What changed:** `app/Support/VenuePresenter.php` — added `private static function sanitizeIcon(string $svg): string` and applied it in all three locations where `display_icon` is accessed (`categoryRows()`, `accordionCategories()` map closure, and the drinks-only fallback `array_splice` block).

The sanitizer strips `<script>` blocks via regex and removes `on*="..."` event handler attributes:
```
<script\b[^>]*>.*?<\/script>  →  removed
\s+on\w+="[^"]*"              →  removed
```

**Why this mattered:** Category icons are SVG strings stored in the database by admins (via the Filament admin panel) and rendered with `{!! $icon !!}` (unescaped) in three public Blade templates. A malicious or compromised admin account could set a category icon to an SVG containing a `<script>` block or an `onclick` event handler. This would constitute stored XSS — the injected script would execute in every visitor's browser on every page that displays venue categories (venue tiles, venue profiles, map popups). The admin panel is the attack surface; the risk is a compromised admin credential, not an external attacker who can't write to the DB.

**Implementation note:** No new dependencies were added (CLAUDE.md constraint). The sanitizer is applied at the data-preparation layer in VenuePresenter so all callers (tile, show page, map popup) are covered automatically — no per-template changes needed.

### Business Impact

**Stored XSS closed before launch.** The SVG injection surface wasn't theoretical — it was a real attack path for a compromised admin account. Fixing this before the first real users arrive means the product's security baseline is solid. A post-launch XSS discovery in a food/drink discovery app would be a trust-ending event.

**Social sharing now works correctly.** Every venue profile shared before this fix showed "0 napojów" in the preview card (Facebook, WhatsApp, iMessage link previews). This is the first point of contact for many users who find UNI via a shared link — seeing "0 napojów" before clicking suggests the venue page is empty. Fixed before any real traffic arrives.

**Analytics complete for outbound map clicks.** The "Pełna mapa" link is the highest-intent action on a venue profile — a user who clicks it is almost certainly going to the venue. That intent signal is now captured alongside website and Instagram clicks, completing the outbound engagement picture for the analytics stack.

**Dead code cleaned up before production.** Three files that would have crashed the queue worker are gone. A crashed queue worker in production would silently drop analytics events, notifications, and any future background jobs without visible errors — the kind of failure that's hard to diagnose.
