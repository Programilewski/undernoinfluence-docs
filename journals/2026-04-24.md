## What Was Built

### 1. `is_canary` Migration — `database/migrations/2026_04_24_072722_add_is_canary_to_venues_table.php`

**What:** Adds a `boolean is_canary DEFAULT false` column to the venues table, positioned after `is_active`. Fully reversible with `dropColumn` in `down()`.

**Why:** Canary venues (fictional honeypots for detecting data scraping) were stored in the database with `is_active = true` and no distinguishing flag. This meant they appeared in the public discovery page, category pages, the sitemap, and the claim form's venue selector. The sitemap was actively submitting canary URLs (`bezalkohol-spolka-uni-canary-1`, etc.) to Google for indexing — a serious problem because Google would index fictional venues as real. Adding a dedicated `is_canary` boolean lets a single change in `scopeActive()` propagate exclusion to every public query without touching any other file.

**Current state:** Migration applied. Both canary venues have `is_canary = true` set by the CanarySeeder.

---

### 2. Venue Model — `scopeActive()` Updated — `app/Models/Venue.php`

**What:** Added `->where('is_canary', false)` to the `scopeActive()` scope. Also added `'is_canary' => 'boolean'` to the model's `casts()` array.

**Why this is the right place to put the guard:** `scopeActive()` is the single query constraint called by every public-facing feature — the discovery page, category pages, the sitemap, the venue show controller, and the claim form's venue select. Putting the canary exclusion here means it propagates automatically to all six sites without touching any of them. This is the safest, most maintainable approach: one change, zero risk of forgetting a call site.

**Before:** `return $query->where('is_active', true);`
**After:** `return $query->where('is_active', true)->where('is_canary', false);`

**Current state:** All public queries now silently exclude canary venues.

### 3. CanarySeeder Updated — `database/seeders/CanarySeeder.php`

**What:** Added `'is_canary' => true` to each canary venue array. Changed `firstOrCreate` to `updateOrCreate` so that existing canary venues already in the production database get the flag set retroactively when the seeder is re-run.

**Why `updateOrCreate` matters:** If the migration runs on a server where the CanarySeeder has already run (canary venues already exist), `firstOrCreate` would find the existing rows but not update them — they'd have `is_canary = false` indefinitely. `updateOrCreate` ensures the flag is stamped on existing rows during the next deploy.

**Current state:** Seeder correct. Any environment re-seeding will correctly mark canaries.

## Decision Register

### `skipOnSqlite()` helper vs creating a PostgreSQL test database

- **Chosen:** `skipOnSqlite(string $feature)` helper that calls `markTestSkipped()` when running on SQLite. The 7 affected tests are skipped cleanly with a descriptive message.
- **Rejected:** Creating a dedicated PostgreSQL test database (`undernoinfluence_test`) in the current environment.
- **Why rejected:** The `undernoinfluence_user` role lacks the `CREATEDB` privilege. Granting it requires a PostgreSQL superuser and a sudo password — not available in the current environment without manual intervention. Skipping is not a permanent compromise: any developer or CI environment running PostgreSQL as the test database will execute all 35 tests. The skips are clearly labelled and won't silently pass on wrong infrastructure. Status: **revisit when CI is configured** — add `DB_CONNECTION=pgsql` to CI to run the full suite.

### `RefreshDatabase` vs `LazilyRefreshDatabase`

- **Chosen:** `RefreshDatabase` to match the existing pattern in the codebase's only pre-existing test file (`ExampleTest.php`).
- **Rejected:** `LazilyRefreshDatabase` (the Laravel best-practices recommendation for speed — only resets the DB if a test actually touches it).
- **Why match the existing convention:** The `laravel-best-practices` skill recommends `LazilyRefreshDatabase`, but the Consistency First rule takes precedence: the codebase already uses `RefreshDatabase`. Introducing a second trait creates inconsistency without a clear benefit at the current test count. Status: **revisit** — if the test suite grows large enough that DB reset time becomes a bottleneck, migrate all tests to `LazilyRefreshDatabase` in one PR.

### Sentinel strings in test venue names vs asserting on model data directly

- **Chosen:** Use unique sentinel strings embedded in venue names (`__BEER__`, `__CANARY__`, `__INSIDE__`) and test with `assertSee`/`assertDontSee` on the rendered HTML.
- **Rejected:** Asserting on PHP collection contents returned by Livewire component data properties, or using database assertions only.
- **Why:** The discovery page renders through a Blade view — the ultimate test is whether the venue name appears in the HTML that users see. Asserting on component data would test internals, not output. Sentinel strings make `assertSee`/`assertDontSee` reliable regardless of what other venues the factory might create with colliding random names. Status: **permanent pattern for all Livewire view tests**.

### Stage D and E together in one pass

- **Chosen:** Write and run Stage D (AdminClaimActionsTest) and Stage E (AuthorizationBoundariesTest) together in one session pass.
- **Rejected:** One stage per session to preserve context.
- **Why:** The stages are thematically related (admin actions + authorization) and small enough (~24 tests combined) that doing them together was efficient without burning excessive context. Status: **no ongoing implication, just session logistics**.

## Learning Path

**For understanding the `is_canary` approach:**
Canary traps (sometimes called "honeypot records" or "copyright canaries") are a standard anti-scraping technique used by mapping services, directories, and datasets. Famous examples: the A-to-Z map company included a fictitious street "Trap Street" in its London maps — any competitor map that showed the same street was provably copying. Yell.com has used fictional business listings for years. The technique works because there is no legitimate source from which a scraper could obtain the canary data — any system that contains it must have scraped UNI. The key is that canaries look real (active, with coordinates, properly named) so scrapers don't filter them out.

**For understanding Filament panel authorization:**
Filament v5 uses the `canAccessPanel(Panel $panel)` method on the user model (via the `FilamentUser` interface) to gate panel access. When a logged-in user fails this check, Filament's `Authenticate` middleware returns a 403 — not a redirect. Redirects to login only happen for unauthenticated (guest) users. This is important to remember when writing tests: `assertForbidden()` for wrong-role users, `assertRedirect('/panel/login')` for guests.

**For understanding PHPUnit 12 data providers:**
PHPUnit 12 removed the `@dataProvider` annotation. You must now use the `#[DataProvider('methodName')]` PHP 8 attribute. The old annotation silently does nothing in PHPUnit 12 — the test method is called once with no arguments, causing an `ArgumentCountError`. The fix is a two-line change: add `use PHPUnit\Framework\Attributes\DataProvider;` at the top and replace `/** @dataProvider ... */` with `#[DataProvider('...')]` above the test method.

### 2. Bug Fix: DiscoveryPage 500 Error — Cache Serialization — `app/Livewire/DiscoveryPage.php`

**What:** Removed two `Cache::remember()` calls that were caching Eloquent Collections into the `database` cache store. The categories and districts queries now run directly on every render.

**Why it broke:** The `database` cache driver serialises values using PHP's native `serialize()`/`unserialize()`. Eloquent Collections carry internal state — event listeners, model observer hooks, and lazy-load closures — that PHP cannot cleanly unserialise. When the cache retrieved a previously-stored Collection, PHP reconstructed an "incomplete object" that crashed on the first method call (`$allCategories->isNotEmpty()` at line 71). Installing `php8.4-intl` likely changed PHP's internal class-loading order just enough to surface this latent bug.

**Why removing the cache is the right fix:** The two queries are trivially fast — 6 rows from `categories`, a `DISTINCT` on `districts`. Caching them saved a few milliseconds at the cost of making the page crash unpredictably on any environment using the database cache driver (which is the default). The risk/reward tradeoff is clear: don't cache Eloquent objects with the database driver.

**Before:**
```php
'allCategories' => Cache::remember('discovery:categories', 300, fn () => Category::...->get()),
'districts'     => Cache::remember('discovery:districts', 300, fn () => Venue::active()->...->pluck(...)),
```
**After:** Direct queries, no cache wrapper.

**Current state:** `/szukaj` returns 200. Categories and districts load correctly on every render.

### 3. Bug Fix: DiscoveryPage Alpine Crash — Self-Referential JS Variable — `resources/views/livewire/discovery-page.blade.php`

**What:** Fixed line 205 from `const __initialVenues = __initialVenues;` to `const __initialVenues = @js($venuesForMap);`.

**Why it crashed:** The Session 2 refactor ("replace 4 separate `@js($venuesForMap)` calls with one constant") introduced a typo: the right-hand side was set to `__initialVenues` instead of `@js($venuesForMap)`. In JavaScript, `const` declarations are hoisted but not initialised — accessing a `const` before its declaration completes is the "Temporal Dead Zone" (TDZ), which throws `ReferenceError: Cannot access '__initialVenues' before initialization`. This error fired before `Alpine.data('discovery', ...)` could register, so Alpine started initialising the DOM but couldn't find the `discovery()` component — producing a cascade of `discovery is not defined`, `currentView is not defined`, and `showSearchAreaBtn is not defined` errors. The entire map, the view toggle, and the filter logic were non-functional.

**Symptoms in the browser:**
- `Uncaught ReferenceError: Cannot access '__initialVenues' before initialization`
- `Alpine Expression Error: discovery is not defined`
- `Alpine Expression Error: currentView is not defined` (×4 occurrences)
- Map pane invisible, FAB button non-functional

**Current state:** The map, view toggle, filters, and all Alpine state initialise correctly.

### 4. Security Fix: Inactive and Canary Venues Accessible via Direct URL — `app/Http/Controllers/VenueController.php`

**What:** Added `abort_if(! $venue->is_active || $venue->is_canary, 404);` at the top of `VenueController@show`.

**Why it was a gap:** Laravel's implicit route model binding resolves a `Venue` by slug using a plain `findOrFail` — it does not apply any scope. `scopeActive()` is a *local* scope called explicitly, not a global scope applied to every query. This meant that anyone who knew (or guessed) the slug of an inactive venue or a canary venue could visit its public profile page and get a 200 response. Canary venues were especially problematic: their entire purpose is to be invisible to the public, but they were publicly accessible via `/miejsce/bezalkohol-spolka-uni-canary-1`.

**Why `abort_if` in the controller rather than overriding `resolveRouteBinding` in the model:** Overriding `resolveRouteBinding` to apply `scopeActive()` would also affect Filament's admin panel, which uses the same route model binding mechanism to load venues for editing. Admins legitimately need to view and edit inactive venues. The controller-level check applies only to the public profile route and leaves admin access intact.

**Current state:** Inactive venues → 404. Canary venues → 404. Active non-canary venues → 200. Admin panel edit pages unaffected.

## Decision Register

### Remove cache vs keep cache with a different serialization approach

- **Chosen:** Remove `Cache::remember()` entirely from the two DiscoveryPage queries (categories, districts).
- **Rejected option A:** Keep the cache but convert the result to a plain PHP array before storing, then `collect()` on retrieval.
- **Rejected option B:** Switch the cache store to `redis` or `file` for these specific calls (both handle serialization more robustly than `database`).
- **Why rejected:** Option A requires Blade template changes (from `->` property access to array access) or a re-collection step on retrieval that adds complexity with no user-visible benefit. Option B introduces a per-call cache-driver override pattern that would be inconsistent and confusing. The queries are fast enough (sub-1ms) that caching them was a premature optimisation. Removing the cache is the simplest correct answer.
- **Status:** Permanent. If categories or districts ever become slow (e.g., hundreds of categories), revisit with Redis and store arrays not objects.

### `abort_if` in controller vs `resolveRouteBinding` override in model

- **Chosen:** `abort_if(! $venue->is_active || $venue->is_canary, 404)` in `VenueController@show`.
- **Rejected:** Override `resolveRouteBinding()` in `App\Models\Venue` to call `->active()` before resolving.
- **Why rejected:** `resolveRouteBinding` is used by both the public routes (`/miejsce/{slug}`) and Filament's admin resource routes (`/admin/venues/{record}/edit`). Applying `scopeActive()` in the model override would prevent admins from editing inactive venues — a legitimate admin operation. The controller-level check is narrower and only applies to the one public route where it belongs.
- **Status:** Permanent for V1. If future routes (API, preview links) also need this guard, consider a dedicated `resolveRouteBinding` with a flag parameter.

### Venue-without-coordinates test removed

- **Chosen:** Remove the `venue_without_coordinates_renders_without_error` test rather than trying to work around the database constraint.
- **Rejected:** Create the venue directly via `DB::table('venues')->insert(...)` to bypass Eloquent model casting and the PostgreSQL NOT NULL constraint.
- **Why:** The NOT NULL constraint on `latitude` and `longitude` is enforced at the database level and is intentional — every venue must have coordinates for the map to work. Testing a state that the schema prohibits would be testing the wrong thing: it would test whether the controller handles a corrupt database row gracefully, not whether the application handles a valid user scenario. If the schema ever changes to allow null coordinates, the test should be written then.
- **Status:** Permanent unless the schema changes.

## Learning Path

**Temporal Dead Zone (TDZ) in JavaScript:**
`const` and `let` declarations are *hoisted* (the engine knows they exist before execution) but not *initialised* (their value is not set). Between the start of the block scope and the declaration line, the variable is in the TDZ. Any access during the TDZ throws `ReferenceError`. This is different from `var`, which is hoisted AND initialised to `undefined`. The self-referential `const __initialVenues = __initialVenues` hits the TDZ because the right-hand side is evaluated before the left-hand side is initialised.

**Why PHP `serialize()` breaks Eloquent Collections:**
PHP's `serialize()` walks the entire object graph and converts it to a string representation. Eloquent Collections contain Eloquent Model instances, which carry closures (event listeners, `with()` constraints, observer callbacks). PHP cannot serialise closures — attempting to do so either throws an exception or silently drops the closure, leaving the object in an inconsistent state on `unserialize()`. When the database cache store retrieves the value and calls `unserialize()`, PHP reconstructs an "incomplete object" for `Illuminate\Database\Eloquent\Collection`. The lesson: never cache Eloquent objects with a PHP-serialising cache driver. Cache raw arrays, IDs, or scalars. Use Redis if you need to cache complex data structures.

**Route model binding and scope isolation in Laravel:**
Laravel's implicit route model binding calls `Model::where($keyName, $value)->firstOrFail()` under the hood. It knows nothing about local scopes like `scopeActive()`. This is intentional — local scopes are opt-in, not automatic. The three ways to restrict route binding: (1) add a global scope to the model (applies everywhere — be careful); (2) override `resolveRouteBinding()` in the model (applies to all routes that bind the model); (3) add an explicit check in the controller (applies to only that controller method). Option 3 is the right choice when different routes need different access rules for the same model.
