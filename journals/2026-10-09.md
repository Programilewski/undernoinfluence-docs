## Decision Register

### 1. The real catalogue reaches production only — **permanent**
**Chosen:** the 35 real venues (and their menus and products) are imported once, on production, through the admin importers; the PC and the home server carry test data built to break things. **Rejected:** rehearsing with the real files on the home server (the 04.10 plan) — it mixes real and invented data in the one place they must be told apart; a seeder and a database copy were already rejected on 04.10. The rehearsal of the order and the messages is `LaunchLoadTest`; the one thing it cannot check, your spreadsheet's column names, is checklist row E7.

### 2. Venues go live through the existing activation gate; "Aktywny" is the manual lever — **permanent (already decided in May, re-confirmed)**
I first proposed a bulk "switch on" action and then a computed readiness scope. Both duplicated `activateIfReady()`/`deactivateIfEmpty()` and the hourly check, which already do exactly what you asked for: automatic in both directions, with `switched_off_at` as the lever. **Rejected:** both of my proposals. Recorded as a lesson: grep the code and the records before proposing a mechanism.

### 3. Every non-live venue returns 404 in V1 — **revisit on a trigger**
**Researched:** Google treats 404 and 410 the same and drops a `noindex` page too, so for search the choices are equivalent; the honest page only helps someone already holding the link. **Considered:** a 200 `noindex` page for an emptied venue ("we can't currently confirm any non-alcoholic drink here") and a "closed" page for a switched-off one. **Chosen:** 404 for all. **Revisit when** Search Console shows venue pages as a large share of landings, or its 404 report lists `/miejsce/` addresses still requested.

### 4. GUGiK is the only geocoder, and it supplies the Warsaw district — **permanent**
**Chosen:** the address register for the point, its cadastre for the district. **Rejected:** Nominatim (ODbL, and it wrote OSM addresses into venues); GUS (dead forward, inaccurate reverse); storing district boundaries for a point-in-polygon check, suggested by another assistant (sound, but more machinery than ~30 lookups need, and OSM boundaries bring back the licence question). That assistant's first claim, that GUGiK's address TERYT carries the district, was checked live and is false.

### 5. A venue serves drinks if it has a Drinki product or any house drink — **permanent**
One rule in two scopes, the SEO counts and the ranking. **Rejected:** keeping per-place definitions; they had drifted into opposites.

### 6. The tile highlight is a trial — **revisit**
Kept in two commits named "Trial:" so `git revert` removes it whole. **Rejected:** a config switch (the 18.09 rule: no visual variant switch reaches production), and the first tinted version (you found it stark). Category colours on the names were rejected for contrast: some are too dark to read as text.

### 7. Scale is After launch, with a trigger of 1 000 live venues — **revisit**
Measured, not assumed: 0.14 s at 85 venues, 0.6 s at 1 000, 1.3 s at 3 000 per load and per filter click, out of memory at 5 000. The fix (paginated tiles, a lean pin query) is described in the backlog row.

### 8. `gh` lives on the PC only — **permanent**
Its single job is the tag guard, which runs on the PC; a GitHub login on a server would be a push-capable credential it never needs.

### 9. Ansible escalates with `sudo.ws` on Ubuntu 26.04 — **revisit when `sudo-rs` and Ansible agree**
**Rejected:** switching the system's sudo back by hand (a manual server change the playbook would not reproduce).

### 10. No demo seeder on deployed servers — **permanent**
`DemoDataSeeder` needs faker, a dev package, and deploys are `--no-dev` like production. The home server gets test data by hand and through the importers. **Rejected:** dev packages on the home server (it would stop rehearsing production) and rewriting the seeder without faker (real work for data you said you would rather add yourself).

## Learning Path

- **SSH keys, agents and config:** a key pair is a private file and a `.pub` file; the agent holds unlocked keys for a login; `~/.ssh/config` maps short names to addresses and users. Today showed all three: a forgotten passphrase meant a new key, the agent kept serving the old one until `ssh-add -D`, and the config is what lets Ansible and Deployer say `uni-home` instead of an address. `man ssh_config`.
- **Why `sudo` needs `-t` over SSH:** sudo asks for a password only on a terminal; `ssh host command` has none unless forced.
- **Stored XSS:** text saved once and shown to every visitor. JSON inside a `<script>` block is still HTML to the browser, which ends the block at the first `</script>`. OWASP's "Cross Site Scripting Prevention Cheat Sheet".
- **Trusted hosts:** an app that answers only its own name cannot be tricked into building links with a forged one; it is why the smoke test got 400.
- **Idempotence:** a playbook run that changes nothing the second time (`changed=0`) proves it describes a finished state, so it is safe to run again on production at any time.
- **404 vs 410 vs `noindex`:** Google's "HTTP status codes" and "Block indexing" pages in Search Central.

## Session close, continued — the switch, and an unstyled page

**The Tailscale switch did happen** on the second attempt (run by you with `sudo` on the laptop): `homeserver.tailad824e.ts.net` now proxies the new container. The 400 seen before it came from the **old** container, which answers 400 to everything; it is retired in Phase 5.4.

**Then the page loaded without CSS and JS.** It arrived over https but linked its assets as `http://`, which browsers block as mixed content. Cause: Tailscale serve speaks plain HTTP to the container, no proxy is trusted, and https was forced only when `APP_ENV` is `production`; the home server is `preprod`. **Fix:** links now follow `APP_URL`'s scheme (`App\Support\LinksFollowTheSiteAddress`, called from `bootstrap/app.php`, with a test that fails without it). Production's `APP_URL` is https, so nothing changes there. Released as **`v0.1.6`** (CI green) and deployed; the page now asks for `https://…/build/…` and the stylesheet answers 200. `v0.1.6` is also the later tag Phase 5.1's rollback test needs.

**Decision:** the scheme of every link comes from the site's own address, not from the environment's name — **permanent**. **Rejected:** trusting the Tailscale proxy's `X-Forwarded-Proto` (the 12.09 decision removed proxy trust, and a per-server trusted address would be one more thing to keep right).
