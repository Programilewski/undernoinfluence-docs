# 2026-05-15 — Saved Venues, Registered Reports, Owner Incentives

## Session Overview

**Goal:** Give B2C registration a real purpose without weakening the owner-accountable freshness system.

**Outcome:** Saved venues are now the first consumer account feature. Registered users can privately report inaccurate menus. Owners get save/view signals and an inline guide for improving visibility. The SSOT was updated in `inspo/interactive_v1_feature_spec_SSOT.html`.

## What Was Built

### Saved venues

- Added `user_venue_saves` pivot table with unique `user_id + venue_id`.
- Added save relationships on `User` and `Venue`.
- Added Livewire save button on discovery cards and venue profiles.
- Guests get an auth prompt instead of an anonymous save.
- Added `/moje-miejsca` for authenticated users.
- Added "Moje miejsca" to the authenticated account menus.

### Registered-only menu reports

- Added `venue_inaccuracy_reports`.
- Reports require authentication.
- No guest reporter fields and no IP hash are stored.
- Duplicate pending reports by the same user for the same venue are blocked.
- Reports are private admin signals only and do not affect freshness, verification, ranking, or owner notifications.
- Added Filament admin queue for review, resolve, and dismiss actions.

### Freshness streak foundation

- Added `venues.freshness_streak_started_at`.
- Added `Venue::markOfferFresh()` and derived `freshness_streak_months`.
- Fresh confirmations preserve an active streak.
- Stale confirmations restart the streak.
- The hourly freshness command clears missed streaks.

### Owner incentives

- Owner status widget now shows 30-day views and saved-user count.
- Added inline "Jak zwiększyć wyświetlenia?" tip with direct links to freshness, products, and custom drinks.
- SSOT now documents streaks as future factual copy, not named consumer-facing tiers.

## Decision Register

| Decision | Choice | Why |
|---|---|---|
| B2C registration value | Saved venues first | It is useful immediately and creates owner-side demand signals. |
| Reporting scope | Registered users only | Reduces spam and avoids storing guest identifiers. |
| IP storage | No IP hash for reports | Hashed IP is still personal data risk. Rate limiting + auth is enough for V1. |
| Freshness streak data | `freshness_streak_started_at` | A timestamp is safer than a mutable month counter. |
| User reports vs freshness | Reports never affect badges automatically | Freshness stays owner-accountable and under owner control. |
| Loyalty language | No public tier names in V1 | Factual streak text is clearer and more trust-compatible. |

## Data Model State

- `user_venue_saves`: `user_id`, `venue_id`, timestamps, unique pair.
- `venue_inaccuracy_reports`: `venue_id`, `user_id`, `note`, `status`, `reviewed_at`, `resolved_by`, `admin_notes`, timestamps.
- `venues.freshness_streak_started_at`: nullable timestamp used to derive streak months.

The migrations were created and exercised through the test database. They were not manually run against a long-lived local database in this session.

## Session 2 — Security & Performance Audit

### Session Overview

**Goal:** Full security and database performance audit covering the top-50 OWASP attack vectors plus all DB read/write patterns.

**Outcome:** No critical vulnerabilities found. 11 issues identified (5 security, 6 performance) and fixed in the same session. SSOT updated with a dedicated "Security & Performance Audit" section.

### What Was Built

#### Missing database indexes (P6 — highest priority)

PostgreSQL does not auto-index FK columns. The `venues` table was missing indexes on `city_id`, `district_id`, `claimed_by`, `(is_active, is_canary)`, and `offer_updated_at`. Every `Venue::active()` call (used everywhere) was doing sequential scans on these columns. Added via migration `2026_05_15_add_missing_indexes_to_venues_table`.

#### Security headers (S2)

`SetSecurityHeaders` middleware only set `X-Robots-Tag`. Added `X-Frame-Options: SAMEORIGIN` (clickjacking protection), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, and `Permissions-Policy: geolocation=(), camera=(), microphone=()`.

#### Website URL scheme validation (S3)

`VenueRedirectController` passed `$venue->website_url` directly to `redirect()->away()` without validating the URL scheme. A `javascript:` URL stored in the DB would produce a `Location: javascript:…` header. Fixed: added `safeWebsiteUrl()` that rejects anything that isn't `http` or `https`.

#### Mass assignment protection (S1)

`Venue`, `VenueClaim`, and `VenueFeatureFlag` all had `$guarded = []`. Replaced with explicit `$fillable` arrays covering every writable column. Admin panel code continues to work; future bugs that accidentally call `create($request->all())` are now blocked from silently overwriting admin-only fields like `is_canary`, `plan`, and `seeding_status`.

#### N+1 in district loading (P1)

`DiscoveryPage::loadGroupedDistricts()` was looping over selected cities and issuing one `District::where('city_id', $city->id)->get()` per city. Replaced with a single `District::whereIn('city_id', $cityIds)->get()` + in-PHP grouping.

#### Deduplicated city query (P2)

`getTitle()` and `resolveDefaultCity()` both called `City::active()->where('slug', …)->first()` independently on every Livewire render. Added a private `$resolvedCity` property; `resolveDefaultCity()` memoizes with `??=`; `getTitle()` now calls the shared resolver.

#### Search input length cap (S4)

`$search` Livewire URL property had no length cap. Added a 100-character truncation in `updatedSearch()` to prevent excessively long `ILIKE '%…%'` patterns reaching the database.

#### Merged count queries (P4)

`VenueAnalyticsReportService::blankMenuWarning()` issued two separate `COUNT(*)` queries with the same `WHERE district_id = ?` filter. Merged into a single `COUNT(*) AS total, COUNT(CASE WHEN offer_updated_at >= ? THEN 1 END) AS fresh` aggregate.

#### Venue lookup cache in FormRequest (P5)

`StoreAnalyticsEventRequest::venue()` called `Venue::findOrFail()` every time it was invoked, while `rules()` had already confirmed the row exists via `Rule::exists()`. Added `$venueCache` property; `venue()` now memoizes with `??=`.

### Decision Register

| Decision | Choice | Why |
|---|---|---|
| Mass assignment: $guarded vs $fillable | `$fillable` with all writable columns | Documents intent and guards against future bugs. All admin-editable fields included so Filament paths continue to work. |
| Search length cap | Silent truncation at 100 chars | Returning a validation error for a URL-synced search field would break the discovery URL deep-link pattern. Truncation is invisible to users and prevents abuse. |
| blankMenuWarning queries | Single aggregate SQL | Two round trips to the same table for the same `WHERE` clause is wasteful; SQL CASE-based aggregation is idiomatic and easy to read. |

### Data Model State

No schema changes in this session beyond the index migration. No new tables or columns.

## Session 3 — Backend Code Quality Audit

### Session Overview

**Goal:** Full backend code quality audit — fat controllers, duplicated logic, unclear service boundaries, mixed responsibilities, poor naming, inconsistent patterns.

**Outcome:** 8 issues identified. 6 fixed in the same session. 2 deferred (enum clean-ups with no runtime risk). SSOT updated with a new "Code Quality Audit" section (and the Audits nav group).

### What Was Built

#### Q1 — Auth redirect duplication eliminated

`LoginController` and `RegisterController` had byte-for-byte identical `storeSafeIntendedUrl()` and `storeClaimIntendedUrl()` methods. Created `InteractsWithIntendedUrl` trait in `app/Http/Controllers/Concerns/`. Both controllers now `use` it. The copy-paste risk is gone.

#### Q2 — Route closure replaced with controller

`routes/web.php` had an inline closure for the About page that ran `Venue::count()`. DB queries do not belong in the routing layer. Created `AboutController` (invokable single-action). Route is now `Route::get('/o-nas', AboutController::class)`.

#### Q3 — Duplicate category venue query extracted to scope

The "venues with fresh products for a category" Eloquent query was copy-pasted across `CategoryController::show()`, `CityController::category()`, and `CityController::districtCategory()`. The three copies had already diverged. Extracted to `Venue::scopeWithFreshProductsForCategory(Category, int)`. All callers now read cleanly.

#### Q4 — Validation logic moved from controller to FormRequest

`VenueInaccuracyReportController::store()` manually queried for a duplicate pending report and returned a flash message, bypassing the FormRequest. Moved to `StoreVenueInaccuracyReportRequest::withValidator()` — consistent with how `StoreVenueClaimRequest` handles it. Test updated to check `assertSessionHasErrors` instead of `assertSessionHas('status')`.

#### Q5 — Domain factory methods moved to Venue model

`VenueClaimController` contained `uniqueVenueSlug()` and `createDraftVenue()` — venue domain logic on a controller. Moved to `Venue::uniqueSlug()` and `Venue::createFromClaimSubmission()`. Controller `store()` now delegates cleanly.

#### Q6 — Repeated JSONB query pattern extracted

`VenueAnalyticsReportService` had the same two-source UNION ALL JSONB events query repeated 5 times. Extracted to private `queryCategoryDemand(int $cityId, $from, $until, $limit)`. Note: `gapReport()` intentionally keeps its own SQL — it only queries `discovery_empty_results`, not the combined filter+empty demand signal.

### Decision Register

| Decision | Choice | Why |
|---|---|---|
| Trait vs service for auth intent methods | Trait | Two controllers share the logic, no third caller is expected; a shared service would be over-engineering. |
| Move gapReport to queryCategoryDemand | Rejected | gapReport semantically differs — only empty-result events, not combined demand. Forcing it into the shared helper would silently change the data. |
| TrackableColumn enum (Q7) | Deferred | Would require updating VenueAnalytics, VenueRedirectController, and multiple tests. No runtime risk — the guard throws on bad input. Worthwhile cleanup for a future session. |
| VenueInaccuracyStatus enum (Q8) | Deferred | Same reason — touches Filament admin and tests. String constants are consistent internally; the enum is consistency across the project. |

## Session 5 — API Design Audit

### Session Overview

**Outcome:** 10 issues found. 5 fixed immediately (all tested). 5 documented for future work. SSOT updated with new `#api-audit` section.

**Architecture note:** This is an SSR app with no separate REST API layer. One explicit JSON endpoint (`POST /analytics/events`), one redirect-as-API endpoint, Livewire wire protocol, and standard HTML form/PRG routes.

### What Was Fixed

#### A1 — Hardcoded `redirect('/panel')` in VenueClaimController (server-side)
`VenueClaimController::create()` redirected owners to `/panel` as a bare string. Changed to `route('filament.panel.pages.dashboard')`. Test updated.

#### A2 — `analytics-events` rate limiter keyed by session ID
Session IDs rotate on login/logout/regenerate, silently resetting the per-user bucket. Multiple tabs also got independent buckets (2× effective rate). Changed key to `auth()->id() ?: $request->ip()`.

#### A3 — `venue-redirect` rate limiter had dead `instanceof Venue` check
At middleware time, route model binding hasn't run yet; the `venue` param is always a raw slug string. Removed the dead branch. Added explaining comment.

#### A4 — `SavedVenuesController` over-eager-loaded `products.category` and `drinks`
The saved venues list view only uses `products_count`, `districtRelation->name`, and `city->name`. Removed `products.category` and `drinks` from the eager-load.

#### A5 — `SitemapController` ran N×M queries on every request — no caching
With 18 districts × 8 categories, a single crawl request could fire 144+ EXISTS queries. Wrapped builder in `Cache::remember('sitemap.xml', 3600, …)`.

#### A6 — `failedValidation` in `StoreAnalyticsEventRequest` had misleading fall-through
Missing `else` made the two branches (JSON 422 vs bare 422) look like sequential code. Added explicit `else`.

### Documented (not fixed this session)

- **A7** — No result limit on city/district/category pages.
- **A8** — Generic `/{citySlug}` catch-all must always stay last in routes.
- **A9** — `password_status` flash key inconsistent with `status` used everywhere else.
- **A10** — `DiscoveryMapData::forVenues()` has no server-side venue count cap.

### What Was Built

#### A7 — Result caps on city/district and category listing pages

**Files:** `app/Http/Controllers/CityController.php`, `app/Http/Controllers/CategoryController.php`

`CityController::district()` builds a venue list for a single district. `CategoryController::show()` builds a venue list for a category across all cities. Both issued unbounded `->get()` queries — if a district or category ever grew to hundreds of venues, the page would serialize and render all of them on a single request.

Added `->limit(100)` before `->get()` in both queries. 100 is a practical ceiling for an SEO landing page; users who want to explore further have the discovery map. The limit is consistent with the cap philosophy used elsewhere (categories: `->limit(20)` on array input, analytics: 900-second max).

**Why this matters:** Without a cap, a single popular category page could generate a 10 MB HTML response on a busy city. The limit makes worst-case page size predictable.

#### A9 — Flash message key normalization on the profile page

**Files:** `app/Http/Controllers/Auth/ProfileController.php`, `resources/views/auth/profile.blade.php`

The profile page had two separate flash message zones: one near the top for the "update profile" form (using the `status` key) and one near the password form (using a different `password_status` key). This was inconsistent with every other controller in the app that uses `status` as the universal flash key.

Changed `->with('password_status', ...)` to `->with('status', ...)` in `updatePassword()`. Removed the dedicated flash zone next to the password form in the view. The existing `status` zone at the top of the page now handles feedback for both forms. After a password change, the user sees the success message at the top of the page and is scrolled there by the redirect.

**Decision considered and rejected:** Keep two separate flash zones, both reading `session('status')`. Rejected because Laravel flash values are consumed on first read — only whichever `@if` runs first would display the message, making the behaviour order-dependent and fragile to template refactors.

**Why this matters:** Inconsistent flash keys mean a future developer has to know which key to check for which form. `status` is the project's universal convention; this brings the profile page in line.

#### A10 — Server-side venue count cap in discovery map serializer

**File:** `app/Services/DiscoveryMapData.php`

`DiscoveryMapData::forVenues()` accepts a collection of venues and serializes each one into a JSON-ready array for the Leaflet map. It had no upper bound — whatever the query returned, every venue was serialized and sent to the browser as inline JavaScript.

Added `->take(500)` on the input collection before the `map()` call. 500 venues is a large but realistic upper bound; the Leaflet MarkerCluster library handles 500 markers well. Beyond that, map performance degrades visibly regardless of data size.

**Why this matters:** Without this cap, a user with no active filters could trigger serialization of every active venue in the database into a single page response. As the venue count grows, this becomes a latency and memory risk. The cap ensures a predictable worst-case payload size.

#### F8 — Auth-prompt modal accessibility

**File:** `resources/views/livewire/save-venue-button.blade.php`

The "Zapisz miejsce" auth-prompt modal that appears when a guest clicks the save button had zero accessibility attributes. Screen readers could not identify it as a dialog. Keyboard users had no way to close it with the Escape key. Focus was not moved into the modal when it opened — a screen reader or keyboard user could remain "behind" the modal overlay.

Three changes made:
1. **Role attributes:** Added `role="dialog"`, `aria-modal="true"`, and `aria-labelledby="save-venue-modal-title"` to the inner modal container. The heading (`h2`) received a matching `id`. Screen readers now announce "Zapisz miejsce, dialog" when the modal opens.
2. **ESC key close:** Added `@keydown.escape.window="$wire.closeAuthPrompt()"` to the overlay div. Alpine adds this listener to the window while the modal is rendered and cleans it up when Livewire removes the element. Pressing Escape now dismisses the modal.
3. **Auto-focus:** Added `x-init="$el.focus()"` to the close button. When Livewire renders the modal, Alpine immediately moves keyboard focus to the × button. Tab from there cycles naturally through the two action links.

**What was NOT done:** A full focus trap (preventing Tab from leaving the dialog entirely) requires the `@alpinejs/focus` plugin, which is not installed. The decision was to get 80% of the accessibility value (role, ESC, auto-focus) without adding a new dependency. The three focusable elements in this modal (close button, "Zaloguj" link, "Rejestracja" link) are few enough that a user is unlikely to Tab out accidentally.

#### F9 — Venue tile card converted from `<div @click>` to `<a>`

**Files:** `resources/views/components/venue-tile.blade.php`

Every venue card on the discovery page was a `<div>` element with an Alpine.js `@click` handler that set `window.location.href`. This meant:
- Keyboard users could not navigate to a venue (no Enter key support without tabindex gymnastics)
- Right-clicking a card had no "Open in new tab" option
- Screen readers announced an interactive region with no role
- The link destination was invisible to crawlers in a `@click` attribute

Changed the outer `<div>` to an `<a href="{{ route('venues.show', $venue->slug) }}">` with `display: block`. Added `block` Tailwind class to preserve the block layout. Removed the `@click="window.location.href='...'"` handler — the anchor element handles navigation natively.

**Nested anchor fix:** The inner "Nawiguj" button was an `<a>` element (linking to the directions redirect). Nesting `<a>` inside `<a>` is invalid HTML and breaks browser parsing. Converted the Nawiguj `<a>` to a `<button type="button">` with `@click.stop` and `window.open(route, '_blank', 'noopener')`. The `@click.stop` prevents the click from bubbling to the outer `<a>`. The analytics capture call moved inline to the same handler.

**Trade-off:** The Nawiguj button now opens the directions URL via JS rather than a native link. Right-clicking it will not show "Open in new tab" from context menu. This is a secondary UX loss accepted in exchange for valid HTML and full card keyboard accessibility. The directions redirect is a utility action, not a primary navigation path.

**Existing `@click.stop` patterns preserved:** The "Na mapie" button already had `@click.stop` — unchanged. The `<livewire:save-venue-button>` wrapper already had `x-on:click.stop` — unchanged. Both correctly prevent their clicks from triggering the outer anchor navigation.

### Decision Register

| Decision | Chosen | Rejected | Why |
|---|---|---|---|
| A9: flash message layout | Single zone at top, shared `status` key | Two zones both reading `status` | Two zones reading the same flash key is order-dependent — first `@if` consumes the flash, second never shows. Single zone is deterministic. |
| A10: cap placement | `take(500)` in `forVenues()` service method | Cap in `DiscoveryPage` Livewire component | The service is the serialization boundary. The cap belongs at serialization time, not at query time. The query still returns the right venues; the service limits what gets written to the page. |
| F8: focus trap | ESC + auto-focus without full trap | Install `@alpinejs/focus` | Adding a dependency to fix one modal is disproportionate. The modal has only 3 focusable elements; the partial fix covers the real accessibility gap (keyboard dismissal + context announcement). |
| F9: outer element | `<a href>` replacing `<div @click>` | `tabindex="0"` + `role="link"` on existing div | Native anchor semantics are superior — they give crawlers, screen readers, and browsers (right-click, tab order) correct behaviour without polyfilling. |
| F9: Nawiguj inner link | `<button>` + `window.open()` | Keep as `<a>`, accept invalid nesting | Nested anchors cause browsers to close the outer `<a>` tag early, silently breaking the card link in some parsers. Invalid HTML is worse than the minor UX loss on right-click. |

### Business Impact

- **F9 (venue tile as link):** Keyboard and assistive-technology users can now actually navigate to venues from the discovery list. This removes an invisible barrier that was silently excluding a segment of potential users.
- **F8 (modal accessibility):** The "save venue" flow is now operable by keyboard and announced correctly to screen readers. Saving venues is the primary reason for a consumer account — making it accessible improves registration conversion from non-mouse users.
- **A9 (consistent flash key):** No direct user impact, but removes a subtle inconsistency that would confuse any developer maintaining the profile page. Clean code is faster to iterate on.
- **A7/A10 (query and serializer caps):** Prevent a category or district with many venues from generating pathologically large responses as the database grows. The caps are invisible today but become important after launch as data density increases.
