## Decision Register

### D-37: "0%" suffix instead of "0"
- **Chosen:** `Piwo 0%`, `Wino 0%`, `Drinki 0%`, `Cydr 0%`, `Szampan 0%`
- **Rejected:** `Piwo 0`, `Wino 0` etc. (introduced yesterday)
- **Why:** `0%` is unambiguous — it reads as "zero percent alcohol." `0` is more abstract and could be misread as a score or version number. The `%` adds one character but eliminates any possible confusion.
- **Status:** Permanent

### D-38: "Szampan 0%" for the sparkling category
- **Chosen:** `Szampan 0%` (Champagne 0%)
- **Rejected A:** `Bąbelki` (Bubbles) — charming but doesn't signal the drink type clearly enough. Someone scanning filter pills for the first time might not know what "Bąbelki" means in a bar context.
- **Rejected B:** `Musujące bezalkoholowe` — accurate but long and clinical
- **Rejected C:** `Napoje musujące` — descriptive but doesn't fit the `0%` brand convention
- **Why:** "Szampan" immediately communicates "sparkling wine / celebration drinks." The `0%` suffix ties it to the product family. It's the most evocative and commercially recognisable name in the category.
- **Status:** Permanent

### D-39: Instagram links on venue profiles — keep but don't over-invest in tracking
- **Context:** The question arose whether Instagram links are worth having on venue profiles and whether `instagram_clicks` in VenueStat is meaningful.
- **Chosen:** Keep Instagram links on venue profiles. When implementing server-side redirect tracking (TODO 1), decide at that point whether `instagram_clicks` in VenueStat belongs there or gets dropped to PostHog-only.
- **Rejected:** Remove Instagram links — overly cautious. Many Polish bars/restaurants use Instagram as a de facto menu and mood board. It's a genuine user utility.
- **Why:** The field already exists, it costs nothing, and it's useful. The tracking question is a separate concern from the display question. Decision on tracking deferred to the TODO 1 work session.
- **Status:** Revisit when implementing server-side redirects

### Decision Register

#### D-44: Venue CSV import upserts by slug
- **Chosen:** `firstOrNew(['slug' => ...])` — existing venues matched by slug are updated, new slugs create new records
- **Rejected:** Always create new records — would create duplicates on re-import
- **Why:** Idempotent imports are essential for data workflows. Admin can fix a column in the spreadsheet and re-import without creating duplicate venues.

#### D-45: VenueDrink base_category uses DB enum, not category slugs
- **Context:** FakeVenueSeeder initially tried to use category slugs (piwo, wino, drinki...) as `base_category` values. The `venue_drinks` table has a CHECK constraint restricting to: `mocktail`, `koktajl_nolo`, `drink_spirytus_0`, `virgin_classic`.
- **Chosen:** Map drink names to the actual enum values
- **Why:** The `base_category` enum represents drink preparation style, not product category. A venue's custom house drinks are classified by how they're made (mocktail vs spirit-free spirit vs virgin classic), not which product catalog category they belong to.

#### D-46: Import resolves relationships by name/slug, not ID
- **Chosen:** City by name, District by name, Category by slug
- **Rejected:** Require numeric IDs in CSV
- **Why:** Nobody preparing a CSV knows internal database IDs. "Warszawa" is obvious; "1" is not. Slug resolution for categories avoids ambiguity (there could be categories with similar names in other languages).

**How `hasFeature()` works:**
```
$venue->hasFeature(VenueFeature::GapReport)
  → loads featureFlags collection (lazy, once)
  → looks for override matching this feature
  → if override exists: return override->isActive()
     (isActive = enabled=true AND (enabled_until null OR future))
  → if no override: check in_array($feature, $this->plan->features())
```

**Why this architecture and not the alternatives:**

The initially-discussed approach put `venue_feature_flags` as the source of truth, with plan assignment writing rows to the flags table. That was rejected because:
- "Give me all Pro venues" requires a flags table query instead of `WHERE plan = 'pro'`
- Re-seeding flags on plan change is fragile compared to just changing a single column

`venues.plan` is the source of truth. `venue_feature_flags` is the exception layer. When paid tiers launch, the transition is one line: `$venue->update(['plan' => VenuePlan::Basic->value])`. Manual overrides continue to work as exceptions for comped accounts, beta testers, and partnership deals — forever.

### Decision Register

#### D-47: `venues.plan` as source of truth, `venue_feature_flags` as override layer
- **Chosen:** Plan column drives default access; flags table stores exceptions only
- **Rejected:** Flags table as primary source, plan auto-populates flags on change
- **Why:** `WHERE plan = 'pro'` is a trivially efficient query. Finding all Basic-tier venues from a flags table requires grouping and filtering by feature set — complex and expensive. Plan is the canonical state; exceptions are the minority.
- **Status:** Permanent

#### D-48: No standalone gap-report SKU
- **Chosen:** Basic tier at 79 PLN/mo with the gap report as its anchor feature
- **Rejected:** "39 PLN/month for gap report only" introductory SKU
- **Why:** A dead-end price point with a confusing upgrade path. It creates cognitive friction ("wait, do I have the 39 plan or the 79 plan?") and makes it harder to justify the upgrade. The gap report needs surrounding context (category ranking, percentile) to feel like a product rather than a single data point.
- **Status:** Permanent

#### D-49: Gap report in Basic, not Pro — optimise for learning at this stage
- **Chosen:** Gap report anchors Basic (79 PLN/mo)
- **Rejected:** Gap report in Pro (129 PLN/mo) for higher revenue per owner
- **Why:** At ≤20 claimed venues, adoption feedback matters more than revenue optimisation. Putting the highest-value feature in the entry tier reduces friction, gets more owners paying, and generates more pricing signal faster. Revisit at 20+ active paid subscriptions — if Basic conversion is strong, consider moving gap to Pro and introducing a lighter Basic.
- **Status:** Revisit at 20+ paid subscriptions

#### D-50: Manual delivery before dashboard — 3-signal test
- **Chosen:** Manually pull gap data from DB and email venue owners for months 1–2 post-launch. Build the dashboard only when 3+ owners reply / add products / ask to keep getting the report.
- **Rejected:** Build the analytics dashboard before validating owner willingness to pay
- **Why:** The tier structure is a planning artefact, not a build instruction. Engineering tier infrastructure for 5 venues is waste. Manual delivery is zero engineering and generates real signal. The feature flag system gives you the toggle to flip features on per-venue the moment you're ready to charge.
- **Status:** Permanent for pre-launch phase

#### D-51: `FeatureOverrideReason` as typed enum, not free-text string
- **Chosen:** `enum FeatureOverrideReason: string` with `Beta | Comp | Partner | ManualTest`
- **Rejected:** `nullable string` column with ad-hoc values
- **Why:** Free strings are footguns. Typos create phantom values. IDE autocomplete doesn't work. Filtering by reason in Filament (or in a future query) requires exact string matching that breaks silently. The enum makes the reason space explicit and queryable. New reasons require a code change, which is intentional — it prevents reason sprawl.
- **Status:** Permanent

#### D-52: `enabled_by` + `enabled_at` audit trail on feature flags
- **Chosen:** Store which admin set each override and when
- **Rejected:** No audit trail (just the enabled state)
- **Why:** When a comped venue owner asks "when does my free access end?", you need to look it up. When an override is disputed, you need to know who set it. When a trial period expires silently and the owner loses a feature, the audit trail is how you reconstruct the timeline. Low-cost addition at schema time; expensive to retrofit later.
- **Status:** Permanent
