## Decision Register

### 1. Production gets its catalogue from the admin importers, not from seeders — **recommended, waiting on one answer from you**

**Chosen (recommended):** two kinds of data, two tools.
- **Reference data** is owned by the code: cities, categories, districts, canaries. It keeps its seeders, which already run everywhere.
- **Catalogue data** is owned by you: products, brands, producers, venues, menus. It reaches production **once**, through the three CSV importers in this order: products, then venues, then menus. The load is rehearsed first with the same files on the rebuilt home server. **After that load, the production admin is the only source of truth** and the spreadsheet is retired. Producers are entered by hand, because there are few of them and they never appear publicly.

**Rejected:** a "real catalogue" seeder run on production. Four reasons:
1. **Two sources of truth.** The first time you correct an ABV in the production admin, the seeder file is wrong. Re-running it either overwrites your correction or is quietly skipped, and neither is acceptable.
2. **Every new drink would need a commit and a deploy.** The catalogue would move at release pace instead of cataloguing pace, and it would live in the application repository.
3. **Provenance.** The data-gathering record requires every drink to carry the menu address and the date it was read. A seeder hard-codes those dates, so every run would look like a fresh check that never happened.
4. **It reverses a decision on purpose.** `ProductSeeder` is demo-only by design, and the 22.09 record (invented data is allowed everywhere except production) keeps production empty of anything not entered deliberately.

**Also rejected:** copying the home server's database to production. The home server holds demo data on purpose, so a dump would carry invented venues into production, and the staging-is-seeded record refuses dumps in both directions for the same reason: copies that nobody guards.

**The answer this waits on:** **where do the 35 venues actually live?** If they're in the venue spreadsheet, the plan works as written. If you've been typing them into the home server's admin, the data is in a database that also holds demo rows, and we need an export step (a Filament exporter for venues and menus, filtered to the real ones) before the plan works.

### 2. V1 catalogues the venues with the best NA offer first — **your direction; recommended with four guardrails**

**Your reasoning:** with only 70–100 venues in V1, alphabetical order spends the budget on a random sample. Many of the first 70 names would barely clear the bar.

**Chosen (recommended):** best offer first, with these guardrails:
1. **"Best" decides the order of work, not who qualifies.** The eligibility rule doesn't change: one named NA item in the venue's own published offer. The ordinary pub with a single Heineken 0.0 is still a UNI venue, and it's exactly the harm-reduction case ("I'm going out with friends tonight"). V1 just doesn't start there.
2. **A threshold you can check from the menu in two minutes.** Proposed: at least 3 named NA items across at least 2 categories. That's close to what `breadth_score` measures, so the venues chosen first will also rank first.
3. **District spread.** Strong venues cluster in Śródmieście. District pages below the thin-district threshold are noindexed (see the thin-district-pages record), so a few strong venues in Mokotów, Praga and Wola do more for search than the fifteenth one in the centre.
4. **How candidates are found.** Brand "where to drink us" pages make a good lead list, but used alone they tilt the map toward one brand's stockists, which is the brand influence the mission excludes. Use them alongside menu searches like "koktajle bezalkoholowe Warszawa", never instead of them.

**Rejected:** carrying on alphabetically (it wastes the V1 budget). Also rejected: making "best" an eligibility rule. That would turn UNI into a curated "best NA bars" list, which is a different product from "what can I order here tonight".

**Kept:** the 35 already done stay if they're eligible. Rejected venues keep being logged with a reason in the spreadsheet, as the data-gathering record requires, because that list measures your pace and doubles as the sales prospect list.

**The answer this waits on:** the threshold for "best". Accept 3 items in 2 categories, or name your own. Then it becomes a record beside venue-data-acquisition-flow.

## Business Impact

**"Best first" is the cheapest improvement to the launch this month.** It costs no code and changes what a first-time visitor sees. A map where every pin opens onto a real choice of three or more drinks earns a second visit; a map where half the pins open onto a single 0.0 beer reads as thin, however honest it is. ## Learning Path

- **Reference data vs content.** Reference data is what the code needs in order to work (the list of categories); content is what the people running the product create (the drinks). Seeders suit the first and migrations suit structure, but content belongs to whoever edits it. Search "seed data vs reference data vs master data".
- **Idempotent imports.** An import is idempotent when running it twice gives the same result as running it once. UNI's importers manage this by matching on slug (`firstOrNew`). It's what makes a rehearsal on the home server, followed by the real run on production, safe.
- **Sampling for a launch.** Why the first 70 alphabetically are a random sample of quality, and why a deliberately chosen strong set makes early numbers easier to interpret. Search "convenience sampling bias" for the general idea.
