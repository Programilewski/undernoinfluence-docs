# 2026-09-28 — The deploy process, checked line by line, and a new one decided

## Session Overview

**Goal:** move four pending changes (the homepage showcase and its test) to the home server, and understand exactly how that differs from a production deploy under Ploi.

**Outcome:** the changes were **not** deployed — the session turned into the thing that had to come first. The two-column deploy table was built, then every line of it was checked against the code, the installed packages, Laravel's own source, the Ubuntu archive and Ploi's documentation. Five of its claims were wrong, including one that three documents had repeated as fact since early September (that building the site's assets would crash the production database). Research then showed that **Ploi causes most of the differences between the home server and production**, and after two independent research reports and a review of both, the plan changed: **no panel; Ansible provisions both servers from your PC; Deployer deploys tags to both.** That is now a decision record. The next session writes the full step-by-step plan as a two-column table.

**Nothing in the application changed today.** The four uncommitted files from before the session are still uncommitted, and still become `v0.1.4` when you tag them.

## Decision Register

### 1. No server panel — Ansible and Deployer, run from your PC (recorded)
**Chosen:** one Ansible playbook sets up both the home-server container and the OVH server; Deployer 8 deploys tags to both; both run stock Ubuntu 26.04. **Rejected:** Ploi Basic (its script pulls a branch and skips `--no-dev`, zero-downtime is only on Pro, its nginx needs hand-fixing anyway, and it would be a GDPR processor with server access); Ploi Pro (pays for something free tools do); CloudPanel (proprietary licence, won't run in a container); HestiaCP (Ubuntu 26.04 support unclear); Coolify (Docker). **Why — honestly:** not the €8 a month. The setup is about 25–35 hours, which the fee would take years to repay. It's right because production becomes a copy of the environment where you rehearse, nobody else holds access to personal data, and one fix reaches both servers. **Status:** permanent until someone else operates the server or admin exceeds 3–4 hours a month.

### 2. Your PC is the control node, not the home server
**Chosen:** Ansible and Deployer run only from the PC. **Rejected:** the home server — it would need a key that opens production, on the box that is meant to be broken freely, and it isn't always on. **The PC being off is not a risk to the site:** everything that must run 24/7 (the site, workers, cron, backups, updates, certificate renewal, the monitor ping) runs on the server itself. The real risks are access ones, mitigated by a second SSH key in your password manager and a three-line manual rollback. **Status:** permanent.

### 3. Reach the home-server container over SSH, not the Incus plugin
**Chosen:** SSH through the home-server host, exactly like production is reached. **Rejected:** Ansible's Incus plugin (suggested by report 1, and it does exist) — it saves installing an SSH server in the container, but Deployer needs SSH there anyway, so it would only add a second connection method. **Status:** permanent.

### 4. Assets are built once on the PC and uploaded to each server
**Chosen:** keep building on the PC, now by Deployer from a clean copy of the tag. **What changed:** the old reason (a build crashes Postgres) was measured and is false. **The reasons that remain:** one identical build on every server, and no Node runtime on production to maintain. **Rejected:** building on the server (report 1) — viable, but not needed. **Status:** revisit when a second person deploys (then CI builds it).

### 5. Migrations only go forward, and production backs up first
**Chosen:** a rollback switches code back but never undoes a migration; risky schema changes are split across two releases; production takes a database-only backup before any deploy that has migrations waiting. **Rejected:** automatic down-migrations on rollback. **Why:** undoing a migration can destroy data, and the backup is the real undo. The backup idea came from a DeployHQ article you found. **Status:** permanent.

### 6. A deploy never runs `optimize:clear`
**Chosen:** `optimize` only. **Rejected:** report 2's step that clears everything first. **Why:** it includes clearing the application cache, and UNI's cache is in the database — every deploy would wipe the scheduler heartbeat (the dashboard would show "never ran"), the signal that restarts the workers, and the login rate-limit counters. **Status:** permanent.

### 7. Two users, not one
**Chosen:** `deploy` owns the code; `www-data` runs the website, the worker and cron. **Rejected:** report 1's single user for everything — it removes the permissions problem fixed on 25.09, but lets the website process rewrite the code on a server holding personal data. **Status:** permanent.

### 8. Backup retention stays as decided on 16.09
**Rejected:** report 2's 14 daily, 8 weekly and 12 monthly backups, and its idea to postpone deletion protection. **Why:** a backup is where personal data outlives its retention rule, so the five-week cap is what keeps the privacy policy true. Neither report knew about it — the research prompt didn't say, which is a lesson in itself. **Status:** permanent.

### 9. CI tests, never deploys
**Chosen:** GitHub Actions runs the tests and the asset checks in a clean environment, holds no production key. **Why:** it catches exactly the `public/hot` problem found today, for free. **Status:** revisit when deploys happen several times a week.

### 10. Four libraries you found — none adopted
Email validation (`egulias/EmailValidator`) and error pages (`filp/whoops`) are **already installed** as part of Laravel and its test tooling. Mobile-Detect duplicates something UNI already does better (it asks the browser directly and stores only "mobile" or "desktop"). UnoPim is a whole product-catalogue application for large retailers, not a library. **Also rejected:** DeployHQ — a paid service with server access, the same objection as Ploi.

### Superseded today
**Deployer on top of Ploi** — briefly recommended mid-session, replaced by Decision 1 once the numbers were in.

## Learning Path

- **What "OOM-kill" means.** When Linux runs out of memory it doesn't slow down — it picks the process holding the most memory and kills it instantly. On a small server that's often the database. Today's lesson is the other half: a warning is only as good as its measurement.
- **Agentless configuration (Ansible).** Nothing runs on the servers between changes; your PC connects over SSH, applies the playbook, and leaves. Running it twice should change nothing — that's how you know it describes the server rather than a one-off sequence. Search: "Ansible getting started control node".
- **Atomic releases.** Each deploy goes into a fresh folder, and a single link (`current`) is switched at the end — visitors see the old version or the new one, never half of each. Search: "Deployer Laravel recipe".
- **Why the symlink needs care.** PHP remembers where `current` pointed (for two minutes) and caches compiled code by path — so after a switch it can keep serving the old release. The fixes are nginx's `$realpath_root` and reloading PHP-FPM. Search: "nginx realpath_root opcache symlink deploy".
- **Expand-contract migrations.** Change a database in two releases — add the new shape, move to it, remove the old shape later — so every release works with the schema before and after it. Search: "expand and contract database migrations".
- **Reading research critically.** Two reports agreed on the big picture and each contained one step that would have hurt. The assessment document is a worked example of checking claims against the thing itself.
