# 2026-11-26

## Session Overview

**Goal:** my item from the 24.11 backlog: find out what Taproom's weekly-rotating tap list puts back in the approval queue when its menu is refreshed, and decide what to do about it.

**Outcome:** The refresh itself was cheap and safe: a changed menu is read again (about $0.01) and every line waits for approval, with lines already on the venue offered as certain matches and drinks that left the card offered for removal. ## What Was Built

**A venue's own menu check interval** (application). New column `venues.menu_check_days` (7 to 90 days; empty means 28), set on the venue form in the admin panel under *Administracja* as **"Sprawdzaj kartę co (dni)"**. *Why:* a rotating tap list goes stale in a week, while most menus change seasonally; one interval for all either leaves Taproom wrong for weeks or pays for re-reading menus that didn't change. The refresh job (`QueueMenuRefreshes`) now runs **daily at 04:30 instead of weekly on Mondays**, and a menu is due once its venue's interval has passed since its last check, counted in calendar days. *Why daily:* on a weekly run, a check made a few seconds after the run started would miss the next week's run by seconds and drift to every 14 days. It still takes at most 50 menus per run, which bounds a day's reading cost. The column was added to the venues create migration (production has not been deployed yet), `database/schema.md` and the column count in the app's CLAUDE.md (now 465). *State:* shipped in v0.1.22, Taproom (venue 17) set to 7 on the home server.

**A producer printed beside a line is its brand** (application, menu-reading prompt only). When a drink's name carries no brand and the menu prints its producer beside it, the reader takes the producer as the brand, as a guest would say it ("Amber"), and keeps the line as a branded product instead of dropping it as a generic line. A name that has a brand keeps it: Bavaria stays Bavaria, never Royal Swinkels. *Why:* tap lists built like Untappd pages print every beer as name · producer · strength; two of Taproom's 25 alcohol-free beers were lost on 20.11 for this reason alone. *State:* shipped in v0.1.22 and already proven on a real reading (below).

**Tests:** three for the interval (a 7-day venue is due on day 7 and not day 6; the interval counts from the last check and is found through the menu's own venue; a venue with no interval waits 28 days), two for the venue form (7 saves; 3 is refused), one for the prompt rule. 601 tests in the sourcing, admin and venue folders green; CI green on the tag.

**The `/end-session` skill** (application repository, `.claude/skills/end-session/`). Combines the decision-record skill, the journal skill, and a hand-off checklist: the roadmap row, the index, the memory resume point, open threads from the conversation, both repos committed and pushed, and the state of each environment. *Why:* Paweł asked for one command that closes a session so the next one loses nothing.

**Decision records:** [[decisions/product/a-rotating-menu-is-checked-more-often]] and [[decisions/product/a-producer-printed-beside-a-line-is-its-brand]], both listed in the Product Decisions table.

## Business Impact

UNI's promise is a drink you can order tonight. For a venue whose list moves every week, a monthly check meant UNI showed about three quarters of what was really on tap and, for weeks, a beer that was gone. Now such a venue is checked weekly for about a cent and a few minutes, and only where it's needed. Taplists are where the widest choice of alcohol-free beer is (Taproom alone has 32), so they are among the most useful venues UNI can list. The producer-column fix matters more widely than Taproom: every Untappd-style list prints beers this way, and those beers were being dropped silently, with nothing in the queue to show they existed.

## Learning Path

- **Unix file permissions and service users.** Why the same server can show a file to the web app and hide it from an admin's command: each process runs as a user, and a folder with mode 2700 lets only its owner in. Search "Linux file permissions owner group other".
- **Scheduling with calendar days.** Why "every 7 days" on a weekly timer drifts: the comparison happens a few seconds earlier than the last check. Search "cron job drift interval scheduling".
