## What Was Built

### 1. Development Lazy-Loading Safety Net

**File:** `app/Providers/AppServiceProvider.php`

Added `Model::preventLazyLoading(!app()->isProduction())` at the top of `boot()`. In local and staging environments this causes Laravel to throw an exception the moment a relationship is accessed without being eagerly loaded. In production, nothing changes — the code path is identical to before. This is the single most impactful quality-of-life addition for catching N+1 bugs: instead of silently firing extra queries, the app blows up during development so the problem can't be ignored.

**Why now:** The audit revealed that while the main query paths were clean, the codebase had no automated net to catch future regressions. Every code change that touches views or serialisation is now automatically guarded.

### 2. `UserRole` Backed Enum

**File created:** `app/Enums/UserRole.php`

```
UserRole::User  = 'user'
UserRole::Owner = 'owner'
UserRole::Admin = 'admin'
```

The `users.role` column stores one of three string values. Before this session, those values were compared using raw string literals (`$this->role === 'admin'`) in two places in the `User` model and written as a string literal in `ApproveVenueClaimAction`. This meant no IDE autocomplete, no refactor safety, and no type-checking.

**File updated:** `app/Models/User.php`
- Added `'role' => UserRole::class` to `casts()`. `$user->role` now returns a `UserRole` enum instance, not a string.
- `isAdmin()` and `isOwner()` updated to compare with `UserRole::Admin` and `UserRole::Owner`.

**File updated:** `app/Services/Actions/ApproveVenueClaimAction.php`
- Changed `$user->role = 'owner'` to `$user->role = UserRole::Owner`.

**File updated:** `app/Filament/Resources/Users/Tables/UsersTable.php`
- The role badge column had a closure typed `fn (string $state)`. Now that `$state` is a `UserRole` instance, the type hint and match arms were updated to use the enum.

**Tests updated:**
- `tests/Feature/OwnerPanelRegistrationTest.php` — `assertSame('user', $user->role)` → `assertSame('user', $user->role->value)`
- `tests/Feature/VenueErasureFlowTest.php` — same pattern
- `tests/Feature/SchemaHardeningTest.php` — the "database rejects unknown role" test previously expected a `QueryException` from the DB check constraint. Now the enum cast throws a `ValueError` before the query reaches the database, which is actually *earlier* and *stricter* rejection. Updated `expectException` accordingly.

Factory calls like `User::factory()->create(['role' => 'user'])` and `assertDatabaseHas('users', ['role' => 'owner'])` needed no changes — Laravel's enum cast accepts backing-value strings on set, and `assertDatabaseHas` compares raw database strings.

### 3. OSM Import Optimisation

**File:** `app/Console/Commands/ImportOsmVenues.php`

**Two problems fixed:**

**Before (N+1 exists-check):** The loop called `Venue::where('osm_id', $osmId)->exists()` once per element in the JSON file. A 2000-element Overpass export fired 2000 `SELECT EXISTS` queries just to skip duplicates.

**After:** All known `osm_id` values are loaded into a PHP hash map once before the loop: `Venue::whereNotNull('osm_id')->pluck('osm_id')->flip()->all()`. The duplicate check becomes a `isset($existingOsmIds[$osmId])` in-memory lookup — zero queries per element.

**Before (per-row INSERT):** `Venue::create([...])` inside the loop fired one `INSERT` per valid element.

**After:** Valid rows are accumulated into a `$batch[]` array with explicit `created_at`/`updated_at` timestamps. After the loop, `Venue::insert()` is called in chunks of 500. A 2000-element import now fires at most 4 INSERT statements instead of 2000.

**Why `Venue::insert()` is safe here:** All imported venues start `is_active = false` and have no products, so they cannot appear in the sitemap or discovery page. The `Venue::saved()` listener in `AppServiceProvider` (which clears the sitemap cache) is an Eloquent event — `insert()` bypasses it. This is fine because inactive venues are never in the sitemap. No other observers fire on venue creation (only `VenueDrinkObserver` and `VenueProductObserver` fire, and those are triggered by drink/product attachment, not venue creation).

### 4. `MassPrunable` on Three Accumulating Log Tables

Previously, `audit_logs`, `venue_offer_logs`, and `venue_stats` had no retention policy. They grew indefinitely with every product change, click, and view. Over months or years this creates query overhead, backup bloat, and storage costs.

**`app/Models/AuditLog.php`** — 12-month retention. Audit logs track admin and owner actions; a year is enough operational lookback. Older records are anonymous anyway (GDPR erasure redacts them).

**`app/Models/VenueOfferLog.php`** — 6-month retention. These are per-venue offer change logs (product added/removed, drink added/removed). Six months covers any reasonable analytics lookback window.

**`app/Models/VenueStat.php`** — 24-month retention. Daily stat rows (views, clicks, shares) per venue. Two years provides enough history for trend analysis while keeping the table manageable.

All three use `MassPrunable` (not `Prunable`) because deletion events don't need to fire per record — these are operational logs, not business objects.

**`routes/console.php`** — Added `Schedule::command('model:prune')->daily()`. Without this line, the `prunable()` methods exist but are never called.

**`tests/Feature/ModelPruningTest.php`** — New test file with four tests: one per model verifying that the `prunable()` scope returns records beyond the retention window but not within it, plus a schedule test confirming `model:prune` appears in `schedule:list`.

### 5. CategoryController N+1 (Bonus — Caught by `preventLazyLoading`)

**File:** `app/Http/Controllers/CategoryController.php`

The category browse page (`/kategoria/{slug}`) was calling `Venue::active()->withFreshProductsForCategory(...)` without eager-loading `districtRelation` or `city`. The view template accesses both for each venue card. This was silently firing one query per venue before today. The test suite confirmed it via a 500 error the moment `preventLazyLoading` was active.

Added `->with(['districtRelation', 'city'])` to the query. This was a genuine production N+1 — not hypothetical — and `preventLazyLoading` caught it automatically on the first test run.

## Business Impact

- **Category pages are faster.** The `districtRelation` N+1 was a real, silent production bug on the category browse page. Every venue card was causing an extra database query. For a page with 50 venues, that was 50 hidden queries. Fixed without changing any visible behaviour.
- **The OSM import scales properly.** Importing 5000 venues from OpenStreetMap previously fired ~10,000+ queries. It now fires ~10 + a handful of bulk inserts. This matters for the multi-city expansion plan where OSM imports are the primary seeding mechanism.
- **Log tables won't grow unbounded.** Without retention policies, `audit_logs`, `venue_offer_logs`, and `venue_stats` would accumulate forever. At current write rates these tables would become meaningfully large within 12–18 months of launch. The pruning jobs protect both query performance and hosting costs.
- **Role bugs will fail loudly, not silently.** With `UserRole` as a real enum, any future code that tries to compare `$user->role === 'admin'` will get a type error in development instead of a silent wrong answer. This protects the access control layer — the most security-sensitive part of the app.
- **Development speed improves.** `preventLazyLoading` means future N+1 bugs surface as immediate test failures rather than as production slowdowns discovered by users.

## Session 2 — Filament Directory Restructure + Admin Security Planning

### Session Overview

**Goal:** Clean up a confusing Filament directory structure and document the Tailscale admin security decision.

**Outcome:** The Filament codebase is now symmetrically organised into `Admin/` and `Owner/` subfolders at every layer — PHP classes, view files, and provider naming all speak the same vocabulary. A silent auth bug in `User::canAccessPanel()` was caught and fixed during the process. The Tailscale VPN decision is documented in full detail in the interactive SSOT. Old SSOT files (EN/PL) have been archived. 474/474 tests pass.

---

### What Was Built

#### 1. Filament PHP Directory Restructure

**The problem:** `app/Filament/` had an asymmetric structure. The admin panel lived at the root (`app/Filament/Widgets/`, `app/Filament/Resources/`, `app/Filament/Imports/`) while the owner panel lived in a subdirectory called `Panel/` (`app/Filament/Panel/Widgets/`, etc.). The name `Panel` was meaningless — it didn't communicate who the panel was for or why it was separate.

**What changed:**

```
Before:                          After:
app/Filament/                    app/Filament/
├── Imports/                     ├── Admin/
├── Widgets/                     │   ├── Imports/
├── Resources/                   │   ├── Widgets/
└── Panel/                       │   └── Resources/
    ├── Pages/                   └── Owner/
    ├── Widgets/                     ├── Pages/
    └── Resources/                   ├── Widgets/
                                     └── Resources/
```

Every PHP file's namespace was updated accordingly:
- `App\Filament\Resources\*` → `App\Filament\Admin\Resources\*`
- `App\Filament\Widgets\*` → `App\Filament\Admin\Widgets\*`
- `App\Filament\Imports\*` → `App\Filament\Admin\Imports\*`
- `App\Filament\Panel\*` → `App\Filament\Owner\*`

Both panel providers updated their `discoverResources`, `discoverWidgets`, `discoverPages` filesystem paths to match.

#### 2. `PanelPanelProvider` → `OwnerPanelProvider`

**File renamed:** `app/Providers/Filament/PanelPanelProvider.php` → `app/Providers/Filament/OwnerPanelProvider.php`

`PanelPanelProvider` was named after the panel ID (`panel`), producing a nonsensical double word. Renamed to `OwnerPanelProvider` to match the new `Owner` vocabulary. The class name inside the file and the `bootstrap/providers.php` registration were both updated.

#### 3. Filament View Directory Restructure

**The problem:** Blade views did not follow the same `admin/owner` structure. They were scattered across three locations with no consistent logic:
- `resources/views/filament/panel/` (owner panel views, using the old `Panel` name)
- `resources/views/filament/resources/venues/` (admin resource views)
- `resources/views/filament/widgets/` (admin top-level widgets, no panel prefix)

**What changed:**

```
Before:                                       After:
filament/                                     filament/
├── panel/                                    ├── admin/
│   ├── pages/claim-venue.blade.php           │   ├── resources/venues/
│   └── widgets/                             │   │   ├── pages/venue-analytics.blade.php
│       ├── venue-analytics.blade.php        │   │   ├── pages/partials/owner-analytics-preview.blade.php
│       └── venue-status.blade.php           │   │   └── widgets/venue-analytics.blade.php
├── resources/venues/                         │   └── widgets/
│   ├── pages/venue-analytics.blade.php      │       └── discovery-insights.blade.php
│   ├── pages/partials/...                   └── owner/
│   └── widgets/venue-analytics.blade.php       ├── pages/claim-venue.blade.php
└── widgets/                                     └── widgets/
    └── discovery-insights.blade.php                 ├── venue-analytics.blade.php
                                                      └── venue-status.blade.php
```

All `protected string $view` properties in PHP widget and page classes updated to match the new paths.

#### 4. Panel ID Changed + URL Decision

**`OwnerPanelProvider`:** `->id('panel')` changed to `->id('owner')`. The panel ID drives Filament's internal naming — route name prefixes, `canAccessPanel()` matching. It does not need to match the URL path.

**URL path:** After discussion, `->path('panel')` was kept — the owner panel is accessible at `/panel`. Considered alternatives: `/owner` (matches internal naming but English in a Polish product), `/moj-lokal` (descriptive but breaks if multi-venue management is ever added), `/dashboard` (generic), `/zarzadzaj` (Polish but too long). `/panel` won because it is short, language-neutral, universally understood, and makes no assumption about how many venues an owner manages — a property that matters if the product ever supports multi-venue accounts.

#### 5. Silent Auth Bug Fixed: `User::canAccessPanel()`

**File:** `app/Models/User.php`

`canAccessPanel()` had:
```php
'panel' => $this->isOwner(),
```

After the panel ID changed to `owner`, this match arm would never fire — every owner would receive a 403 when trying to access `/panel`. The bug was caught immediately by the test suite (19 failing tests) during the panel ID change. Fixed to:
```php
'owner' => $this->isOwner(),
```

This was a production-critical silent failure path: if deployed without this fix, every venue owner would be locked out of their panel permanently.

#### 6. Downstream Reference Sweep

After the panel ID and URL changes, a full sweep caught additional stale references that would have broken at runtime:

- `resources/views/filament/owner/widgets/venue-status.blade.php` — four hardcoded `url('/panel/venues/...')` links
- `app/Notifications/ClaimApproved.php` — email action button pointed to `url('/panel')`
- `app/Http/Controllers/VenueClaimController.php` — redirect to `route('filament.panel.pages.dashboard')`
- `resources/views/partials/nav.blade.php` — two `route('filament.panel.pages.dashboard')` hrefs
- `tests/Feature/ClaimFlowTest.php` — route assertion using old panel route name
- `architecture-explorer/src/data/architecture.json` — stale file paths throughout
- `.posthog-events.json` — stale file paths in event source references

All updated. `resources/views/filament/panel/widgets/venue-status.blade.php` also had a hardcoded `\App\Filament\Panel\Pages\ClaimVenue::getUrl()` call in a Blade template — this would have caused a fatal error for owners who haven't claimed a venue yet.

#### 7. Tailscale SSOT Documentation

**File:** `inspo/interactive_v1_feature_spec_SSOT.html`

Added a new `#admin-security` section with full detail on the decided (not yet implemented) Tailscale + Nginx admin access strategy. Covers: architecture (two separate traffic paths), the three-layer trust chain (Tailscale device auth → WireGuard tunnel → Nginx IP allowlist → Filament login), implementation steps (Forge Nginx config, tailnet setup), free tier implications, privacy policy considerations, and known limitations. Nav entry added in the System group.

| Future Filament upgrade auto-generates files into old paths | Low | Both providers now have explicit `discoverResources`/`discoverWidgets`/`discoverPages` pointing to `Admin/` and `Owner/`. New Artisan-generated files will need to be placed in the correct subfolder manually — `php artisan make:filament-resource` outputs to a default path that may need moving. |
| Admin panel publicly reachable until Tailscale is implemented | Medium | Filament auth is the only barrier for now. Use a strong password. Tailscale implementation is the next infrastructure priority. |
| Multi-venue ownership makes `/panel` semantically odd | Very low | `/panel` was chosen precisely because it makes no singular assumption — "your panel" not "your venue". This risk is explicitly not a concern with this URL choice. |

### Business Impact

This session was infrastructure housekeeping, not product features. The business impact is indirect but compounding:

- **The codebase is easier to navigate.** Every future session starts with a clearer mental model of where to find owner-panel vs admin-panel code. Faster orientation = faster feature development.
- **A silent owner lockout bug was caught before production.** If the panel ID change had shipped without fixing `canAccessPanel()`, every venue owner would have received a 403 on every panel visit. This would have been a hard-to-diagnose production incident during a critical pre-launch period.
- **The admin panel security decision is documented and queued.** Tailscale implementation is now clearly the next infrastructure priority. Until it's done, the admin panel is publicly reachable — acceptable pre-launch, not acceptable post-launch.
