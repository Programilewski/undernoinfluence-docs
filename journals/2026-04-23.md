## What Was Built

### 1. Filament Owner Panel — `app/Providers/Filament/PanelPanelProvider.php`

**What:** A second Filament panel at the path `/panel`, completely separate from the admin panel at `/admin`. This is the panel that venue owners see after registering and getting their claim approved.

**Why separate panels:** Filament supports multiple independent panels, each with their own routes, auth guards, resources, and navigation. Owners and admins have fundamentally different capabilities and should never share a UI surface. The admin panel exposes everything; the owner panel exposes only what belongs to that specific owner.

**Configuration:**
- `->login()` — standard Filament login page at `/panel/login`
- `->registration()` — standard Filament registration at `/panel/register` (this is the entry point from `/dla-lokali`)
- Brand name: "UNI — Panel właściciela"
- Color: Amber (visually distinct from admin's Rose)
- Discovers resources from `app/Filament/Panel/Resources`
- Discovers pages from `app/Filament/Panel/Pages`
- Discovers widgets from `app/Filament/Panel/Widgets`

**Current state:** Live. All 7 panel routes registered and responding.

### 2. User Model — FilamentUser Interface — `app/Models/User.php`

**What:** Added `implements FilamentUser` to the User model and implemented `canAccessPanel(Panel $panel): bool`. Without this, Filament's default behaviour in non-local environments is to deny all access.

**Why this matters:** The two panels need different role gates. Admins go to `/admin`; owners go to `/panel`; regular users can access neither. The `canAccessPanel()` method receives the current `$panel` object, making per-panel logic straightforward:

```php
public function canAccessPanel(Panel $panel): bool
{
    return match ($panel->getId()) {
        'admin' => $this->isAdmin(),
        'panel' => $this->isOwner(),
        default => false,
    };
}
```

A user who registers via `/panel/register` gets `role = 'user'` by default (Filament's built-in registration doesn't set a role). They are allowed to log in to the owner panel but cannot access any venue resources until their claim is approved and their role is changed to `'owner'`. This is intentional — the claim form is the next thing they see.

**Current state:** Correct. Verified in tinker that `isOwner()` and `canAccessPanel()` both behave as expected.

### 3. Owner Panel — VenueResource — `app/Filament/Panel/Resources/VenueResource.php`

**What:** A Filament resource that lets an owner view and edit their claimed venue. The critical detail is query scoping:

```php
public static function getEloquentQuery(): Builder
{
    return parent::getEloquentQuery()
        ->where('claimed_by', auth()->id());
}
```

This means the owner can only ever see their own venue — not other venues in the database. The list page will show exactly one row. Editing another owner's venue by manipulating the URL is impossible: the record is resolved through the scoped query, so it will 404.

**Editable fields (limited):** description, phone, email, website_url, instagram_handle, image_path, opening_hours. The fields an owner cannot touch — name, slug, venue_type, address, is_verified, is_claimed, source — are simply not in the form. There is no "disabled but visible" pattern here; the fields do not exist on this form at all.

**Opening hours format:** A `Repeater` component with (day, open time, close time) per row. Owners add days they're open and leave closed days out. This matches the `opening_hours` jsonb column.

**Edit page extras:** A "Podgląd profilu" header button opens the public venue profile in a new tab, so owners can see what customers see immediately after saving.

**Current state:** Live. Accessible to users with `role = 'owner'` who have a `claimed_by` venue.

### 4. Owner Panel — ProduktyRelationManager

**File:** `app/Filament/Panel/Resources/VenueResource/RelationManagers/ProduktyRelationManager.php`

**What:** Relation manager on the venue edit page. Shows all products currently in the venue's offer. Owners can:
- **Add** a product from the global catalogue (searchable by name and brand)
- **Remove** a product from their offer

**Key difference from admin:** When an owner attaches a product, the pivot record is created with `added_by = 'venue_owner'` and `confirmed_at = now()`. Admin attachments use `added_by = 'admin'`. This attribution data is valuable for quality analysis: products confirmed by owners are more reliable than admin-entered ones.

**What owners cannot do:** Edit product details (name, brand, ABV, category). Products are a shared catalogue. An owner adds/removes existing products; they cannot create new products or change catalogue data. If a product they need doesn't exist, they would contact the UNI team to add it (post-V1, this could be a submission form).

**Current state:** Live.

### 5. Owner Panel — SwiezoscRelationManager

**File:** `app/Filament/Panel/Resources/VenueResource/RelationManagers/SwiezoscRelationManager.php`

**What:** A second relation manager on the venue edit page, dedicated to freshness confirmation. This appears as a second tab ("Świeżość oferty") next to "Produkty w ofercie."

**Why a separate tab:** Freshness confirmation is a different mental mode from product management. "Do I carry this product?" (Produkty) vs "Is this product still available right now?" (Świeżość). Mixing both on one screen with the same action buttons would be confusing. Separating them into tabs lets the owner treat "freshness review" as a distinct weekly task.

**Freshness display:** Each product row shows:
- Name and category
- `confirmed_at` date in green/amber/red (green = ≤90 days, amber = 91–180 days, red = >180 days or null)
- A human label: "Świeże" / "Nieaktualne od X dni" / "Wygasłe — X dni temu"

**Actions:**
- Per-row: "Nadal w ofercie" button → updates `confirmed_at = now()` for that product
- Bulk: "Potwierdź wybrane" → updates all checked products at once, with confirmation modal

**Current state:** Live.

### 6. Owner Panel — ClaimVenue Page — `app/Filament/Panel/Pages/ClaimVenue.php`

**What:** A custom Filament page at `/panel/claim-venue` where a newly registered user (with `role = 'user'`) can submit a claim for their venue.

**The form has three fields:**
1. **Venue select** — shows only unclaimed active venues (`where claimed_by IS NULL`). A venue that's already claimed doesn't appear. If the owner's venue isn't in the list (e.g., not yet added by admin), there's helper text pointing them to contact the team.
2. **Verification method** — email or phone. Currently informational only (stored in the claim, no automated verification step in V1).
3. **Message** — optional free-text field for the owner to explain their connection to the venue.

**Guard logic in `mount()`:**
- If the user already has `role = 'owner'` and has a claimed venue → auto-redirect to their venue edit page
- If they have a pending claim → the page shows a "waiting" state with the venue name and submission date (the form is hidden)

**Navigation visibility:** The page only appears in the panel sidebar if the user has no pending claim. Once submitted, the nav item disappears to reduce confusion.

**Duplicate prevention:** Before creating a VenueClaim, the action checks for an existing pending claim from the same user. Submitting twice shows a warning notification instead.

**Current state:** Live. Accessible at `/panel/claim-venue`.

### 10. Bug Fixes During Build

**Bug 1 — Static vs instance `$view` property:**
Filament's `Page` and `Widget` base classes declare `$view` as a `protected string` (instance property). When creating new page/widget classes, attempting to declare `protected static string $view = '...'` causes a PHP `FatalError`: "Cannot redeclare non-static Filament\Pages\Page::$view as static." Fixed in both `ClaimVenue.php` and `VenueStatusWidget.php` by removing the `static` keyword.

**Bug 2 — NavigationIcon type mismatch:**
Filament v5's `$navigationIcon` property is typed `string|BackedEnum|null`. Declaring it as `protected static ?string $navigationIcon = 'heroicon-o-flag'` caused a type error because the parent declares the union type including `BackedEnum`. Fixed by using the `Heroicon` enum directly: `Heroicon::OutlinedFlag`.

Both bugs were caught during the route registration check (`php artisan route:list`) before any code was deployed.

## Decision Register

### Separate panel resource namespace vs reusing admin resources

- **Chosen:** Entirely separate namespace `App\Filament\Panel\Resources` with new resource classes for the owner panel
- **Rejected:** Using the same `VenueResource` with a configuration key (Filament's configurable resource feature) to show it in both panels
- **Why:** The owner's venue form has radically different fields, different scoping logic, and different relation managers. Trying to branch all of this inside a single resource class would create a branching mess. Separate classes make each panel's logic independent and readable. The shared admin resource stays clean. Status: **permanent**.

### Filament registration page for owner signup vs custom Livewire form

- **Chosen:** Use Filament's built-in `->registration()` page at `/panel/register`
- **Rejected:** A custom Livewire component on `/dla-lokali` that combines registration + claim in one step
- **Why:** The spec describes a two-step flow: register → then submit claim. Filament's registration page handles password confirmation, validation, and session management out of the box. Building a custom combined form would duplicate all of that. The two-step flow also feels more deliberate — the user has a panel account first, then claims a venue from within that context. Status: **permanent for V1**. A combined single-page flow (register + claim in one step) could improve conversion and is worth testing post-launch.

### Freshness confirmation as a separate relation manager tab vs merged with product list

- **Chosen:** Two separate relation managers: "Produkty w ofercie" (add/remove) and "Świeżość oferty" (confirm availability)
- **Rejected:** One relation manager with both "Add/Remove" and "Confirm" actions mixed together
- **Why:** These are different mental tasks with different cadences. Owners add products rarely (when the menu changes). They confirm freshness regularly (weekly or monthly). Separating them reduces cognitive load and makes the freshness-check workflow a focused, repeatable task. Status: **permanent unless user research shows otherwise**.

### Email notifications — synchronous vs queued

- **Chosen:** Synchronous notification dispatch (`$user->notify(...)` inline in the action closure)
- **Rejected:** Queue the notifications via `ShouldQueue` on the notification class
- **Why:** V1 has no queue worker set up. Adding `ShouldQueue` without a running queue worker would silently fail — notifications would sit in the `jobs` table unprocessed. Synchronous dispatch works reliably in all environments. The trade-off is that the admin's HTTP request takes slightly longer while the email is sent. This is acceptable for low-volume admin actions (claim approvals are rare events). Status: **revisit when a queue worker is configured** — see Technical Debt Log.

### Venue select on claim form — unclaimed only vs all venues

- **Chosen:** Show only unclaimed active venues (`WHERE claimed_by IS NULL AND is_active = 1`)
- **Rejected:** Show all venues including already-claimed ones
- **Why:** An owner can't claim a venue that's already been claimed. Showing claimed venues in the dropdown would be confusing (they'd select it, submit, and get rejected). Filtering to unclaimed venues shows only actionable options. Edge case: a venue whose claim is pending (but not yet approved) will still appear in the list, since `claimed_by` is only set on approval. This could allow duplicate pending claims for the same venue. The duplicate-claim check in the action prevents the same user from submitting twice, but two different users could both claim the same venue. Admin resolves this in the review step. Acceptable for V1. Status: **revisit post-V1** if duplicate claims become a support burden.

## Open Questions

1. **Mail provider for production** — what SMTP service will be used? (Postmark, Mailgun, Resend, SES?) This must be configured before any claim can be reviewed. The claim flow is broken end-to-end if email isn't working.

2. **Queue worker** — do you want claim approval emails to be queued (async) or synchronous? If synchronous, slow email providers will make the admin's approve action feel sluggish. If async, you need a background process running (Supervisor + Laravel Queue).

3. **Registration spam prevention** — the owner panel has `/panel/register` open to anyone. Should reCAPTCHA or email verification be added to prevent registration spam before any claim review?

4. **Claim review SLA** — how quickly will claims be reviewed? The ClaimVenue page and widget both say "we'll notify you" but give no time estimate. Setting an expectation (e.g., "within 2 business days") reduces owner churn during the waiting period.

5. **What happens if an owner's claimed venue is removed by admin?** — if a venue is deleted from the database after a claim is approved, the owner's panel will show an empty "Moje Miejsce" list. There's no graceful handling. Edge case but worth deciding before launch.

## Learning Path

**For understanding Filament multi-panel architecture:**
- Filament docs §05 Panel Configuration > "Creating a new panel"
- Filament docs §07 Users > "Authorizing access to the panel" — the `FilamentUser` contract
- Filament docs §09 Advanced Security > "Scoping queries" — why `getEloquentQuery()` override is the correct scoping mechanism

**For understanding the owner isolation approach:**
- The `getEloquentQuery()` override on a resource is Filament's recommended way to scope resources to the current user. It's applied to every query the resource makes — list, edit resolution, URL-based record lookup — so there is no way to bypass it by manipulating the URL.

**For understanding the two-panel auth separation:**
- Each Filament panel uses Laravel's standard auth guards. The `canAccessPanel()` method is checked by Filament's `Authenticate` middleware. Users without the correct role are redirected to that panel's login page.

## What Was Built

### 1. PostHogService — `app/Services/PostHogService.php`

**What:** A thin service class wrapping the PostHog PHP SDK (`posthog/posthog-php` v4.2, newly installed). Reads `POSTHOG_KEY` from `config('services.posthog.key')`, initialises the SDK once on construction, and exposes a single `capture(string $event, string|int $distinctId, array $properties = [])` method.

**Why a service class rather than inline SDK calls:** Three reasons. First, the SDK initialisation (`PostHog::init(...)`) only needs to happen once per request — a service class managed by the container handles this naturally. Second, centralising the `enabled` guard (PostHog is disabled if no API key is set, which is true in local/CI environments) means individual call sites don't each need to check. Third, injectable services are testable via dependency injection; static facade calls are not.

**Usage:** `app(PostHogService::class)->capture('claim_submitted', auth()->id(), ['venue_id' => ...])`. The `distinctId` is the user's database ID, matching the PostHog JS SDK which uses the same ID when users are identified.

**Current state:** Live. Instantiated fresh per request via the Laravel service container.

## Decision Register

### PostHogService as a class vs global helper function vs inline SDK calls

- **Chosen:** Injectable service class `App\Services\PostHogService`
- **Rejected (option A):** A global helper `posthog_capture(...)` function in `helpers.php`
- **Rejected (option B):** Direct `PostHog::capture([...])` calls with inline `PostHog::init()` at each call site
- **Why:** Option A is non-injectable and untestable. Option B means calling `init()` multiple times per request (the SDK is stateless, each call re-sends setup). The service class initialises once in its constructor, uses constructor injection (or `app()`), and is easy to swap for a null implementation in tests. Status: **permanent**.

### Dynamic robots.txt via route vs static file with hardcoded URL

- **Chosen:** Dynamic route that renders a Blade view
- **Rejected:** Static `public/robots.txt` with the production URL hardcoded
- **Why the static approach is fragile:** Any environment change (domain, staging URL, local dev) would serve a robots.txt pointing to the wrong sitemap URL. The Google Search Console sitemap submission also compares the URL in robots.txt to what it fetches — a mismatch causes indexing confusion. Dynamic rendering costs one extra PHP request per crawler visit (crawlers check robots.txt rarely), acceptable trade-off. Status: **permanent**.

### Sitemap controller vs Spatie's SitemapCrawler vs standalone sitemap command

- **Chosen:** `SitemapController` building the sitemap programmatically using `Spatie\Sitemap\Sitemap::create()` and `Url::create()`
- **Rejected:** Spatie's `SitemapCrawler` which crawls your own app's URLs like a spider
- **Why:** The crawler approach discovers URLs by HTTP-crawling the app — slow, fragile in environments without a running server, and susceptible to including admin URLs if redirects aren't set up correctly. The programmatic approach has explicit control over exactly which URLs are included, their priorities, and their change frequencies. Perfect for this app where URL patterns are well-defined and finite. Status: **permanent**.

### Search_performed fires per-keystroke-debounced vs on-form-submit

- **Chosen:** Fires on every debounced input event (300ms, matching Livewire's debounce)
- **Rejected:** Fire only when the user presses Enter or focuses away
- **Why:** The discovery page does live search — there's no submit action. The result list updates as you type. PostHog needs to see the queries people actually use, including intermediate states. 300ms debounce prevents flooding. Empty queries are excluded by the `$event.target.value.trim()` guard. Status: **permanent**.

## Learning Path

**For understanding PostHog server-side tracking:**
- The PHP SDK uses the same event model as the JS SDK. Events have a `distinctId` (identifying the user), an event name, and a properties object. The key is using the same `distinctId` in both SDKs so PostHog can stitch server-side and client-side events into a single user journey.
- PostHog docs: "Server-side tracking" > "PHP library"

**For understanding XML sitemaps:**
- A sitemap is a list of URLs you want Google to consider for indexing. It doesn't guarantee indexing — Google still crawls and decides. But it tells Google your pages exist and when they last changed. The `priority` attribute is a hint (0.0–1.0); the `changefreq` is also a hint. Google ignores both sometimes. `lastmod` is the most respected attribute because it signals freshness.
- Google Search Console allows you to submit your sitemap URL and monitor indexing status.

**For understanding Open Graph tags:**
- When someone shares a URL on Slack, LinkedIn, Twitter, or iMessage, the platform fetches the page and looks for `og:title`, `og:description`, and `og:image`. Without these, the platform guesses — usually badly. `og:url` is important for canonical URLs (so the share link resolves to the right page even if the sharer copied a redirected URL).
