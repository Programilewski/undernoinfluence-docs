# 2026-05-13 — Venue Analytics Admin Preview and Product Surface Split

## Session Overview

Goal: fix confusion around the per-venue analytics page by separating internal admin diagnostics from the future paid owner analytics product, while still giving the founder a way to QA owner-facing analytics with real venue data.

Outcome: the admin analytics page now has two modes on the same route:

- diagnostics mode for internal inspection;
- owner preview mode via `?preview_plan=free|basic|pro|premium`.

The SSOT was updated to document the product decision, progressive disclosure upsell rules, and the implemented admin QA bridge.

---

## What Was Built

### Admin diagnostics stays internal

`/admin/venues/{id}/analytics` remains the internal report viewer.

It shows all report groups and keeps the page useful for debugging:

- Profile Health;
- Demand Intelligence;
- Competitive Intelligence;
- Engagement Detail.

The page now explicitly labels itself as `Admin diagnostics view`.

### Preview as owner

The same admin route can render the owner-facing preview with real venue data:

```text
/admin/venues/{id}/analytics?preview_plan=free
/admin/venues/{id}/analytics?preview_plan=basic
/admin/venues/{id}/analytics?preview_plan=pro
/admin/venues/{id}/analytics?preview_plan=premium
```

The header now includes quick actions:

- Diagnostics;
- Preview Free;
- Preview Basic;
- Preview Pro;
- Preview Premium;
- Edit Venue.

Invalid preview plans fall back to diagnostics mode.

### Admin preview CSS fixed

The first preview implementation rendered correctly in Blade but appeared as plain vertical text in the admin panel. The cause was theme loading, not the analytics presenter:

- `/admin` did not load the custom Filament Vite theme;
- the theme source paths were too narrow for admin resource views.

Fixes:

- `AdminPanelProvider` now loads `resources/css/filament/panel/theme.css` with `viteTheme`;
- the shared theme scans all `app/Filament/**/*` classes and `resources/views/filament/**/*` views.

This matters because preview mode is the founder's manual QA surface for paid analytics. If the preview CSS silently disappears, plan testing becomes misleading.

### Owner-facing preview presenter

Added a separate owner preview Blade partial. It uses the same `VenueAnalyticsReportService` data but presents it like a customer product surface.

Plan visibility:

- Free: Overview only.
- Basic: Overview + Demand.
- Pro: Overview + Demand + Competition.
- Premium: Overview + Demand + Competition + Engagement.

Recommendations are inline, not a separate tab. This follows the product decision that recommendations should appear next to the metric they help explain.

### Progressive disclosure upsell

The owner preview applies the discussed progressive disclosure pattern:

- lower tier shows the existence of a real signal;
- higher tier unlocks the actionable resolution;
- teasers must be based on real report signals;
- Free should not become a wall of locked cards.

Current preview examples:

- Free can tease demand signals only if the report has real demand gaps.
- Basic can tease competitive context if competitor/search-spike signals exist.
- Pro can tease Premium engagement timing and alerts.

### Breadth score protection

Exact breadth percentile/rank stays hidden from owner-facing presentation. The UI uses qualitative labels such as `Leading breadth` instead of exposing raw internal scoring.

### Entitlement modules documented

Documented the principle that paid analytics capabilities are modules, not just plan sections.

The model is:

- Plan = commercial package.
- Feature module = runtime entitlement.
- Trigger = why the entitlement is active.

This means a module can be active because of a paid plan, manual admin override, beta access, comp, partner deal, trial, or future add-on payment. Runtime code should check feature entitlement (`hasFeature`) instead of hardcoding plan names, except for pricing labels and upgrade prompts.

### SSOT updates

Updated `inspo/interactive_v1_feature_spec_SSOT.html` to reflect:

- admin analytics is diagnostics, not the paid owner product;
- owner preview mode is now live as admin QA tooling;
- `preview_plan` is the manual regression path;
- progressive disclosure upsell rules and teaser density;
- paid analytics as entitlement modules that can be triggered by plans, manual overrides, or future payment events;
- real owner-panel paid analytics is still deferred until validation.

## Decision Register

### Decision: same route, different presenter

Chosen: keep `/admin/venues/{id}/analytics` as the single admin route and switch rendering with `preview_plan`.

Rejected: separate route/controller or fake owner account workflow for day-to-day QA.

Reason: this lets the founder test Free, Basic, Pro, and Premium owner experiences against the same real venue data without context switching.

### Decision: preview is not impersonation

Chosen: preview mode is clearly labelled `Admin Preview`.

Reason: it avoids confusing screenshots, demos, and admin QA with actual owner sessions. It tests presentation and plan gating, not authentication state.

### Decision: owner analytics uses product tabs, not tier walls

Chosen: owner preview uses Overview, Demand, Competition, and Engagement.

Rejected: showing all tier sections as one long scroll.

Reason: owners should see a product experience, not the internal report matrix.

### Decision: plans package modules, modules control access

Chosen: document analytics reports as entitlement modules controlled by `VenueFeature` and checked with `hasFeature`.

Rejected: implementing paid analytics as plan-name conditionals spread through views/controllers.

Reason: this keeps Basic/Pro/Premium flexible. The same module can be sold in a plan, manually comped, enabled for beta testing, granted to a partner, or later sold as an add-on without rewriting the UI.

## Risk Register

| Risk | Impact | Mitigation |
|---|---|---|
| Preview UI becomes mistaken for the final owner panel | Founder may overestimate customer readiness | Banner says `Admin Preview`; real `/panel` integration remains a separate step |
| Preview currently covers structure more than polished UX | It may still feel early as a paid product | Treat it as QA scaffold; improve visual design before owner launch |
| Admin preview CSS can disappear if the theme entrypoint or Tailwind sources drift | Founder may QA an unstyled or misleading owner experience | Admin and owner panels both load the shared Filament theme; theme scans all Filament app/view paths |
| Teasers may appear too often if future logic is careless | Free tier could feel like a nag wall | SSOT caps Free teasers at 1–2 and requires real signals |
| Same report service feeds both presenters | Internal report fields could leak into owner UI | Tests assert exact breadth percentile/rank stays hidden |
| Plan names get hardcoded into access checks | Future add-ons/manual grants become expensive to support | Use feature entitlement checks; keep plan names for packaging and labels |

## What to Test in the Browser

Open one real venue in admin analytics and test:

1. Diagnostics mode: `/admin/venues/{id}/analytics`
2. Free preview: `?preview_plan=free`
3. Basic preview: `?preview_plan=basic`
4. Pro preview: `?preview_plan=pro`
5. Premium preview: `?preview_plan=premium`
6. Invalid fallback: `?preview_plan=enterprise`

Check:

- the yellow preview banner appears only in preview mode;
- preview pages render as cards/tabs/sections, not plain vertical text;
- Free does not show Demand, Competition, or Engagement sections;
- Basic shows Demand but not Competition or Engagement;
- Pro shows Competition but not Engagement;
- Premium shows Engagement;
- breadth appears as a qualitative position, not exact percentile/rank;
- dark mode surfaces are readable.

## Business Impact

This solves the immediate product/design confusion:

- the admin page is now clearly an internal diagnostic tool;
- the founder can still preview the owner experience using real venue data;
- paid-plan upsell logic is now represented in both the SSOT and UI scaffold;
- the future owner analytics product has a concrete shape before subscription work begins.

The most important monetization decision is now encoded: each plan should deliver value while making the next plan's missing decision obvious.
