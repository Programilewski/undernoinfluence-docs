## What Was Built

### Required NIP verification for venue claims

Added a dedicated `ValidNip` validation rule:

- strips formatting before validation through request preparation;
- requires exactly 10 digits;
- rejects repeated placeholder values such as `0000000000`;
- validates the control digit using weights `6, 5, 7, 2, 3, 4, 5, 6, 7`;
- stores the normalized 10-digit NIP.

Files:

- `app/Rules/ValidNip.php`
- `app/Http/Requests/StoreVenueClaimRequest.php`

## Decision Register

### Decision: require NIP on B2B claims

Chosen: NIP is required for all venue-claim submissions.

Rejected: keeping NIP optional as “supporting proof.”

Reason: venue claiming is a B2B ownership/authorization workflow. NIP gives a verifiable legal-business anchor, improves manual review, and prepares future billing without adding major user friction.

### Decision: validate NIP locally with checksum

Chosen: implement local checksum validation in `ValidNip`.

Rejected: only checking length or waiting for external API verification.

Reason: checksum validation catches obvious bad input immediately and avoids adding external dependency risk to the submission path.

### Decision: keep NIP out of analytics

Chosen: store NIP for admin verification, but do not send it to PostHog.

Reason: NIP can be sensitive in some contexts, especially for sole proprietors. Analytics does not need it.

## Technical Debt Log

- NIP is stored as plain normalized text. This is practical for admin review, but if claim volume grows, consider access logging or encryption-at-rest for claim verification fields.
- NIP validates format/checksum, not real-world authority. Manual review is still required.
- The claim form still uses a normal select for existing venues. It may need autocomplete once venue volume grows.

- business verification: `business_nip`, `claimant_role`;
- contact verification: `contact_name`, `contact_email`, `contact_phone`, `verification_method`;
