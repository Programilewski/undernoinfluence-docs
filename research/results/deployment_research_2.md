## Recommended architecture

- **Provisioning:** Ansible community package 14.4.0, pinned on the developer workstation; it is GPL-3.0-or-later, acceptable for an internally run tool.[^1_1]
- **Deployment:** Deployer 8.0.5, pinned in the repository; it requires PHP 8.3 or later and uses the MIT licence.[^1_2]
- **Release model:** `/srv/app/releases/<release-id>`, `/srv/app/shared`, and `/srv/app/current`.
- **Application runtime:** Nginx, PHP-FPM, PostgreSQL, Supervisor and cron directly on Ubuntu—no Docker and no resident deployment agent.
- **Build:** A clean local Linux build using locked Composer and npm dependencies; production receives only an allow-listed artifact containing `vendor/` and generated public assets.
- **CI:** GitHub Actions verifies commits and tags but does not hold production SSH keys or deploy.
- **Monitoring:** A hosted EU monitor only after verifying its DPA and residency; otherwise use a separate home-server Incus container as the temporary monitor.
- **Backups:** Encrypted application/database backups to Scaleway plus OVH’s whole-machine backup. OVH’s included daily system backup retains only the current daily backup for 24 hours, so it is not adequate as the application’s historical backup scheme.[^1_3]


## Ordered process

### Provisioning

1. **Create one infrastructure repository area.** Keep `ansible/`, `deploy.php`, Nginx templates, Supervisor configuration, cron definition, smoke tests and restore documentation beside the application code. Pin Ansible collections and deployment dependencies rather than pulling floating versions.
2. **Rebuild the Incus guest as Ubuntu 26.04.** The laptop host can remain Ubuntu 24.04; the guest should match production’s OS release, architecture and package sources. Differences should be limited to inventory variables such as domain, IP address, TLS method, mail credentials, backup bucket and resource limits.
3. **Run the same Ansible playbook against both hosts.** Use inventories such as:

```text
inventories/home/hosts.yml
inventories/production/hosts.yml
```

The same roles should install and configure Nginx, PHP 8.5 FPM/extensions, PostgreSQL 18 client/server, Supervisor, cron, Certbot, firewall, log rotation and the application users. Assertions should fail provisioning unless PHP reports `8.5.x`, PostgreSQL reports `18.x`, and all required extensions are loaded.
4. **Create two Unix identities.** `deploy` owns releases and connects through SSH; `www-data` runs PHP-FPM, queue workers and the scheduler. Add `deploy` to the application group, but do not run PHP-FPM as `deploy`.
5. **Use predictable ownership.**

```text
releases: deploy:app, directories 2750, files 0640/0644
shared/storage: deploy:app, directories 2770, files 0660
shared/.env: root:app, 0640
```

Set `umask 0002` for deployment commands and runtime processes. Setgid on writable directories preserves the `app` group on newly created files.
6. **Harden network access.** Expose only ports 80 and 443 publicly. Restrict SSH to keys and preferably a known address or Tailscale; disable password and direct root login. PostgreSQL should listen only on loopback, with no public 5432 rule.
7. **Generate local secrets on each box.** Create `APP_KEY`, database password and backup-encryption password once, idempotently, and never rotate them during an ordinary deploy. Insert provider-issued Scaleway credentials through an interactive encrypted workflow; suppress all Ansible output with `no_log`.
8. **Store `.env` outside releases.** Keep it as `/srv/app/shared/.env`, root-owned and group-readable, and link it into every release before running Artisan. Escrow the backup-decryption password and recovery instructions in a password manager outside both servers.
9. **Install production TLS automatically.** Use Certbot’s Nginx or webroot integration, verify the systemd renewal timer, and run `certbot renew --dry-run`; Certbot installations provide scheduled renewal support. Let’s Encrypt’s default certificates remain 90 days in 2026, falling to 64 days in February 2027, which makes tested automation more important than certificate duration.[^1_4][^1_5][^1_6]
10. **Treat home TLS as an adapter.** Prefer a trusted Tailscale certificate or a dedicated DNS-challenge certificate. The certificate acquisition mechanism may differ, but the Nginx TLS directives, application headers and smoke tests should remain the same.

### Commit and CI

11. **Work through short-lived branches or direct commits to `main`.** Before push, run the fast local PHPUnit suite, formatter/static checks and an asset build. Never tag a dirty working tree.
12. **Run minimal CI on every pull request and `main` push.** It should:

- Install the pinned PHP 8.5 toolchain and PostgreSQL 18 service.
- Run `composer validate` and `composer install`.
- Run database migrations against an empty database.
- Run all PHPUnit tests.
- Run `npm ci` and `npm run build`.
- Assert that the required MapLibre `.mjs` files, Vite manifest and Filament assets exist.
- Assert that `public/hot` does not exist.
- Run formatter/static-analysis checks already adopted by the project.
- Report Composer and npm vulnerability findings without automatically deploying.

Pin third-party GitHub Actions to full commit SHAs; GitHub identifies this as the only immutable way of referencing an action.[^1_7]

13. **Tag only a green commit.** Create a signed annotated tag where practical, push it, resolve the tag to its full commit SHA, and record both in a deployment manifest. The deployment must fail if the remote tag resolves to another SHA.

### Artifact build

14. **Build from a clean temporary worktree.**
```text
git worktree add --detach .deploy/work/<tag> <tag>
composer install --no-dev --prefer-dist --no-interaction --optimize-autoloader
npm ci
npm run build
```

Composer’s post-autoload scripts generate Filament assets in this build directory. Copy MapLibre modules as part of the version-controlled build script, not as an undocumented manual command.

15. **Create an allow-listed artifact.** Include only:
```text
vendor/
public/build/
public/vendor/
bootstrap/cache/packages.php
bootstrap/cache/services.php
```

Do not archive `.env`, Composer authentication, npm configuration, `storage`, logs, caches or arbitrary files from the workstation. Include a manifest containing tag, commit SHA, tool versions, lockfile hashes, critical asset paths and the archive’s SHA-256 hash.

16. **Use the exact same artifact for both environments.** Rehearse it on home pre-production first, then upload that unchanged artifact from the developer PC to production. Nothing is copied from home to production, and neither environment builds another environment’s release.

### Atomic deployment

17. **Acquire a deployment lock.** Deployer should reject concurrent runs and perform preflight checks for free disk space, current backup health, tag/SHA agreement and artifact checksum.
18. **Create the new release.** On the target, clone or fetch the private repository, checkout the exact tag, and independently verify its full SHA. Link `.env` and `storage`, then extract the artifact into the release.
19. **Reject incomplete assets.** Before touching `current`, fail unless:

- `public/build/manifest.json` exists.
- Every configured critical MapLibre `.mjs` file exists.
- Filament’s expected CSS/JS entry points exist.
- `public/hot` is absent.
- `vendor/autoload.php` exists.
- No `.env` or credential file exists inside the artifact.

20. **Prepare release caches.** Run `php artisan optimize:clear`, followed by package/application sanity checks. Do not ship config, route or view caches produced on the developer machine.
21. **Handle migrations by compatibility class.**

- **Compatible migration:** Additive schema change first, while old code still runs; execute `php artisan migrate --force`, then switch code.
- **Destructive or incompatible migration:** Put the application into maintenance mode, stop queue workers gracefully, take an immediate database backup, migrate, switch the release, start workers and exit maintenance mode.
- **Preferred strategy:** Use expand-contract across two releases—add new schema, deploy code that supports both forms, migrate data, and remove old schema only in a later release.

A code rollback does **not** reverse database migrations. Automatic `migrate:rollback` must not be part of release rollback.

22. **Cache the new release.** After the final production `.env` link and migration, run `php artisan optimize`. Keep `bootstrap/cache` release-local, while `storage` remains shared.
23. **Switch atomically.** Replace `/srv/app/current` with a symlink to the prepared release using an atomic rename. Requests in progress continue on the old real release; new requests resolve the new target.
24. **Refresh long-lived processes in this order.**
25. Gracefully reload PHP-FPM.
26. Execute `php /srv/app/current/artisan queue:restart`.
27. Wait until Supervisor has two new workers.
28. Run HTTP and application smoke tests.
29. Remove old releases only after old workers have exited.

Do not run `cache:clear` after `queue:restart`, because both use the configured cache store and clearing it could remove the restart signal.

25. **Run post-deployment smoke tests.**

- HTTPS redirect and certificate validity.
- `/health/live`.
- Database-backed readiness endpoint.
- One real public page.
- Admin authentication page without submitting credentials.
- A known `.mjs` URL with an accepted JavaScript `Content-Type`.
- Vite assets with expected cache headers.
- A synthetic queue job updating a database heartbeat.
- Scheduler heartbeat freshness.
- Optional real browser map smoke test against home pre-production.

26. **Record the deployment.** Append environment, tag, SHA, artifact hash, migration list, deployment time and outcome to a local and server-side append-only deployment log.

### Rollback

27. **Rollback by deploying the previous tag through the same recipe.** If its release directory remains, Deployer can switch directly; otherwise recreate it from the tag and its artifact. Then reload PHP-FPM, gracefully restart workers and repeat smoke tests.
28. **Escalate schema-related rollback.** If the previous code cannot operate on the current schema, do not improvise an automatic down-migration. Enter maintenance mode and use the documented forward fix, explicit reverse migration or database restore.

## Nginx requirements

The server root may retain the convenient symlink, but PHP paths should resolve it:

```nginx
root /srv/app/current/public;

location / {
    try_files $uri $uri/ /index.php?$query_string;
}

location ~ \.php$ {
    include fastcgi_params;
    fastcgi_param SCRIPT_FILENAME $realpath_root$fastcgi_script_name;
    fastcgi_param DOCUMENT_ROOT $realpath_root;
    fastcgi_pass unix:/run/php/php8.5-fpm-app.sock;
}
```

Manage `/etc/nginx/mime.types` through Ansible and add an idempotent mapping inside its existing `types` block:

```nginx
application/javascript mjs;
```

Use long `immutable` caching only for content-hashed Vite files. Give non-hashed MapLibre or Filament paths a shorter cache lifetime unless the URL contains a package or release version. Include both `application/javascript` and `text/javascript` among gzip types, then require `nginx -t` before every reload.

## Runtime processes

Supervisor should run both queue processes as `www-data`:

```ini
[program:app-worker]
process_name=%(program_name)s_%(process_num)02d
command=/usr/bin/php artisan queue:work database --sleep=3 --tries=3 --max-time=3600 --timeout=120
directory=/srv/app/current
user=www-data
numprocs=2
autostart=true
autorestart=true
stopasgroup=true
killasgroup=true
stopwaitsecs=150
redirect_stderr=true
stdout_logfile=/var/log/app/worker.log
```

The shown 120-second timeout is an **example**, not a recommendation confirmed against the jobs. Set it above the longest legitimate job and below the database queue connection’s `retry_after`, then set `stopwaitsecs` above the worker timeout.

Use one root-managed `/etc/cron.d/app-scheduler` entry:

```cron
* * * * * www-data cd /srv/app/current && /usr/bin/flock -n /run/lock/app-scheduler.lock /usr/bin/php artisan schedule:run >> /var/log/app/scheduler.log 2>&1
```

Pre-create the lock and log paths with `app` group ownership. The cron command resolves `current` afresh each minute, so it does not retain an old release.

## CI decision

Implement CI **before the first external beta**, but keep deployment manually approved and local. The estimated setup is 3–5 hours, ongoing maintenance is 0.25–0.75 hour monthly, and it should save approximately 0.5–2 hours monthly while catching failures in a clean environment.

A complete run will probably take **2–5 minutes**, an estimate that includes dependency installation and PostgreSQL startup rather than only the measured 30-second test suite. At 50 runs per month this is roughly 100–250 minutes, so it fits comfortably inside the user-stated 2,000-minute allowance if that allowance remains accurate.

Do not initially:

- Deploy production from Actions.
- Store production SSH or `.env` secrets in GitHub.
- make every dependency audit advisory a hard deployment failure.
- Build an elaborate matrix of PHP/PostgreSQL versions.
- Automatically tag or release every merge.

CI becomes the artifact builder later when reproducible artifacts must be available independently of the developer PC. At that point, publish tag-keyed artifacts with checksums to a private EU object-storage bucket and retain them at least as long as deployment rollback is supported.

## Backups

Use three independent layers:

1. **OVH machine backup:** Fast disaster recovery for the most recent host state, but only a 24-hour restore point under the included standard service.[^1_3]
2. **Daily application backup:** PostgreSQL dump plus user-generated files, encrypted before upload to Scaleway.
3. **Pre-migration backup:** An additional database-only backup immediately before an incompatible or destructive migration.

Spatie Laravel Backup v10 requires PHP 8.4 and Laravel 12 or later, uses `pg_dump` for PostgreSQL, supports AES-256 archive encryption and can verify that the completed archive opens and contains files. Pin the version actually resolved in `composer.lock`, enable archive verification, and restore with matching PostgreSQL 18 client tools.[^1_19][^1_20][^1_21]

Recommended initial retention:

- 14 daily backups.
- 8 weekly backups.
- 12 monthly backups.
- Monthly automated restore to a temporary database after launch.
- Manual full restore drill before launch and after changing backup configuration.

Scaleway’s listed Standard Multi-AZ rate is €0.01606 per GB-month before tax; Scaleway’s April 2026 pricing notice says products not listed as changing retained their pricing. Therefore, 20 GB-month would be approximately **€0.32/month before VAT**, an arithmetic estimate excluding exceptional retrieval or transfer charges.[^1_22][^1_23]

Exclude logs, caches, sessions, compiled assets and temporary backup files. Include PostgreSQL, claimed-venue uploads and any irreplaceable application files.

## Monitoring

Before launch, monitor:

- Public HTTPS homepage.
- A cheap liveness endpoint that does not query every subsystem.
- A readiness endpoint checking PostgreSQL and essential configuration.
- The existing five-minute scheduler heartbeat.
- A synthetic queued job that updates a timestamp after being processed.
- Daily backup success and maximum backup age.
- Disk space and inode usage.
- TLS expiry and Certbot renewal failure.
- Failed-job count and oldest pending queue job age.

Better Stack’s 2026 published free offer includes ten monitors, ten heartbeats, email/Slack alerts and a status page at \$0. It is economically appropriate—estimated setup 1–2 hours, under 0.25 hour monthly and low protocol lock-in—but use it only after confirming a suitable DPA and EU data processing for the free account.[^1_24]

If that legal verification fails, run Uptime Kuma 2.5.5 in a separate Incus container on the home server, not inside application pre-production; version 2.5.5 was released in September 2026. Its non-Docker installation requires Node.js 20.4 or later, Git and a process manager, so this alternative adds an estimated 1.5–3 setup hours and 0.2–0.5 maintenance hour monthly.[^1_25][^1_26]

Do not expose exception traces, email addresses, tax IDs or signed URLs to monitoring providers. Send only status, duration, environment name and an opaque check identifier.

## OS maintenance

- Enable automatic installation of security updates.
- Rehearse ordinary package upgrades on the Incus guest, observe it for 24–72 hours, then apply them to production.
- Apply critical actively exploited security fixes sooner, even if that shortens rehearsal.
- Check `/var/run/reboot-required`; reboot production in a declared maintenance window.
- Run the complete smoke-test set after PHP, Nginx, PostgreSQL or kernel updates.
- Record installed package versions after every provisioning or patch run.
- Keep PHP and PostgreSQL major versions pinned, but allow supported patch/security updates.
- Test Ansible idempotence: a second playbook run should report no unexpected changes.


## Failure controls

| Failure mode | Prevention | Deployment validation |
| :-- | :-- | :-- |
| FPM serves old code after symlink switch | `$realpath_root` and graceful PHP-FPM reload | Response exposes expected release SHA internally |
| Nginx passes logical `current` path | Set both `SCRIPT_FILENAME` and `DOCUMENT_ROOT` from `$realpath_root` | Nginx integration test |
| Old queue worker keeps old code | `queue:restart`, Supervisor autorestart, wait for two replacements | Worker heartbeat contains new SHA |
| Old release deleted too early | Keep at least five releases; clean only after worker replacement | No process has an executable/CWD in removed release |
| Runtime cannot write storage | Shared `storage`, setgid directories, common `app` group and `umask 0002` | Write/delete probe as `www-data` |
| Deploy overwrites runtime files | Release code is immutable; only `shared/storage` and `.env` are linked | Permission audit |
| Sessions disappear | `storage/framework/sessions` remains in shared storage | Session survives a pre-production deploy |
| Cached config contains build-machine values | Never ship application config cache; run `optimize` after target `.env` link | `config:show` sanity checks |
| `public/hot` points to Vite dev server | Explicitly exclude and fail if present | Asset preflight |
| Missing MapLibre module | Artifact manifest lists critical files | File and browser map checks |
| `.mjs` gets wrong MIME type | Ansible-managed MIME mapping | `curl -I` assertion |
| Filament assets are absent | Composer scripts run during clean artifact build | Expected asset files checked before switch |
| Rollback fails after schema change | Expand-contract migrations | Compatibility checklist on every migration |
| Restart signal is erased | Run `optimize:clear` before `queue:restart` | Verify worker PIDs change |
| Two deployments overlap | Deployer lock | Second deploy intentionally rejected |
| Scheduler fires twice | `flock` plus Laravel overlap guards for long commands | Scheduler heartbeat and logs |
| Artifact contains secrets | Allow-list archive paths and scan archive contents | Fail on `.env`, `auth.json`, `.npmrc` |
| Disk fills during release | Preflight free-space threshold and bounded release retention | Disk check before extraction |
| Backup exists but is unusable | Archive verification and regular restore tests | Restored row count/schema checks |

## Defer list

| Defer | Bring it back when |
| :-- | :-- |
| Paid server panel | Server administration exceeds 3–4 h/month or a nontechnical operator must administer multiple applications |
| Dedicated hosted staging VPS | Home pre-production no longer reproduces integrations, multiple contributors need simultaneous access, or production data migrations become risky |
| Automatic production deployment | More than four safe deploys per week and the manual approval step has become measurable friction |
| CI-built release registry | A second deployer/workstation appears, local rebuild reproducibility becomes a problem, or historical artifacts must survive workstation loss |
| Blue-green deployment | Material traffic or an SLA makes a maintenance window unacceptable |
| Redis | Database queue/cache contention, lock latency or throughput measurements justify it |
| Managed PostgreSQL | Database resource contention, operational patching exceeds 2 h/month, or RTO/availability requirements exceed one VPS |
| Point-in-time recovery | Accepted RPO becomes less than 24 hours or claim data becomes expensive to recreate |
| Object-lock/WORM backups | Root compromise or malicious deletion enters the formal threat model |
| Centralised logs/APM | Production incidents take more than one hour monthly to diagnose or 5xx/latency trends become invisible |
| CDN/WAF | Geographic latency, bandwidth cost or abuse is measured—not merely anticipated |
| Premium OVH seven-day backup | Application-level restores prove insufficient for whole-machine recovery |
| Public status page | External users or partners begin depending on service availability |
| Automated browser-map checks | A second blank-map regression occurs or map releases become frequent |
| Multi-server scheduler/queue design | A second application node is introduced |

## Unverified assumptions

- The stated OVH VPS-1 CPU, RAM, disk, datacentre and commercial terms were treated as fixed inputs, not independently revalidated.
- The ≈€8/month Ploi Basic price, branch-only deployment behaviour, `composer --no-dev` omission and paid-tier zero-downtime limitation were not verified against a qualifying 2026 primary source.
- The stated GitHub Free allowance of 2,000 private-repository Actions minutes and its exhaustion behaviour were not independently verified.
- Availability of the exact required PHP 8.5 and PostgreSQL 18 packages from the selected Ubuntu/third-party repositories must be confirmed by the first Ansible dry run.
- No 2026 primary-source confirmation of a suitable Ploi DPA, Better Stack free-tier DPA or guaranteed EU residency was obtained.
- Scaleway TEM pricing, DPA terms and exact backup-bucket lifecycle capabilities were not verified here.
- Exact queue `timeout`, `retry_after`, job duration, backup duration, database size, growth rate, RPO and RTO cannot be selected without measurements.
- The local build recommendation assumes the developer workstation is Linux on the same CPU architecture as production and can run the pinned PHP 8.5, Composer, Node and npm versions.
- Provider-issued Scaleway credentials cannot literally be generated on the application box; only their local storage and environment-specific configuration can be created there.
