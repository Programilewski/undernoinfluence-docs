# V1 — Data Authority MVP

**Theme:** Become the trusted source of truth for NoLo venue data in Warsaw.
**Target:** ~~Live by early June 2026~~ — **missed; no new date set.** The June target assumed
code was the constraint. It was not: the code has been feature-complete since roughly then,
and the launch is gated on real venue data, hosting and backups. Set a new date from the
seeding rate once the first ten real venues are in.
**Success metric:** 50-60 real Warsaw venues seeded, site indexed by Google, first venue owners claiming profiles.
**Reality check (2026-08-18):** 0 real venues, 0 claims, no hosting, no backups, no outbound mail.

## Exposure tiers — what is visible at launch

**Added 2026-08-27**, answering the feature-mapping request in `../Phone notes/27.08.md`. The tables
above say what exists; this says what a visitor can reach. Everything below is already built and
tested — the tier is a decision about visibility, not about work. Cutting a finished feature costs
removal time; hiding one costs nothing.

| Tier | Features | Why |
|---|---|---|
| **Exposed at launch** | Discovery map, list and filters · venue profiles with full menu · SEO cluster (city × district × category) · sitemap and JSON-LD · freshness and "Sprawdzona karta" badges · static pages · anonymous analytics (`events`, `venue_stats`) · admin panel · canary venues and AI-crawler blocking | This is the product: a browsable, indexable directory. The analytics are the validation instrument — the whole launch exists to produce them |
| **Built, deliberately dark** | Owner panel at `/panel` · claim flow (admin-recorded) · product proposals · owner drink CRUD · inaccuracy reports (admin side only) · `VenuePlan` price list | `browse-only-v1.md` and `admin-recorded-claims-v1.md`. The panel answers at a known URL — see pre-launch checklist item 6 |
| **V2** | Public user accounts · saves and collections · post-visit confirmation · community reporting · public `/dla-lokali` page · owner analytics dashboard · tiered badges · opening hours · venue photos | Each needs accounts, real traffic, or owner demand that does not exist yet |
| **V3** | Multi-city · i18n · B2B monetization · public API | Gated on V2 metrics |

**What this changes about the launch date: nothing.** Every V1 feature is `DONE` and covered by the
suite — **465 tests passing, re-run and verified on 27.08**. The critical path below is data, infrastructure and one basemap migration — not
features. Two levers do shorten it, and neither is a feature:

- **SMTP moves off the critical path.** Mail notifies owners when a claim is approved. With the
  panel dark at launch there are no claims on day one, so Scaleway TEM becomes "before the first
  owner is onboarded", not "before the site is public".
- **50–60 venues is self-imposed.** 25–30 venues concentrated in three central districts rank the
  district pages as well as 60 spread across eighteen, and halve the longest task on the list.

## Priming Work for V2

Things to build/configure in V1 that make V2 features dramatically easier. These are NOT V2 features — they're V1 infrastructure investments.

### PR-1: PostHog Event Schema for Post-Visit Confirmation

> **Withdrawn 2026-09-17.** This section instructed adding a `user_session_id` and a persistent `visitor_id` cookie to events so a V2 flow could ask "who clicked directions to venue X in the last 30 minutes". **The analytics architecture decided afterwards forbids exactly that**: the events table holds no identifier of any kind — no IP, no cookie, no session id — and automated traffic is dropped at the write rather than filtered later. A V2 confirmation flow will need a mechanism that does not depend on recognising a returning visitor, or it does not get built. Left here with its reasoning visible, because the trade it assumed is the one the project deliberately took the other side of.

### PR-2a: User Registration for End Users (B2C) — Technical

**V2 feature it enables:** Saves/collections (V2-F2), post-visit confirmation (V2-F1), community reporting (V2-F4)

**What to do now:**
> **Corrected 2026-08-18:** there is no `/panel/register` route and no public registration anywhere in the app — verified with `route:list`. Owner accounts are created by an admin (`../decisions/product/admin-recorded-claims-v1.md`), and public registration is explicitly out of scope for V1 (`../decisions/product/browse-only-v1.md`). **Do not build this in V1.** It stays here as a V2 note.

- The `users` table has a `role` enum column (`admin` / `owner` / `user`), no Spatie Permissions package.
- V2, not V1: a lightweight public registration flow outside the owner panel.
- V2: add a nullable `phone` column to users if push notifications happen.

**Why now:** Almost every V2 feature requires knowing who the user is. The owner panel registration exists but is B2B-focused. A public registration flow is the foundation for V2's B2C features.

**Effort:** 2-3 hours for basic auth scaffolding

### PR-2b: User Registration — Privacy & Legal Preparation

**V2 feature it enables:** Same as PR-2a. This is the non-code prerequisite.

**What to do now:**
- Update the privacy policy (`/polityka-prywatnosci`) to cover: user account data, saved venues, visit tracking, session data
- Define legal basis for data processing under GDPR/UODO (legitimate interest for core functionality, consent for optional tracking like visit confirmations)
- Define data retention policy: how long are visit confirmations kept? What about deleted accounts?
- Design account deletion flow: user requests deletion → what cascades? (venue_visits anonymized? saves deleted? reports retained but de-identified?)
- Document this in a data processing record (required by GDPR Art. 30 for any controller)

**Why now:** Once you store user data beyond the owner panel (which has a clear contractual basis), you're subject to GDPR obligations. Poland's UODO enforces this actively. Shipping user registration without a compliant privacy policy and deletion flow is a legal risk that grows with every user who signs up. This isn't "nice to have" — it's a hard blocker before V2-F2 goes public.

**Effort:** 3-5 hours (draft privacy policy update + deletion flow design). No lawyer needed for initial draft — use UODO guidance templates. Consider legal review before V2 public launch.

**Status:** BLOCKED until privacy policy update is drafted

### PR-3: `venue_visits` Table (Empty, Schema Only)

**V2 feature it enables:** Post-visit confirmation (V2-F1), visit analytics for owners (V2-F3)

**What to do now:**
```
Schema (create migration, don't build any feature around it):

venue_visits
- id (bigint PK)
- venue_id (bigint FK -> venues)
- user_id (bigint FK -> users, nullable)
- session_id (varchar, nullable — for anonymous tracking)
- source (varchar — 'directions_click', 'manual_checkin', 'confirmed_visit')
- visited_at (timestamp, nullable — when user confirms they visited)
- menu_accuracy (enum: null, 'accurate', 'inaccurate', 'partial')
- feedback_note (text, nullable)
- created_at (timestamp)
- updated_at (timestamp)

Indexes: (venue_id, created_at), (user_id, created_at)
```

**Why now:** Creating a table costs nothing. But if you wait until V2, you either (a) lose the window to correlate directions clicks with visits, or (b) have to backfill from PostHog events, which is messy. Having the table ready means V2 can start writing to it immediately.

**Effort:** 15 minutes (migration only, no model/controller/UI)

**Status: `DONE`** — `database/migrations/2026_06_17_000014_create_venue_visits_table.php`. Table exists and is empty, as intended.

### PR-4: Queue Infrastructure

**V2 feature it enables:** Delayed notifications (V2-F1), async email (V2-F3), background scoring jobs

**What to do now:**
- Ensure Laravel queue worker is running in production (Supervisor/Horizon)
- Test that `dispatch()->delay()` works end-to-end
- Move claim notifications from synchronous to queued (`implements ShouldQueue`)

**Why now:** V2's post-visit confirmation flow requires `dispatch(new SendVisitConfirmation($visit))->delay(now()->addMinutes(30))`. If queue infrastructure isn't production-ready, none of the delayed features work. And making claim notifications queued is a standalone improvement anyway.

**Effort:** 1-2 hours

**Status: `DONE` in code, `TODO` in production** — the four claim and erasure notifications implement `ShouldQueue`, and `supervisor/uni-worker.conf` exists. `.env` runs `QUEUE_CONNECTION=database`. What is untested is a worker actually running on a production host, because there is no production host yet.
