## 1. `kawiarnia` and `hotel` — shorter, as you asked

You wrote: *"Add these, but the name `kawiarnia_koktajlbar` is too long, we need some polish descriptive word for it that is shorter."*

**Agreed, and shortening it also made the taxonomy better.** My compound came from `venue-type-filtering`'s own phrasing — *"kawiarnia/koktajlbar"* as one category — but once I tried to write it as a single value, the reason it was hyphenated in the record stopped being a good reason for the code:

**A cocktail bar is already a `bar`.** The enum has had `bar` since April. Pairing it with "kawiarnia" created one lumpy category whose only justification was that both are drinks-led — which `bar` already covers on its own. What was genuinely missing was the café.

**Shipped:**

| Value | Label | What it is |
|---|---|---|
| `restauracja` | Restauracja | Food-led; a NoLo offer of realistically three to five |
| `pub` | Pub | |
| `bar` | Bar | **Cocktail bars live here** — drinks-led, the widest NoLo capacity |
| **`kawiarnia`** | Kawiarnia | **New.** A café that makes named mocktails. One word, nine letters |
| **`hotel`** | Hotel | **New.** A hotel bar answers to a different guest |
| `inne` | Inne | A cinema bar, a bowling alley, a theatre foyer |

**And the default is gone from the form.** `inne` stays as a *deliberate* answer and stops being what a venue gets when nobody chose. That was the actual defect: a default made "nobody classified this" and "this really is other" the same value, and `venue-type-filtering`'s whole purpose is comparing like with like, which `inne` cannot do if it is half the catalogue.

**None of this admits anybody.** `venue_type` is a label and a filter, never an admission gate — the scope rule decides who gets in. Six values, a CHECK constraint edited in place while production is empty, and `publicOptions()` now offers five (everything but `inne`).

The June deadline — *"decide before importing, not after"* — is met with the catalogue still empty.

## 2. "What is the UNI_OWNER_MANAGED_BADGE here?" — a workaround, and now deleted

> **Correction, 18.09 — the badge reads `is_claimed`, not `claimed_by`.** The switch to `claimed_by` described below was reverted the same evening. The "fourteen venues with no claims" were factory output in a local database that has never been production, and reading `claimed_by` split the badge from the "Zarządza właściciel" filter, which reads `is_claimed`. The orphan state is prevented where it can arise: `ApproveVenueClaimAction` writes both columns in one update, `UserObserver` releases every venue before an owner's account is deleted, and no importer maps either column. **What still holds:** the flag is deleted, and your V2 sequence is still two switches — `UNI_OWNER_ACCESS=true`, then approve the claim; the badge follows on its own.

You asked, having agreed to the sequence: *"Then each venue that is claimed gets the badge. But what is the `uni_owner_managed_badge` here?"*

**The honest answer is that it was a workaround for a data defect, and your question is what made me look at it properly.** Here is what it actually was:

Fourteen venues carried `is_claimed = true` with **zero claims in the database** — an import had set the column. The badge asserts that a named person is answerable for a venue's offer, so on those fourteen it was making a promise nothing could honour. The fix at the time was a config flag that turned the badge off globally, chosen deliberately over cleaning the rows, because `is_claimed` is a column an import could set again and cleaning would have hidden the problem until the next spreadsheet.

**That reasoning was right about the danger and wrong about the remedy.** The problem was never that the badge was on; it was that the *condition* was a boolean a spreadsheet could write. A flag mutes the symptom for everybody, including the venues that would have been correct.

**What it reads now:** `claimed_by`, not `is_claimed`. That is a real foreign key to a real user, written by `ApproveVenueClaimAction` and by nothing else — **no importer maps it**, which I checked rather than assumed. So:

- A venue with an approved claim has `claimed_by` set → badge shows.
- A venue with `is_claimed = true` and nothing behind it → `claimed_by` is null → **no badge**, with no flag involved.
- The copy that *explains* the badge on the homepage, `/jak-to-dziala` and `/mapa` appears once any venue qualifies (`Venue::anyOwnerManaged()`), so it cannot describe something a visitor is unable to find — which is the `v1-copy-truth` failure the flag existed to prevent.

**The flag is deleted** — from `config/uni.php`, from `.env.example`, and from five views. Its test is rewritten to assert the new behaviour, including the exact shape of the old defect: `is_claimed` set, no owner, no badge.

**So your V2 sequence is two switches, not three:**

1. `UNI_OWNER_ACCESS=true` — yes, an environment variable you set on the server, the day the first venue owner asks for an account.
2. You record and approve their claim in the admin panel. **The badge appears on that venue by itself**, and the explanatory copy appears with it.

There is nothing to remember and nothing to flip afterwards, which is the point.

**One consequence worth knowing.** Because the badge now follows real ownership, it will be accurate before you think about it — including the case where an owner's account is deleted, which releases the venue and clears `claimed_by`, and therefore clears the badge, without anybody touching a config file.

## 3. The schema map exists — 33 tables, 336 columns

You said build it now, so it is built: **`docs/tech/schema.md`**, generated from the live schema and annotated by hand.

**What is in it:**

- **Every table grouped by what it is for** — reference lists, the catalogue, the venue, people and requests, numbers, records and operations, and framework plumbing kept separate so it does not compete for attention.
- **Every column** with its type, whether it is nullable, its default, and where its foreign key points **including the delete rule**.
- **Which columns identify a person**, per table, stated plainly — and which tables identify nobody, which is why `events`, `venue_stats`, `venue_category_stats` and `search_stats` have no retention rule at all.
- **How long each is kept, and why that period** — because Art. 30 asks for the period and a regulator asks why that one.
- **What the database itself enforces** — every CHECK constraint's allowed values and every unique index, which is how you can see at a glance that `venue_drinks.base_category` is four values and none of them is coffee.
- **What a delete takes with it**, per parent table. This section I first wrote by hand and it was wrong in three places, so it is now generated from the real `ON DELETE` rules. Deleting a venue cascades into nine tables and nulls three; deleting a city is **refused** while venues point at it.

**The rule that keeps it true**, written into `CLAUDE.md`: a migration that adds, drops or renames a column updates this file in the same commit — the same discipline the decision records now carry via `Superseded:`.

It is the structural companion to the systems map (P43, still to write), which covers behaviour: what runs, what triggers it, what it touches. Structure and behaviour, two pages.
