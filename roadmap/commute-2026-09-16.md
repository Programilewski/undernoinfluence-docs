### 2.1 History — what is kept, what is not, and what we actually need

**What exists today.** Six tables hold history, and they were each built for a different reason, which is why the coverage is uneven.

| What is recorded | Where | How long | What it can answer |
|---|---|---|---|
| **Every product and house drink added to or removed from a venue** — with who did it, when, which pass it came from (`discovery_type`), and free-form metadata | `venue_offer_logs` | **24 months** | *"What did this venue carry last March?"* — yes, reconstructable. *"Who put it there?"* — yes, `user_id`. *"Was this a real change or just us finding out?"* — yes, that is what `discovery_type` is for, and it is why a first import cannot be read as a wave of Warsaw demand |
| **Claim approvals and rejections, proposal submissions and decisions, admin creation** | `audit_logs` | **12 months** | *"Who approved this claim, and when?"* — yes, with the properties snapshot |
| **The source and date of every menu fact** — not a log, a current value | `venue_products.source_url` / `checked_at`, same on `venue_drinks` | For as long as the link exists | *"Where did we read this, and when?"* — yes, and this is what the 14.09 modal now forces. | **Daily counts per venue and per category; search terms** | `venue_stats`, `venue_category_stats`, `search_stats` | **Indefinitely** — deliberately not prunable | *"How did interest in this venue move over two years?"* — yes. These are the numbers the paid reports are built from |

| **Menu spellings learned from confirmations** | `product_aliases` | Permanent | *"What does this venue's card call Heineken 0.0?"* — and site search uses it |

- **Products have no price column at all** — so there is no price history because there is no price. That is a scope decision, not an oversight, but worth naming while we are counting.

**What I would do about the gap, and what I would not.** I would **not** add a general-purpose versioning package that snapshots every model on every save. ### 2.2 The menu importer as a seeding point for ERP and POS integration

**Yes, it is viable, and yes, it has been discussed — earlier and more than you remember, though never in this shape.**

What the record actually holds: on **07.04** the project decided to build the events table partly as *"the foundation of paid API"*, and rated scraping protection and coordinate fuzzing as things that *"protect the API product"* — a paid API was an assumed part of the business model in the first week. That week's own open questions end with *"Authenticated API design. What are the endpoints? What's the pricing model?"* It was never answered. `docs/business/pricing.md` carries the descendant of that question as one line: **"API or export access: TBD."** Nothing since then has touched it. So: the *outbound* direction (UNI's data, sold to somebody) has a history. The direction you are describing — **venue pushes its NA range into UNI** — is new. Nothing in the journals proposes it.

**Why the direction you are describing is the better one, and not only commercially.** An outbound API sells the catalogue, which means selling the thing that helps a person find a drink to somebody who is not that person; it needs a hard test against `mission-is-the-healthy-choice` every time it is discussed. An inbound sync has no such problem — it makes venue data *more* accurate and more current, which is the entire proposition. The freshness badge is currently maintained by us, by hand, forever; an inbound sync is the only mechanism that ever makes freshness free.

**What the importer already got right for this, by accident.** The CSV design from 14.09 is, structurally, the integration contract. One row per drink as the menu writes it; `venue` + `drink` + `source_url` + `checked_at`; attach only on a confirmed spelling or a unique exact match; everything else fails with a reason and comes back as a review list. **Swap "a CSV a person uploads" for "a payload a POS posts nightly" and nothing about the resolution logic changes.** `product_aliases` is the part that makes it work at all: a venue's POS calls it "HEIN 0.0 BUT" forever, and after one human confirmation it resolves forever. The alias table is the integration's memory, and it is already being filled by the manual work you are about to do anyway. That is the real answer to *"is this a seeding point"* — **it is, and the seeding happens whether or not the integration is ever built**, because cataloguing the first venues by hand is what populates it.

**Why it is not V1, beyond the obvious.** Three reasons, in order of weight:

1. **Polish gastronomy POS is fragmented and mostly not API-first.** The market is dominated by systems whose export story is a CSV or an XML file, not a documented REST API with webhooks. A "POS integration" in this market usually means *parsing somebody's export*, which is the importer you already have — not a partnership.
2. **You have no venue asking for it.** `abstraction-needs-a-second-user` is directly on point: the second user is what tells you which of your assumptions were about the problem and which were about your first guess. Building a sync protocol before one venue has ever kept a menu up to date manually would be designing for a behaviour nobody has demonstrated.
3. **It inverts who is responsible for the data**, and that is a product decision, not a technical one. Today every published fact is one we read and dated. A sync means a venue's own system publishes onto UNI. The moment that happens, "sprawdzone" means something different, and the whole trust model — source URL, check date, the freshness badge — needs re-deciding. That is the expensive part, and it is not code.

**How I would price it, if it happens.** Not as Enterprise. Enterprise implies scale UNI will not have, and a bespoke contract you do not want to negotiate. The shape that fits: **the sync is a Premium module**, sitting alongside the freshness-warning e-mails it would make redundant, because it solves the same problem — a menu going stale — by removing the work instead of nagging about it. A venue that pays for Premium and syncs never gets a freshness warning again, and that is a sentence a venue manager understands in one go. Chains with multiple locations are the natural first customer, which is also the one row in the pricing table that is still TBD: *"Multi-location management."* Those two belong together.

**What I would do now — and it is nearly nothing, deliberately.** Two lines of work, both cheap: (1) **write the decision record** that says the importer's resolution path is the integration contract, so that nobody later builds a second, differently-behaved ingestion path — this is the same rule `catalogue-links-change-through-one-path` already enforces internally, extended outward; (2) **when cataloguing the first ten venues, note which of them run a POS whose name you recognise, and whether their online menu is generated by it.** That costs nothing during work you are doing anyway, and it is the only evidence that would tell you whether this is one integration or twenty. Revisit when a venue asks, or when ten venues are catalogued and three of them share a POS.

## 3. The questions, re-answered with what was missing

### P38 — Should the consent banner ask instead of block?

**What it does now.** On a phone the panel is 435 px of an 844 px viewport — just over half the screen. Behind it sits a 30% black overlay covering everything else, marked `role="dialog" aria-modal="true"`. No tap reaches the page through it and the page does not scroll. Fixed controls, including the Mapa button, hide themselves while it is open, because on 12.09 the Mapa button sat directly on top of "Zaakceptuj wszystkie" and a tap aimed at the map granted analytics consent instead.

**Why this is a real question and not a tidy-up.** The record that governs the banner, `consent-banner-design` (22.06), lists the options it considered and **explicitly rejected the blocking full-page modal** — *"forces a choice but feels aggressive for a venue discovery app; harms first impressions"* — then chose "category-based bottom panel with overlay". The overlay grew into the thing the record turned down. Its `Executed:` line already says so: *"the panel, buttons and equal weight are built, but its overlay blocks every tap and the scroll, which this record rejected."*

**The legal position, which is the part that decides it.** EDPB Guidelines 05/2020 require consent to be freely given, unambiguous and **as easy to refuse as to grant**. They do not require a blocking banner anywhere — what they forbid is treating *inaction* as consent. Those are different things. A non-blocking banner that stores nothing until a button is pressed, and fires no analytics in the meantime, satisfies the regulation completely. Our own analytics never starts without an explicit yes, so scrolling past it grants nothing.

**The asymmetry that bothers me most.** A desktop visitor sees the site behind the panel and can read it. A phone visitor sees half a screen of cookie language and nothing else — and phones are the majority of this product's traffic, because the use case is standing outside a bar. So the strictest treatment lands on the visitor with the least patience, for a product whose whole method is being useful rather than preachy.

**Recommendation: make it ask, not block.** Drop the overlay and the scroll lock; keep the three equal buttons, the equal-prominence rule and the cookie icon; keep the Mapa button hidden while the panel is open so the mis-tap cannot return; keep `role="dialog"` but drop `aria-modal`. **The cost, stated honestly:** fewer PostHog acceptances, because some people will simply use the site. Nothing owner-facing depends on PostHog — every number in every owner report comes from our own `events` table, which counts anonymously without consent — so the loss is our own product analytics, not revenue and not a report. Amend `consent-banner-design` rather than write a new record, since it is the record's own rejected option being un-chosen.

### P41 — Create the outside healthcheck, and can it be tested before production?

**What is built and dormant.** Every five minutes the scheduler dispatches `PingExternalHealthcheck` to the queue. The job runs `select 1` against the database, then fetches the site's own `/up` over its public address, then POSTs to whatever URL is in `UNI_HEALTHCHECK_PING_URL` — to `.../fail` with a reason if either check failed, to the plain URL if both passed. With no URL set it returns immediately and does nothing.

**Why this exists when the dashboard heartbeat already does.** Everything else that watches this server runs *on* it. If the machine dies, the dashboard dies with it. If the queue worker dies, the disk-space warning cannot be sent, because it needs the queue. This is the only check whose failure signal is **silence**, and silence survives anything — that is what a dead man's switch is. One successful ping proves six things at once: cron ran, the worker is alive, Postgres answers, nginx answers, the certificate is valid, PHP executes.

**"Can we test it before prod by switching off each service it monitors?"** — **yes, and better than you are imagining, because two of the three cases can be tested without switching anything off.** Here is the ladder, cheapest first:

1. **In the test suite, no services touched.** `PingExternalHealthcheckTest` already exists. `Http::fake()` intercepts the ping, and the database failure is induced by pointing the connection at a dead socket, the site failure by faking a 500 from `/up`. This proves the *decision* logic — plain URL vs `/fail`, and the right reason string — deterministically, in milliseconds, on every future run. It does not prove the network path.
2. **Locally, against a real Healthchecks.io check, switching things off for real.** Create a free check, put its URL in `.env`, then in four passes: (a) everything up → the check goes green; (b) `sudo systemctl stop postgresql` → within five minutes it goes red and you get the e-mail, with "database:" and the driver's own message in it; (c) Postgres back, stop the web server → red again, with "site unreachable"; (d) everything up but **stop the queue worker** → no ping at all, and the check goes red on its own grace period. **(d) is the important one and the one a test can never cover**, because it is the failure that produces silence rather than a message, and it is also the most likely real failure — a worker that has quietly stopped is the classic Laravel production incident.
3. **On staging, once it exists.** Same four passes against the real deploy, which additionally proves the crontab line is installed. This is where it belongs on the checklist (B9), but it does not have to wait for staging — step 2 can be done on the laptop this week.

**Recommendation: yes.** Healthchecks.io free tier, 20 checks, Latvian company with data on Hetzner in Germany, so no new transfer question and nothing about any visitor is ever sent — the ping body carries only our own failure string. Do step 2 on the laptop before the deploy, so the alarm is proven before it is relied on. An alarm nobody has ever heard ring is not an alarm.

Answer: I would be hesitant here. I'd see daily if the site is down, the OVH hosting should notify my as well. I cannot spend more money on healthchecks.io, hobby plan is free because its not for commercial use. 

### P16 + P40 — 2FA, and what actually protects the admin panel in production

**What kind of 2FA, exactly.** Filament 5 has multi-factor authentication built in — no plugin, no new dependency, contrary to what `cis.md` still says. Two providers ship with it:

- **App authentication (TOTP)** — a six-digit code from Google Authenticator, Authy, 1Password or any compatible app, rotating every 30 seconds. Needs one text column, `app_authentication_secret`, on `users`; the `HasAppAuthentication` interface and its trait on the model; and `->multiFactorAuthentication([AppAuthentication::make()])` on the panel.
- **Email authentication** — a one-time code e-mailed at sign-in, valid four minutes by default.

Plus two things worth having with them: **`->recoverable()`**, which generates eight single-use recovery codes against a second text column, so losing the phone does not lock you out of your own product; and **`isRequired: true`**, which forces setup at the next sign-in rather than leaving it optional. Setup happens on the Filament profile page, which needs `->profile()` on the panel — currently not enabled on either panel.

**Which to choose.** **TOTP, not e-mail.** E-mail codes make your mailbox the second factor, and the whole point is that a stolen password should not be enough — a password reused somewhere that also leaked the mailbox defeats e-mail codes entirely. TOTP also works in a venue with no signal on the way in. One caveat the Filament docs are explicit about: preventing a TOTP code from being accepted twice requires a cache store with atomic locks. **Ours is `CACHE_STORE=database`, which qualifies**, so nothing needs changing — but it must not quietly become `file` or `array` on the server.

**The important half of your question: what protects `/admin` on production?** Right now, and honestly: **a password, and nothing else.** Filament's rate limiting counts failed logins per IP address, so a distributed attempt is not slowed. There is no IP restriction, no VPN, no second factor. That is one column of one row between an attacker and every claim's `contact_name`, `contact_email`, `contact_phone` and `business_nip` — which is precisely what `cis.md` CIS4 says.

**And on Tailscale — you remembered a real decision, and I am reversing v2.0's advice.** As [[#1.1 Two compliance audits state that Tailscale protects the admin panel in production. It does not, and under the current plan it never will.|§1.1]] sets out, Tailscale + nginx allowlist was decided on 20.05, written into the BRD as NFR-10 and PL-03, and called a pre-launch blocker three times in the 29.06 journal. v1.6 dropped it in a clause, with no record. I think the drop was wrong, for a reason the earlier write-up already states better than I would: an nginx IP allowlist is enforced **at the infrastructure layer, before any application code runs**. It costs nothing per request, it does not depend on Laravel being correct, and it means a Filament authentication bug — theirs or ours — is not reachable from the public internet at all. 2FA and the allowlist are not alternatives; they are different layers, and the layering is the point.

**Recommendation — three things, in this order, one session:**

### P24 — The catalogue scope rule: is it about the description, or about what is allowed in?

**Both, and you are right to separate them, because they are two different pieces of work.**

**What already exists and is genuinely settled:** `catalogue-excludes-actual-alcohol` (04.09) fixes the ABV boundary permanently — nothing above 0,5% ever enters, and the 1–3% range is **refused, not deferred**, so that a later reader cannot treat it as an invitation. A product with `abv_status = unknown` is treated as an unverified claim rather than missing data, and is never published as a verified alternative. That record is executed and enforced, and `PublishedPagesAreTrueTest` now fails if a category description mentions low-alcohol.

**What is not settled is the other axis entirely.** ABV answers *how alcoholic may it be*. It says nothing about *what kind of drink belongs here at all*. That is the "Szampan 0%" case: the category describes itself as *"kombucha, toniki, wody smakowe i napoje musujące"*, and a tonic at 0,0% passes the ABV rule effortlessly while arguably not being in the catalogue's business at all. Left unanswered, the practical failure is not philosophical — it is that at venue four you enter a bottle of flavoured water, at venue nine you decide those do not belong, and now the first three venues are wrong and you are editing data instead of entering it.

**So: the description follows the rule, not the other way round.** The rule is the decision; the "Szampan 0%" wording is one place that currently contradicts whatever the rule turns out to be, and it needs correcting once the rule exists.

**Recommendation — one line, then the consequences.** The rule: **a drink qualifies when the venue offers it as the alternative to an alcoholic one.** Not "is it non-alcoholic" (water passes) and not "is it interesting" (unjudgeable). The test is the venue's own framing, which is also the only test a person can apply while standing in a bar reading a card.

What that rule decides, concretely, so it can be checked against real menus before you commit to it:

- A tonic listed among mixers, next to the gin — **out**. A tonic listed as a drink in its own right, in a "bez alkoholu" section — **in**.
- Kombucha and craft sodas in a "bez alkoholu" section — **in**; the same bottles in a fridge listed under "napoje" with the Coke — **out**.
- Flavoured water — **out** essentially always, because no venue offers it as the thing you have instead of a beer.
- Non-alcoholic beer, wine, spirits, and every house mocktail — **in**, unconditionally.

**It is deliberately a written rule and not a `catalogue_status` column.** `catalogue_status` was proposed in the 04.09–09.09 journals as an enum on venues, and it solves a different problem — tracking which venues have been *assessed* versus which are merely *not yet catalogued*, so the denominator of "how much of Warsaw have we done" stays honest. The scope rule cannot wait, because it governs the first row you type.

### P15 — Backups to object storage: is it the right product, and what does it cost?

**Prices, fetched today from Scaleway's pricing page.** Per GB per month: **Standard One Zone €0.00803**, **Standard Multi-AZ €0.01606**, **Glacier €0.00254**. Ingress and requests are included at no charge; egress has **75 GB free every month**, then €0.01/GB. Transfers between Paris, Amsterdam and Warsaw are free.

**What we would actually store.** The local database, with 67 fabricated venues and months of development, is **11 MB**. A `pg_dump -Fc` of it compresses to a couple of megabytes. Take a deliberately pessimistic V1 — a thousand real venues and a full year of events — and call the compressed dump 500 MB. Seven daily plus four weekly copies is eleven files, so **about 5.5 GB**, which is **€0.04 a month** on One Zone and **€0.09** on Multi-AZ. Restoring the whole set once would use 5.5 GB of a 75 GB free egress allowance. **At V1 scale the price is not a factor in this decision and should not be used to make it** — which is the useful finding, because it means the decision is purely about where the copy lives and who holds it.

**Is object storage the right shape, or is "some file storage" enough?** Object storage is the right shape, for three reasons that are not about price. It is **S3-compatible**, which is the protocol `spatie/laravel-backup` and `restic` both speak natively, so no glue code exists to break. It supports **object lock and versioning**, meaning a compromised server cannot delete its own backups — which is the single most important property a backup can have, and the one a plain file server over SFTP does not give you. And **Scaleway is already a processor for this project** through Transactional E-Mail, so there is no new DPA, no new vendor-register entry and no new recipient to disclose in the privacy policy. That last point is worth more than the price difference between any two providers at this scale.

**The alternatives, and why not.** Hetzner Storage Box is cheaper per GB and would be a **new** processor with a new DPA — paying real paperwork cost to save cents. Backblaze B2 is US-headquartered, so it becomes a transfer question. **Ploi's own automatic backups are a Pro feature and are not a substitute**, because backups held by the same party that holds root on the box fail the one scenario backups exist for. And the 27.08 decision — nightly `pg_dump` over Tailscale into the home server's existing restic rotation — is a genuinely good *second* layer, but it cannot be the first one: it needs the home machine to be on.

**One correction to the 15.09 recommendation.** It said Multi-AZ. At €0.04 versus €0.09 a month the difference is meaningless, so take Multi-AZ — but for the right reason, which is that a single-zone failure with an un-rehearsed restore is a bad week, not because it is cheap.

**Recommendation: yes — Scaleway Object Storage, `pl-waw`, Multi-AZ, `gpg`-encrypted before upload, 7 daily + 4 weekly, object lock on.** The part that actually matters is the last line of deploy-checklist A6: **a restore rehearsed into an empty database before the first real venue exists.** Art. 32(1)(d) requires the restore to be *tested*, and an untested backup is a belief.
