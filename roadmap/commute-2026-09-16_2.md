## 1. Findings — five, ranked

### 1.1 The canary venues cannot detect scraping. They are invisible on the public site.

You asked: *"we got only 2 fixed canaries or is it dynamic?"* Two, fixed, seeded by `CanarySeeder` and never generated. But checking how they work turned up something worse than the count.

`CanarySeeder`'s own docblock states the purpose: *"if these names appear in a competitor's product, dataset, or AI output, it proves they scraped Under No Influence."* For that to happen, a scraper has to be able to see them. It cannot. Every public path excludes them:

- `VenueController` — `abort_if(! $venue->is_active || $venue->is_canary, 404)`. The venue page returns **404**.
- `SitemapController` — uses the `active()` scope, which is `where('is_active', true)->where('is_canary', false)`. **Not in the sitemap.**
- Discovery, the map and the venue list — same `active()` scope. **Not on `/mapa`, not in any list.**
- `VenueRedirectController`, `VenueReportController`, the analytics endpoint — all refuse them.

So a crawler that reads every page UNI publishes will never encounter either name. **The only way a canary can leak is a database dump or a stolen backup** — a real threat, but not the one the mechanism was written for, and not the one `block-all-ai-crawlers` and the honeypot are defending against. Today the project believes it can prove a public scrape and cannot.

The honeypot is a separate and working mechanism: `/export/venues.json` is a bait URL that logs `bot.honeypot` on any request, and nothing links to it. That one does fire. But it proves *someone probed an obvious path*, not *someone took our catalogue*.

**What I would do — and it is a decision, not a fix, because the trade is real.** A canary that works has to be visible to a scraper and invisible to a person, and those two things fight. The honest options:

1. **Leave it.** Accept that the canaries are a database-leak tripwire only, and correct the seeder's docblock and the systems map so nobody believes otherwise. Zero cost, zero new risk.
2. **Make them publicly visible but unreachable by a human** — indexed nowhere, linked nowhere, no sitemap entry, but a live page at a real address. A scraper following a pattern of slugs finds them; a person never does. This is how canaries normally work. The cost is that a fictional venue is live on the site, which is the exact thing `homepage-showcase-real-components` refused for the homepage — *"anything shown there reads as an endorsement"*. Mitigated by the page saying plainly it is not a real venue, which also defeats half the purpose.
3. **Canary rows in the data, not canary pages** — a fake `product_alias`, or a deliberately wrong-by-one coordinate on one real venue. Invisible to a person, present in anything copied wholesale, no fictional venue on the site. Cheapest of the three that actually works.

**Recommendation: (1) now, (3) when the catalogue is real.** Before there is a catalogue worth stealing, the tripwire matters less than the honesty of the record; after it, option 3 gives a working defence without putting invented places on a site whose whole promise is that what is listed can be ordered. **P47.**

### 2.3 §1.4 — npm audit, vite, and the fix, in plain terms

**What `npm` is.** The site's build step — turning your source files into the JavaScript and CSS a browser downloads — uses a pile of small open-source tools. `npm` installs them. There are two kinds, and the difference is the whole answer:

- **Tools that build the site.** They run on your laptop, produce files, and are then finished. The browser never sees them.
- **Code that ships.** It is copied into what the browser downloads and runs on every visitor's phone.

**What `npm audit` is.** A command that compares every installed package against a public database of known security problems and prints the matches. It is a lookup, not a scan of our code — it answers *"is any tool I use known to be broken?"*, not *"is my code safe?"*

**What it said here.** `npm audit --omit=dev` — the "only show me things that ship" version — returned **0 problems**. The full run found **8**, all in build-time tools. So no visitor to UNI is exposed to any of this, today or after launch.

**What Vite is.** The build tool itself. It has a second job during development: when you run `npm run dev`, Vite starts a small web server on your laptop so the browser can reload the page instantly as you edit. **That development server never runs in production** — it does not exist on the real machine.

**What the Vite problem actually is.** Two of its five advisories are ways to trick that development server into handing over a file it should refuse — including `.env`, which holds your database password and application key. It is a real problem, and until 14.09 that server answered your entire home Wi-Fi, so anything on the network could have asked. Since 14.09 it answers only your own machine, which is why this dropped from "exposure" to "tidy this up".

**What the fix is.** `npm audit fix` — one command. It updates the eight affected tools to versions where the problem is already patched. It does **not** need `--force`, which is the flag that jumps packages to new major versions and breaks builds. It changes one file, `package-lock.json`, which is the exact list of which version of every tool you use — which is why it is a commit and why I left it to you. Afterwards `npm run build` and `npm run check:render` confirm the site still builds and the maps still draw.

Answer: In that case run the npm audit fix.

### 2.5 P16 follow-up — "what if a B2B owner's account is compromised?"

I checked this properly rather than reassuring you, because it is the right question to ask before owners exist rather than after. **The isolation is real, and it is two independent layers.**

**Layer one — the query never leaves their venue.** `app/Filament/Owner/Resources/VenueResource.php:39` overrides `getEloquentQuery()` with `->where('claimed_by', auth()->id())`. Every list, every table, every record lookup in the owner panel starts from that filter, so another venue's row is not merely hidden — it is not in the result set.

**Layer two — the policy checks ownership per record.** `VenuePolicy` gates `view`, `update`, `delete`, `attachProduct` and `detachProduct` on `$venue->claimed_by === $user->id`. `create` and `deleteAny` return **false** outright, so an owner cannot create a venue or run a bulk delete at all. Even if a crafted request slipped past the scoped query, the policy refuses it.

**And a third thing that matters:** `canAccessPanel()` is a `match` on the panel id — `admin` requires `isAdmin()`, `owner` requires `isOwner()`, everything else is `false`. An owner account cannot reach `/admin` even by typing the address, and `PanelAuthenticate` bounces an admin who lands on `/panel` back to `/admin`. Relation managers all operate through `$livewire->ownerRecord`, which is the already-scoped venue — no unscoped query anywhere in the owner panel.

**So the blast radius of one compromised owner account is: that one venue.** The attacker could edit its profile, attach or detach products, mark its menu fresh, and — the one destructive action — trigger the self-service erasure, which deletes the venue and optionally the account. They would see that venue's analytics, which since 14.09 contain no competitor names and nothing for an area under three venues. They would **not** see any other venue's data, any other owner's contact details, the claims table, or the admin panel.

**The three gaps worth knowing about, all V2:**

- **No 2FA and no e-mail verification on the owner panel.** Deliberate for V1 — owners are created by an admin who verified them by phone and NIP, and the panel has no verification routes. Both become necessary the moment self-service registration opens, and `isRequired: true` on the owner panel is the same one-line change as on admin.
- **Self-service erasure is destructive and needs only the password.** An owner who loses their password loses their listing. Worth a second confirmation step, or a soft-delete window, before real owners exist.
- **`VenuePolicy::before()` gives any admin everything.** Right for one founder; the first additional admin account is when that needs revisiting.

**Verdict: yes, isolated well enough.** The design is the right one — scope the query *and* check the policy, rather than trusting either alone — and the V1 gaps are all consequences of owners being admin-created, which is true until V2.

### 2.7 P41 — the healthcheck, now that the licence reason is gone

Your two arguments were *"it costs money I cannot spend"* and *"I'd see daily if the site is down, the OVH hosting should notify me as well."* The first is answered in [[#1.4 Healthchecks.io's free plan has no commercial-use restriction — your reason for declining does not hold|§1.4]] — the free tier carries no commercial restriction. The second deserves a real answer rather than a rebuttal.

**Where you are right.** For *the site being down*, you are correct and the healthcheck adds little. If `undernoinfluence.pl` returns nothing, you will notice, your OVH panel will show a dead VPS, and OVH does send notifications for infrastructure-level failures on the machine. A total outage is the easiest failure to detect and the one you least need help with.

**Where the argument does not reach.** The healthcheck is not primarily a site-down alarm. It is the only thing that catches the failures where **the site stays perfectly up while something behind it has stopped**. Those are silent by construction, and there are three of them in this application:

- **The scheduler stops** — a missing or wrong crontab line after a deploy. The site serves every page normally. Nothing else runs: no hourly freshness check, so the badge on every venue page slowly starts lying; no nightly rollup, so every owner report is built on a gap; no pruning, so the retention windows you are about to promise in the ROPA quietly stop being true.
- **The queue worker stops** — the classic Laravel production failure, and the one most likely to actually happen. Claim approval e-mails are queued and never send. The owner is approved in the database and never told. You find out when they ask.
- **Postgres refuses connections while nginx still answers** — a disk-full or a connection-limit condition. Some pages cache, some error, and the pattern is confusing rather than obvious.

**None of those look like "the site is down".** Two of them look like nothing at all until somebody complains, and the third makes your own data wrong in ways that are expensive to unpick after the fact. The dashboard heartbeat catches the first *if you open the dashboard*; the outside ping catches all three whether or not you do — and catches them even when the machine itself is gone, which the dashboard cannot.

**The honest cost, both ways.** The job is already written and dormant; the entire cost is creating a free account and pasting a URL into `.env` — call it ten minutes. The cost of not having it is not "the site is down and I did not know"; it is "the scheduler stopped on 3 November and I found out in January because a report looked wrong".

**Revised recommendation: yes, but demoted.** Not a launch blocker, not urgent, and if you would rather not depend on a one-person Latvian company for it, the same dead-man's-switch behaviour exists on several EU services and one could equally be a cron job on your home machine that e-mails you when a ping stops arriving. **What I would not do is leave it unset and call the scheduler monitored**, because the dashboard heartbeat only speaks to somebody already looking at the dashboard. If you still say no, the deploy checklist should say plainly that scheduler and worker failures are undetected — so it is a recorded decision rather than an assumption.

``
**The principle.** GDPR does not set retention periods. Article 5(1)(e) says personal data may be kept no longer than is necessary *for the purpose it was collected for*. So the only question that decides a window is: **does this row identify a person, and is the purpose still live?** A row that identifies nobody has no legal horizon at all — which is why `events` and `venue_stats` are kept forever and that is not a loophole, it is the rule working as intended.

**On P46, why split rather than grow.** A `venue_offer_logs` row is two facts glued together: *"this venue carried Heineken 0.0 from March to July"* — which identifies nobody and is the commercial series that pairs with `venue_stats` — and *"Paweł typed it on 14 March"*, which identifies a person.
