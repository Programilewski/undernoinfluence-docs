# Ansible, from the beginning — and what it does in UNI

**One sentence:** Ansible is a program on your PC that logs into a server over SSH, looks at how the server is, compares that with a description you wrote in YAML, changes only what differs, and logs out.

**Its job in UNI:** building a server, meaning packages, users, the firewall, PHP, Postgres, nginx, the worker and cron. **Not** putting the application on it. That is Deployer's job ([`_3`](commute-2026-09-30_3.md)). The split is the most important idea in both documents:

| | Ansible | Deployer |
|---|---|---|
| Answers | *what is this machine?* | *which version of UNI runs on it?* |
| Runs | rarely: when a server is new, or its setup changes | on every release |
| Connects as | `admin`, full root behind a password | `deploy`, allowed exactly one root command |
| Touches | `/etc`, packages, services, the empty folder layout | `releases/`, the `current` link, `artisan` |
| Lives in | `ansible/` | `deploy.php` |

## 1. The five ideas you need

**Control node.** The machine Ansible runs on. For UNI that is **your PC, and only your PC** (28.09, decision 2). Nothing gets installed on the servers for Ansible's sake. It needs SSH and Python there, both of which Ubuntu already has. This is what "agentless" means: between two runs, nothing on the server knows Ansible exists.

**Inventory.** The list of machines, and the variables that belong to them. UNI has two inventories with one machine each: `inventories/home` (the home-server container) and `inventories/production` (the OVH VPS). You pick one with `-i`, so a single command never reaches both by accident.

**Playbook.** A YAML file that says *on these hosts, apply these roles in this order*. UNI has two: `provision.yml` (everything, run many times) and `bootstrap.yml` (one step, run once per VPS).

**Role.** A folder that bundles everything about one concern, such as `php`, `nginx` or `worker`. Inside it, the folder names carry meaning to Ansible:

| Folder in a role | What Ansible does with it |
|---|---|
| `tasks/main.yml` | the steps, run top to bottom |
| `handlers/main.yml` | steps that run **only if notified**, once, at the end |
| `templates/*.j2` | files with `{{ variables }}` and `{% if %}`, filled in and copied to the server |

**Task.** One step, and it **calls a module**. A module is a small program that knows how to make one thing true. `ansible.builtin.apt` makes a package installed. `ansible.builtin.copy` makes a file have certain content. `ansible.builtin.user` makes a user exist. You describe the **end state** and the module works out whether anything has to change. That's the difference from a shell script. A script says *run `useradd deploy`*, which fails the second time. A task says *a user called deploy exists*, which is already true the second time, so it does nothing.

**Handler.** A task that waits to be called. When `sshd`'s config file changes, sshd has to reload, but only then, and only once even if three files changed. The task that writes the file says `notify: Reload ssh`, and the handler runs at the end of the play if at least one notifying task reported `changed`.

**Idempotence — the one word that matters.** Running the playbook twice in a row must end with **`changed=0`** on the second run. If it doesn't, the playbook isn't describing a server. It is performing a sequence of actions and hoping nothing moved. That's why the runbook's definition of done for Phase 2 is literally "the second run changes nothing". On 29.09 the stand-in server passed this three times, the last time after a live deploy.

**FQCN.** Module names are written in full: `ansible.builtin.copy`, `community.general.ufw`. The first part is the **collection**, a package of modules. `ansible.builtin` comes with Ansible. The other three UNI uses are pinned in `requirements.yml`.

## 2. The folder, as a map

```
ansible/
├── ansible.cfg                  settings for every run started in this folder
├── requirements.yml             the three extra collections, pinned
├── provision.yml                THE playbook: builds a whole server, safe to repeat
├── bootstrap.yml                once per VPS: creates `admin` as OVH's `ubuntu` user
├── group_vars/all.yml           variables true on BOTH servers
├── inventories/
│   ├── home/
│   │   ├── hosts.yml            one host: uni-home
│   │   └── group_vars/all.yml   what is different about the home server
│   └── production/
│       ├── hosts.yml            one host: uni-prod
│       └── group_vars/all.yml   what is different about production
├── files/keys/
│   └── pawel-pc.pub             public keys allowed to log in (uni-backup.pub still missing)
└── roles/
    ├── base/       users, SSH, sudo, updates, timezone, locale, firewall
    ├── tailscale/  the package only (production)
    ├── php/        PHP 8.5 + FPM + Composer
    ├── postgres/   PostgreSQL 18, the app's role and database
    ├── nginx/      the web server and the site config
    ├── app/        the empty folder layout Deployer deploys into
    ├── worker/     supervisor (queue worker) and cron (scheduler)
    ├── tls/        Let's Encrypt certificates (production)
    └── verify/     checks that fail the run instead of warning
```

**Why variables sit at two levels.** Ansible merges variables, and the more specific one wins. `ansible/group_vars/all.yml` holds what is true everywhere (PHP 8.5, the app path, the user names). `inventories/<env>/group_vars/all.yml` holds only what differs. So the production file never repeats `php_version`, and changing PHP means changing one line for both servers. That is the plan's core promise, *one fix reaches both servers*, written as a folder structure.

**Why there are no IP addresses anywhere.** `hosts.yml` names the machine `uni-home` or `uni-prod`, and those are **aliases in `~/.ssh/config` on your PC**. The real address lives only there (the no-machine-addresses-in-the-repo record). Ansible and Deployer both call `ssh uni-prod` and let SSH resolve it.

## 3. The files, line by line

### 3.1 `ansible.cfg`

```ini
[defaults]
roles_path = roles                 # look for roles in ./roles
interpreter_python = auto_silent   # find Python on the server yourself, and don't warn about it
callback_result_format = yaml      # print results as readable YAML instead of one-line JSON
retry_files_enabled = False        # don't litter the folder with *.retry files after a failure

[ssh_connection]
pipelining = True                  # send each module over the open SSH connection instead of
                                   # copying a file to the server first: fewer round-trips, faster
```

Ansible only reads this file when you run commands **from inside `ansible/`**. That's why every command in §5 starts with `cd ansible`.

### 3.2 `requirements.yml`

```yaml
collections:
  - name: ansible.posix          # authorized_key: puts public keys into ~/.ssh/authorized_keys
    version: 2.2.2
  - name: community.general      # ufw (firewall), timezone, locale_gen
    version: 13.4.0
  - name: community.postgresql   # postgresql_user, postgresql_db
    version: 5.0.0
```

Exact versions, not ranges, for the same reason `composer.lock` exists: the server you build in six months should be built by the same code. Installed once on the PC with `ansible-galaxy collection install -r requirements.yml` (done 29.09).

### 3.3 `provision.yml` — the playbook

```yaml
- name: Provision a UNI server
  hosts: all                 # every host in the inventory you passed with -i (one, by design)
  become: true               # run tasks as root, via sudo — this is what -K's password is for
  roles:
    - base                   # first: users and SSH, so everything after has the right accounts
    - role: tailscale
      when: tailscale_on_box # only where the inventory says so: production true, home false
    - php
    - postgres
    - nginx
    - app                    # after nginx and php: it needs the www-data group to exist
    - worker                 # after app: the worker's config points into the app's folders
    - role: tls
      when: tls_mode == 'certbot'   # production only; the home server's TLS is Tailscale's
    - verify                 # last: checks the finished result, fails the run if it is wrong
```

**The order is a dependency list.** `www-data` comes with nginx and PHP-FPM, so `app` can't set a folder's group to `www-data` before they are installed. `verify` goes last because it checks what the others built.

**`when:`** is Ansible's `if`. The same playbook serves both servers because the differences are variables and `when:` reads them.

### 3.4 `bootstrap.yml` — once per VPS

A fresh OVH VPS has one user, `ubuntu`, which OVH created with your key. `provision.yml` connects as `admin`, and `admin` doesn't exist yet. `bootstrap.yml` exists only to fix that chicken-and-egg problem.

```yaml
- name: Create the admin user
  hosts: all
  become: true
  vars_prompt:                        # ask a question before running
    - name: admin_password
      prompt: "admin's sudo password (put it in the password manager first)"
      private: true                   # don't echo what you type
      confirm: true                   # ask twice, so a typo can't lock you out
  tasks:
    - name: Admin exists, in sudo, with a password
      ansible.builtin.user:
        name: admin
        groups: sudo                  # may use sudo…
        append: true                  # …in addition to its other groups, not instead of them
        shell: /bin/bash
        password: "{{ admin_password | password_hash('sha512') }}"   # hashed on the PC;
                                      # the plain password never leaves it
        update_password: on_create    # set it only when creating the user — a re-run never
                                      # silently changes a password you already use

    - name: Both keys may log in as admin
      ansible.posix.authorized_key:
        user: admin
        key: "{{ lookup('ansible.builtin.file', 'files/keys/' + item) }}"   # read the file ON THE PC
      loop: [pawel-pc.pub, uni-backup.pub]   # run this task once per item
```

**`lookup(...)` always runs on the PC**, never on the server. It's how a file from the repository becomes a value. **`loop:`** repeats a task with `item` set to each element.

It runs as `ansible-playbook -i uni-prod-bootstrap, bootstrap.yml`. The **trailing comma** tells Ansible that `uni-prod-bootstrap,` is a list of hosts rather than an inventory file name. Afterwards, `provision.yml`'s SSH rule (`AllowUsers deploy admin`) shuts `ubuntu` out for good.

### 3.5 The variables

**`group_vars/all.yml`** — true on both:

```yaml
php_version: "8.5"               # in quotes: unquoted, YAML reads 8.5 as a number, and "8.50" != "8.5"
app_root: /var/www/undernoinfluence
deploy_user: deploy              # owns the code; Deployer's user
admin_user: admin                # Ansible's user
web_user: www-data               # runs PHP-FPM, the worker and cron
composer_version: "2.10.3"
```

**`inventories/home/group_vars/all.yml`** — the home server's differences:

```yaml
env_name: preprod
apt_force_ipv4: true             # the container has no IPv6 route: apt would hang on IPv6 mirrors (22.09)
server_names: []                 # no domain: nginx answers anything (default_server)
tls_mode: none                   # Tailscale serve on the laptop terminates HTTPS in front of it
db_name: preprod_uni
db_user: preprod_uni_app
firewall_enabled: true           # the runbook's fallback: false if ufw can't load inside Incus
ssh_allow_from: "10.0.0.0/8"     # PLACEHOLDER — replaced with incusbr0's real subnet at runbook 3.3
http_allow_from: "10.0.0.0/8"
https_open: false                # nothing arrives on 443 here
admin_allow_from: []             # empty list = /admin not restricted: the box is tailnet-only anyway
tailscale_on_box: false          # Tailscale runs on the laptop, not in the container
```

**`inventories/production/group_vars/all.yml`** — production's differences:

```yaml
env_name: production
apt_force_ipv4: false
server_names: [undernoinfluence.pl, www.undernoinfluence.pl]
canonical_host: undernoinfluence.pl        # the one name; www redirects to it
tls_mode: certbot
certbot_email: kontakt@undernoinfluence.pl # Let's Encrypt writes here if a certificate is about to expire
db_name: prod_uni
db_user: prod_uni_app
firewall_enabled: true
ssh_allow_from: any
http_allow_from: any
https_open: true
admin_allow_from: [100.64.0.0/10, "fd7a:115c:a1e0::/48"]   # Tailscale's IPv4 and IPv6 ranges
tailscale_on_box: true
```

**`hosts.yml`** (both, apart from the name):

```yaml
all:
  hosts:
    uni-home:              # the ~/.ssh/config alias; `uni-prod` in the production file
      ansible_user: admin  # override the alias's `User deploy` — Ansible is always admin
```

### 3.6 `roles/base` — who may do what

```yaml
- name: Both public keys are in the repository before anything is changed
  ansible.builtin.assert:              # "these must be true, or stop"
    that:
      - lookup('ansible.builtin.fileglob', playbook_dir + '/files/keys/pawel-pc.pub') | length > 0
      - lookup('ansible.builtin.fileglob', playbook_dir + '/files/keys/uni-backup.pub') | length > 0
    fail_msg: >-
      files/keys/ needs pawel-pc.pub and uni-backup.pub. …
  delegate_to: localhost               # check on the PC, not the server
  become: false                        # and without sudo
  run_once: true                       # once per run, not once per host
```

**This is the task that stops you today.** `uni-backup.pub` doesn't exist yet, so the playbook refuses to change anything. That's deliberate: a server whose only key is on one PC is a server you lose when the PC dies.

```yaml
- name: Apt prefers IPv4 (2.1)
  ansible.builtin.copy:
    dest: /etc/apt/apt.conf.d/99force-ipv4
    content: 'Acquire::ForceIPv4 "true";'
    mode: "0644"                       # always a string in quotes: 0644 unquoted is octal-confusion bait
  when: apt_force_ipv4                 # home true, production false

- name: Base packages
  ansible.builtin.apt:
    name: [git, unzip, curl, rsync, 7zip, supervisor, ufw, unattended-upgrades, acl, python3-psycopg2, locales]
    update_cache: true                 # apt update first…
    cache_valid_time: 3600             # …unless it was done in the last hour (keeps re-runs fast and changed=0)
```

Each package is there for a reason: `rsync` for Deployer's upload (29.09 finding 8), `7zip` for encrypted backups, `supervisor` for the worker, `acl` so Ansible can `become_user: postgres`, and `python3-psycopg2` so the Postgres modules can talk to the database.

```yaml
- name: Timezone is UTC — the schedule is written in UTC (2.7)
  community.general.timezone:
    name: UTC

- name: Polish locale generated (2.7)
  community.general.locale_gen:
    name: pl_PL.UTF-8                  # Polish sorting and date names

- name: The deploy user owns the code and is in the web group (2.2)
  ansible.builtin.user:
    name: "{{ deploy_user }}"
    groups: "{{ web_user }}"           # deploy ∈ www-data: files deploy writes are readable by the web
    append: true
    shell: /bin/bash
    password: "!"                      # a locked password: deploy can only ever log in with a key
    update_password: on_create

- name: Both keys may log in as deploy and as admin
  ansible.posix.authorized_key:
    user: "{{ item.0 }}"
    key: "{{ lookup('ansible.builtin.file', playbook_dir + '/files/keys/' + item.1) }}"
  loop: "{{ [deploy_user, admin_user] | product(['pawel-pc.pub', 'uni-backup.pub']) | list }}"
  #        `product` = every combination: (deploy, pc) (deploy, backup) (admin, pc) (admin, backup)

- name: Deploy may reload PHP-FPM and nothing else (2.3)
  ansible.builtin.copy:
    dest: /etc/sudoers.d/deploy
    content: "{{ deploy_user }} ALL=(root) NOPASSWD: /usr/bin/systemctl reload php{{ php_version }}-fpm\n"
    mode: "0440"
    validate: visudo -cf %s            # check the file BEFORE putting it in place — a broken sudoers
                                       # file locks everyone out of sudo, including you
```

That sudoers line is the entire power of the `deploy` user. A stolen deploy key can deploy code (bad) but can't become root (much worse). That's the building-a-server-and-deploying-to-it-are-two-users record.

```yaml
- name: SSH is key-only, no root, and only deploy and admin may log in (2.4)
  ansible.builtin.copy:
    dest: /etc/ssh/sshd_config.d/10-uni.conf      # a drop-in file: Ubuntu's own config stays untouched
    content: |
      PermitRootLogin no
      PasswordAuthentication no
      KbdInteractiveAuthentication no
      AllowUsers {{ deploy_user }} {{ admin_user }}  # this line is what ends `ubuntu`'s access
    mode: "0644"
  notify: Reload ssh

- name: Security updates stay automatic, reboots stay yours (2.6)
  ansible.builtin.copy:
    dest: /etc/apt/apt.conf.d/20auto-upgrades
    content: |
      APT::Periodic::Update-Package-Lists "1";
      APT::Periodic::Unattended-Upgrade "1";

- name: Firewall (2.5)
  ansible.builtin.include_tasks: firewall.yml     # pull in another task file, conditionally
  when: firewall_enabled
```

**The handler** (`roles/base/handlers/main.yml`):

```yaml
- name: Reload ssh
  ansible.builtin.shell: sshd -t && systemctl reload ssh   # -t tests the config; `&&` = reload only if valid
  changed_when: true                                       # a shell command can't know; say "changed"
```

**`firewall.yml`**. The order is the safety feature:

```yaml
- name: SSH allowed first, so enabling the firewall cannot cut this session
  community.general.ufw: { rule: allow, port: "22", proto: tcp, from_ip: "{{ ssh_allow_from }}" }
- name: HTTP
  community.general.ufw: { rule: allow, port: "80", proto: tcp, from_ip: "{{ http_allow_from }}" }
- name: HTTPS
  community.general.ufw: { rule: allow, port: "443", proto: tcp }
  when: https_open
- name: Deny everything else, then enable
  community.general.ufw: { state: enabled, policy: deny, direction: incoming }
```

(The file writes each task over several lines. The `{ }` form above is the same YAML, compacted to fit.)

### 3.7 `roles/tailscale` — the package, not the login

It adds Tailscale's signing key, then its apt repository, then installs `tailscale`. `ansible_facts['distribution_release']` is a **fact**, something Ansible learned about the server when it connected (here the Ubuntu codename), so the repository line is always right for the release you're on. **Joining the tailnet needs a browser login, so Ansible deliberately stops there.** You run `sudo tailscale up --ssh=false` once and turn off key expiry in the admin console (runbook, Phase 2).

### 3.8 `roles/php`

```yaml
- name: PHP from stock Ubuntu 26.04, no PPA (2.8)
  ansible.builtin.apt:
    name:
      - php{{ php_version }}-fpm       # → php8.5-fpm: the variable makes a PHP upgrade a one-line change
      - php{{ php_version }}-cli
      - …mbstring, xml, curl, zip, bcmath, intl, pgsql, gd   # exactly what `verify` checks later

- name: A drop-in directory for PHP-FPM's unit
  ansible.builtin.file:
    path: /etc/systemd/system/php{{ php_version }}-fpm.service.d
    state: directory

- name: PHP-FPM writes group-writable files (2.9)
  ansible.builtin.copy:
    dest: …/php8.5-fpm.service.d/umask.conf
    content: |
      [Service]
      UMask=0002                       # new files are rw for the group, not just the owner
  notify: Restart php-fpm              # a umask change needs a restart, not a reload

- name: PHP-FPM is running and starts at boot
  ansible.builtin.systemd_service: { name: php8.5-fpm, state: started, enabled: true }

- name: Composer, pinned and checksum verified (2.10)
  ansible.builtin.get_url:
    url: https://getcomposer.org/download/{{ composer_version }}/composer.phar
    checksum: sha256:https://getcomposer.org/download/{{ composer_version }}/composer.phar.sha256sum
    dest: /usr/local/bin/composer      # Deployer's deploy:vendors finds it here with `which composer`
    mode: "0755"
```

**Why the umask matters.** On 25.09 the worker and cron wrote the same log file as different users, and whichever created the day's file first locked the other out. The fix has two halves: shared folders are **setgid** (`app` role), so new files inherit the `www-data` group, and **every writer has umask 0002**, so the group can write them. PHP-FPM, the worker, cron and Deployer's `artisan` runs all need it. If one is missing, the bug comes back on whichever day that writer goes first.

**"Is running and starts at boot"** appears in four roles. On 29.09 the stand-in server showed that installing Postgres doesn't necessarily start it. Now every service says so explicitly (29.09 decision 6).

### 3.9 `roles/postgres`

```yaml
- name: PostgreSQL 18 from stock Ubuntu 26.04 (2.12)
  ansible.builtin.apt: { name: postgresql }

- name: Listens on loopback only
  ansible.builtin.lineinfile:          # make ONE line in a file look like this, leave the rest alone
    path: /etc/postgresql/18/main/postgresql.conf
    regexp: "^#?listen_addresses"      # find the line, commented out or not…
    line: "listen_addresses = 'localhost'"   # …and replace it with this
  notify: Restart postgres

- name: /etc/uni exists, root only
  ansible.builtin.file: { path: /etc/uni, state: directory, mode: "0700" }

- name: The database password is generated on the box, once — never on the PC (checklist A7)
  ansible.builtin.shell: set -o pipefail && umask 077 && openssl rand -base64 48 | tr -d '/+=\n' | head -c 40 > /etc/uni/db-password
  args:
    creates: /etc/uni/db-password      # skip entirely if this file exists → idempotent
    executable: /bin/bash

- name: Read it for the role below
  ansible.builtin.slurp: { src: /etc/uni/db-password }   # read a server file into a variable (base64)
  register: postgres_password_file     # store the result under this name
  no_log: true                         # never print it, not even with -vvv

- name: The application's role
  community.postgresql.postgresql_user:
    name: "{{ db_user }}"
    password: "{{ postgres_password_file.content | b64decode | trim }}"
  become: true
  become_user: postgres                # run as the postgres OS user, which is Postgres's superuser
  no_log: true

- name: The application's database, owned by that role
  community.postgresql.postgresql_db: { name: "{{ db_name }}", owner: "{{ db_user }}" }
  become_user: postgres
```

**`creates:`** is how a shell command becomes idempotent: *if this file exists, the command has already done its job.* **`register:`** keeps a task's output for later tasks. **The password never exists on your PC.** You copy it from `/etc/uni/db-password` into `shared/.env` by hand (runbook 3.6 / 7.5). That's the one manual secret step, and it's manual on purpose.

### 3.10 `roles/nginx`

The tasks: install nginx, make sure it's running, add `.mjs` to `/etc/nginx/mime.types` (without it every map is blank while `curl` still says 200, which is checklist C7), check whether a certificate exists yet (`stat` + `register: nginx_cert`), render the site template, link it into `sites-enabled`, remove Ubuntu's default site, and keep logs 30 days, which is the retention the privacy policy states. Every file change does `notify: Reload nginx`, and the handler is `nginx -t && systemctl reload nginx`: test first, reload only if valid.

**The template, `uni.conf.j2`.** `{% %}` is Jinja logic that disappears from the output. `{{ }}` is a value that gets printed.

```jinja
{% set tls = tls_mode == 'certbot' and nginx_cert.stat.exists %}
{#  tls is true only on production AND once a certificate exists. The first run on a new VPS has none. #}

{% if tls_mode == 'certbot' %}
server {                                   # port 80, production only
    listen 80; listen [::]:80;
    server_name undernoinfluence.pl www.undernoinfluence.pl;
    location ^~ /.well-known/acme-challenge/ { root /var/www/letsencrypt; }  # Let's Encrypt's proof
{% if tls %}
    location / { return 301 https://undernoinfluence.pl$request_uri; }       # everything else → HTTPS
{% else %}
    location / { return 404; }             # no certificate yet: answer ONLY the challenge
{% endif %}
}
{% endif %}
```

This is why the TLS role can get the first certificate on a server with no certificate: the playbook renders a port-80-only site first, certbot proves the domain through it, and then (§3.13) the template is rendered again with the HTTPS blocks switched on.

```nginx
server {                                   # https://www… → https://undernoinfluence.pl (production, with cert)
    listen 443 ssl; http2 on;
    server_name www.undernoinfluence.pl;
    return 301 https://undernoinfluence.pl$request_uri;
}

server {                                   # THE site
    listen 443 ssl; …                      # production; on the home server instead:
    # listen 80 default_server; server_name _;   — Tailscale serve does the HTTPS

    root /var/www/undernoinfluence/current/public;   # `current` is Deployer's symlink (see _3)
                                           # public/, never the project root: one level up is .env
    client_max_body_size 10m;              # largest upload (CSV imports, images)
    gzip on; gzip_types text/css text/javascript application/javascript …;

    location / { try_files $uri $uri/ /index.php?$query_string; }   # a real file, or Laravel

    location ~ ^/(build|vendor)/ {         # file names contain a hash or version → cache for ever
        expires max;
        add_header Cache-Control "public, immutable";
        try_files $uri =404;
    }

    location ^~ /admin {                   # only if admin_allow_from is non-empty (production)
        allow 100.64.0.0/10;               # Tailscale IPv4
        allow fd7a:115c:a1e0::/48;         # Tailscale IPv6
        deny all;                          # everyone else: 403, before PHP ever runs
        try_files $uri /index.php?$query_string;
    }

    location ~ \.php$ {
        fastcgi_pass unix:/run/php/php8.5-fpm.sock;
        fastcgi_param SCRIPT_FILENAME $realpath_root$fastcgi_script_name;
        fastcgi_param DOCUMENT_ROOT $realpath_root;
        fastcgi_param HTTP_PROXY "";       # blocks the "httpoxy" header attack
    }

    location ~ /\.(?!well-known) { deny all; }   # never serve .env, .git, any dotfile
}
```

**`$realpath_root`** is where Ansible and Deployer lock together most tightly. `$document_root` would hand PHP the path `…/current/public/index.php`. PHP caches compiled code **by path**, so after a deploy moves `current` it could keep serving the old release. `$realpath_root` resolves the link first and hands PHP `…/releases/7/public/index.php`: a new path, so a fresh compile.

### 3.11 `roles/app` — the empty house Deployer moves into

It creates `/var/www/undernoinfluence`, `releases/`, `shared/` and every folder under `shared/storage/`, all with:

```yaml
    owner: "{{ deploy_user }}"   # deploy can write here (Deployer)
    group: "{{ web_user }}"      # www-data can too (PHP, the worker, cron)
    mode: "2775"                 # the leading 2 is setgid: files created inside inherit group www-data
```

It **never** writes `shared/.env`. The comment at the top of the file says why: secrets are generated on the box, and `deploy.php` refuses to run without them. On production it also creates the ACME webroot `/var/www/letsencrypt`.

### 3.12 `roles/worker`

```yaml
- name: Supervisor and cron are running and start at boot
  ansible.builtin.systemd_service: { name: "{{ item }}", state: started, enabled: true }
  loop: [supervisor, cron]

- name: The queue worker (2.16)
  ansible.builtin.template: { src: uni-worker.conf.j2, dest: /etc/supervisor/conf.d/uni-worker.conf }
  notify: Update supervisor            # handler: supervisorctl reread && supervisorctl update

- name: The one scheduler line, with the shared umask (2.17)
  ansible.builtin.copy:
    dest: /etc/cron.d/uni
    content: |
      * * * * * www-data umask 0002; cd /var/www/undernoinfluence/current && php artisan schedule:run >> /dev/null 2>&1
      # m h dom mon dow  USER   …: files in /etc/cron.d carry a user column; every minute, as www-data
```

**The worker template**, line by line:

```ini
[program:uni-worker]
process_name=%(program_name)s_%(process_num)02d   ; uni-worker_00, uni-worker_01
command=php /var/www/undernoinfluence/current/artisan queue:work database --sleep=3 --tries=3 --max-time=3600 --backoff=30
;   database      the queue lives in the `jobs` table — which is why a job waits rather than being lost
;   --sleep=3     poll every 3 s when the queue is empty
;   --tries=3     give up on a job after 3 attempts → it goes to failed_jobs
;   --max-time=3600  exit after an hour; supervisor starts a fresh one (a stale worker lives at most 1 h)
;   --backoff=30  wait 30 s before retrying a failed job
autostart=true           ; start when supervisor starts (i.e. at boot)
autorestart=true         ; start again whenever it exits, crash or --max-time
stopasgroup=true         ; stopping it stops its child processes too
killasgroup=true
user=www-data
umask=0002               ; the other half of the shared-log fix
numprocs=2               ; two workers
redirect_stderr=true
stdout_logfile=/var/www/undernoinfluence/shared/storage/logs/worker.log   ; shared/, NOT current/:
                         ; supervisor opens the file once, and a release folder is later deleted
stdout_logfile_maxbytes=10MB
stopwaitsecs=3600        ; on stop, let a running job finish (up to an hour) before killing it
```

**Expected on a new box:** before the first deploy, `current` doesn't exist, so supervisor starts the worker, it fails, and it's marked `FATAL`. That's normal. It's restarted once after the first deploy (runbook 4.17).

### 3.13 `roles/tls` (production only)

It installs `certbot`, then `meta: flush_handlers`. That runs any pending handlers **now** rather than at the end, so nginx is already serving the port-80 challenge site. Then it runs `certbot certonly --webroot -w /var/www/letsencrypt -d undernoinfluence.pl -d www.undernoinfluence.pl …` with `creates:` pointing at the certificate, so it runs once in the server's life. If a certificate was just issued, it runs `include_role: nginx` again so the template now renders the HTTPS blocks. It also installs a renewal hook that reloads nginx, and finishes with `certbot renew --dry-run`, which fails the whole run if renewal wouldn't work.

**Webroot, not certbot's nginx plugin.** The plugin edits the site config, Ansible then puts it back, and the two fight on every run (2.19).

### 3.14 `roles/verify` — checks that fail instead of warn

`flush_handlers` first, so what's checked is what's live. Then: PHP's `major.minor` equals `php_version`; each of the eight extensions is loaded; `psql --version` says 18; `nginx -t` passes; `.mjs` is in `mime.types`; the running PHP-FPM master has `Umask: 0002` (read from `/proc/<pid>/status`, not from the config file, so it proves the restart happened); and `sudo -l -U deploy` shows **exactly one** `NOPASSWD` line, which is the reload.

`changed_when: false` on each one: a check never changes anything, so it must never spoil `changed=0`. `failed_when:` defines what counts as failure when an exit code alone can't tell you.

## 4. How Ansible and Deployer meet

Neither tool calls the other. They agree on **names and paths**, and the agreement is the whole integration:

| Ansible provides | Deployer relies on it for |
|---|---|
| the `deploy` user, key-only, in group `www-data` | logging in; `writable_mode: chgrp` on `bootstrap/cache` works only because deploy ∈ www-data |
| `/var/www/undernoinfluence` with `releases/` and `shared/storage/…`, setgid | `deploy_path`; Laravel's `storage` is linked to `shared/storage` in every release |
| `/usr/local/bin/composer` (2.10.3) | `deploy:vendors` runs `which composer` and uses it |
| `rsync` | `upload()` of the code archive and the assets tarball |
| sudoers: `systemctl reload php8.5-fpm` and nothing else | `uni:reload` after every switch and every rollback |
| nginx root `…/current/public` with `$realpath_root` | the `current` symlink Deployer switches |
| supervisor running `…/current/artisan queue:work` | `artisan reload` in `uni:reload` restarts it |
| cron running `cd …/current && php artisan schedule:run` | the scheduler always runs the live release |
| **not** `shared/.env` | `deploy:env` (UNI's override) stops if it's missing |

**The one seam no test covered: the PHP version.** It's written in four places. `php_version: "8.5"` in Ansible, which drives the packages *and* the sudoers line. `set('bin/php', 'php8.5')` and `sudo /usr/bin/systemctl reload php8.5-fpm` in `deploy.php`. And `php-version: '8.5'` in the CI workflow. `DeployRecipeKeepsTheRulesTest` pins seven rules about `deploy.php`, and none of them compares its PHP version with Ansible's. The day PHP 8.6 arrives, changing only `group_vars` would rebuild the servers with a sudoers line for `php8.6-fpm`. Every deploy would then fail at `uni:reload`, *after* the symlink has already switched. **Closed 30.09:** `DeployRecipeKeepsTheRulesTest` now reads `php_version` from the playbook and fails unless `deploy.php`'s PHP binary, its reload command and CI's PHP all match it. Proved by setting the playbook to 8.6: the test went red.

## 7. Reading an Ansible run

Every task prints one line per host:

| Status | Meaning |
|---|---|
| `ok` | already as described; nothing done. **What you want on a second run** |
| `changed` | Ansible made it so. Expected on a first run; on a second run, it's a bug in the playbook |
| `skipping` | a `when:` was false (e.g. `tailscale` on the home server) |
| `failed` | stopped. Ansible stops **that host** at the first failure; nothing after it runs |
| `RUNNING HANDLER` | a notified handler, at the end of the play |

The last lines are the **recap**:

```
PLAY RECAP
uni-home : ok=58  changed=0  unreachable=0  failed=0  skipped=9  rescued=0  ignored=0
```

`unreachable` means SSH failed, so check the alias and the key before suspecting the playbook. `failed=0 changed=0` on a second run is the finish line for Phase 2 and Phase 7.

**A failed run is safe to repeat.** That's the practical meaning of idempotence. Fix the cause, run the same command again, and everything already done reports `ok`.
