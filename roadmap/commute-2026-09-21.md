## 2. Findings raised unprompted

Ranked by consequence.

### 2.1 Creating the workspace repository would have corrupted it, and the plan said the opposite

Step 9 of the repository migration was `cd docs && git init`. That puts a git object store — thousands of small files, rewritten constantly — inside the directory Syncthing replicates continuously to the homeserver and your phone. Three machines writing to one git object store with no locking is a corrupted git object store, and the thing corrupted is the only copy of every journal and decision record UNI has.

**Somebody already saw this coming, once.** `docs/.stignore` carries the rule, and the comment above it reads: *"Git metadata. docs/ has none today (the repo root does), but a nested repo here would otherwise be replicated file-by-file and corrupted."*

**But that protects one machine of three.** [`tech/obsidian-sync.md`](../tech/obsidian-sync.md) records that *"Syncthing does not sync `.stignore` between devices. Ignore patterns are per-device configuration… The homeserver and the phone each need the same patterns entered by hand."* So the laptop is safe, the other two are safe only if someone typed the rule there, and the rule has never been tested against a folder that actually contains `.git`.

Meanwhile v3.0 of the plan said, in plain words, *"Obsidian and Syncthing are untouched."*

**Fixed:** the plan is v4.0 and step A10 is a gate — open the folder's Ignore Patterns on the homeserver and on the phone, confirm `.git` is listed, and only then create the repository. One minute.

### 2.2 The 31.08 journal carries a correction that is wrong, and deleting the commit ids would bury it

This is the answer to your question about the first commit, and it is the best argument for the decision you took.

- `docs/journals/2026-08-30.md` says the database password has been in `phpunit.xml` since **"First working version"**, 29 April.
- The next day, `docs/journals/2026-08-31.md` "corrects" that — debt item T-30e — to **5 April**.
- **The correction is wrong.** Both commits are real and they describe different files. 5 April is when the value first entered history, through `.env.example`. 29 April is when `phpunit.xml` got it. The migration plan's own credential table agrees: `phpunit.xml`, *in the repository since 29 April*.

So we never needed to *cite* either id — under your D9 answer both are deleted with all the others. What we need is for the **fact** to survive: the sentence that replaces it says 29 April, and the false correction in the 31.08 journal is fixed in the same pass. Otherwise the sweep deletes the evidence and leaves the error standing.

Written into [[decisions/product/journals-cite-dates-not-commit-ids]] and into step A5.

### 2.3 The badge record described six of the eight things a tile claims

You asked whether it was complete. It was not. Audited line by line against `venue-tile.blade.php`:

## 5. Answers to the questions you asked

### Why the commute filenames went wrong in the first place

On the evening of 16.09, four commute documents were written in one sitting, each named for the morning it was meant to be read: 19.09, 20.09, 21.09, 22.09. That works until the calendar catches up. It did. By this morning `commute-2026-09-21.md` was a file describing a project of 774 tests and a switch called `UNI_OWNER_PANEL` that no longer exists — and it occupied the exact name D13 prescribes for a document written today. Naming a file for the day it will be read is a bet on the future; naming it for the day it was written cannot be wrong.

### Community reporting — is there really a legal requirement, and is your design right?

**You remember roughly right, but the trigger is V2, not V1.** Worth confirming in the compliance hour rather than taking from me:

- There is **no general duty** to offer a "report an error" button for a catalogue you write yourself. In V1 UNI publishes its own data, so nothing attaches.
- The duty appears **when you host other people's content**. The DSA (Reg. (EU) 2022/2065) Art. 16 requires hosting services to provide an easy electronic notice mechanism; Polish UŚUDE art. 14 is the older analogue. **The moment an owner manages their own menu — which is V2 — UNI becomes a hosting service for that content and the duty applies.**
- GDPR Art. 16 (rectification) is a different thing and does not cover this: it is about personal data concerning the person asking, not a venue's drinks list.

**So your design is the right shape and the timing lines up exactly.** Anonymous reporting exists now with no duty behind it; the weighted account path arrives in the same release that creates the duty. Two things to settle before anyone builds it:

1. **One table or two.** Keeping V1's `venue_inaccuracy_reports` and adding a nullable `user_id` plus a weight is the version where the V1 data carries forward, which is what you asked for. A second table for account reports splits the history.
2. **It still needs public visitor accounts**, which V1 deliberately does not have (`browse-only-v1`). So this is not "F4 behind a switch" — it rides along with whenever accounts are built. That is the honest sequencing, and it is why F4 was never gateable.

### D2 — do the documentation files stay where I edit them?

**Yes, and nothing about how you work on them changes.** `docs/` does not move: same path, same Obsidian vault, same Syncthing folder. The only two changes are that the application repository cannot see the folder — one `.gitignore` line — and that the folder has its own `.git`. In practice: `git status` at the root shows application changes, `cd docs && git status` shows documentation changes. `schema.md` is the single file that physically moves, to `database/schema.md`, because it is the only one with a rule binding it to a code change in the *same* commit.

### T2 — what does `git clean -xffd` do, and does it delete `docs`?

**Yes, and it is worse than it looks.** The flags stack:

| Flag | What it adds |
|---|---|
| `-d` | include untracked **directories** |
| `-f` | force — git refuses without it |
| `-x` | also delete **gitignored** files, which after the split means all of `docs/` |
| `-ff` | the second `f` is what lets git delete an untracked directory that **contains its own `.git`** — with a single `-f` it refuses and prints a warning |

So `git clean -xffd` in this working directory deletes the vault, its history, and every journal and decision record in it — **and Syncthing then replicates the deletion to the homeserver and your phone.** The only net is the homeserver's Simple File Versioning (keep 10), which restores file by file rather than as a snapshot, so recovering 450 files is 450 operations. Written into the plan under *"The one command never to run here."*

Two things that save a surprise: **an imported venue is created inactive and marked `imported`**, so nothing goes live until you activate it — and the scope rule is still the three tests (can you drink it there, is it a named priced item in the venue's own drinks offer, is it a non-alcoholic member of a drinking category).

**Where the file lives matters:** not the repository root, which is where `uni_filtered_venues.xlsx` sits and session A removes it.

The event set is complete for what V1 does: eighteen event types firing, and the six listed as planned all belong to features V1 does not have. **The real gap is upstream.** `.env.example` ships `POSTHOG_PUBLIC_ENABLED=false`, and your rule is that `.env.example` is production.
