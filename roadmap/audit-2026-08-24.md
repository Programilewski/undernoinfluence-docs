# Audit — commute answers and notes vs. running code (2026-08-24)

during the commute of 24.08, checked against running code rather than against another document.
Twelve of the questions had factual answers waiting in the codebase. Four of the notes describe

## The two findings nobody wrote down

### 1. The 90-day event prune makes a feature you have already priced impossible

`VenueFeature::SeasonalForecast` sits in the **Basic** tier — `app/Enums/VenuePlan.php:56`, and
Basic is labelled **79 PLN/mo** at `VenuePlan.php:17`. Seasonality needs at least two comparable
periods a year apart.

`analytics:prune-events` deletes every row in `events` older than
`ANALYTICS_RAW_EVENT_RETENTION_DAYS` — default **90 days** (`config/analytics.php:6`), scheduled
daily at `routes/console.php:8`. **Corrected 2026-08-26:** scheduled, but never run — there is no
cron entry invoking the scheduler (T-25b), so no event has been pruned. The window first bites on
**2026-09-15**, ninety days after the oldest surviving event.

`venue_stats` survives 24 months (`app/Models/VenueStat.php:32`), so seasonality is buildable for
**views and clicks**. It is *not* buildable for **search demand**, because search events live only
in `events`. Search demand is the Tier 3 metric identified in `analytics-three-tiers.md` as the
thing an owner would actually pay for.

The data cannot be reconstructed after the prune runs. Every day at the current setting destroys
a day that a paid feature will need.

Two exits, not mutually exclusive:

1. **Raise raw event retention to 24 months.** Legally free — the `events` table holds no
   identifier (`migration ...000020`, `pii-columns-dropped.md`), so no storage-limitation rule
   applies to it. Cost is disk.
2. **Add a monthly search-demand rollup that runs before the prune**, so the aggregate survives
   even when the rows do not.

(1) buys the ability to define (2) later without having lost the inputs.

### 2. `venue_offer_logs` is pruned at six months, which defeats its own purpose

`app/Models/VenueOfferLog.php:19` prunes offer logs older than **6 months**, via `model:prune`
daily (`routes/console.php:9`).

That table is the dispute record: who added a product or drink to a venue, when, and with what
metadata. The dispute it exists to answer — *"we never carried that"* — characteristically
arrives **long after** six months, because that is how long it takes for a listing to reach
someone who disagrees with it.

Either the window is extended substantially or the table stops being described as provenance.

## 1. `uni:check-offer-freshness` — what it does (A2)

Three jobs, all repair, none producing user-visible state:

1. **`fixOfferTimestamps()`** — SQL-compares each active venue's `offer_updated_at` against the
   newest `venue_products.updated_at` / `venue_drinks.updated_at`. Newer child rows mean a write
   **bypassed the model observer** that stamps the timestamp. Repairs it: within
   `UNI_FRESHNESS_DAYS` → `markOfferFresh()`, older → set the timestamp and clear the streak.
2. **`clearMissedFreshnessStreaks()`** — clears `freshness_streak_started_at` where the offer is
   stale, null, or `breadth_score = 0`, so no venue holds a streak it did not earn.
3. **`fixBreadthScores()`** — recomputes `breadth_score` for every active venue through
   `VenueScoring`, chunked at 100, fixing mismatches with `updateQuietly()`.

**Nothing expires because of this cron.** `has_verified_menu` (`app/Models/Venue.php:299`) and
`computeFreshnessState()` are evaluated **at read time** from the stored timestamps. A badge goes
stale the moment it is stale, whether or not the job has run.

So the frequency question is not "how many venues" but **"how often does something write to an
offer without going through the observer?"** — bulk imports, seeders, direct SQL, Filament bulk
actions.

Against the 200-venues-in-two-weeks scenario:

- **Cost** scales with venue count and is negligible — rescoring a few hundred venues is seconds.
- **Risk** scales with bypassing writes. A bulk import is *one* such event. Hourly catches it up
  to an hour later by luck; running the command as the last step of the import catches it
  immediately by design.

Relevant constants: `UNI_FRESHNESS_DAYS = 90`, `UNI_VERIFICATION_VALID_DAYS = 180`
(`config/uni.php:17,34`). A one-hour repair SLA against a 90-day window is precision theatre.

Minor: the class docblock still reads *"Runs hourly."*

## 2. Search ranking (B1)

`Venue::scopeSearch()` (`app/Models/Venue.php:386`) is a filter, not a ranking signal. It ILIKEs
the term across venue name, street name, district name, **product names** and **drink names**, all
OR-ed into one `where` group.

The surviving rows then receive the ordinary default ordering
(`app/Services/Discovery/VenueQuery.php:116`):

```
breadth_score DESC
  → catalog_category_diversity DESC
  → custom_drink_diversity DESC
  → name ASC
```

Consequences:

- Searching *Lech* ranks a 40-product venue holding one Lech above a smaller venue built around
  it. Relevance to the query contributes **nothing**.
- The final tiebreak is alphabetical, which quietly and permanently favours venues whose name
  starts with A.

Two contained changes: rank by **count of matching products** first when the term matches
products — the mechanism already exists as `categoryBreadthExpression()` — and replace the `name`
tiebreak with `offer_updated_at DESC`, which is defensible when an owner asks why they are
seventh.

Storing result identities does **not** affect ranking; `no-pay-to-rank.md` is permanent. Cap at
the first 20 IDs in rank order — position is then implicit and needs no second field.

**Second-order risk:** selling *"you appeared in 340 searches"* invites *"so why am I seventh?"*,
which `credibility-formula-opacity.md` deliberately does not answer. Decide that reply before the
first invoice.

## 3. The three verification columns (B2)

All on **`venues`** — `database/migrations/2026_06_17_000007_create_venues_table.php:32-34`.

`is_verified` is **not** derivable from `last_menu_check_at`. `VenuesTable.php:118` has a "mark
checked" action that writes `last_menu_check_at` **without touching `is_verified`**, so
*checked recently and not verified* — "we looked, it did not meet the bar" — is a reachable and
meaningful state. Deriving the flag deletes the ability to express it.

`verified_at` is the genuinely dead one: no logic anywhere reads it. It survives only in
`VenueFactory.php:21` and the unrelated `venue_erasure_requests.verified_at`.

## 4. Plan gating (B3)

A price list and a lock mechanism, with no doors installed:

- `venues.plan` — free / basic / pro / premium, prices already in the labels
  (`app/Enums/VenuePlan.php:16-19`).
- `VenuePlan::features()` maps plan → 4–17 features.
- `Venue::hasFeature()` (`app/Models/Venue.php:209`) checks the per-venue override table, then
  the plan.
- **No caller anywhere.** Every owner report computes and renders regardless of plan.

The commercial risk is not the missing gate but the **clawback**: sell Basic and the buyer sees
Premium, then features have to be taken away from someone who has paid. The cheaper protection,
while the panel is unexposed (O-2), is to **ship Tier 2 only** per `analytics-three-tiers.md` —
nothing to gate, nothing to reclaim. Gating becomes real work the day a real package is sold.

## 6. The analytics flow, corrected (note 14)

| Stage | Reality |
|---|---|
| Raw events | `events` — `type`, `venue_id`, `city_id`, jsonb `properties`, `created_at`. No identifiers, by design. |
| "Rollups" | `venue_stats` is **not derived from events**. `VenueStat::track()` is called at the same moment the event is written (`VenueAnalytics.php:44,51,86`). Two parallel writes, not a pipeline. |
| Granularity | Daily only. Weekly and monthly are summed on read. |
| Prune | `analytics:prune-events` — `events` older than 90 days, daily. |
| Also pruned | `model:prune` daily: `venue_stats` 24 months, `venue_offer_logs` 6 months, `audit_logs` 12 months. |

"Prune" is the correct word — it is Laravel's own. The policy word is *retention period*.

Two consequences of the parallel-write design: `venue_stats` **survives** the event prune, which
is deliberate and good; but a missed `track()` call **cannot be repaired** from events. That is
the same drift class `uni:check-offer-freshness` exists to fix, in a second place.

## 7. Retention law (note 15)

Because `events` holds no identifier and cannot be linked to a person — the position established
in `eventlogger-identifier-stripping.md` and `pii-columns-dropped.md` — **GDPR does not apply to
it at all** (Recital 26, anonymous information). There is no legal retention ceiling. The 90 days
is self-imposed policy: good practice, evidence of good faith, and freely changeable.

What would change that: reintroducing any identifier — IP, cookie ID, fingerprint — at which
point Art. 5(1)(e) storage limitation applies with a documented justification.

Separately, the consent banner and the `uni_consent` cookie answer to **ePrivacy**, in Poland the
*Prawo komunikacji elektronicznej* replacing art. 173 of the *Prawo telekomunikacyjne*. That is
the law behind the banner — not GDPR.

## 8. B2B analytics without identifiers (note 13)

One person making fifty searches and fifty people making one each are **indistinguishable**, and
always will be, because every identifier was deliberately removed. That was the right trade; this
is its price.

Truthfully sellable: **"340 appearances, 12 taps"** — a ratio between two counts measured on the
same basis, comparable across venues and across time even if one visitor produced all of it. Also
share of category demand in a district, percentiles, and trends.

Never printable: *unique users*, *reach*, *customers*.

If dedup is wanted, the only version that does not undo the GDPR position is **client-side** — a
`sessionStorage` flag suppressing duplicate search events inside one browsing session, labelled
honestly as *sesje wyszukiwania*. A salted IP+UA hash would be pseudonymous personal data under
Art. 4(5) and would reverse the achievement.

**Rule worth adopting:** every B2B number carries its measurement basis in its label.

## 9. Consent gating undercounts campaign attribution (note 3)

`AnalyticsEventController.php:14` aborts with 403 unless `uni_consent === 'granted'`. Everyone who
declines is invisible — including on exactly the campaign traffic UTM parameters are meant to
measure.

Use standard UTM (`utm_source=instagram&utm_medium=social`) rather than a bespoke `source=` param:
PostHog and every other tool parse it for free. Then add a **server-side landing counter** for the
part consent removes — one `events` row, `type=landing`, `properties={source:instagram}`, no
cookie, no identifier, therefore no consent required and still outside GDPR scope. Same
architecture, one more use.

## 10. DSA Art. 16 exposure is downstream of the owner-panel toggle (notes 10–11)

Art. 16 binds **hosting services**. V1 is browse-only (`browse-only-v1.md`) with all content
admin-entered — arguably not hosting third-party content at all. That changes the moment the
owner panel or product proposals are exposed.

**So DSA exposure and the owner-panel decision are the same decision.** Not lawyer-verified.

The erasure mechanism itself is complete: `EraseVenueAction` handles venue data, raw events,
uploaded files and optional account deletion. But requests can only be created from **inside the
admin panel** (`Admin/.../EditVenue.php:69`) or the **owner panel** (`createSelfServiceRequest`,
gated on `claimed_by`). An owner without an account has no route but email — which is still a
working mechanism, since the obligation is a route and a response, not a form.

Four notes collapse into one page: **`/kontakt`**, one form, a subject selector routing to
`venue_inaccuracy_reports` or `venue_erasure_requests` — both tables and both admin queues already
exist.

**Captcha:** neither Google nor Cloudflare yet. `throttle` middleware is already on two routes and
a `HoneypotController` pattern exists. Both captcha vendors are US processors and would add a
transfer to the privacy policy in the same breath as CARTO, against the stated EU-resident
preference. Honeypot plus rate limit until spam actually arrives.

## 11. `intl` — what is actually lost (C3)

Verified on this machine: **ICU 76.1**, and the Polish names are correct — `Polska`, `Niemcy`,
`Czechy`, `Kosowo`.

- **Determinism** is only cosmetically at risk: ISO codes are stored, never names. A different ICU
  version can rename a label (this is how *Turkey* became *Türkiye*). Data never moves.
- **Sorting** requires a `Collator('pl_PL')` or Polish diacritics sort wrongly. One line.
- **Curation** is required: ICU returns ~250 "regions" including continents, the EU and `ZZ`
  (Unknown), so a filter to real ISO-3166-1 countries is needed, plus a small override map.
- Realistically **~15 lines and an override array**, not ten.

`CountryCodes` is referenced only from five Filament schemas
(`Brands`, `Producers`, `Products`) — **zero public views**. Admin-only blast radius, and
independent of which OS the work happens on.

## 12. Provenance logging (note 16) — mostly built already

`venue_products` (`migration ...000008`) already carries **`added_by`** under a CHECK constraint
and **`confirmed_at`**. `venue_offer_logs` already records **who** (`user_id`), **what**
(`product_added` / `product_removed` / `drink_added` / `drink_removed` / `drink_updated`), **on
what** (polymorphic subject), **when**, and a free-form `metadata` jsonb. That is "where it came
from, who put it there, and when" — built, in production, unused.

Gaps, in order of severity:

1. **Six-month prune** — see the top of this document. Fatal to the stated purpose.
2. **No UI.** The promise is a ten-second answer to a dispute.
   `Filament/Admin/Resources/Venues/RelationManagers/` holds Drinks, Products and FeatureFlags —
   **no offer log**. The data exists; the answer does not.
3. **The `added_by` vocabulary is corrupted.** The CHECK allows
   `'admin', 'venue_owner', 'proposal_approved', 'seed', 'seeder', 'owner', 'community'` — with
   `seed`/`seeder` and `venue_owner`/`owner` as duplicate pairs. Two vocabularies merged and never
   reconciled; any provenance report will split its own counts.
4. **`venue_drinks` has no row-level `added_by`**, though the offer log does cover drinks.
5. Unverified: offer logs contain `user_id`, so unlike `events` they **are** personal data —
   whether `EraseVenueAction` clears them needs checking.

Conclusion: fix retention, add the relation manager, normalise the vocabulary. Three small things
instead of one new subsystem.

## 13. The ADR note (note 17) — right in general, wrong about this stack

`docs/decisions/adr/` holds ten ADRs and `docs/decisions/product/` holds sixty-plus records shaped
*Problem → Options considered → Decision → Rules → What this prevents → Revisit when*. That shape
is **stronger** than the classic Context/Decision/Consequences the note proposes: "What this
prevents" and "Revisit when" are exactly the anti-drift function it argues for.

What the note actually supplied:

- A draft **"ADR-004: OpenStreetMap for tiles only"**. ADR-004 is *Scoring Simplification*.
  Pasting it in would have collided with a real record.
- A claim that tiles come from **OSM/MapTiler**. They come from **CARTO**
  (`dark-map-tile-provider.md` — and A3 of the decisions document is about CARTO).
- A decision about OSM that was already made in `osm-dropped.md`.

Confidently written, three factual errors about this codebase. The one piece worth adopting:
**never delete a record — supersede it**, with the new one naming the old.

## 14. Two research files are tracked, not one (A4)

`git ls-files` returns **both** `uni_filtered_venues.csv` and `uni_filtered_venues.xlsx`. The
decisions document named only the CSV.

Removing them from HEAD does not remove them from history. If either holds contact names or email
addresses gathered during venue research, that is a personal-data-in-git-history question rather
than a tidiness one, and the contents decide whether `git rm` is sufficient.
