### 0.2 Four ideas behind the open questions

**Why every visitor gets a session (P33).** The report form and the map's filters carry a CSRF token — a random value the server hands out with the page and expects back with the request, which proves the request came from our page and not from someone else's site. The token has to be kept somewhere between the two requests, and that place is the session. The question is only where: Laravel's `database` driver writes a row with the visitor's IP address and browser string beside it, while the `file` driver writes the session and nothing else. Same protection, less personal data — that is the whole of P33.

**A computed state and a human override (P32, P35).** Whether a venue is live is *computed* from facts: a point on the map and something on its menu. Switching it off by hand is an *override*: a person saying closed, or wrong. Stored in the same `is_active` column, the two cannot be told apart, so the next time the computation runs it undoes the person. The usual fix is to record that a person set the value, and when — the one column P32 proposes. P35's second call is the same rule facing the other way: a person switching on an empty venue does not change the fact that it is empty.

**Why commit ids die in the repository migration (step 4).** A commit id is the start of a fingerprint computed from the commit's content *and its parent's fingerprint*, so it cannot be carried into another history — a new repository built from the same files has one commit with a new id. Every id the documentation cites then points at nothing, except in the archived old repository. That is why step 4 replaces the 389 seven-character ids and look-alikes across 32 files with dates and descriptions **before** step 8 squashes, and why it is the step that cannot be redone.

**The two processes that are not the website (§10 step 4).** nginx and PHP answer visitors. The *worker* runs what was queued for later — every e-mail, and the CSV import, which is a queued job. The *scheduler* runs what happens on a clock — the heartbeat, the hourly offline check, the nightly pruning of personal data. If either is missing, nothing errors and the site looks perfect. The heartbeat proves the scheduler; **nothing proves the worker** — §6.26.

## 1b. The mobile map — you were right, and the cause was not the map

**Reproduced, fixed, and covered.** Every phone visitor on their first visit could not open the map, and the reason is worth reading in full because the failure was not where it looked.

**What was happening.** The cookie consent panel is `role="dialog" aria-modal="true"`, anchored to the bottom of the screen. At 390×844 it is **435 pixels tall — more than half the screen.** The map button ("Mapa") is fixed at the bottom right, at y 772–820, which is *inside* that panel. The element actually under your thumb was the consent panel's **"Zaakceptuj wszystkie"** button.

So the first tap did not open the map. **It granted analytics consent.** Measured, not inferred: after one tap at the map button's coordinates, `uni_consent=granted` was set and a PostHog cookie appeared, `currentView` stayed `list`, and there was no map canvas on the page. No JavaScript error, nothing in any log.

**Why that is worse than a missing map.** `consent-banner-design` exists to stop this product nudging anybody toward accepting, and this is the strongest possible nudge: the accept button placed under the site's primary mobile control. A tap aimed at a map is not an unambiguous indication of anybody's wishes, so what it produced was not consent.

**Why nothing caught it.** `scripts/check-map-render.mjs` was written for exactly this class of bug — its own comment describes "a CSS cascade change collapsed a container to zero height so the map rendered perfectly into a box nobody could see" — and it only ever ran at 1280×900. On a desktop the map is always on screen and never depends on that button, so the check was green while the map was unreachable on every phone.

**What changed.** Four things, and only the first is the fix:

1. **Fixed controls hide themselves while the consent dialog is open** (`body.consent-open`, one CSS rule). A control under a modal must not merely be unreachable — it must not look tappable.
2. **The render check now runs every surface at 390×844 as well as 1280×900**, and answers the consent dialog by rejecting, the way a first-time visitor must. That is what reproduced this, and it is now permanent coverage.
3. **A second, older bug fell out of it:** `revokeConsent()` called `window.posthog?.opt_out_capturing()`, which guards the object but not the method — and PostHog's CDN snippet installs a stub object before the library loads. So "Odrzuć wszystkie" could throw a `TypeError`, and because the throw happened *before* `visible = false`, the dialog stayed open over the whole page while the decision had already been saved. The button looked broken while doing exactly what it was asked. All four PostHog calls now guard the method, and the dialog closes before the vendor is told anything.
4. **Both decision records are amended** rather than a new one added: `consent-banner-design` gains the rule about what may sit under the panel, and `map-correctness-needs-a-browser` gains the two viewports.

**Verified end to end on a 390×844 viewport:** consent pending → the map button is `display: none`; reject → button visible, `uni_consent=denied`, no PostHog cookie; tap → one canvas, 390×764 CSS pixels. `npm run check:render` is 6 of 6, `check:map` and `check:consent` pass, 684 PHP tests pass.

**One thing for you to decide, and it is a product question rather than a bug.** On a desktop the map is on screen before consent is answered; on a phone it now cannot be reached until the dialog is answered, because the dialog is modal by design. That is consistent, and it is also a wall in front of the first thing a new visitor wants. The alternatives are to let the overlay stop capturing taps (the banner asks rather than blocks), or to leave it as it is. **P27.**
Interjection: we need to investigate it further. How come the consent banner blocks the map? In terms of loading scripts, or it is just a matter of z-index? I don't understand how these two are correlated. Map loads independently of cookie consent, we don't need the user accepting cookies for map to load. Cookie banner controls only posthog as far as I understand it.

### 1c.1 Production would have been built from a file nobody had updated since August

Laravel has two ways to build an empty database: run the migration files one by one, or load a single SQL snapshot — a *schema dump* — and then run only the migrations newer than it. **If the snapshot exists, it wins.** ADR-010 kept one and required it to be regenerated every time a migration changed.

On 01.09 `venue_visits` — which held a `session_id` the identifier decisions forbid — and `user_venue_saves` were removed and their migrations deleted. The snapshot was never regenerated. So the local database was right and **every other database built from this repository was wrong**: the test database, a Ploi staging site, and production's first `php artisan migrate` would all have created both tables. The suite could not notice, because it ran on the wrong schema too, and two tests were passing only because of it — one inserted into `venue_visits`, the other "proved" a constraint by failing on a column that did not exist.

**It was the second time.** On 24.08 the same file was found still holding the four `events` identifier columns from June. A rule that depends on remembering a manual step failed twice in ten weeks, so the step is gone rather than re-promised: **the dump is deleted, not regenerated**, and the migrations are **27 files, one per table** — replaying them takes under a second, so the dump saved nothing. A database built from the old files and one built from the new were compared column by column, constraint by constraint and index by index: identical, except that one primary key lost a stray `1` from its name. `SchemaHardeningTest` now fails if any file appears in `database/schema/`, if either removed table exists, or if an `events` identifier column returns, and it was checked to fail against the old dump. ADR-010 carries a dated revisit section naming the rule it replaced.

**Why this is the headline rather than a footnote.** A product whose promise to venue owners is accountable data would have opened production with a table of session identifiers it decided months ago never to keep — invisible to everyone except the person who checks, which is the one person that matters.

### 1c.2 Nobody could have logged in to `/admin` on day one

The local admin comes from the seeder, and the seeder creates users only in `local`. Filament's own `make:filament-user` prints *"Success! … may now log in"* — and creates the account with role `user`, which `User::canAccessPanel()` refuses. Verified both ways in the rehearsal: that account bounces back to the login page, and the same account promoted to admin gets in. The only way in was a tinker one-liner nobody had written down.

**Built:** `php artisan uni:create-admin`. It asks for an e-mail, a name and the password twice; the password is only ever typed at a prompt, never passed as an option, so it stays out of the server's shell history; twelve characters minimum. An e-mail that already exists is offered for promotion, defaulting to **no**, and a venue owner is warned they would lose `/panel`. Every grant writes an `admin_created` or `admin_promoted` audit record. Eight tests. **Deploy checklist A10** makes it the first step after the first deploy — over SSH, never from a deploy script. Recorded in `the-first-admin-is-made-at-the-console`.

This changes P16's shape rather than its answer: the first login now works, and 2FA is the second half of the same job.

### 1c.3 The map library had a critical advisory, and the patch on its own blanked every map

`npm audit` reported **GHSA-jrc7-96c5-q579**, a sanitiser bypass in `maplibre-gl`, fixed only in 6.x while we were on 5.24. Our exposure was low — all three map popups escape what they put into HTML, and every value comes from data an admin typed — but it is the library behind the screen a visitor from Instagram lands on.

**Version 6 is a different kind of package:** ES modules only, no default export, and a background worker in a separate file the build tool has to be told about. With the version bumped and the loader unchanged, **the production bundle failed all six render checks** — homepage, `/mapa` and a venue page, desktop and phone — on *"Cannot read properties of undefined"*. Every PHP test passed. The fix is one file, `resources/js/map-loader.js`; after it, six of six on the built bundle, three more clean runs, six of six on a dev server, and `check:map` and `check:consent` pass. **`npm audit --omit=dev` reports 0 vulnerabilities, re-run 13.09.**

**The cost, stated plainly:** a page that draws a map now downloads about **423 KB gzipped on a first visit, against 270 KB on 5.x** — roughly 150 KB more, cached afterwards. ## 3. The two explanations you asked for twice

### 3.1 `trustProxies` — from the beginning

You wrote: *"let's work on this carefully, explain what's going on here, you're cutting context."* Fair. Here it is from the start.

**Why the header exists at all.** When a request arrives, the web server knows exactly one address for certain: the address of the machine at the other end of the TCP connection. If that machine is the visitor's phone, that address is the visitor. If there is something in between — a load balancer, Cloudflare, a reverse proxy — then the address belongs to the middleman, and every visitor in the world looks like the same address. To solve this, proxies add a header: `X-Forwarded-For: <the real visitor>`. The application reads the header instead of the connection.

**The header is written by whoever sends the request.** It is not a protocol feature, it is a string. Anyone can send it. `curl -H 'X-Forwarded-For: 8.8.8.8' https://example.com` is one line. So an application that reads it is trusting a value the client chose. That is fine when a proxy you control **overwrites** it before the app sees it, and it is a hole when nothing does.

**What the line in our code does.** `bootstrap/app.php`, inside `withMiddleware`:

```php
$middleware->trustProxies(at: '*');
```

`'*'` is not "be flexible". In `Illuminate\Http\Middleware\TrustProxies` it resolves to:

```php
$request->setTrustedProxies(['0.0.0.0/0', '::/0'], $this->getTrustedHeaderNames());
```

`0.0.0.0/0` and `::/0` are every IPv4 and every IPv6 address that exists. Every machine on the internet is registered as a trusted proxy. And the header list that becomes authoritative is not just one header:

```php
X-Forwarded-For | X-Forwarded-Host | X-Forwarded-Port | X-Forwarded-Proto | X-Forwarded-Prefix | X-Forwarded-AWS-ELB
```

So `$request->ip()` stops meaning "who connected" and starts meaning "whatever the client typed in a header", and `$request->getHost()` does the same for the hostname.

Worth knowing, because it explains how the line got there: **Laravel itself only turns this on automatically when it detects that it is running on Laravel Cloud, Forge or Vapor** — the framework checks the hostname for `.on-forge.com` and `.on-vapor.com` before defaulting to `'*'`. On an ordinary VPS the framework's own default is to trust nothing. The line is a copy-paste from a managed-hosting setup.

**What in UNI asks for the visitor's address.** Six places, and this is the part yesterday's document compressed into one sentence:

| Where | What it protects | What `'*'` does to it |
|---|---|---|
| `vendor/filament/.../Auth/Pages/Login.php:76` → `$this->rateLimit(5)` | The login form on `/admin` and `/panel`, 5 attempts per minute | The limiter's key is `sha1($component.'\|'.$method.'\|'.request()->ip())`. A different header value is a different key, so **every attempt can have its own private bucket. Password guessing becomes unlimited.** This is the one that matters. |
| `AppServiceProvider.php:47` — `auth` limiter | Nothing. It is registered and referenced by no route (§2.5) | — |
| `AppServiceProvider.php:56` — `venue-redirect` | 10 outbound clicks per minute per IP + venue + link type | Click counts on a venue page can be inflated to any number. Those counts feed the owner reports we intend to sell. |
| `AppServiceProvider.php:62` — `analytics-events` | 30 events per minute | Event spam, which lands in the tables the whole analytics story is built on. |
| `AppServiceProvider.php:66` — `reports` | 5 inaccuracy reports per minute | The report button becomes a way to flood the admin queue. |
| `HoneypotController.php:14` — `hash('sha256', $request->ip().config('app.key'))` | Scrape detection: the fingerprint recorded when something takes the canary bait | One scraper becomes thousands of distinct fingerprints. The canaries stay in place and stop being evidence of anything. |
| `InternalTraffic.php:64` | Excluding our own visits by address | Someone who guessed the configured address could exclude themselves from the counts. Minor, and third of three signals — the signed-in check and the opt-out cookie do not depend on the header. |

**The second family, and its limits — because I would rather you know where my claim stops.** `X-Forwarded-Host` is trusted too, so `$request->getHost()` is attacker-controlled, and absolute URLs built during that request (the canonical tag, `og:url`, the addresses inside `/sitemap.xml`) would carry the attacker's hostname. In practice that poisons only the attacker's own response, because nothing caches responses in front of the app and nobody can inject a header into Google's crawler. **The e-mail path is closed**: all four notifications are queued, a queued job runs with no HTTP request, so those links are built from `APP_URL`. And neither panel has password reset, so there is no reset link to redirect. That is the whole of it — I am not going to inflate this half.

**Why it is safe to simply delete the line.** On this server nginx and PHP-FPM sit on the same machine, and nginx sets `REMOTE_ADDR` from the actual TCP peer. `$request->ip()` is then correct with no trusted-proxy configuration at all. Deleting the line restores every limiter above.

**Done 12.09.** The line is gone and `tests/Feature/Security/TrustedProxiesTest.php` asserts that `X-Forwarded-For` (single, chained, and claiming localhost), `X-Forwarded-Host` and `X-Forwarded-Proto` are all ignored — plus one test that sends three different spoofed addresses and asserts they produce one limiter key rather than three. The test is the part that makes it permanent, and it sits beside the other guard tests that exist for exactly this reason (`RobotsTest` asserting a file's absence, `ProducerNamesStayInternalTest`). **If a proxy is ever put in front** — Cloudflare, most likely — the correct form is `trustProxies(at: [<that proxy's published ranges>])` and only the headers it actually sets. Never `'*'` again.

### 4.5 SEO on brands and drinks — you are right about intent, and it changes the job of those pages rather than their existence

Three questions in your note. They separate cleanly, so let me take them separately.

**(a) "Since the legal documents said we cannot promote drinks themselves and brands, is it good to base our SEO on the product/brand?"**

The alcohol-advertising analysis left the repository on 07.09 by your decision (`legal-analysis-stays-out-of-the-repo`), and I am not going to rebuild it here — if you want that question answered with authority it belongs with a lawyer who can be held to the answer, not with a document in `docs/`.

**But there is a stronger test available, and it is ours:** `mission-is-the-healthy-choice` already says *"brand pages exist only while they help somebody choose, and the day they mostly help brands they are a candidate for deletion."* That is a sharper instrument than the legal question, because it decides the design rather than just permitting it.

Applied: a page whose job is *"this drink is served in fourteen places in Warsaw, here they are"* helps a person find something they would otherwise have missed, and the brand benefits as a side effect. A page whose job is *"here is what this drink tastes like, here is the bottle, here is the brand story"* helps the brand, and the person benefits as a side effect. Same URL, same data, opposite product. **The 30.08 decision already mandates the first shape** — a counted call to action naming a real number, no photographs at launch, the word "mocktail" never in a title — and it does so for SEO reasons, which happens to also be the mission-safe shape. So the answer is: brand and drink pages are fine, and the thing that keeps them fine is editorial discipline about what is on them, which the record already specifies.

**(b) "Isn't it true that when someone googles 'piwo bezalkoholowe' the intent is purchase, not seeking places?"**

**Yes. This is the sharpest observation in your notes, and it corrects the reasoning behind a Decided record.**

The 30.08 decision was built on volume: five years of Google data showing a real and growing curve for non-alcoholic beer, flat zero for "mocktails", and nothing measurable for phrases about non-alcoholic bars in Warsaw. **Volume is not intent.** "Piwo bezalkoholowe" is a transactional query, its results page belongs to retail — shops, price comparison, marketplaces — and UNI cannot outrank them. Worse, if it did, the visitor's next question is *"where do I buy it"*, which UNI does not answer and should not pretend to.

What UNI can serve is the same demand with a place attached: `piwo bezalkoholowe warszawa`, `[brand] warszawa`, `[brand] na kranie`, `gdzie napić się bezalkoholowego piwa`, `bar bezalkoholowy mokotów`, `0% śródmieście`. Lower volume, correct intent, and **that is what the existing cluster already targets** — `/{city}`, `/{city}/{district}`, `/{city}/{category}`, `/{city}/{district}/{category}`, `/kategoria/{slug}`. The 30.08 finding that venue-concept phrases have no measurable volume is consistent with this: the category is not searched by name, so the entry has to be product-or-brand *plus place*.

**The correction is to the job of the pages, not to whether they exist:**

1. They are **not** head-term ranking plays. Nothing on them should be written to compete for `piwo bezalkoholowe`.
2. They are **long-tail catchers** for `[brand] + [city]` and `[brand] + na kranie`, where the intent is availability and UNI is the only plausible answer.
3. They are **internal hubs** — a drink page collecting the venues that serve it passes authority to exactly the venue and city pages that are the conversion surface. That is the real return, and it does not depend on the drink page ranking for anything by itself.
4. Consequence for build order: nothing changes, they stay last (§10, item 8), because a drink page with no venues behind it is an empty page. What changes is scope — a template that leads with availability, not a content library with 200 tasting notes.

This is worth a revisit note on `brand-and-product-pages.md`. Its own revisit trigger is *"Search Console shows which product pages actually earn traffic"* — your observation is the reason to revisit **before** building rather than after spending the effort.

**(c) "In case anyone had problem due to making the brands and products SEO friendly, we can just noindex nofollow that, right?"**

**`noindex`: yes, and the machinery already exists.** It is per-page, reversible, and the codebase already does exactly this in three places: national category pages are held out of the sitemap and noindexed until a second city gives them something to aggregate; district pages need three active venues (`thin-district-pages-are-noindexed`); `SeoCluster` makes the page and the sitemap read the same counts so the two can never disagree (`empty-landing-pages-noindex`). Brand and drink pages should be wired into the same gate from the start — indexable only when the product is actually served somewhere. That gives you the switch you are asking for as a **property of the page**, not an emergency lever.

**`nofollow` on the internal links: no, and this is the part to separate out.** Nofollow on internal links throws away the hub value that is the main reason to build the pages at all (point 3 above). If a page must leave the index, it stays linked and followed. Long-term noindex is eventually treated as nofollow by Google anyway, which is another reason the gate should be about whether the page has content rather than a permanent state.

**And the caveat that matters most:** `noindex` removes a page from search. It does not remove it from the web. If the concern is that a page reads as advertising, a de-indexed page is still a published page — the remedy is editing or deleting it, not hiding it from Google. Also, for the record, `robots.txt Disallow` is not the same tool: a disallowed page can still be indexed from external links, and a crawler that cannot fetch it cannot see a `noindex` on it. If a page must go, it goes by meta tag or `X-Robots-Tag`, and it stays crawlable.

### 4.6 What the import does not solve — and it is the thing your launch definition turns on

You defined launch (P11) as: *"v1, working code, SEO setup, working admin panel, tests passing, entire stack working, then deploy and initial import of venues, products, brand, producers."* That is a good definition and I am adopting it. Two things it implies that are not in it:

**First: an imported venue cannot go live.** ~~`VenueImporter` sets `is_active = false` by default~~ *(wrong until 13.09 — it set the value only in data the import never wrote, so an imported venue took the database default, which is live; fixed, §1d.2)*, and `venue-activation-gate` means a venue activates only once it has at least one drink attached *(since 13.09: a catalogue product or a house drink, and it goes offline again when the menu is emptied)* — which is also the `kebab-rule`: a venue qualifies by having a named NoLo item, not by existing. **There is no import path for the venue↔drink relationship.** Drinks are attached one at a time per venue, through the Products relation manager in the panel. A CSV importer for the pivot would have to reproduce all five or it would silently produce venues with no offer history, wrong scores and no activation. That is the real argument for P21's recommendation — not that the work is small, but that the hand path already gets five things right.

**Second: order matters for brands and producers.** `ProductImporter` creates a missing brand with `firstOrCreate(['name' => ...])`, which produces a brand with a name and nothing else — no country, no website, and **no producer link**. Producers are internal by decision (`producers-stay-internal`), so "importing producers" means admin data entry with no public surface, and it should happen **before** products so that `firstOrCreate` finds rather than invents. This is not hypothetical: the 09.09 session found Crodino entered as "Campari Group" and Somersby as "Carlsberg" — producer names rendering as brands — which is exactly the failure mode of doing this in the wrong order. `ProducerNamesStayInternalTest` now guards the rendering; it does not guard the data entry.

**So the launch order inside "initial import" is:** producers → brands → products → venues → attach drinks. Four of the five have an import path or a form; the fifth is the work.

### 4.7 Backups — where they go, what it costs, and what makes it an actual backup

Your P3 answer picked object storage. Agreed, and the record agrees (§2.2). Choosing between the two you named:

**Scaleway Object Storage, Warsaw region (`pl-waw`).** Reasons in order:

1. **A different provider from the host.** OVH object storage would put the backup and the machine it protects with the same vendor — one account compromise, one billing dispute, one provider incident. Scaleway is already a vendor for TEM, so this adds **no new processor and no new DPA**, which is the specific thing you flagged.
2. **EU and Polish.** `pl-waw` keeps everything in the country the data is about; no transfer question at all.
3. **Cost is a rounding error.** Standard Multi-AZ is €0.01606/GB/month, One Zone €0.00803/GB/month, and 75 GB of egress is free every month. A full dump of this database at 100 venues is single-digit megabytes. Eleven copies (7 daily + 4 weekly) are still single-digit megabytes. **This costs cents, and the restore drill is free.**
4. `spatie/laravel-backup` writes to any S3-compatible disk and will warn when the newest backup is too old, which is the part that catches silent failure. Re-verified on Packagist 12.09: **v10.3.2, released 20.08.2026, MIT, requires PHP ^8.3 and `illuminate/*` ^12.40|^13.0** — fits this application exactly.

**Two places in the repository name Backblaze B2 and will need the same edit:** `spec.html`, and `tech/dependencies.md:63`, where the package is listed as a *"V1 launch blocker — targeted at Backblaze B2"*. `next-session.md` repeats it from there. One decision, three files.

**What makes it a backup rather than a feeling**, and this is the half that keeps getting skipped: `gpg --symmetric` before upload, so the storage provider holds ciphertext; the passphrase kept where you would still have it if the server were gone; **and one documented restore into an empty database before the first real venue exists, repeated quarterly.** Art. 32(1)(d) requires the restore to be *tested* — "we have backups" without a drill does not satisfy the article, and more practically, the 25.08 migration proved the dump/restore path once, by hand, with someone watching. That is evidence that it can work, not evidence that it does.

**And keep a third copy on the home server.** Not as the primary — you are right that it should not be — but restic is already running there and pulling a copy from object storage costs nothing. Three copies, two media, one off-site, which is the rule the home server was already implementing for everything else.

### 4.8 "Why not drop the coordinate requirement and resolve it from the address via the government API?"

**That is the right design, and it is better than what §6.1 proposed.** Three separate things have to be true for it to work, and I tested all three today rather than reasoning about them.

**One: dropping the requirement costs nothing.** `venues.latitude` and `venues.longitude` are `decimal(9,6) nullable` and have been since the table was created. The `required` rule lives only in `VenueImporter`, so removing it is two lines and needs no migration. There is a check constraint on the range, which nulls do not violate.

**Two: the government API is the right source — and the one the code calls is not answering.** This is the part worth knowing before you plan around it.

| Endpoint the code calls | Result, live, 12.09 |
|---|---|
| `geo.stat.gov.pl/api/fts/gc/pkt` — forward, GUS | HTTP 200, and `relevance: 0.0, src: null` for **every** payload I tried: street alone; street + number; `"Warszawa, Górczewska 124"` in one field; with an `ul.` prefix; with full `woj/pow/gm/miejsc` fields; and with `useExtServiceIfNotFound` both ways. `GusGeocodingService` discards anything under 0.6 relevance, so the panel button reports failure every time |
| `geo.stat.gov.pl/api/fts/ref/qq` — reverse, GUS | HTTP **500, "Read timed out"** from their own backend, twice, thirty seconds apart. A query without a bounding box returned `total: 0` |

**And the repository has the answer to the obvious objection, which I had not read when I wrote this.** `docs/reference/gus-api/` holds the whole API documentation, converted from the source, with a per-endpoint breakdown and a `CLAUDE.md` whose rule is *"do not guess field names"*. Two things come out of it:

- **Their own documented example fails the same way.** The doc's example request for `gc/pkt` is `{"miejsc_nazwa":"dabrowa gornicza","ul_pelna":"orzeszkowej","pkt_numer":"15"}`. Sent verbatim, it returns `relevance: 0.0, src: null`. The documented `ref/qq` example returns HTTP 500. With `useExtServiceIfNotFound: true` the response comes back `"extTimeMs": 25000, "xmessage": "timeout"` — their external fallback times out too. Meanwhile `ref/ac` answers a malformed call with a proper HTTP 400 naming the missing parameter, so **the service is up and validating; its index is not answering.** That is a provider-side failure, not a payload we got wrong.
- **But our request is also missing a field their example includes.** `GusGeocodingService::geocodeBatch()` sends only `ul_pelna` and `pkt_numer` — never `miejsc_nazwa`, even though the venue's city is available and the same method loads `$venue->city` a few lines later for the radius check. The documentation is explicit that structured input improves accuracy (*"Dane ustrukturalizowane zapewnią lepszą trafność usługi"*). So **even after their service recovers, we would be asking for a street name with no town attached, nationwide.** That is a real defect and it is ours.

Neither of those makes GUS the mechanism to bet the launch import on, and **nothing in the test suite would ever have told us about either**, because all nine geocoding tests use `Http::fake()`. Same shape as the three features 09.09 found had never worked.

**One licence detail from the same folder, which matters if GUS is ever repaired:** the API's stated terms are *"Licencja: Komercyjna… wykorzystanie… w celach komercyjnych lub niekomercyjnych dozwolone jest bezpłatnie, pod warunkiem podania źródła"* — free for commercial use **provided the source is cited.** That is an attribution obligation, and `map-attribution-lives-in-the-style` is where attribution already lives.

**The service that does work is GUGiK's** — Główny Urząd Geodezji i Kartografii, the state mapping authority, which is the actual address registry rather than the statistical office's portal:

```
GET https://services.gugik.gov.pl/uug/?request=GetAddress&address=Warszawa, Górczewska 124&srid=4326
```

Four real addresses, no key, no auth, response in **6 ms**:

| Query | Returned | Accuracy |
|---|---|---|
| Warszawa, Górczewska 124 | `ulica Górczewska 124`, 52.241309 / 20.930867, code 01-460 | 0.8 |
| Warszawa, Nowy Świat 22 | `ulica Nowy Świat 22`, 52.232742 / 21.019998, code 00-373 | 0.79 |
| Warszawa, Marszałkowska 1 | `ulica Marszałkowska 1`, 52.214327 / 21.020953, code 00-624 | 0.79 |
| Kraków, Floriańska 3 | `Floriańska 3`, 50.062210 / 19.939447, code 31-019 | **1.0** |

It also returns TERYT, SIMC and ULIC codes, the postcode, and — importantly — **ranked alternatives with their own scores**, so a wrong street is visible rather than silent: the Kraków query returned Floriańska at 1.0 followed by Ariańska, Słowiańska and Loretańska at 0.52–0.65. A threshold rule like *"accept the top result only at accuracy ≥ 0.8 and when the city matches"* is the same shape as the `MIN_RELEVANCE = 0.6` already in the GUS service. Reverse geocoding works too: a point on Nowy Świat came back as `ulica Nowy Świat 50`, 12.7 m away.

**Lineage, which is the real prize here.** GUGiK data is the state address register, published as open data — **not ODbL**. So a coordinate derived this way carries no licence question at all. `osm-dropped` does permit Nominatim ("service calls are not produced works"), and Nominatim works — I checked, it answers and it returns `suburb: "Wola"` for Górczewska 124 — but its response carries *"Data © OpenStreetMap contributors, ODbL 1.0"* in every payload, and the point of your question was to stop having that conversation. A government source ends it.

One caveat on Nominatim that argues the same way: the Górczewska 124 lookup matched **Auchan the supermarket**, a shop POI, because structured search with `limit=1` takes the top hit whatever its type. It landed on the right building here, but the mechanism is "first result wins", where GUGiK returns the address point itself.

**Three: where the call belongs — after the import, not inside it.** Three options, and the middle one is wrong:

1. **Bulk action after import** — already exists, `VenuesTable` has "Geokodowanie (GUS)" and "(Nominatim)" for selected rows, and `GeocodeVenueAction::executeBatch()` is already written against the `Geocoder` interface. Select all, one click. **Zero new code beyond a working provider.**
2. **Inside the import job** — Filament's importer has an `afterSave()` hook, so it is possible. It is still wrong: it couples a queued import to an external service's availability, so an API hiccup becomes failed rows in the middle of a batch, and it turns one batched call into seventy separate ones.
3. **A scheduled `uni:geocode-missing` command** — chunks every venue with no coordinates and geocodes it. Thirty lines, and it is the safety net that stops a venue sitting uncoordinated because somebody forgot to click. Worth having, after the bulk action proves the provider.

**Built 12.09, and it was one class and two lines**, because everything already routed through the `Geocoder` contract. `GugikGeocodingService` is wired first in the provider list on both the single venue page and the bulk actions; the importer's `required` rules are gone; 21 tests use payloads captured from the real service, and `GeocodingLiveTest` calls it for real in the `live` group. **The acceptance rule is stricter than the API's own score**, because the score alone cannot be trusted: a match is taken only when the city matched exactly, the returned street name contains the requested one (type prefix stripped, diacritics normalised), the house number is the one asked for, and the point is within 60 km of the city centre. The whole thing is recorded in `decisions/product/geocoding-comes-from-the-state-register.md`.

**Two things the government services do *not* give you, so they do not come as a surprise mid-import:**

- **The Warsaw district.** `citypart` came back `null` for every Warsaw address, and GUS's equivalent field is `gm_nazwa`, the gmina — which for Warsaw is "Warszawa", not "Mokotów". `GeocodeVenueAction` matches `district_name` against the `districts` table by name, so **`district_id` would stay empty.** That matters more than it sounds: district pages, `/{city}/{district}/{category}` and `thin-district-pages-are-noindexed` all hang off it. Nominatim's `suburb` does return "Wola", so the practical answer is GUGiK for the coordinate and either Nominatim or one pass of hand-assignment for the district — a dropdown per venue while you are attaching drinks anyway.
- **A pin you can trust without looking.** 0.8 accuracy is a good match, not a verified one. Sixty-odd pins should be eyeballed on `/mapa` once, which is twenty minutes and catches exactly the failure a directory cannot afford. *(13.09: the per-venue preview on the admin edit page, which is the other place to check a pin, had never rendered until 12.09 — §1c.4.)*

**And the address itself is still the input**, which is why P22 does not go away: if the street and number came out of the OSM export, then geocoding them stores a coordinate derived from an OSM attribute, and the address is stored too. Re-deriving the address from the venue's own website is part of the enrichment pass you are doing anyway — you need the website, the phone and a menu confirmation from that same page. The CSV's address column stays useful as the hint that helps you find the place. That costs nothing extra; it just has to happen in that order.
