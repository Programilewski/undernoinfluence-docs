# Audit — the 27.08 phone note and the infrastructure log vs. running code

Two things arrived together in [`../Phone notes/27.08.md`](../Phone%20notes/27.08.md): a request to
map every feature to a version and define the minimal V1, and an eight-record infrastructure
decision log (`INFRA-01` … `INFRA-08`) written by another LLM. Both were checked against running
code, the database, the `.env`, and the vendors' own pages — not against other documents.

**No code, database or config was changed in the session that produced this.**

Condensed founder-facing version: [`../journals/2026-08-27.md`](../journals/2026-08-27.md).

> **Read this as a dated snapshot.** Per `docs/README.md`, a planning document older than two weeks
> is a hypothesis. Every line below was true on 2026-08-27 — re-check before acting on it.

---

## The two findings nobody wrote down

### 1. Every map in the application is currently watermarked

CARTO now requires an API key on `basemaps.cartocdn.com` and stamps keyless requests. All three
styles the app uses were fetched and rendered during this session:

| Surface | File | Style | Result |
|---|---|---|---|
| Discovery `/mapa` | `resources/js/map-config.js:18` | `dark_all` | 200 OK, **"API KEY REQUIRED"** across every tile |
| Venue profile | `map-config.js:32` | `rastertiles/voyager` | same |
| Homepage showcase | `map-config.js:45` | `dark_nolabels` | same |

This is not a licensing hypothesis for later. It is the current appearance of the homepage hero,
the discovery map and every venue page, on a product whose entire pitch is being the trustworthy
source of venue data. It is invisible today only because nothing is public and access is over the
tailnet.

Settled the same day: [`../decisions/product/vector-basemap-on-openfreemap`](../decisions/product/vector-basemap-on-openfreemap.md).

### 2. The privacy policy does not name CARTO, although a decision record says it does

[`carto-named-as-recipient.md`](../decisions/product/carto-named-as-recipient.md) is dated
2026-08-24 and marked **Decided**: *"CARTO is named in the privacy policy as a recipient of visitor
IP addresses."* Section 6 of `resources/views/privacy-policy.blade.php` (**Odbiorcy danych**) names
**PostHog** and **Scaleway SAS**, and nothing else. There is no occurrence of the string "CARTO"
anywhere in that file. Bunny Fonts — five families loaded on every page from
`layouts/app.blade.php:20` — is not named either.

This is the same class of fault as the six corrected on 26.08: **a document that describes code
that was never written.** It matters twice over, because the map decision above says the CARTO
entry "changes rather than disappears" when the tile vendor changes — and there is no entry to
change.

## Part 1 — the feature mapping the note asked for

**The exercise as framed has almost no leverage, and the answer already exists.** `v1.md`, `v2.md`
and `v3.md` are that mapping. `next-session.md` states the finding that makes redoing it moot:
there are no code tasks left blocking V1. The suite was re-run during this session: **465 tests
passing**, every V1 feature marked `DONE`.

Minimising V1 normally means building less. Here everything is already built, so cutting features
**costs** time — removal, test churn, doc drift — instead of saving it. What the mapping was
missing is not a version column but an **exposure** column: which finished features are visible at
launch, and which stay dark. That tier has been added to [`v1.md`](v1.md).

Two real levers were found, and neither is a feature:

1. **SMTP moves off the critical path.** Mail exists to notify owners when a claim is approved.
   With the owner panel unlinked at launch there are no claims to approve on day one, so Scaleway
   TEM becomes "before the first owner is onboarded" rather than "before the site is public".
2. **50–60 venues is a self-imposed number.** 25–30 venues concentrated in three central districts
   ranks the district pages as well as 60 spread across eighteen, and halves the longest task on
   the critical path. Density beats coverage for a local SEO cluster.

### INFRA-01 — environments

The note argues a staging environment's value is proportional to what a bad deploy costs, and at
zero users that is one evening. That rebuts the *uptime* rationale only.
[`../tech/going-to-production.md`](../tech/going-to-production.md) argues something different:
preprod is where SELinux, `config:cache`, proxy headers, the supervisor user and HSTS fail for the
first time, cheaply.

**Synthesis: one server, two phases.** Provision production, run the whole "what preprod must
prove" table on it with no DNS and no HSTS, then cut DNS over. Zero extra cost, both arguments
satisfied. HSTS stays off until certificate renewal has been proven once — it hard-blocks the site
for a year if the certificate later lapses.

### INFRA-02 — Ploi Pro

Verified against Ploi's pricing page: Free / Basic €8 / Pro €13 / Unlimited €30; automatic database
and file backups, server monitoring and zero-downtime deployment all begin at **Pro**. The note's
correction of its own earlier error is accurate. Ploi is Dutch, "hosted in Europe", month-to-month
— consistent with the EU-residency and pay-as-you-go constraints in `../tech/stack.md`.

Two omissions. Ploi holds root on a machine containing owner personal data, so it is a **ROPA entry
with a processing agreement**, exactly like Hetzner. And choosing Ploi implies an **Ubuntu**
production host against a Fedora workstation, which silently answers open question 2 in
`going-to-production.md` — the OS and the package supplier per component must be recorded before
the machine is built, per [`one-vendor-per-system-library`](../decisions/product/one-vendor-per-system-library.md).

### INFRA-03 — backups

Conflicts twice. [`dependencies.md`](../tech/dependencies.md) already selected
`spatie/laravel-backup` targeting Backblaze B2 and marked it a **V1 launch blocker**. And "production
pushes a dump to the home server" inverts
[`pull-never-push-when-migrating`](../decisions/product/pull-never-push-when-migrating.md), whose
rule ends: *"a host clones from git and restores from a dump; a working directory is never pushed
into a live tree."*

It also under-prices GDPR. Production dumps carry owner names, e-mail addresses and claim history.
A home machine plus an offline USB copy adds storage locations to the ROPA and the data map, and
forces a written position on erasure requests versus backup retention.

**Recommendation:** keep `spatie/laravel-backup`; move the target from Backblaze (a US company) to
**Scaleway Object Storage in Paris** — the same vendor as the already-decided transactional e-mail
provider, one processing agreement, EU-resident, pay-as-you-go. That also removes the transfer
inconsistency that [`transactional-email-provider`](../decisions/product/transactional-email-provider.md)
explicitly rejected for e-mail. Keep the home copy as a second layer, with the home server *pulling*
from object storage. The note's demand for a **rehearsed restore** is its best paragraph and stands
unchanged.

### INFRA-04 and INFRA-05 — tiles and the map library

The conclusion is right; the stated reason is not. The note says CARTO's free tier is
non-commercial. CARTO's FAQ says free up to **5 million tile requests per calendar month**, that
you need not declare commercial use in advance, and that above the limit a commercial project *may*
be asked onto an agreement. The real facts are the watermark above and CARTO's own statement that
the raster basemaps are being retired.

Verified alternatives, all checked on 27.08:

| Provider | Free tier | Commercial on free | Paid entry |
|---|---|---|---|
| CARTO (with key) | 5M tiles/mo | Tolerated; page says "intended for non-commercial" | Negotiated, unpublished |
| OpenFreeMap | No key, no stated limits | **Yes, explicitly** | — (donation-funded) |
| Geoapify | 3,000 credits/day; a tile = 0.25 credit | Yes, with "Powered by Geoapify" | $59/mo |
| Stadia Maps | 200k credits | **No** | $20/mo Starter |
| MapTiler Cloud | 5k sessions | **No**, plus forced logo | $30/mo Flex |
| Thunderforest | 150k tiles/mo | Not stated | $125/mo |
| Protomaps PMTiles | Self-hosted, one file | Yours | — |

The structural finding: **there is no durable free raster option left.** Raster hosting is now a
paid product; free-plus-commercial-plus-sustainable exists only on the vector side, and vector
means MapLibre. That is a stronger argument for the migration than the note's aesthetic one.

On scope, the note calls the map "a core UI component at its smallest". The real surface is
`map-config.js` (71), `discovery.js` (588), `venue-map.js` (160), `demo-map.js` (195),
`bootstrap.js` (15), the admin mini-map Blade view that loads Leaflet from unpkg (77), and the
pin, cluster and tooltip rules in `app.css`. Three public map surfaces on three CARTO styles. It
also missed that **`leaflet.markercluster` has no MapLibre equivalent** — clustering there means
wiring supercluster by hand, or dropping it. Two to four days, not an afternoon.

Settled in [`vector-basemap-on-openfreemap`](../decisions/product/vector-basemap-on-openfreemap.md),
including the decision not to take a CARTO key as a stopgap: nobody sees the broken map, so an
hour of work that gets deleted within days buys nothing.

### INFRA-06 — geocoding

Already built. `app/Services/NominatimGeocodingService.php` enforces the 1-req/sec policy
(`SLEEP_BETWEEN_US = 1_100_000`) with an identifying User-Agent, alongside
`GusGeocodingService` hitting `geo.stat.gov.pl` — batch, official Polish registry, no rate ceiling.
Both are wired into the admin panel as row and bulk actions
(`VenuesTable.php:135–222`, `EditVenue.php:92–98`). For 2,378 CSV rows, GUS is the one that scales;
Nominatim is the fallback. [`osm-dropped`](../decisions/product/osm-dropped.md) already permits
both. **No action.**

### INFRA-07 — import command

Half-redundant: geocoding already happens through admin actions, not at import time. The real
question is open question 6 in `going-to-production.md` — what happens to `uni_filtered_venues.csv`
(2,378 rows, `osm_id` columns, sitting at the repository root against two standing decisions). The
command is the trivial part. The note's "retire it, do not evolve it into a sync" rule is right and
worth keeping.

### INFRA-08 — PostGIS

**Factually wrong for this application.** There is no PostGIS: no `CREATE EXTENSION`, no geometry
or geography column anywhere in `database/`, `app/` or `config/`. Proximity is
`Venue::HAVERSINE_SQL` — raw trigonometry over `decimal:7` latitude and longitude — plus
`GusGeocodingService::haversineKm()` in PHP. The record invents an install step and, worse, would
have constrained the hosting choice toward superuser database access that nothing needs.

### Cost summary

The total (~€20/month) survives; the vendor list does not. **Resend appears twice**, contradicting
[`transactional-email-provider`](../decisions/product/transactional-email-provider.md), which chose
Scaleway TEM on compliance grounds rather than preference. The "Resend Pro for cold outreach" line
breaks a second rule in that same record: outreach must never share the transactional provider or
domain. Missing from the table: object storage for backups, and Scaleway TEM itself (300 e-mails a
month free, then €0.25 per 1,000 — effectively zero at launch). Separately, Polish electronic
communications law should be checked before any cold B2B e-mail; that is a legal question, not a
budget line.

## What the note missed entirely

1. **The watermark** (finding 1 above).
2. **The privacy-policy gap** (finding 2 above).
3. **A dated conflict with its own strategy.** The note's plan is to launch and gather events.
   `analytics:prune-events` hard-deletes raw events past 90 days; search demand lives only in
   `events`; search demand is the Tier-3 metric the B2B thesis rests on. The scheduler has never
   run, so nothing is lost yet — the first destructive run lands on or after **2026-09-15**. The
   rollup must precede the cron entry. This is the sharpest link between the two halves of the
   phone note, and the log does not mention it.
4. **PostHog identity** — one anonymous visitor currently carries three identifiers. If launching
   is how data gets gathered, that is a before-traffic fix; the history cannot be reconstructed.
5. **`supervisor/uni-worker.conf` says `user=www-data`** (T-26b). If production is Ubuntu under
   Ploi it happens to be correct, which makes it a landmine rather than a bug.
6. **The `phpunit.xml` password in git history** (T-25a) must be settled before production secrets
   exist.
7. **The privacy policy names two recipients of at least five.** Hetzner, Ploi, the tile vendor and
   Bunny Fonts all need entries before the site is public.

## Where the note is simply right

Its closing section. The tractable risks produced eight records; the untractable ones — will Warsaw
owners pay for NoLo demand data, can venue density be reached fast enough for the SEO cluster to
rank, do Polish consumers search for this yet — got one paragraph, and no amount of research
resolves them. `v1.md` already carries this as BV-1 and BV-2. The addition worth making: **those
are the same phone calls as venue enrichment.** One call, two outcomes — which is what makes 40–60
hours affordable rather than a second project.
