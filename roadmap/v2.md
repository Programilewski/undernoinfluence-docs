# V2 — Engagement & Trust Loop

**Theme:** Turn passive browsing into active participation. Users confirm data, owners see engagement, the platform gets smarter.
**Target:** Start when V1 traffic justifies it.
**Entry trigger:** 20+ daily `venue_directions_clicked` events AND 10+ claimed venues.
**Why these triggers:** Post-visit confirmation needs enough directions clicks to generate statistically useful responses. Engagement features need enough owners to create a visible feedback loop.

---

## Features

### V2-F1: Post-Visit Confirmation

**What:** 30 minutes after a user clicks "Directions" to a venue, send a notification: "Did you make it to [Venue]? Was the NA selection as listed?"

**Why it matters:**
- **Data freshness validation** — "11/12 users confirmed the menu was accurate" is a stronger trust signal than raw check-in counts
- **Visit confirmation** — proves users actually go to venues they find on UNI (critical B2B metric)
- **Owner dashboard value** — "12 users reported visiting, 11 confirmed the menu was accurate" is a compelling stat

**Dependencies:**
- User accounts (V1 priming PR-2)
- Queue infrastructure with delayed dispatch (V1 priming PR-4)
- `venue_visits` table (V1 priming PR-3)
- PostHog directions events with user_id (V1 priming PR-1)
- Push notification or email delivery channel

**Implementation outline:**
1. When authenticated user clicks "Directions", dispatch `SendVisitConfirmation` job with 30-minute delay
2. Job sends push notification (if PWA) or email
3. User responds via 2-tap micro-survey: "Did you visit?" (yes/no) → "Was the menu accurate?" (accurate/inaccurate/partially)
4. Response writes to `venue_visits` table
5. Aggregate responses surface in owner dashboard and on public venue page as trust signal

**Micro-survey UI:**
- Maximum 2 taps to complete
- First tap: "Tak, bylem/am" / "Nie, nie dotarlem/am"
- Second tap (only if visited): "Menu zgodne z opisem" / "Czesciowo zgodne" / "Niezgodne" + optional free-text note
- Must work from email (no app install required for MVP)

**Metrics to track:**
- Response rate (% of directions clicks that get a response)
- Menu accuracy rate (% confirming accurate)
- Time-to-response (do people respond immediately or later?)
- Per-venue accuracy trend (declining accuracy = stale data signal)

**Estimated scope:** 2-3 days (backend + notification + micro-survey UI)

### V2-F2: User Saves & Collections

**What:** Authenticated users can save venues to personal collections ("Favorites", custom lists like "Na weekend", "Date night spots").

**Why it matters:**
- Retention mechanism — saved venues give users a reason to return
- Signal data — "most saved venues" is a ranking input and B2B metric
- Engagement depth — users who save are 3-5x more likely to click directions

**Dependencies:**
- User accounts (V1 priming PR-2)

**Schema:**
```
collections
- id (bigint PK)
- user_id (bigint FK -> users)
- name (varchar) — "Ulubione" default, custom allowed
- is_default (boolean) — one default per user
- created_at / updated_at

collection_venue (pivot)
- collection_id (bigint FK -> collections)
- venue_id (bigint FK -> venues)
- created_at
```

**Implementation outline:**
1. Heart/bookmark icon on venue cards and venue page
2. Quick-save to default collection (one tap)
3. "Save to..." dropdown for custom collections
4. "My saves" page accessible from user profile
5. PostHog event: `venue_saved` with collection_id

**Estimated scope:** 1-2 days

### V2-F3: Owner Analytics Dashboard

**What:** Expand the owner panel dashboard beyond the current status widget. Show real engagement data.

**Why it matters:**
- B2B retention — owners who see value keep their data fresh
- Upsell foundation — "you're getting X views, upgrade to get Y" (V3)
- Data flywheel — owners who see engagement are motivated to improve their listing

**Dashboard metrics:**
- Profile views (this week / this month / trend)
- Directions clicks (this week / trend)
- Saves count (how many users saved this venue)
- Menu accuracy rating (from V2-F1 confirmation data)
- Freshness status with "days until badge drops" countdown
- Competitive context: "Your venue ranks #X of Y in [district] for NA selection breadth"

**Dependencies:**
- PostHog events flowing reliably (V1)
- Post-visit confirmation data (V2-F1, optional but enriches dashboard)
- User saves data (V2-F2, optional)

**Implementation outline:**
1. Aggregate PostHog events server-side (scheduled job pulls daily stats into a `venue_stats` table)
2. Build Filament dashboard widgets showing key metrics
3. "Competitive context" queries the `breadth_score` ranking within the venue's district

**Schema (priming — consider creating in V1):**
```
venue_daily_stats
- id (bigint PK)
- venue_id (bigint FK -> venues)
- date (date)
- profile_views (integer, default 0)
- directions_clicks (integer, default 0)
- saves (integer, default 0)
- visit_confirmations (integer, default 0)
- menu_accuracy_positive (integer, default 0)
- created_at / updated_at

Index: (venue_id, date) unique
```

**Estimated scope:** 3-5 days

### V2-F4: Community Data Reporting

**What:** Authenticated users can report changes to a venue's offering: "This product isn't available anymore", "They added a new NA beer", "This venue is closed."

**Why it matters:**
- Scales data freshness beyond owner self-reporting
- Users become invested in data quality (ownership effect)
- Provides a signal for stale data even when owners are disengaged

**Dependencies:**
- User accounts (V1 priming PR-2)
- Post-launch data showing which venues go stale fastest (informs priority)

**Implementation outline:**
1. "Report a change" button on venue page (authenticated only)
2. Structured report types: product unavailable, product missing from list, venue closed/moved, hours wrong, other
3. Reports go into admin moderation queue
4. Trusted user tier (based on report accuracy history): reports from trusted users auto-apply, others require admin review
5. PostHog event: `venue_report_submitted`

**Design constraint:** Do NOT pre-design the trust scoring system. Build a simple moderation queue first. Add trust tiers only after you have 50+ reports and can see abuse patterns.

**Estimated scope:** 2-3 days

---

### V2-F5: Tiered Badges (if data supports it)

**What:** Graduate from binary "Zweryfikowany" to a tiered system (e.g., Silver/Gold) based on engagement quality.

**Why it matters:**
- Differentiation — owners who invest more get more recognition
- Incentive gradient — binary badge has a ceiling; tiers keep owners engaged
- Trust signal — users can distinguish "claimed and occasionally updated" from "actively maintained"

**Dependencies:**
- Enough claimed venues (30+) to calibrate thresholds
- Owner engagement data showing differentiation between active and passive owners
- Post-visit confirmation data (V2-F1) to validate tier definitions

**Revisit trigger from V1:** "Post-launch data shows owners want differentiation from competitors" (D-01)

**Possible tier criteria:**
- Silver: claimed + offer updated within 90 days
- Gold: Silver + 5+ confirmed visits + 80%+ menu accuracy rate + responds to reports within 7 days

**Design constraint:** Do NOT define thresholds until you have 3+ months of owner behavior data. The thresholds should be data-driven, not aspirational.

**Estimated scope:** 1-2 days (once criteria are defined)

### V2-F6: Opening Hours (Owner Self-Managed)

**What:** Let claimed venue owners enter and manage their opening hours through the panel.

**Why it matters:**
- Revisit trigger from V1 D-05: "Claimed owners want to self-manage hours through the panel"
- Reduces friction for users who want to visit — no need to leave UNI to check Google Maps
- Another engagement touchpoint for owners

**Dependencies:**
- 10+ claimed venues actively managing their profiles
- Owner feedback requesting this feature specifically

**V1 already has:** `opening_hours` JSONB column on venues (exists but not exposed). The schema is ready — this is purely a UI/UX task.

**Implementation outline:**
1. Add opening hours form to owner panel (Filament repeater by day of week)
2. Display on public venue page (collapsible, show today's hours prominently)
3. "Closed now" / "Open now" indicator on venue cards (optional, adds complexity)
4. Freshness check: if hours haven't been confirmed in 6 months, hide them and show "Check with venue"

**Estimated scope:** 1-2 days

---

### V2-F7: Venue Images (Moderated)

**What:** Allow claimed venue owners to upload a profile photo and interior shots.

**Why it matters:**
- Revisit trigger from V1 D-03: "Owner feedback post-claim shows strong demand"
- Visual content improves engagement and conversion
- Makes social sharing more compelling (og:image)

**Dependencies:**
- S3/R2 storage configured
- Image moderation strategy (manual review queue or AI-based)
- 15+ claimed venues (enough to justify the infrastructure)

**V1 already has:** `image_path` column on venues (exists but not used). Storage column is ready.

**Implementation outline:**
1. Single hero image upload in owner panel (max 2MB, auto-resize to 1200x630)
2. Admin moderation queue — images pending until approved
3. Display on venue page and venue card
4. Use approved image as og:image for social sharing
5. Consider: AI moderation via Claude Vision API to auto-flag inappropriate content

**Estimated scope:** 2-3 days

## V2 Priming Work for V3

### PR-V3-1: Multi-City Data Architecture

**V3 feature it enables:** City expansion (V3-F1)

**What to do in V2:**
- Ensure all queries are city-scoped (no `Venue::all()` without city filter)
- Make the city selector prominent in the UI (not hidden)
- Test with a second city in staging (Gdansk or Krakow) even if not launched
- Ensure `districts` table handles multiple cities cleanly (already has `city_id` FK)

### PR-V3-2: Analytics Export Format

**V3 feature it enables:** B2B premium reports (V3-F3)

**What to do in V2:**
- Standardize the `venue_daily_stats` aggregation so it can be exported as CSV/PDF
- Build the aggregation pipeline to be city-aware from day one
- Track which metrics owners look at most (informs what to put in paid reports)

## Non-Goals for V2

- B2B monetization (premium listings, paid analytics) — V3
- Public API — V3
- Multi-city launch (build for it, don't launch it) — V3
- Mobile native app — evaluate at V3 based on PWA engagement data
- AI-powered recommendations ("venues like this") — V3
- Drink price tracking — complexity for unclear value
