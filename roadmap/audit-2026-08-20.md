## 1. Backend built but not publicly exposed

### The one that is actually broken: inaccuracy reports

`resources/views/how-it-works.blade.php:268` tells users, in the public FAQ:

> *"Jeśli coś się nie zgadza, kliknij przycisk **Zgłoś nieaktualne dane** na stronie lokalu."*

**That button does not exist.** Not on `venues/show.blade.php`, not anywhere in `resources/views/`.

The backend is finished: `venue_inaccuracy_reports` with a four-state workflow
(`pending` / `reviewed` / `resolved` / `dismissed`), the `VenueInaccuracyReport` model, and a
complete Filament admin resource with form, table and pages. Nothing in the codebase ever calls
`VenueInaccuracyReport::create()`. Zero rows.

Public copy promises a feedback channel, the admin has a queue to work it, and there is no wire
between them. It is also load-bearing: that FAQ answer sits directly under *"the venue has a
Sprawdzona karta badge and the drink wasn't there — is this data reliable?"*, so the moment a
user loses confidence in the badge, we send them to a channel that was never built. The badge is
the product's primary quality signal.

**Blocker before building:** `venue_inaccuracy_reports.user_id` is `NOT NULL`. With no public
accounts in V1, the form needs either a nullable column or a session/fingerprint identity — the
latter drags in a data-map entry. Same GDPR calculus that rejected the leads table in O-3.

### The structured claim form from note 7 — already written

`app/Http/Requests/StoreVenueClaimRequest.php` is a complete, unreferenced FormRequest. Nothing
routes to it. It validates exactly the shape the note describes:

`claim_type` (existing\|new) · `contact_name` · `contact_email` · `contact_phone` ·
`business_nip` (via `App\Rules\ValidNip`) · `claimant_role` · `verification_method` ·
`proof_url` · plus `submitted_venue_name` / `submitted_city_id` / `submitted_street_name` /
`submitted_street_number` / `submitted_website_url` for claiming a venue not yet on the map.

It also blocks duplicate pending claims and already-claimed venues in `withValidator()`. The
columns behind all of it exist on `venue_claims`. The `claim_type='new'` path — an owner
submitting a venue UNI has never seen — is fully built at the data and validation layer and
reachable from nowhere.

### A live contradiction in the claim path

`decisions/product/admin-recorded-claims-v1.md` states: *"Every claim carries a NIP and a
claimant role, because those are what the admin verified."* Two paths exist; one obeys it:

| Path | NIP | `claimant_role` | Contact fields |
|---|---|---|---|
| Admin — `VenueClaimForm` | required, `ValidNip` | yes | yes |
| Owner panel — `Filament/Owner/Pages/ClaimVenue.php` | **none** | **none** | none |

`ClaimVenue.php:133-146` creates a claim with only `venue_id`, `verification_method` and
`message`. Worse: `VenueClaimForm` disables `business_nip` when `$record !== null`, so **a claim
submitted through the panel can never have a NIP filled in by the admin afterwards.** It is
permanently a claim the decision record says cannot exist.

Not theoretical: any admin-created account with `role=user` reaches that form and can claim any
venue in `Venue::claimable()`.

## 2. Removing light mode

The reasoning holds, and the code makes it cheaper than the usual theme removal. The public site
is almost entirely token-driven: `app.css` defines the palette on `:root` and flips it under
`.dark`. Across all public Blade templates there are exactly **four** hardcoded `dark:`
utilities — one in `nav.blade.php`, three in `cookie-consent.blade.php`. The other 148 live in
Filament panel views.

What removal touches:

1. `resources/css/app.css` — fold the `.dark` values into `:root`, delete `.dark` and the `@custom-variant dark` line.
2. `resources/views/layouts/app.blade.php:14-37` — delete the pre-paint FOUC script and the `matchMedia` listener. Nothing replaces it: if `:root` is dark there is no flash to prevent.
3. `resources/views/partials/nav.blade.php` — the three-icon toggle button (~20 lines) and its handler (~45 lines), including the `uni:theme-changed` dispatch.
4. `resources/js/map-config.js` — `TILES.light`, `DEMO_TILES.light`, `tileConfig(dark)`, `isDarkMode()`. Collapse `applyTiles()` to one layer.
5. `resources/js/discovery.js:49` and `:144`, `resources/js/demo-map.js:73` — the `uni:theme-changed` listener and `swapTiles`.
6. The four stray `dark:` utilities.

**It removes a third party.** Light mode is the only consumer of
`https://{s}.tile.openstreetmap.org` (`map-config.js:24`); dark uses CARTO. Deleting light mode
drops one recipient of visitor IPs — a small free win on the privacy-policy recipient list that
`next-session.md` §6 already flags as incomplete.

**Filament is a separate decision.** The panels run Filament's own dark mode, not these tokens,
and hold 148 of the 152 `dark:` classes. The two arguments split there: brand identity does not
apply to an internal tool nobody outside sees; maintenance cost does. Recommendation: leave the
panels alone. `viteTheme` is already pinned per panel, and the panel views are where a theme
rewrite would actually cost hours.

*Skipped: any migration for users holding `uni-theme` in localStorage. It becomes an ignored key;
nothing reads it. Not worth a cleanup script.*

## 3. Event naming

Outbound events are built by string concatenation in `VenueRedirectController.php:29`:

```php
'event' => 'venue_'.$type.'_clicked',
```

against a hardcoded `OUTBOUND_EVENTS` map in `VenueAnalytics.php:15-31`. Adding TikTok means: a
new key in that map, a new `resolveUrl()` arm, a new entry in the route's `in_array` allowlist, a
new event name in the docs table, and a new column (see §4).

The proposal — `venue_socials_clicked` with `type: instagram` — is right, and the data layer
already supports it for free. `EventLogger` writes `properties` as JSONB, and the redirect
controller **already** passes `redirect_type` in properties. The event name is the only redundant
part; the parameter is already there.

**The correction:** do not collapse all four into one event. `directions` and `maps` are not
socials — they are navigation intent, the single most valuable B2B signal ("someone was on their
way to your bar"). Merging them into a socials bucket makes the one number an owner will pay for
harder to read. Three events:

| Event | `type` values | Business question |
|---|---|---|
| `venue_navigation_clicked` | `directions`, `maps` | Did the listing send someone to the door? |
| `venue_socials_clicked` | `instagram`, `facebook`, `tiktok`, … | Did they go look the venue up? |
| `venue_website_clicked` | — | Own axis; keep separate |

**The caveat:** PostHog charges and filters per event name. Fewer names is cheaper and tidier,
but every PostHog insight then needs a property breakdown rather than a bare event count, and
breakdowns are a step slower to build in their UI.
`decisions/product/posthog-analytics-role.md` resolves it: PostHog is additive, the first-party
stack is canonical for owner-facing data. Optimise naming for the first-party stack, accept the
extra click in PostHog.

### Two defects this surfaced

**Double-counting in PostHog.** `venue_website_clicked`, `venue_instagram_clicked` and
`venue_directions_clicked` fire **twice per click** — client-side via `window.__capture`
(`show.blade.php:149, 163, 196`) and server-side in `VenueAnalytics::outboundClicked()`, which
also calls `postHog->capture()`. Same for `venue_viewed` (`show.blade.php:454` plus
`VenueController`). The `events` table and `venue_stats` are clean; only PostHog inflates.
**Every PostHog outbound number looked at so far is 2×.** Fix before real traffic, alongside the
identity defect already logged for 14.08.

**Convention drift.** 36 event names, three coexisting shapes:

- `<object>_<verb>` — `venue_viewed`, `city_viewed`
- `<surface>_<verb>` — `discovery_searched`, `map_area_searched`
- `<object>_<verb>_by_<actor>` — `product_added_by_owner`, `venue_erased_by_owner`

If names are being standardised, the third form should go — actor moves into properties, same
argument as the socials type. One axis less in the name.

## 4. `venue_stats.instagram_clicks`

Confirmed hardcoded, and worse than the event name because it is schema:

```sql
instagram_clicks integer DEFAULT 0 NOT NULL,
CONSTRAINT venue_stats_non_negative_check CHECK (… AND (instagram_clicks >= 0) AND …)
```

Adding a platform costs a migration, a check-constraint rewrite, and edits to
`VenueStat::TRACKABLE_COLUMNS`, `$fillable`, `VenueAnalytics::OUTBOUND_EVENTS`, both analytics
widgets, both widget Blade views, and `VenueAnalyticsReportService::monthlyViews()` plus
`clickDetailReport()` — which has `SUM(direction_clicks + website_clicks + instagram_clicks)`
inlined in raw SQL. Nine places for one platform. Removing one is worse: the column cannot be
dropped without destroying history.

**The shape to move to** — long instead of wide:

```
venue_stats(venue_id, date, metric, count)   -- metric: 'view' | 'card_click' | 'click:instagram' | …
```

A new platform then costs zero DDL. `TRACKABLE_COLUMNS` becomes a validation list in PHP, or
nothing. It costs a `GROUP BY` / pivot in the four read sites, and the check constraint
(replaceable with `count >= 0` on one column).

**The honest part:** there are 30 rows in `venue_stats`, all from internal clicking, and zero
paying customers. The wide table's cost is a migration written once, when the data is worthless
and can be truncated without a thought. The narrow table's benefit lives entirely in a future
with Facebook and TikTok links and 24 months of history that cannot be lost.

**Recommendation: do it, but not now — do it in the same pass as the `shares` fix and the event
renaming, before the first real venue goes live.** All three touch the same six files. One
migration, one set of tests, one journal entry. Doing it after real traffic means backfilling a
real table; doing it in three passes means touching `VenueAnalyticsReportService` three times.

*Skipped: an events-derived aggregate that removes `venue_stats` entirely. Tempting, but §9
explains why the aggregate table is the thing that must be kept.*

## 5. SEO status codes

Verified by pushing real requests through the HTTP kernel against the live DB (25 cities, 24 of
them empty):

| URL | Status | robots |
|---|---|---|
| `/warszawa` (63 venues) | 200 | `index, follow, noai, noimageai` |
| `/krakow` (0 venues) | **200** | **`noindex, follow`** ✅ |
| `/krakow/piwo-bezalkoholowe` (0) | **200** | **`noindex, follow`** ✅ |
| `/warszawa/mokotow` | 200 | `index, follow, noai, noimageai` |
| `/kategoria/piwo-bezalkoholowe` | 200 | `index, follow, noai, noimageai` |
| `/nieznane-miasto` | 404 | — |

**Cities, city+category, district+category and category pages are correct** and match
`empty-landing-pages-noindex.md`. Sitemap generation independently filters on `active()`
(canary-excluding), so a noindexed URL is never submitted. That decision is implemented as
written.

**The district page is the exception, and it is the one that fires first on expansion.**
`CityController.php:60`:

```php
abort_if($venues->isEmpty(), 404);
```

`resources/views/city/district.blade.php:15` carries an unconditional
`<meta name="robots" content="index, follow, noai, noimageai" />` — no empty branch, because the
controller guarantees it never renders empty. `empty-landing-pages-noindex.md` calls this out as
*"a known inconsistency, left untouched because it is covered by tests."*

Two things that decision record does not say:

- **It is unreachable today.** All 18 districts are Warsaw's and all 18 have venues. The 404
  branch has never fired against production-shaped data. It fires the first time a district
  exists before its first venue — exactly the seeding order used in a new city.
- **`SeoLandingPageTest` has no test for a district that exists but is empty.** It covers
  unknown-district 404 (`:77`) and empty city+district+category 200+noindex (`:59`), not this
  branch. "Covered by tests" is protecting the *unknown*-district case. The four-line fix — drop
  the `abort_if`, add the `@if ($venues->isEmpty())` branch the other three views already
  have — breaks nothing.

**Separately:** `regulamin` and `polityka-prywatnosci` both carry a bare
`<meta name="robots" content="noindex" />`. Terms and privacy pages are trust signals search
engines expect to find. Probably not deliberate. Worth a look, not urgent.

## 6. The `is_verified` flow

No owner-driven mechanism exists — confirmed. Full current state, traced through the code.

### Three columns, two load-bearing

| Column | Written by | Read by |
|---|---|---|
| `is_verified` | Admin form toggle (`VenueForm.php:137`), importer, seeders | `Venue::has_verified_menu`, `scopeVerifiedMenu`, `StatsOverview`, `CityController`, PostHog properties |
| `last_menu_check_at` | Admin form, `mark_checked` row action, `bulk_mark_checked` | Same as above |
| `verified_at` | Admin form, seeders, factories | **Nothing.** Decorative. |

### The badge rule

`Venue::getHasVerifiedMenuAttribute()` (`Venue.php:298`) — the badge shows only when **both**
hold:

```
is_verified === true  AND  last_menu_check_at within uni.verification_valid_days (180)
```

`scopeVerifiedMenu()` mirrors it in SQL, which is why the discovery "verified" filter and the
badge agree. `is_claimed` feeds neither. Freshness (`offer_updated_at`, 90 days) feeds neither.
Three independent signals, as D-01 / D-14 corrected on 18.08.

### What owner actions currently do

Every owner path — attach product, detach product, add/edit/delete a custom drink, "Nadal w
ofercie" reconfirmation — routes through `Venue::markOfferFresh()` via `VenueProductObserver` /
`VenueDrinkObserver`. That sets `offer_updated_at` and `freshness_streak_started_at`. **It never
touches `is_verified` or `last_menu_check_at`.**

**And that is correct.** The public copy commits to it: *"zespół UNI przeszedł jego kartę napojów
pozycja po pozycji"* (`how-it-works.blade.php:98`). The badge asserts *UNI checked*, not *the
owner says so*. An owner action can never satisfy it without turning the badge into a
self-declaration — which is `no-pay-to-rank` and `credibility-formula-opacity` territory. The
absence is the system working.

### Two defects in the admin path

**"Oznacz jako sprawdzone" often does nothing.** `VenuesTable.php:118` and the bulk action at
`:126` set **only** `last_menu_check_at`. On a venue where `is_verified` is `false` — the
default, and what `RealVenueSeeder.php:88` sets — clicking produces no badge, no error and no
feedback. The admin has done the work and the UI reports success. The one-click action should set
both, or say why it cannot.

**`StatsOverview` uses the wrong constant.** `StatsOverview.php:29-30` computes "stale" as
`last_menu_check_at < now() - freshness_days` (90), but the badge lives to
`verification_valid_days` (180). The admin dashboard reports venues as needing a re-check roughly
three months before the badge actually expires — in the same widget that computes
`$expiredVerifications` correctly via `verifiedMenu()` one line above. Exactly the drift D-14's
18.08 correction was written to stop.

### On the automation proposal

> *"if the admin updated the offer within a month, the is_verified toggles automatically"*

Sound in principle, with one boundary drawn carefully: **an admin editing the venue is not the
same as an admin editing the offer.** Fixing a postcode is not a menu check. The rule should key
on the offer-mutation observers (`product_added` / `product_removed` / `drink_*`) **and** on the
actor being an admin — both facts are already recorded in `venue_offer_logs` (`user_id` +
`action`), so the audit trail to build it exists today.

The condition is roughly: *an admin actor mutated this venue's offer → `last_menu_check_at =
now()`, and set `is_verified = true` if it wasn't.* Owner actor → nothing, ever.
`venue_offer_logs` also gives the historical data to check how often that would have fired before
building it.

**Settle before writing the record:** `verified_at` is written by the admin form and read by
nothing. Either drop it or give it a job — the obvious one being "when a human first verified
this venue", distinct from `last_menu_check_at` = "most recent check". Today it is a third column
that looks meaningful in the admin form and means nothing.

Write this up through `/problem-solution` as a decision record — it is exactly the recurring
"should X set Y?" shape that skill is for, and D-01 / D-14 have now been corrected twice for want
of a written flow.

## 7. Owner account creation and the compliance question

The instinct in the note is right, and the conclusion is the opposite of what "form = more
compliance burden" suggests.

**"On the other hand if we encourage sending request via email, we process such data anyway."**
Correct, and stronger than that. Under GDPR the legal position does not turn on the *interface*.
A NIP, a name, a role and a phone number are personal data whether they arrive in a `<form>`, an
email body, or notes taken during a phone call. Article 30 requires the ROPA entry, Article 13
requires the privacy notice, and retention rules apply, in **all three** cases.

**The email channel is the weaker posture, not the safer one.** Today that data lands in a
mailbox — unstructured, unretained by policy, undeletable in any systematic way, sitting with
whatever mail provider is in use, and copied into `venue_claims` by hand. A form writes exactly
the declared fields into a table that already exists, with a schema the ROPA can point at, a
retention rule enforceable with `MassPrunable`, and an erasure path (`EraseVenueAction`) that
already works.

**The genuine cost is three items, none of them legal risk:**

1. A public endpoint accepting unauthenticated personal data — needs rate limiting and spam defence. `HoneypotController` shows this thinking is already present.
2. A `docs/compliance/data-map.md` ingress entry and a `ropa.md` processing activity. Both files are `status: draft` with `TODO` placeholders — this would be the first real entry in either, arguably overdue regardless.
3. A privacy-notice line naming the purpose and retention.

That is the same list O-3 weighed and rejected — but O-3 was rejecting a *lead capture* form
whose whole purpose was collecting contact details from strangers with no verification step
behind it. A claim form is different: the data is submitted by someone asserting a legal
relationship to a business, it is verified out of band before anything is granted, and **it is
being collected today anyway, just less well.**

**Recommendation:** the compliance argument favours the form. What argues against it is
`admin-recorded-claims-v1.md`'s actual reasoning, which is not about data at all — *"An automated
claim flow at fifty venues would need three independent verification signals to be trustworthy,
and would still be slower and weaker than one phone call."* That still holds. Nothing in a form
changes it.

So the V1 shape is a **structured intake, not self-service**: a form that writes a `pending`
claim with NIP and role and nothing else — no account, no access, no automatic anything. The
admin still verifies by phone and still approves as a separate audited step.
`StoreVenueClaimRequest` already validates precisely that shape, and the O-3 venue-page CTA would
have somewhere real to point.

**Regardless of whether it gets built: fix the NIP hole in §1.**

## 8. B2B events and reports

**All 17 `VenueFeature` modules are implemented** in `VenueAnalyticsReportService`. The admin has
a full preview at `admin/venues/{record}/analytics`. So "do we have reports" is answered — the
question is whether the events feed them.

| Report | Source | Verdict |
|---|---|---|
| `monthly_views` | `venue_stats` | ✅ except `shares`, permanently 0 (§1) |
| `verification_impact` | `venue_stats` around `claimed_at` | ✅ |
| `catalog_completeness`, `breadth_percentile`, `strongest_category_badge` | venue/product tables | ✅ no events needed |
| `blank_menu_warning`, `freshness_warning` | `offer_updated_at` | ✅ |
| `seasonal_forecast` | hardcoded month → editorial string | ⚠️ Not analytics. Four canned paragraphs keyed on `now()->format('n')`. Sellable as editorial; do not describe it as data. |
| `gap_report`, `category_demand_ranking`, `search_spike_alerts`, `district_demand_map`, `mom_demand_trend` | `events` (`discovery_*`) | ⚠️ Events fire correctly. **Killed by the 90-day prune** — §9 |
| `competitor_gap`, `trending_products` | `venue_offer_logs` | ⚠️ Measures *UNI's own seeding activity*, not market demand. With one claimed venue and every product entered internally, "5 venues added this drink" means "it was typed 5 times." Real signal only at meaningful owner adoption. |
| `click_detail_report` | `venue_stats` + `events` over **90 days** | ❌ Queries `events` for `created_at >= now()-90d` while the pruner deletes at exactly 90d, daily. Structurally cannot return a full window. |

### Two structural gaps

**Nothing is gated.** `Venue::hasFeature()` exists at `Venue.php:209` and is called by zero code.
`venue_feature_flags` has zero rows. `VenuePlan` sits on `venues.plan` (default `free`) and gates
nothing. `generateAll()` computes all 17 unconditionally and the admin preview renders all 17.
The entitlement architecture `tech/analytics.md` describes as the design rule — *"analytics UI
asks whether the feature is entitled, never whether the plan name matches"* — is a documented
intention, not a mechanism. Not urgent while nothing is sold, but it is the difference between
"we have tiers" and "we have a `plan` column".

**The owner sees almost none of it.** The owner panel has two widgets — `VenueStatusWidget` and
`VenueAnalyticsWidget` (six raw counters plus a line chart, one of them the always-zero
`shares`). Every interesting module — gap report, demand ranking, percentile — renders only in
the *admin* preview. The founder can see what an owner would get; the owner cannot.

### The missing signal

The events are adequate for the demand-side reports. What is missing entirely is **conversion**.
`venue_viewed` → `venue_directions_clicked` is captured, but nothing records that a view was
*comparative*: which venues appeared alongside yours in a result set and lost.
`discovery_searched` logs `result_count` but not result identity.

*"You appeared in 340 searches and were clicked 40 times, while the average venue in Mokotów was
clicked 60"* is the single most sellable number in a directory business, and it is the one thing
the current event schema cannot produce. It is a properties change on one event, not new
infrastructure — but decide it before the history worth having starts accruing.

## 9. History for B2B — the most urgent item

```php
Schedule::command('analytics:prune-events')->daily();
```

```php
$days = config('analytics.raw_event_retention_days', 90);
AnalyticsEvent::query()->where('created_at', '<', $cutoff)->delete();
```

**Every day, every event older than 90 days is destroyed. There is no rollup. It is not
recoverable.**

| Store | Retention | Contents |
|---|---|---|
| `events` | **90 days, hard delete** | Every search, filter, empty result, menu view, outbound click |
| `venue_stats` | 24 months | Six daily counters per venue, nothing else |
| `venue_offer_logs` | prunable | Product add/remove |
| `audit_logs` | 12 months | Claim approvals — **and no UI to read them** |

**`venue_stats` is the only durable history, and it holds six integers per venue per day.**
Everything category-level, everything search-side, everything an owner would pay for — gap
report, demand ranking, spike alerts, district demand map, MoM trend — is computed live from a
table that forgets at 90 days.

Concretely:

- **"What did my venue get in March?"** — asked in July, unanswerable beyond the six counters.
- **Year-over-year, seasonality, "you were top 10% last summer"** — permanently impossible. Each year of operation destroys another year of it.
- **A billing or performance dispute** — `venue_stats` defends a view count. Nothing defends "we showed you 340 times in searches for piwo bezalkoholowe."
- **`click_detail_report`** — reads a 90-day window from a table pruned at 90 days. Broken by construction, today.

**The fix is small and the window is now.** Keep the 90-day prune on raw events —
`eventlogger-identifier-stripping.md` and the whole GDPR posture depend on not hoarding raw rows,
and that is a genuinely good decision. Add a **daily aggregation job that rolls events up before
they are deleted**: per venue (or per city) per day per category — searches, filters, empty
results, impressions. Small table, no personal data, no new legal surface, indefinite retention.

There are 476 events in the DB and no customers. Building the rollup now costs a migration and a
command. Building it after twelve months of real traffic costs those twelve months, permanently.
**This is the only item in this audit where the cost of waiting is irreversible.**

## Open questions

1. **Does `verified_at` get a job or get dropped?** Obvious candidate: "when a human first verified this venue", distinct from `last_menu_check_at` = "most recent check". Today it is a third column that looks meaningful in the admin form and drives nothing.

3. **Should `discovery_searched` record result identity?** Unlocks the only genuinely sellable B2B number. Costs larger `properties` on every search event.
4. **When does feature gating stop being theory?** 17 reports compute unconditionally, `hasFeature()` is called by nobody. Pointless before the first sale — but it is the difference between packaging and a `plan` column.
