# UNI — Infrastructure Decision Log

Decisions taken 2026-08-27, covering environments, deployment, hosting panel, map stack, and seed-data geocoding. Pricing verified as of this date against vendor sources after an initial pass contained errors; re-verify before committing spend.

> [!note] ADR numbering
> Numbered `INFRA-01` onwards to avoid collision with the existing product ADR sequence (`ADR-002` covers CEIDG prospecting). Renumber if merging into one series.

---

## Context

UNI is pre-launch: zero users, zero paying customers, one part-time solo founder with a full-time salaried job. The scarce resource is **hours**, not money. Every decision below is weighted accordingly — where €5–20/month buys back an evening, it is spent without further debate.

Target for V1: 50–80 manually enriched Warsaw venues. The dominant cost of launch is 40–60 hours of venue enrichment (websites, social media, phone calls), not infrastructure.

**Stack:** Laravel monolith · TALL (Tailwind, Alpine, Livewire 3) · FilamentPHP · PostgreSQL + PostGIS · Hetzner Ubuntu · commercial product, EU/GDPR.

---

## INFRA-01 — Two environments, not three

**Decision.** Local development plus production. No preprod for now.

**Rationale.** A staging environment's value is proportional to what a bad deploy costs. At zero users that cost is one wasted evening. Building preprod means an Incus container on the home server, documenting version parity, and maintaining a second host — 6–10 hours that buys nothing until someone depends on uptime.

**Consequences.**
- Migrations are rehearsed against a local copy of the prod database, not a separate server.
- Riskier migrations (anything touching `venues`, `products`, or the pivot tables) get a `pg_dump` taken immediately before.
- The home server remains dedicated to n8n, restic backups, and Metabase later — its existing, working roles.

**Revisit when.** The week before onboarding the first paying venue, or the first time a broken deploy is visible to someone who isn't you.

**If revisited:** Incus system container on the home server (deliberately not Docker — prod is bare Ubuntu under Ploi, and parity is the entire point). Match OS, PHP, PostgreSQL and PostGIS versions exactly. Record them in `docs/environments.md`. Deploy over Tailscale SSH with the same command sequence as prod.

---

## INFRA-02 — Ploi over Forge, Pro tier

**Decision.** Ploi Pro (~€13/mo) once production is live. Free or Basic while still building locally.

**Rationale.** Not the backups — the monitoring. Disk-full is the most common quiet death for a small Laravel app: logs, `failed_jobs`, and PostGIS indexes fill a 40 GB volume faster than expected, and the symptom is a white screen with no notification. An 80% disk alert justifies the tier alone. Zero-downtime deploys are useless today but are a one-time toggle, avoiding a retrofit later.

Forge's equivalent capability sits at $39 Business. Ploi Pro is roughly a third of that.

**Correcting an earlier error:** Ploi Basic (~€8) does **not** include automatic backups, monitoring, or zero-downtime deploys, and caps at 5 servers. Those begin at Pro. Any plan built on "Basic includes backups" is wrong.

**Consequences.**
- One vendor manages nginx, PHP-FPM, certbot, supervisor (queue worker), and cron (`schedule:run` — the B2B rollup commands depend on this).
- Server limits (5 on Basic, 10 on Pro) are irrelevant at this scale.
- Migration to another panel, or to plain SSH deploys, remains an afternoon's work.

**Revisit when.** Never, most likely. This is a low-stakes, easily reversed choice; further deliberation is waste.

## INFRA-03 — Own backups, independent of the panel

**Decision.** Nightly `pg_dump` pushed to the home server over Tailscale, captured by the existing restic 3-2-1 rotation. Ploi's automated backups run alongside as a second, independent layer.

**Rationale.** Once 80 venues have been hand-enriched, that data represents weeks of phone calls and website digging — it is unreconstructable. Two independent backup systems, only one of which depends on personal discipline.

The self-hosted copy is the stronger one: off-site relative to Hetzner, versioned, with an offline USB copy in rotation. This is the one place where "use infrastructure I already own" is straightforwardly correct, because the owned version is genuinely better than the vendor's.

**Action — do not skip.**
- [ ] `pg_dump` cron on prod, output to home server via Tailscale
- [ ] Confirm restic picks up the new path
- [ ] **Restore-test once**: pull last night's dump into the local database, boot the app against it, click through the map and a venue profile

An untested backup is decoration. Fifteen minutes, once, then it's known rather than assumed.

## INFRA-04 — OpenFreeMap for tiles

**Decision.** OpenFreeMap public instance, `positron` style at launch. Custom dark theme matching `#7c3aed` deferred to post-launch polish.

**Rationale.** CartoDB Dark Matter's free tier is non-commercial, and UNI is commercial. Verification confirmed the same applies to the alternatives:

| Provider | Free tier | Commercial entry |
|---|---|---|
| OpenFreeMap | Free, no key, no stated limits, commercial OK | — |
| MapTiler Cloud | Non-commercial only, logo required, 5k sessions/mo | Flex $25/mo |
| Stadia Maps | Non-commercial only | Starter $20/mo |
| Protomaps (self-hosted) | Free — ODbL, attribution required | — |
| `tile.openstreetmap.org` | Donation-funded, unsuitable for production | — |

OpenFreeMap is the only genuinely free hosted option for a commercial product. Attribution is required and MapLibre adds it automatically.

**Risk.** Donation-funded, effectively single-maintainer, no SLA.

**Mitigation — and why the risk is acceptable.** The fallback is cheap and known: extract a Poland-only PMTiles file from Protomaps, serve it from nginx on the Hetzner box via HTTP range requests, point MapLibre at it. Same style JSON, no code change beyond a URL. Roughly an afternoon.

- [ ] Evaluate `positron`, `liberty`, `bright` — 5 minutes
- [ ] Keep the Protomaps fallback documented so it stays an afternoon, not a research project

**Note on Protomaps aesthetics.** The reference style is a starting point, not the product. With vector tiles the basemap's appearance is a JSON file you own. Recolour from the palette object, or use Maputnik to edit visually.

**Design target for the custom theme.** Not "make it pretty" — manage the contrast budget. Near-black land, roads two steps lighter, water slightly cooler, labels dim enough to require looking for. Dark Matter works because it is desaturated and low-contrast, leaving the visual range for the data. `#7c3aed` pins should be the only saturated thing on screen. A discovery map where the basemap outshouts the venues has failed at its job.

## INFRA-05 — MapLibre GL JS, replacing Leaflet

**Decision.** Migrate the map component from Leaflet to MapLibre GL JS.

**Rationale.** Free vector tile hosts serve vector tiles, which Leaflet cannot render natively. This is also the only expensive-to-reverse decision in this log — it is a rewrite of a core UI component — and it is cheapest to do now, while that component is at its smallest.

Secondary benefit: full control of basemap styling, which raster tiles cannot offer at any price.

**Trade-off accepted.** Bundle size rises from ~42 KB to ~200 KB+ gzipped. On a mobile-first Polish product this is real.

**Mitigations.**
- Lazy-load MapLibre — on mobile the map is behind a FAB toggle, so many first-time visitors never download it
- SEO landing pages don't carry the map, so rankings are unaffected
- `dragRotate.disable()` and `touchZoomRotate.disableRotation()` — a tilted map on a venue-discovery interface is a way to get lost, and the top cause of "why is my map crooked" messages
- DOM markers via `new maplibregl.Marker({element})`, not WebGL symbol layers — keeps Tailwind styling, keyboard focus, and Alpine bindings. Revisit only above a few thousand pins per city.

**Unchanged.** The Livewire integration pattern is identical: `wire:ignore` container, Alpine owns the instance, listen for `moveend`, `map.getBounds()`, dispatch to Livewire, PostGIS bbox query. Different constructor, same wiring.

**Alternative if the existing Leaflet map already works well.** Ship on Leaflet with Stadia raster tiles at $20/mo and defer the rewrite until UNI is validated. €240/year to avoid rewriting something that might get thrown away is a defensible trade.

## INFRA-06 — Nominatim for seed geocoding

**Decision.** Public Nominatim for the one-off venue import. Coordinates persisted permanently.

**Rationale.** Nominatim's usage policy permits small one-off batches at ≤1 request/second with an identifying User-Agent and caching of results. 80 venues takes ~80 seconds. Results are ODbL-derived, so permanent storage in the database is fine. Cost: €0.

**Constraints.**
- ≤1 req/sec, identifying User-Agent, cache results, never re-query the same address
- Not for ongoing or bulk geocoding — if venue volume grows into continuous geocoding, self-host Nominatim or Photon
- **Avoid `photon.komoot.io`** — explicitly a demo server, throttled, no guarantees
- Stadia permits permanent geocode storage only from Standard ($80) upward, not Starter — so paid geocoding is a poor fallback anyway

---

## INFRA-07 — Venue import via idempotent Artisan command

**Decision.** `php artisan uni:import-venues venues.json` — idempotent, upserting on a natural key (slug or NIP). Geocode at import time, persist coordinates, never re-geocode.

**Rationale.** Split by data nature:
- **Reference data** (cities, the 6 categories) → idempotent seeders, in git, run in every environment
- **Venues** → real business data, prod is the source of truth

Idempotent means running it twice yields the same result as once. `updateOrCreate(['slug' => ...], [...])`, not `insert`. This matters because it *will* be re-run: after a failed import, after a restore, while iterating on the JSON.

**Retirement.** Once owners can edit venues through Filament, the JSON is stale and re-importing would clobber their edits. The command is a bootstrapping tool — retire it, don't evolve it into a sync.

- [ ] Guard the command so it refuses to run against prod after a cutover date or flag

## INFRA-08 — PostGIS is manual on any panel

**Decision.** Accept it. Not a selection criterion between panels.

**Detail.** `CREATE EXTENSION postgis;` requires PostGIS binaries installed at OS level and a role with superuser or DB-owner privileges. Neither Forge nor Ploi automates this for self-managed VPS. (Ploi Cloud's *managed* Postgres offers PostGIS via its interface, but that is a different product from a Ploi-managed VPS.)

Roughly ten minutes per server. It is the most common first-deploy wall on this stack — expect it, don't be surprised by it.

- [ ] Record the exact package names and commands in `docs/environments.md` so the second server takes two minutes

## Deploy sequence

Versioned in the repo as `deploy.sh`, not retyped:

```bash
cd /home/ploi/uni.pl
git pull origin main
composer install --no-dev --optimize-autoloader
npm ci && npm run build
php artisan migrate --force
php artisan config:cache route:cache view:cache
php artisan queue:restart
```

**Portability notes.** No absolute paths in code — `base_path()`, `storage_path()`, never a literal. Everything reproducible lives in git: migrations, seeders, `deploy.sh`, `.env.example` listing every variable. If a server needs something that isn't in the repo or in `docs/environments.md`, that document is wrong.

**Migration discipline.** Schema flows forward, data flows backward. No hand-run `ALTER` on prod — if it isn't in a migration, it doesn't exist. Migrations are forward-only in practice; for destructive changes use expand/contract (add column → backfill → dual-write → switch reads → drop old column in a later release) rather than relying on `down()`.

## Open questions — not technical

The infrastructure risks above are noisy and tractable. Every correction the research pass produced (pricing tiers, usage policies, extension privileges) was cheap to fix and none would have killed the project.

The risks that aren't tractable:

1. **Will Warsaw venue owners pay for NoLo demand data?** The B2B tier is designed but unvalidated.
2. **Can venue density be reached fast enough** for SEO pages to have anything to rank with?
3. **Do Polish consumers search for this yet?**

No amount of research resolves these — the answers don't exist online, they exist in ten phone calls to Warsaw bars. Ask whether they'd pay for data on what NoLo drinks people search for near them. If the calls go badly, repositioning before enriching 80 venues is worth a great deal. If they go well, there are first customers waiting before launch.

**Next action:** the phone calls, not the server.
