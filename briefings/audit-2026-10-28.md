# Engineering Audit, 28.10.2026

**Report only: no code, configuration or dependency was changed.** Each finding is checked against the code at the time of writing, with `file:line` references into the application repository. Fixes wait for your decision, one at a time.

## A. Executive summary

**Overall:** This is a well-engineered small Laravel 13 / Filament 5 / Livewire 4 app on PHP 8.5 and Postgres 18. The full suite passes (1141 tests), and Pint, Rector, composer audit and npm audit are all clean. Security decisions are explicit and tested: no trusted proxies, trusted hosts on, JSON-LD escaped, signed POST-to-confirm links, a partial unique index for claims, and approval rules enforced inside the actions rather than the buttons. I found **nothing exploitable in production today**.

**Biggest risks:**

1. **The `/zglos-lokal` form can be abused to send email (High, but off in production).** It sends email to any address, with a venue name the attacker types (it can contain a link), from your transactional domain. It also lets anyone use up the 100-a-day VAT white-list quota. It goes live the day `UNI_OWNER_ACCESS` flips.
2. **`search_stats` counts empty searches wrongly.** Zero-result searches are counted twice, and the partial words typed on the way to a query are recorded too.
3. **Contact details on requests nobody decides are kept forever.** Undecided claims and reports, and rejected erasure requests, keep their contact data indefinitely, so the documented retention rule never applies to them.
4. **Nothing checks the production settings.** No step verifies `APP_DEBUG=false`, `APP_ENV=production` or `SESSION_SECURE_COOKIE` before a deploy, and `.env.example` ships `APP_DEBUG=true`.

**Strongest parts:** the deploy recipe's guards, CI with actions pinned to a commit SHA, the backup encryption guard, analytics events that store no identifier, the action classes, and the test coverage of rules and decisions.

**Production readiness:** V1 (owner access off) looks ready, within what this audit covered. Fix F1 before V2 opens.

**Top changes by value:** F1 (before V2), F4, F3, F2, F5.

## C. Detailed findings

### F1: The owner-request form works as an email relay and can use up the registry quota (High, but unreachable while the switch is off)

- **Evidence:** `VenueRequestController::storeNewVenue` saves `submitted_venue_name` exactly as typed (up to 255 characters). `SubmitVenueClaimAction.php:51` queues a registry lookup and `:55` emails `contact_email`, which can be any address. `ClaimReceived.php:52,54,68` puts `venueName()` into the subject and into a Markdown line. `Markdown::withSecuredEncoding()` isn't enabled anywhere, so `[tekst](https://…)` becomes a real link, and bare URLs get linked by mail clients anyway.
- **What it does today:** Each POST that passes validation sends one email to any recipient, carrying attacker-written text from your sending domain. The only limits are `throttle:reports` (5 per minute per IP or /64) and the honeypot field. Varying the venue name gets past the duplicate check. Each POST also uses one VAT white-list lookup. The rule in `.ai/rules/registry.md` says 100 a day, then a lockout until midnight.
- **Impact:** Phishing or spam sent through your domain will hurt sender reputation (password resets go through the same subdomain). Using up the quota means real owners get `registry_lookup.error = unavailable`, and the admin's on-demand lookup fails too.
- **Preconditions:** `UNI_OWNER_ACCESS=true`. The routes return 404 today (`EnsureOwnerAccessIsOpen`, `config/uni.php:148`), so it's **latent**.
- **Smallest fix:**
  - Rate-limit by recipient address (e.g. one request email per address per 24 h), plus a global daily cap on request emails.
  - Write the venue name in mails as plain text: escape `[`, `]`, `(`, `)`, `*`, `_`, or call `Markdown::withSecuredEncoding()` in a provider.
  - Cap registry lookups per day; when the budget is spent, mark the claim "pending lookup" instead of calling the API.
- **Verification:** A feature test: N requests to one address send one mail. Another test: a name with `[x](https://e.vil)` renders without an `<a>`.
- **Effort:** Small–medium. **Regression risk:** A genuine resubmission gets limited (acceptable; it can say "check your inbox").

### F2: The search rollup counts zero-result searches twice and records prefixes (Medium)

- **Evidence:** `trackAfterQuery` (`AnalyticsTracker.php:56`) records `discovery_empty_results` (with `query`) on each render, i.e. after each 300 ms debounce, once per distinct filter fingerprint. `commitSearch` then records `discovery_searched` with `result_count = 0`. `RollUpAnalytics.php:138` and `:144` both add to `zero_result_searches`.
- **Result:** A finished empty search for "xyz" gives `searches=1, zero_result_searches=2`. Each empty prefix ("xy") gets its own row with `searches=0, zero=1`. That is exactly the prefix noise `commitSearch` was written to remove. `AnalyticsRollupTest` only uses `discovery_searched` events, so the tests don't catch it.
- **Impact:** `search_stats` has no reader yet, so the damage is deferred. The first "what people search for and don't find" report will overstate failures.
- **Fix:** In `rollUpSearches`, read only `discovery_searched`. Keep `discovery_empty_results` for the filter-combination signal it was made for.
- **Verification:** Add a test with both event types for the same query → expect `zero_result_searches = 1`.
- **Effort:** Small. **Regression risk:** Past days change when backfilled. That is the correction, and the command is idempotent.

### F3: Contact data on undecided requests is never cleared (Medium)

- **Evidence:** `AnonymiseExpiredData.php:85` and `:114` require `reviewed_at IS NOT NULL`. `schema.md` covers only decided rows ("12 months after the claim is decided / report is closed"). Rejected `venue_erasure_requests` keep `requester_name`/`requester_email` indefinitely ("Kept — it is the evidence"). Only *completed* ones are nulled, in `EraseVenueAction::complete`.
- **Impact:** A spam report or claim that is never actioned keeps the email address, NIP and registry extract forever. That breaks the storage-limitation principle the rest of the design follows carefully. For claims, the morning reminder makes this unlikely; for reports, nothing nudges the admin.
- **Fix:** Add an outer horizon: clear contacts where `reviewed_at IS NULL AND created_at < now() - N months`. For rejected erasures, decide whether the evidence needs the email or just the dates. Update `schema.md` in the same commit.
- **Effort:** Small. **Regression risk:** None to the data you keep.

### F4: Nothing checks production safety settings at deploy (Medium)

- **Evidence:** `.env.example:2,4` has `APP_ENV=local` and `APP_DEBUG=true`. `.ai/rules/general.md` says "A real production .env is copied from .env.example, so every value here ships". The safe values sit only in a commented "Production Baseline" block. `deploy.php:121` checks only that the file exists and has a key. No Ansible verify task checks `.env`.
- **Impact:** One missed line when writing `shared/.env` means debug pages printing the environment, or session cookies without `Secure`. Nothing catches it.
- **Fix:** In `deploy:env`, when `isProduction()`, refuse unless `APP_ENV=production`, `APP_DEBUG=false` and `SESSION_SECURE_COOKIE=true`. Also fix the general rule's wording, which contradicts the file.
- **Verification:** Extend `DeployRecipeKeepsTheRulesTest`.
- **Effort:** Small.

### F5: Discovery search cuts by bytes, not characters (Low–Medium)

- **Evidence:** `DiscoveryPage.php:224` uses `substr($value, 0, 100)` and `strlen`, and `:241` does the same. A string like "a" followed by 60 × "ł" gets cut in the middle of a two-byte character.
- **Impact:** The invalid UTF-8 goes into an `ilike` binding (Postgres error 22021) or the Livewire JSON snapshot, and either way the user gets an error page. It needs a long paste, so it's rare. Medium confidence: reasoned from the code, not reproduced.
- **Fix:** Use `mb_strlen` and `mb_substr` in both places. Add a test that sets a 101-byte Polish string.

### F6: The old `ClaimVenue` owner page conflicts with the current owner check (Medium, maintainability)

- **Evidence:** Only users with the owner role can enter the panel (`User::canAccessPanel`), so `shouldRegisterNavigation` is always false. The page is still reachable by URL for an owner with no venues.
- **What's wrong with it:**
  - It offers `'phone' => 'Telefon'` (`:97`), against "nobody is phoned".
  - It creates the claim directly (`:150`): no `verification_token`, no registry lookup, no confirmation email.
- **Mitigation:** Approval still requires a confirmed channel or a written reason (`ApproveVenueClaimAction`), so nothing can be approved through it unchecked.
- **Impact:** There are two ways to make an owner claim with different rules, and the old one contradicts the decision record.
- **Fix:** Delete the page and its view, or route it through `SubmitVenueClaimAction`. Either way it needs a decision from you.

### F7: Page analytics failures aren't handled the same way everywhere (Low–Medium)

- **Evidence:** `VenueController`, `CategoryController` and `DiscoveryPage` wrap event writes in `AnalyticsFailureReporter`. The pages listed in the table call `$eventLogger->log()` directly.
- **Impact:** If the `events` insert fails (disk, lock, constraint), city and drink pages return a 500 while venue pages keep working. It also leaves two ways of writing the same table.
- **Fix:** Wrap them, or move the protection into `EventLogger::log` itself, which is simpler: one rule in one place.

### F8: The product `is_active`/`is_approved` flags are only partly enforced (Low–Medium; the meaning needs a decision)

- **Where they are respected:** `DrinkController`, the sitemap and `MenuItemResolver`.
- **Where they are ignored:** venue pages (`products.category` loaded unfiltered), `VenueQuery`, the breadth counts, and the owner `AttachProductsTable`, which has no query filter.
- **Impact:** A product you deactivate keeps appearing on every venue that carries it, and owners can still attach it.
- **Fix:** Decide whether `is_active` means "hidden everywhere" or "not offered for new attachments", then apply one scope.

### F9: Discovery does the full query on every interaction (Medium, future; measure first)

- **Evidence:** `VenueQuery::get` loads every matching venue nationwide, with all products, categories and drinks. It runs on every debounced keystroke, filter toggle and `loadMoreVenues`. Only the map payload is capped (`take(500)`), and that cap is applied after loading.
- **When it matters:** Fine at today's catalogue. At a few thousand venues × ~10 products, each interaction loads tens of thousands of models.
- **Verify:** Seed 2k venues on the home server and log the queries and memory of one `render()`.
- **Option when needed:** Count products per category in SQL instead of loading them; load products only for the visible 24 cards.
- **Leave alone until measured.**

### F10–F15 (brief)

- **F10:** The rollup's `delete()` + `insert()` per day isn't in a transaction (a crash leaves a day half-gone until rerun). `whereDate('created_at', …)` can't use the `(type, created_at)` index on a table that is never pruned. Fix: `DB::transaction` plus `whereBetween(startOfDay, endOfDay)`; use `lazy()` instead of `get()`.
- **F11:** `selectedDistricts` isn't locked or validated on Livewire updates (only on mount). A tampered request sending `["abc"]` makes Postgres throw on the integer column. Fix: `array_filter(..., ctype_digit(...))` in `filters()`.
- **F12:** The erasure modal's "Usuń także moje konto" doesn't tell a chain owner that their other venues lose their owner (`UserObserver::deleting`).
- **F13:** No CSP. Output escaping is consistently good (`{!! !!}` only on JSON-LD that is HEX_TAG-encoded, static copy, and admin SVG), so this is defence in depth. Alpine would need its CSP build; medium effort.
- **F14:** The nginx comment says admin is "enforced before any application code runs". Livewire's update/upload endpoints and Filament's import/export download routes sit outside `/admin`. They are covered by auth, checksummed snapshots and Filament's own export ownership check, so this isn't exploitable; only the claim is too broad.
- **F15:** `Category::display_icon` returns raw `icon_svg` that the admin types. Fine while you are the only admin.

## D. Security assessment

**Reviewed:**

- All public routes and controllers, the form requests, middleware, and the owner-request and confirmation flow.
- Claim approval and rejection, erasure, `VenuePolicy`, both panel providers, the owner resource and its relation managers.
- Output escaping across every Blade view (`{!! !!}`, `@js`, `Js::from`), redirects (scheme-checked), mass assignment, and raw SQL (all bound or built from constants).
- Rate limiters, the trusted proxy/host setup, security headers, the nginx template, `deploy.php`, CI, and dependency audits.

**Mitigations confirmed:**

- CSRF on every web POST.
- Signed, expiring confirmation links that need a POST (safe against mail scanners).
- The partial unique index keeps one active claim per venue.
- Owner queries are scoped to `claimed_by` and also go through the policy.
- Livewire `#[Locked]` on analytics state; validation of coordinates and bounds.
- The LIKE wildcards in search are escaped.
- Dev tools (`laravel-brain`, Boost) are local-only and `--no-dev` in deploys.

**Unverified assumptions:**

- The live `shared/.env` contents.
- Whether Filament's owner-panel password reset refuses admin email addresses (not checked; the `/admin` allowlist limits the damage anyway).
- Mail-client rendering of injected links (inferred from Laravel's Markdown pipeline).

No exposed credentials were found in the repository. No obvious vulnerability doesn't make the application secure. F1 is the one to close before V2.

## E. Architecture and complexity assessment

- **Keep as is:**
  - Single-purpose action classes (`Approve…`, `Submit…`, `EraseVenueAction`) that enforce rules inside themselves.
  - `AnalyticsGateway` with its fake. It has a real second user: the tests.
  - Config-driven `OwnerAccess`, `ReservedPaths` plus its route-walking test, and plain controllers with no repository layer.
  - No caching on public pages. None is needed yet.
- **Simplify:**
  - There are three ways to record analytics: `EventLogger`, `AnalyticsGateway` and `PostHogService`, each wrapped or not wrapped differently. Making `EventLogger` swallow its own failures (F7) removes most of the variation.
  - Remove `ClaimVenue` (F6).
- **Duplication worth removing:** "Claimable / public" already exists as both a scope and a method, consistently. The product-visibility rule is the duplicated one; decide it once (F8).
- **Unnecessary:** Repositories, a service layer above the actions, or a query/caching layer for discovery before F9 is measured.
- **Minor:** `app/Testing/FakeAnalyticsGateway.php` ships in the production autoload. It's harmless; `tests/` would be its natural home.

## F. Performance assessment

- **Verified inefficiencies (cheap):** the F10 `whereDate` index bypass and full-day `get()`.
- **Suspected, needs profiling:** F9 discovery hydration. The many `ilike '%…%'` `whereHas` subqueries in `scopeSearch` scan the tables; a `pg_trgm` index could help later.
- **Fine at current scale:** sitemap built on each request, the footer city query on every page, no page cache.
- **Priority:** F10 (minutes of work) now. F9 only after a seeded benchmark.

## I. Final verdict

- **Dangerous or broken?** Nothing exploitable in production now. F1 is the real risk and arrives with V2. F2 is a confirmed data-correctness bug.
- **Unnecessarily complicated?** Very little. The analytics write paths (three ways, protected inconsistently) and the duplicate claim page.
- **Where a small change pays off:** move failure handling into `EventLogger`, and give product visibility one scope.
- **Biggest performance risk:** discovery loading everything on every interaction, as the catalogue grows.
- **Missing checks:** a production `.env` guard at deploy, plus the tests listed in G.
- **Fix first:** F4 now (cheapest), F1 before V2, then F3 and F2.
- **Leave unchanged:** the action-class structure, the proxy/host decisions, the deploy recipe, no page caching, the escaping approach.
