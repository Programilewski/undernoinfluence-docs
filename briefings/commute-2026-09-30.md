## 2. What happened since the last commute

**28.09 — the deploy process, checked line by line.** It started as "deploy four files to the home server" and became the thing that had to come first. Five claims in the deploy documents were wrong. The biggest was the one three documents had repeated since early September: building assets on a 4 GB server would kill Postgres. Measured, the build peaks at about 370 MB, and roughly 2.5 GB is spare. Research then showed that Ploi caused most of the difference between the home server and production, and the decision went to **no panel: Ansible builds both servers from your PC and Deployer deploys tags to both.** Ten decisions came out of it. The two you are most likely to meet again: *a deploy never runs `optimize:clear`*, because UNI's cache is a database table holding the scheduler heartbeat and the login limiter; and *migrations only go forward*, with production backing up before any deploy that migrates.

**29.09 — the plan, built and proved.** The runbook (`ops/deployment-runbook.md`) came first. Reading Deployer's own source while writing it found six things the plan would have got wrong. The worst: a missing `shared/.env` would have made Deployer copy `.env.example` into place, with debug on and no key, and the first error page would have printed the database password. The playbook, `deploy.php`, the CI workflow and four tests were then written and run against a throwaway Ubuntu 26.04 container. That run found four more problems no reading had, including one that would have blocked every deploy: a clean copy of the code can't build the admin CSS, because Filament's theme imports from `vendor/`. All ten are fixed and proved. **Not proved anywhere yet:** the firewall, certificates, Tailscale and the VPS first-login script. A container can't run any of them.

## 3. Findings raised unprompted

### 3.1 The first CI run is the single point everything waits on

`deploy.php` refuses a tag without a passed CI run on that exact commit. That is deliberate, and there is no bypass switch (29.09, decision 8). So the whole chain goes: CI green → tag `v0.1.5` → the home-server sitting → Phase 5's rebuild from nothing → production. It all hangs on a result that already exists on GitHub and that nobody has looked at. If it is red, the fix is probably small, because the suite passes locally and CI mirrors the test configuration. But it has to be found before the sitting, not during it. **Five minutes, and it's the only item on today's list with no dependency of its own.**

### 3.2 The "lost, not delayed" wording is still in two documents

On 25.09 this workspace corrected itself: with the database queue driver, a notification queued while the worker is down **waits in the `jobs` table** and goes out when a worker starts. There is a record for it (a-queued-job-waits-it-is-not-lost). Two documents still say the opposite:

- **Deploy checklist A2** says "lost, not delayed", and it still shows the row as **TODO with a 09.09 date**. The worker has run on the home server since 25.09, and the playbook now writes its config.
- **`ops/home-server-setup.md`** line 323 says the same. That document is due to be retired at the rebuild (runbook 8.1), so it matters less, but it is what you'd read if the rebuild slipped.

The wrong version leads to the wrong incident response: you'd go looking for lost e-mails to resend when you only need to start the worker. **Fixed later on 30.09**, in both documents.

### 3.3 The commute index stops at v11.0

`roadmap/README.md` lists every commute document with its version and date, and its last row is `commute-2026-09-21.md`. The two written on 25.09 aren't in it. One is v12.0. The other, `commute-2026-09-25_2.md`, is a different kind of document: a standing description of what UNI is, versioned 1.0 on its own track. **Fixed this morning** along with today's row, and the table now says that `_2` is not part of the commute sequence.

### 3.4 Two 25.09 items have no recorded outcome

Neither journal since says whether they happened. They matter for different reasons. The first proves the archive opens. This is the runbook's Phase 0, in the order that unblocks the most soonest. **Everything here is on the PC or in a browser. No laptop needed.**

1. **`gh auth login`**, then `gh run list --workflow tests.yml --limit 3`. Green → step 2. Red → paste me the failing job, and it gets fixed before anything else.
2. **Tag and push `v0.1.5`.** It's the first release the new process can deploy.
3. **A passphrase on the existing SSH key** (`ssh-keygen -p -f ~/.ssh/id_ed25519`), then `ssh-add`. Keeping the key and adding a passphrase closes the real gap, and GitHub already trusts it.
4. **The backup key.** Make it, put the private half in the password manager, and put the public half at `ansible/files/keys/uni-backup.pub` and commit it. **The playbook won't start without it**, deliberately. While the password manager is open, store the backup-archive password (§3.4) and, if you're ready, the future `admin` sudo password.
5. **`~/.ssh/config`** from the runbook's template. There is none on the PC today.
6. **Push the workspace** (`git -C docs push`), 9 commits.

## 8. Deliberately not doing

**On preprod, permanently:** no real personal data, no outside health monitor, no backup anything depends on, nothing production depends on in either direction.

**In the deploy process, permanently (28–29.09):** no `optimize:clear`, no down-migrations on rollback, no GitHub key on any server, no bypass for the CI check, no panel with access to a server that holds personal data.

**Carried forward:** `UNI_OWNER_ACCESS` stays `false` everywhere until V2 is a decision with a date. Raw events stay unpruned, because they hold no identifier. Retention is anonymisation, never deletion.

**Added today:** no more work on the current home-server container beyond reading it. It is being replaced, and every hour spent on it is an hour of a process that no longer exists.
