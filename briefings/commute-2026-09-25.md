## 3. Findings raised unprompted

Ranked by consequence.

### 3.1 "A queued notification is lost, not delayed" is wrong, and the correction changes what you do in an incident

Two documents in this workspace and one deploy-checklist row say that with no worker running, a queued notification is *lost rather than delayed*. That is true for some queue drivers. It is not true for this one.

`QUEUE_CONNECTION=database`. A dispatched job is **a row in the `jobs` table**. With no worker, the row sits there. Start a worker a week later and the week's backlog is delivered, in order, because nothing ever removed the rows.

**Why the distinction is worth the paragraph.** The morning you discover on production that the worker has been down since Tuesday, the correct action is to start the worker and let the backlog drain — not to hunt through the database working out who never got their claim approval and re-sending by hand. The second one sends duplicates on top of the first one.

**The urgency the documents attach to A2 is still right.** While the worker is down, the owner has not been told, and from the owner's side that is indistinguishable from lost. The rows are also genuinely destroyed by a `queue:flush`, by rebuilding the environment, or by exceeding `--tries=3` into `failed_jobs`, and `queue:prune-failed` drops those after 30 days. So: *not delivered, recoverable by starting a worker, genuinely lost only if something clears the table.*

Nothing was lost on the home server — the `jobs` table was empty this morning, because with no cron nothing had ever dispatched anything.

### 3.2 The box was installed without `--no-dev`, against the runbook's own step 3

`laravel/boost`, `phpunit`, `fakerphp/faker` and `laravel/pint` are all in `vendor/` on the box. The runbook says `composer install --no-dev --optimize-autoloader`. The autoloader *was* optimised, so only that one flag was missed.

**Nothing is exposed.** Boost registers its routes only when the environment is `local`, and this box is `preprod`. I probed `/boost`, `/_ignition/health-check`, `/_debugbar/open` and `/telescope`: all four return 404, and `route:list` shows nothing from any dev package. So this is a parity problem, not a security one — but it is precisely the kind of parity problem that makes preprod stop answering the question it exists to answer.

**It has one accidental upside, and it expires the moment you fix it.** Because PHPUnit is installed, that box can run the suite *on PHP 8.4* right now. The suite has only ever run on the laptop's 8.5. [[#6. Decisions still to be made|§6]] turns this into a decision rather than a footnote, because the order matters: run the suite there once, then strip the dev dependencies.

### 3.3 The worker and cron write the same log file as different users, and the loser fails silently

This one was not on any list and is the sort of thing that surfaces three weeks later as "logging just stopped".

The queue worker runs as `www-data`, because that is what php-fpm runs as. Cron runs `schedule:run` as `uni`, because that is who owns the code. Both append to the same file, `storage/logs/laravel-YYYY-MM-DD.log`, and **that file is created fresh at midnight by whichever of them gets there first**.

With the default `umask` of 022, a new file is `rw-r--r--`. The directories are already setgid to `www-data`, so the *group* is right — but the group has no write bit. So whoever creates the file at 00:00 locks the other one out of it for the rest of the day, and the loser's log lines vanish with no error anywhere.

Fixed in three places, because all three writers have to agree: `umask 0002` in the cron line, `umask=0002` in the supervisor program, and a `UMask=0002` systemd drop-in for php-fpm. The repository's `supervisor/uni-worker.conf` now ships that line with its reasoning, and `tests/Feature/Console/WorkerConfigIsDeployableTest.php` pins the four things that file can get wrong silently.

**This will happen identically on production**, where Ploi's deploy user and the web user are also two different accounts.

### 3.4 Regex location order in nginx can serve PHP as text, and the fix for the map bug sat right next to it

nginx takes **the first regular-expression location that matches**, in the order they appear in the file. The 22.09 fix for blank maps is a regex location (`location ~ \.mjs$`). Today's caching fix is another (`location ~ ^/(build|vendor)/`).

Put the caching one above the `.mjs` one and every `/vendor/**/*.mjs` matches the caching block instead, loses `default_type text/javascript`, and **every map goes blank again** — while the diff reads as a caching change. That is a trap with a three-week fuse.

While fixing the order I also moved `location ~ \.php$` above both. There is no PHP under `public/build` or `public/vendor` today, but if there ever were, a `^/(build|vendor)/` block sitting above it would serve the source of a PHP file to anyone who asked. The ordering is now: `.php` first, `.mjs` second, the versioned-asset cache block third.

### 3.5 Two files I created on the box needed their permissions tightening, and I am telling you because you cannot see them

I backed `.env` up before editing it. `cp` produced `-rw-r--r-- root root` — **world-readable, containing the database password**. Not reachable over HTTP (it is outside `public/`, and the dotfile deny rule covers it anyway), but wrong on a box you log into. Both it and the nginx backup are now `600`.

They are `/var/www/undernoinfluence/.env.bak-20260925` and `/etc/nginx/sites-available/uni.bak-20260925`, and they should be deleted once you are satisfied with today's changes. They are in [[#5. Problems to fix|§5]] so they do not become permanent furniture.

## 4. The deployment, explained from the beginning

**This is the section you asked for.** It is not a runbook — [`ops/home-server-setup.md`](../ops/home-server-setup.md) is the runbook and it has the commands. This is the layer underneath: *why each step exists, what it costs when it is skipped, and whether it will happen again on the OVH box*. Each part ends with a line saying what production does differently, because that is the only reason to read it on a train.

A framing that makes the rest easier. **A Laravel application is not one program.** It is four things that have to be true at once, and three of them fail silently:

1. **A web server handing requests to PHP** — fails loudly. You see a 502 or a blank page immediately.
2. **A scheduler**, run by cron once a minute — fails **silently**. Every page still works.
3. **A queue worker**, run by supervisor — fails **silently**. Every form still submits.
4. **A correct environment** — file permissions, `.env`, built assets, caches — fails **silently and later**, usually at midnight or on the next deploy.

Almost everything below is about the three silent ones. The loud one takes an afternoon and then behaves.

### 4.1 Three environments, and what this one is for

The laptop is where things are built. **Preprod is where things are broken on purpose.** Production is where things must not be broken.

The home server is preprod. Nothing depends on it, it holds no real personal data, and `incus delete uni --force` returns it to nothing in seconds. That is what makes it the right place to find out that cron was never installed — finding that out on production means discovering it from a user.

**What it must therefore never have** is in [[#8. Deliberately not doing|§8]], and none of those absences are laziness.

> **Production differs:** it is the opposite of disposable, and every shortcut taken here has to be undone there deliberately rather than by remembering.

### 4.2 Why a container, and why deliberately not Docker

The home server already runs Docker applications — n8n, restic — that are not to be disturbed. So the application goes in an **Incus system container**: a small Ubuntu that has systemd, cron, supervisor and several processes, and behaves like a server.

A Docker container is one process with no init system. It has no cron and no supervisor, so the two silent failure modes above would have to be solved some completely different way — which would mean preprod testing an arrangement production does not use. Production is bare Ubuntu under Ploi. **Parity is the entire point of the environment**, and five extra minutes buys it.

> **Production differs:** no container at all. The container exists here only to keep UNI away from your Docker applications.

### 4.3 The network trap that has nothing to do with Laravel

Docker sets the iptables `FORWARD` policy to `DROP`. A fresh Incus container therefore gets an IP address, resolves DNS perfectly — the bridge's own resolver is not forwarded — and then **every single outbound connection times out**. It presents as a broken package mirror or a DNS fault and is neither.

The fix is two rules in `DOCKER-USER`, the chain Docker guarantees it will never overwrite, plus `iptables-persistent` so they survive a reboot. I checked that persistence today rather than trusting it: `netfilter-persistent` is `enabled` and `/etc/iptables/rules.v4` was saved on 22.09. Without that second half the container silently loses the internet at the next power cut, and the failure looks nothing like its cause.

> **Production differs:** no Docker, no bridge, no forwarding. This whole class of problem does not exist there. It is here because your home server has another life.

### 4.4 PHP: read the lock file, not `composer.json`

On 22.09 `composer.json` declared `^8.3` while `composer.lock` demanded `>=8.4.1` through Symfony and spatie/crawler. The box had been provisioned with Ubuntu's stock 8.3 and `composer install` refused with twenty-two conflicts.

**`composer.json` is the intention; `composer.lock` is what will actually be installed.** Provision from the lock. `composer.json` now says `^8.4.1` and a test keeps the two honest, which is why this cannot recur silently.

The second lesson is smaller and was learned twice on the same day: ondrej's PPA had no 8.5 for Ubuntu 24.04, so the box runs **8.4.25** while your laptop runs 8.5.10. Checking what a repository actually offers takes one command; assuming costs ten `Unable to locate package` lines.

**The consequence to carry:** the suite has only ever run on 8.5. If something behaves oddly on that box, the PHP version is a legitimate suspect rather than something to rule out. §3.2 and §6 turn that into an action, because right now that box can run the suite and in a week it will not.

> **Production differs:** Ubuntu 26.04, so the available PHP versions differ again. Read the lock, check the repository, and decide the version deliberately — it is an open decision, not a default.

### 4.5 Users and permissions — the part that costs the most evenings

Three identities, and confusing any two of them produces an error that surfaces somewhere else entirely.

| Identity | What it is for | What goes wrong |
|---|---|---|
| `root` | installing packages, nothing else | `composer install` as root writes `bootstrap/cache` root-owned; php-fpm then cannot write there, and the failure appears much later as an unrelated permissions error |
| `uni` (deploy user) | owns the code, runs git, composer, artisan and cron | if it is not in the web group, the web server cannot read what it writes |
| `www-data` (web user) | php-fpm and the queue worker | needs to write exactly two trees: `storage/` and `bootstrap/cache/` |

The arrangement that works: code owned `uni:www-data`, `uni` added to the `www-data` group, and the two writable trees set to **2775** on directories and 664 on files. The `2` is setgid: files created inside inherit the directory's group instead of reverting to the creator's own, so the arrangement does not quietly come apart on the next deploy.

**And the half that was missing until today, which is §3.3**: setgid fixes *which group* a new file gets, and `umask` fixes *whether that group can write to it*. You need both. One without the other gives you a file with the right group and no group write bit, which is exactly as useless as the wrong group.

> **Production differs:** Ploi uses its own deploy user and `www-data`, so the same three identities exist with different names. The `umask` lesson transfers unchanged, and Ploi will not do it for you.

### 4.6 `.env` — the file that is production

Two things about this file are worth more than the rest of the section.

**First: `.env.example` is not documentation, it is the template production is built from.** A real `.env` is copied from it, so every value in it ships. That is why it has its own rule and its own test.

**Second, and this is the one that bit hardest:** `env('KEY', 'default')` returns the default **only when the key is absent**. If the key is present but empty — `KEY=` — you get an empty string and the default never applies. On 22.09 `BACKUP_NOTIFICATION_EMAIL=` meant spatie/laravel-backup received an empty address, rejected it, and **every artisan command threw before doing anything at all**. The application was completely dead, and it was invisible on the laptop, whose `.env` predates the key and therefore omits it. That is now pinned by a test.

What legitimately changes per environment is short: `APP_ENV`, `APP_DEBUG`, `APP_URL`, the database credentials, `APP_KEY`, and the mail and backup settings. Everything else should be identical, and a difference you cannot explain is a bug you have not found yet.

**Secrets are generated on the box and never copied from the laptop.** `APP_KEY` via `php artisan key:generate`, the database password and the backup password with `openssl rand` in the shell you are already in. The reverse of the dev-machine rule: a secret that has only ever existed in one place cannot have leaked from a second one.

> **Production differs:** the values live in Ploi rather than in a file you edit by hand, and `UNI_OWNER_ACCESS` stays `false` there until V2. `MAIL_MAILER` becomes real Scaleway SMTP, at which point a mistake in this file sends actual email to actual venue owners.

### 4.7 Assets: built off the box, and three directories rather than one

Vite is not installed on the server and should not be. A Vite build spikes memory, and on a 4 GB VPS that is how a deploy kills Postgres in the middle of itself. So assets are built on the laptop, from the same tag, and shipped as an archive.

**Three directories, and this cost an evening on 22.09:**

- `public/build` — the Vite output, hashed filenames, described by `manifest.json`.
- `public/vendor/maplibre-gl/<version>/` — the map library, copied out of `node_modules` by a build plugin and **gitignored**, so no clone has it.
- `public/map-styles` — tracked, so a clone already has it; shipping it anyway costs nothing and removes a thing to remember.

Ship only `build/` and you get a site where every page renders perfectly and **every map is blank**, because the loader's request for the library 404s in the browser and nowhere on the server.

**The other half of this is `public/hot`.** If that file exists, Laravel emits asset URLs pointing at a Vite dev server that is not running: a fast, complete, correct-looking page whose scripts hang forever. It cannot exist in a fresh clone, which is why a clean clone is the only honest test. It is also why `php artisan test` on your laptop can pass with no `public/build` at all and prove less than it appears to.

> **Production differs:** not at all. Build off the box, ship three directories, confirm `public/hot` is absent. The only change is that the tarball travels further.

### 4.8 nginx — four things, three of which fail quietly

**`root` points at `public/`, never at the project directory.** One level up and `.env` is downloadable over HTTP, which is the most common way a Laravel application hands over its database credentials.

**`.mjs` has no entry in Ubuntu's `mime.types`.** MapLibre ships as ES modules loaded with a dynamic `import()`, and the browser **refuses any module not served with a JavaScript MIME type**. Without the fix nginx falls back to `application/octet-stream`: the file returns 200, downloads completely, and the browser declines to execute it. `curl` reports success, the Laravel log is empty, the nginx error log is empty, and every map is blank. The fix is `default_type` inside a location that matches only `.mjs` — **not** a `types { }` block, which inside `server` *replaces* the inherited MIME map instead of adding to it and would silently break every other content type on the site.

**Regex location order**, which is §3.4 and is the newest trap in the file.

**Compression and caching, both of which were simply absent.** Ubuntu's `nginx.conf` ships `gzip on` with no `gzip_types`, and the default type list is `text/html` alone — so the HTML was compressed and every stylesheet, script and module was not. Adding the type list took MapLibre from 585 KB to 150 KB. Caching is the companion: `/build/` is versioned by Vite's content hash and `/vendor/` by the version in the path, so both can be `immutable` for a year, while unversioned paths like `/map-styles/` correctly get nothing.

One small thing worth knowing because it looks like a mistake in a header dump: `expires max` emits its own `Cache-Control` **in addition to** any `add_header` you write, so using both gives you two `Cache-Control` headers. Valid, but untidy in a file headed for production, so the config now sets one explicitly.

> **Production differs:** Ploi writes the nginx config, so these have to be re-applied there rather than inherited. That is exactly why §6 asks whether this file belongs in the repository.

### 4.9 Laravel's own configuration — the four values that decide how the box behaves

| Value | Set to | Why it matters |
|---|---|---|
| `QUEUE_CONNECTION` | `database` | the queue is a table, so **no Redis anywhere in this stack**. It is also why §3.1's correction is true |
| `CACHE_STORE` | `database` | the scheduler heartbeat lives in the cache, and a database-backed cache survives restarts and deploys. On a file or memory cache the dashboard would report "never ran" after every deploy |
| `SESSION_DRIVER` | `file` | the file driver stores no visitor IP address, which is what the privacy policy describes. The privacy policy describes whichever driver is set, so this is a compliance value wearing a performance value's clothes |
| `LOG_STACK` | `daily` | `config/logging.php` sets 30-day retention on the daily channel, but the *stack* decides which channels are in it. Set to `single` the published 30-day retention is fiction and one file grows until the disk fills |

**And one that has never been run anywhere, which is the most interesting line in this section.** `php artisan config:cache` changes behaviour: once a config cache exists, **any `env()` call outside a `config/` file returns `null`**. That is a class of bug that appears only in a cached environment and never in development. It is deploy-checklist row C4, its first run is supposed to happen on preprod, and preprod now exists. Doing it there is cheap; discovering it on production is not.

> **Production differs:** config caching is not optional there, so C4 stops being a question and becomes a step.

### 4.10 Cron — one line, and the only thing inside the building that can raise an alarm

```
* * * * * umask 0002; cd /var/www/undernoinfluence && php artisan schedule:run >> /dev/null 2>&1
```

**One entry, running every minute.** Laravel decides internally what is due. You do not add a crontab line per task, and adding one would double-run something.

That single line drives ten commands. Three of them are the reason it is not optional: `uni:check-offer-freshness` keeps "sprawdzona karta" from claiming a menu is fresh when it is not; `uni:anonymise-expired-data` enforces four retention windows and nothing else does; `backup:run` is the entire backup story.

**`uni:heartbeat` is the only one that watches the others.** It writes a timestamp every five minutes and the admin dashboard turns red when that timestamp is older than fifteen minutes. Without it, a missing or mistyped crontab line is completely invisible — a healthy box with a broken crontab looks exactly like a healthy box, which is why uptime monitoring cannot answer this question and a heartbeat can.

**And `/up` does not answer it either.** Laravel's health endpoint proves the framework boots. It knows nothing about cron, the worker, or whether anything scheduled has ever happened. Two different questions, and only one of them is answered by a 200.

> **Production differs:** Ploi has its own scheduler toggle rather than a hand-written crontab, but it installs the same single line. The `umask` belongs there too.

### 4.11 The queue worker — and why `RUNNING` is not proof

`supervisor/uni-worker.conf`, two processes, `autostart` and `autorestart` both true so it survives a crash and a reboot. A3's point: `user=` must name a user that exists on the host — `www-data` on Debian and Ubuntu, something else on Fedora and RHEL — and **a wrong value there fails silently until a queued job never runs**.

**`supervisorctl status` showing RUNNING proves a process exists. It does not prove a job can reach it.** A worker pointed at the wrong queue connection, or started before the database was reachable, or running code from before the last deploy, all report RUNNING. The only real proof is a job going in and coming out, which is what the worker log line at 12:25:04 is.

**One line that will bite you on production and cannot bite you here:** `php artisan queue:restart` after **every** deploy. A worker holds your code in memory. Without that command it keeps running the **old** code indefinitely, and you get a system that is half-updated in a way no page reveals — the most common Laravel deploy bug there is.

> **Production differs:** only in that deploys will be frequent, which is precisely what makes `queue:restart` matter there and not here.

### 4.12 Backups — the guard, the password, and the half nobody rehearses

`spatie/laravel-backup` encrypts **only** when `BACKUP_ARCHIVE_PASSWORD` is set, and without it writes a perfectly readable archive without a word of warning. On production that would put every claimant's name, email, phone and NIP into object storage in the clear. So `BackupEncryptionGuard` opens each archive before it goes anywhere and **fails the run** unless every file inside is AES-256. A failed run is a mail; a readable archive is a silent breach.

Which is why the unset password on the box this morning mattered: the guard would have refused every archive, correctly, and you would have collected one failed job a night.

**The half that is almost always skipped is the restore.** Art. 32(1)(d) asks for a restore that has been *tested*, not configured. That means: take an archive, open it with the password, load it into an **empty scratch database** — never into staging — and compare row counts. It was rehearsed on the laptop on 18.09. It has never been rehearsed on a server, and tomorrow morning there will be an archive on one for the first time.

> **Production differs:** the archive goes to Scaleway with object lock and lifecycle rules, and four steps of that are still unexecuted. The rehearsal discipline is identical.

### 4.13 TLS and cookies — why testing over plain HTTP would have hidden a fixed bug

Tailscale terminates TLS on the host and proxies to the container, so the site is reachable on your tailnet over **real HTTPS with a valid certificate**.

That is not cosmetic. The consent cookie is `Secure`, and a browser **silently discards a `Secure` cookie over plain HTTP**. Testing over `http://` would have reproduced exactly the defect fixed on 02.09 — every consent decision lost, the banner returning on every page load — and you would have spent an evening re-finding a bug that no longer exists.

`HSTS_MAX_AGE` is still 300 seconds. HSTS is a promise a browser keeps for the whole max-age and **cannot be withdrawn early**, so it gets raised only after the first unattended certificate renewal has succeeded. Raising it on launch day means a botched renewal locks every visitor out for as long as the value says.

> **Production differs:** a real certificate on a real domain with automatic renewal, and the HSTS value becomes a decision with a date attached rather than a default.

### 4.14 A release is a tag, and a deploy needs more than git carries

The box is checked out at a **tag**, not a branch. A branch moves under you; a tag is a thing you can name in a sentence and return to.

**But git does not carry everything a deploy needs**, which is its own decision record and is worth holding on to as a sentence: built assets are gitignored, `.env` is not in the repository, the map library is not in the repository, and the crontab and supervisor config live on the machine. A clean clone plus `composer install` is **not** a running site, and every one of those gaps fails quietly rather than loudly.

The box is currently on v0.1.2 while v0.1.3 exists. The difference is a seeder and a test — no frontend — so the v0.1.3 asset bundle sitting on a v0.1.2 checkout cannot cause a problem today. It is still wrong in principle, and §5 carries it.

> **Production differs:** the same rule, enforced harder, plus the release notes you will actually want when something regresses.
